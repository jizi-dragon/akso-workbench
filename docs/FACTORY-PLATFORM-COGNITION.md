## 0. 一句话

**手册给语义、真机是唯一的桥。** 这一族认知的两条主线是「**创建顺序**」与「**无撤销键**」——
前者决定配置物之间的依赖与先后，后者决定哪些操作**"试探"就等于"生产写入"**。

## 1. 平台的配置分层与"最小完整集"

- `[手册]` 官方三层口径，自下而上：**数据模型层 → 业务逻辑层 → 界面呈现层**（`06概念 §2`）。
- `[手册]` 一个对象"从零到可用"的**硬最小集**＝对象 + 字段 + 权限集 + 菜单 + 表单布局 + 列表布局/视图；
  生命周期 / 工作流 / 关系 / 对象类型 / 编号规则是**业务需要时的增量**（`06概念 §2`）。
- `[手册]` 推荐顺序：对象 → 字段 → 关系 → **生命周期** → **布局**（`02布局 §1`）。

⚠️ **平台不强制顺序**，但真机有一处**顺序敏感**（F16）：对象一旦启用生命周期，列表布局里的
**状态列不可移除、新建时强制添加** ⇒「先建布局后开生命周期」与「先开生命周期后建布局」
在列表布局上**不等价**。**[待验]**

## 1.5 创建顺序与依赖 ★（含"平台自动派生什么"）

> 逐条带出处的完整版（**51 行配置物**，逐行记"必须先有什么 / 被谁依赖 / 平台自动派生什么 /
> 不可逆点 / 来源"）在
> [`factory-tuning/reports/gaia-v38-study/11-creation-dependency-map.md`](../factory-tuning/reports/gaia-v38-study/11-creation-dependency-map.md)。
> 这里只留结论与**会咬人的那几条**。

**主序列**（把散在各篇「前提条件 / 配置顺序」里的条文拼成一条；拼不上的地方在下面显式列出）：

`1 业务单元 → 2 部门 → 3 职位（必填部门+业务单元）→ 4 角色+权限集 → 5 选项集 → 6 对象 →
7 对象级开关一次定死（不可逆那一族）→ 8 字段 → 9 关系（出站随字段自动生成，入站不用建）→
10 字段级规则族（索引/编号/验证/默认值/引用约束/控制字段/选项依赖）→
11 生命周期状态 + 流转（状态必须先于流转）→ 12 状态类型 → 13 阶段组/阶段 →
14 进入条件→进入动作→用户动作→事件动作 → 15 生命周期角色→状态权限（角色先于状态权限）→
16 工作流 → 17 表单布局/列表布局 → 18 页面链接/动作/自定义视图 → 19 菜单 →
20 标准视图（系统随菜单自动建）→ 21 权限集条目 + DAC 共享规则 →
22 通知/输出模板/运行报告/报表/PDF 封面 → 23 移动端菜单 →
24 跨环境交付（配置包 ≠ 已生效，还要"校验 → 部署"）`

层级口径（手册的权威表述）：**数据模型层 → 业务逻辑层 → 界面呈现层**（`01_平台概述 §配置模型层次`）。

### 平台"不用你建、自己会生成"的东西

| 类型 | 内容 |
|---|---|
| **默认型**（对象一建就有） | 系统字段（`name__ak` / `state__ak` / `status_id__sys`…）、系统默认索引、**标准列表布局**（`所有的{对象}`，Code `{对象Code}_table__ak`，**不可删**）、工作流的开始/结束节点、生命周期的三个标准角色 |
| **开关型**（勾一个开关 → 冒出一族） | **启用生命周期** → 生命周期本体 +「开始/关闭」两状态 + `status_id__sys` + 三个标准角色 + 每状态默认的"工作流取消状态"；**电子签名** → `{Code}_esignature_sys` 子对象；**对象类型** → `基础类型` + 再一个列表布局；**实例锁定** → `是否锁定`/`锁定时间`；**树形** → `…_path__sys`/`…_child_count__sys`；**所属业务模块** → 标准选项集`业务模块` + 字段`模块`；**审批矩阵** → 3~4 个对象 + 选项集 + 同名表单布局部分；**检查表类型** → **一次铺开五类产物** |

### 三条会咬人的冲突（完整 10 条 K1–K10 见簇笔记 §3）

| # | 平台侧事实 | 为什么咬人 |
|---|---|---|
| **K10** | 平台**自动派生**一批配置物（系统字段 / 标准列表布局 / 标准角色…，见上表），它们**不来自任何一次创建动作** | ⇒ "平台上现在有什么"与"发过什么请求"是两件事：不把派生物读回来，改写对象时就一定与它们相撞（叠加 K2 / K8） |
| **K2** | 对象启用生命周期后，平台**强制列表布局带状态列**（F16）；而布局保存是**整份提交**语义 | ⇒ 提交一份自己拼的列数组，**可能覆盖平台的强制列**。平台侧稳妥的写法是「**读旧列 → 合并 → 提交**」，**不是**硬编码 `status_id__sys` |
| **K3** | 工作流依赖 `lifeCycleId`，而**空 id 不报错**：没开生命周期却配 `workflows` 只给 warning、`Status/Create` 不校验空 id、`basicConfig.lifecycleId=""` 直接发出去 | 缺的**不是顺序，是硬门禁**——平台侧不会替你拦住 |

> ⚠️ **两处口径更正（回查手册原文后）**：
> ① 「固定主干顺序：选项集 → 对象 → 字段 → 布局 → 生命周期 → 工作流」**出处不成立**——
> 它引的 `01_对象配置 §2.3` 实为"创建要点"五步、`01B §1.2` 实为"对象内页签"表。
> 只有"选项集先于**选项字段**"有据（`01B §3.8`）⇒ 上文主序列里"选项集最先"应读作**推论**。
> ② **手册自己没有一份总顺序**，且 `04 §前提条件`（建议先做对象+工作流）与 `05 §2.1`
> （生命周期是创建工作流的**必填**字段）**互为循环** ⇒ 别指望手册给出可执行的拓扑序；
> 它是"手册给语义不给流程"的又一例。

## 2. 术语对照：手册用词 ↔ 常见误解

| 手册用词 | 常见误解 | 澄清 |
|---|---|---|
| 「**角色**」与「**权限集**」 | 把两者当成一个东西："一份「角色 + 它有哪些权限」的清单" | 它们是**两个实体**：角色拥有权限集，**中间还有一层** ⇒ 权限语义没法用一层结构表达完整 |
| 「**列表布局**」与「**视图**」 | 以为"列表布局"就把列表页说完了 | 它们是**两层**：列表布局＝列长什么样；视图＝看哪些记录、怎么排。列表页的**默认落点是视图** |
| `13 查找` | 把所有"指向别的对象"的 dataType 并成一类 | 13 = **只读派生字段**（从父/引用对象同步值）；可编辑的关联边是 `15 对象` / `16 父对象` |
| 「**启动状态**」 | 读成"在该状态生成提交按钮" | 手册的「启动状态」＝**可在哪个状态发起**；"在该状态生成提交按钮"是手册的**手动启动** ⇒ 同一意图分两层，不要混 |
| 「**报表**」/「**报表类型**（数据源）」/「**运行报告**（导出模板）」 | 到处说"报表模板" | 平台**没有"报表模板"**这个实体，只有上述三种说法 |
| 「**部分**」（**部分容器**） | 说成"分组 / 分区" | `[手册]` `01D_表单布局.md` 全章「部分」**236 次**，而「分组」只 **2 次**、且都是"部分分组／分组思路"这种**思路**用法，**不是容器名**。**2026-09-22 用户当面纠正**：「布局没有『分组』的概念，只有『部分』」⇒ 本仓文档**统一用「部分」** |
| 「**控件**」 | 把控件当成一种独立的配置物 | `[手册]` `01D §4.1`：**「详情部分中的『控件』即对象字段，新增控件时本质是在该部分中引入字段」** ⇒ **控件 = 选中对象里已有的字段 + 按字段类型呈现为对应的表单控件** |

⇒ 控件既然是**字段的投影**，布局的合法输入就是**对象现有字段全表**（读侧通道 `FieldsByCodes` /
`FieldPage`），**不是**"只认刚建出来的那些字段"；跨层时词汇还会**改名 / 取反**：
`code`/`name`/`dataType` 同名同值搬过去，`isRequired`→`required`、`invisible`→`visible`、
`editable`→`readOnly`（见[控件与字段的词汇对照](../factory-tuning/reports/2026-09-22-控件与字段的词汇对照.md)）。
★ 也就是说 **"必填"在平台上落在控件层**：真机 11 条 `SaveField` 请求体里**一条都没有** `isRequired`，
而字段**读侧** 93 键里**有**它 ⇒ 同一个概念在写侧与读侧**词表不一致**。
**[待验]**：平台收到 `isRequired` 是忽略、还是把字段直接设成必填。

另两条容易读错的：`附件(8)` ≠ 平台`文件字段`；`Sandbox`（Dev/QA/UAT 隔离环境）
与"执行不可信代码的沙箱"**同词两义**。

> ⚠️ **一处簇间冲突，已裁定**：概念簇笔记称"检查表不是平台概念"——那是**阅读范围所限**（它没读 `04_配置指南/`）。
> `04_配置指南\17_检查表配置.md` 证明检查表是平台概念，且**一次创建铺开五类产物**
> （实例对象集 / 页面链接 / 设计对象类型 / 生命周期 / 工作流）⇒ **以检查表簇为准**。

## 4. 分层对照：手册语义 ↔ 平台语义

> ### ⚠️ 平台侧硬约束：配好的对象，业务端**默认看不见**
>
> `[手册] 02_权限配置 §对象与字段权限`：对象的**查看/创建/编辑**以及字段级权限条目，
> 必须**逐项加进权限集**，否则对象在业务端根本不出现。
> ⇒ 这不是"少配了一个东西"，而是**"配完了但没人能用"**——所以权限这一族必须**条目化到
> "对象 X 的查看/创建/编辑 + 字段 A 的查看"**这一粒度；只说一句"配下权限"等于没说。

### L1 对象

| 手册语义 | 平台侧补充 / 注意 |
|---|---|
| 对象是**配置交付单位**，来源三分 `系统/标准/自定义`，系统对象不开放常规修改 | 手册另列 **7 种对象类别**；DAC（动态权限控制）依赖的「用户角色设置」对象属于平台既有对象 |
| 对象级开关族（见 §3） | **全不可逆**：启用后不可关闭 ⇒ 漏配之后**平台无法补救**；其中大容量等开关还是**永久能力切除** |
| `Code`/名称不可改；平台级别名 | ★ **重跑会产生重复产物**：同一批创建请求再发一次，字段/状态/工作流会**再建一份**；而状态**不可删、只能停用**（§3）⇒ 重复出来的状态只能停用、清不掉 |

### L2 字段

| 手册语义 | 平台侧补充 / 注意 |
|---|---|
| 14 种 `dataType`；`对象(15)`=引用关系、`父对象(16)`=父子（层级 ≤3） | ★ **2026-09-22 手册对照更正**：手册 §3 实为 **16 种**（多出**统计 §3.13** 与**组件 §3.16**）；且 `dataType 19` 已在真机字段里出现，**很可能是「组件」**（F71，**推断**） |
| 数字范围键名 = `minValue`/`maxValue`/`scale` | 与 `[手册] 01B §3.4` 一致 |
| 公式字段：返回类型 + 公式表达式；保存期**唯一校验是「语法检查」** | ⇒ 键名与形状写错**不会在保存时被拦下**；`returnType` / `formulaScript` 的真实形状只能真机取（§8） |
| ★ **手册逐类型的数值硬限制（至少 9 处）**：文本 `≤1500`；长文本/富文本 `≤32000`；数字最大值 `≤99999999999999`；对象多选默认最多选 `100`（可调 `1-1000`）；附件数量 `1-100`、单个 `1-2048MB`；查找「一个对象最多 **5** 条关系 / 每条最多 **8** 个字段 / 一个源对象最多被 **8** 条引用」；统计「一个对象最多 **10** 个」；树形「最多 **5** 层」；帮助内容 `0-500` 字符 | 这套上限是**手册的业务语义**（`maxLength` 的上限即来自它：1500 / 32000 等）⇒ 平台侧的拦截面在**保存期**；越界是被拒还是静默接受，**未逐条验** |
| 字段读侧有 30+ 配置键（`isUnique`/`isIndexed`/`codeRuleId`/`enableTree`/`findSourceFieldId`/`iconType`…） | ★ **实测 93 键**（`FieldsByCodes` 响应，2026-09-22 全量录到）⇒ 字段的配置面比手册列出来的宽得多 |

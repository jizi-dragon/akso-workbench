\# 配置迁移
> 本文面向系统管理员、实施顾问和运维人员，介绍 Gaia 平台的多 Sphere 管理、配置包迁移和部署校验。阅读本文后，管理员应能够判断哪些配置可以迁移、如何生成和导入配置包，以及如何在部署前后完成核对。   

---

## 概述

Gaia 平台通过多 Sphere 和配置包机制管理系统变更。管理员通常先在配置 Sphere 或验证 Sphere 完成配置，经过验证和用户验收后，再将配置迁移到生产 Sphere。这样可以减少直接修改生产配置带来的业务风险，并保留完整的部署记录。

数据包 / 配置包在校验、导入体验上的优化以当前版本页面为准。对象实例数据的跨业务单元导入导出规则见 [数据迁移](18_%E6%95%B0%E6%8D%AE%E8%BF%81%E7%A7%BB.md)，不在配置包场景中套用。

典型访问路径：
- 出站配置包：**管理端 \> 部署管理 \> 出站配置包**
- 入站配置包：**管理端 \> 部署管理 \> 入站配置包**
- 配置报告：**管理端 \> 部署管理 \> 配置报告**。详细操作请参阅 [配置报告](16_%E9%85%8D%E7%BD%AE%E6%8A%A5%E5%91%8A.md)。

常见 Sphere 如下：

| Sphere | 主要用途 | 数据特点 | 管理建议 |
|------|------------|------------|------------|
| 配置 Sphere（Dev） | 配置开发、单元验证、方案试做 | 测试数据或样例数据 | 允许频繁变更，不建议承载正式业务 |
| 验证 Sphere（QA） | 功能测试、回归测试、部署包验证 | 测试数据 | 用于验证配置包是否可安装、是否影响已有流程 |
| UAT Sphere | 用户验收测试和业务确认 | 脱敏生产数据或接近生产的数据 | 生产部署前应在此完成签字确认 |
| 生产 Sphere（Prod） | 正式业务运行 | 真实业务数据 | 仅部署已验证的配置包，避免直接手工修改关键配置 |
> \[!IMPORTANT\]
生产 Sphere 部署前，请确认部署窗口、回退方案、配置报告、测试结果和业务确认均已准备完成。配置迁移可能影响对象、字段、生命周期、工作流、权限和业务规则。   

## 配置迁移原则

配置迁移通过出站配置包和入站配置包完成。源 Sphere 负责生成配置包，目标 Sphere 负责导入、校验和部署配置包。
```text
配置 Sphere -> 验证 Sphere -> UAT Sphere -> 生产 Sphere
   |          |           |           |
   +-- 配置包 +-- 配置包  +-- 配置包  +
```

建议迁移顺序如下：
1. 在配置 Sphere 完成配置变更，并生成配置报告作为变更前后对照。
2. 创建出站配置包，确认版本号、摘要和包含范围。
3. 在验证 Sphere 导入配置包，完成校验和部署。
4. 执行功能测试、权限测试、工作流测试和必要的数据验证。
5. 在 UAT Sphere 重复导入和验证，并完成业务确认。
6. 在生产 Sphere 部署同一配置包，部署后生成配置报告并核对关键配置。

### 迁移内容分类

不同类型的配置应采用不同的迁移方式。不是所有 Sphere 相关内容都适合放入配置包。

| 类别 | 示例 | 推荐方式 | 说明 |
|------|------|------------|------|
| 组件配置 | 对象、字段、生命周期、工作流、界面、权限集 | 配置包迁移 | 适合跨 Sphere 复制，部署前需要校验依赖 |
| 业务配置 | 审批矩阵、业务模板、部分报表、业务规则基础数据 | 数据迁移 | 通常与组织、业务单元或客户数据有关，应通过数据迁移迁移，并在迁移后单独核对 |
| 配置种子数据 | 角色、用户组、权限集合、翻译工作台、后台作业 | 全量迁移 | 当前按全量迁移处理，迁移后应核对目标 Sphere 的关键数据 |
| Sphere 参数 | 第三方集成地址、业务流水号、域名、系统信息 | Sphere 内单独维护 | 不建议随配置包从低阶 Sphere 覆盖到生产 Sphere |
| 系统初始设置 | 域设置、安全策略、基础系统参数 | 首次初始化后谨慎调整 | 后续变更应按变更流程审批 |

### 全量迁移

当前配置迁移采用全量迁移方式，不支持增量迁移。全量迁移适用于首次上线、Sphere 初始化和配置基线重建，也用于日常版本变更的配置包部署。

如果目标 Sphere 已有本地差异，部署前应先生成配置报告，确认这些差异是预期保留、需要覆盖，还是需要先合并处理。

## 出站配置包

出站配置包用于从当前 Sphere 导出配置快照。生成完成后，管理员可以下载配置包，并在其他 Sphere 作为入站配置包导入。

### 列表页面

进入 **管理端 \> 部署管理 \> 出站配置包** 后，页面按创建时间倒序显示配置包导出记录。

| 列 | 说明 |
|---|------|
| 名称 | 配置包名称，应能体现版本或变更主题 |
| 版本号 | 配置包版本，用于迁移、追溯和兼容性判断 |
| 摘要 | 简要说明本次配置包包含的变更 |
| 描述 | 记录变更背景、范围、依赖和注意事项 |
| 拥有者 | 创建配置包的用户 |
| 创建时间 | 导出记录创建时间 |
| 出站配置包类型 | 配置包分类。当前配置迁移按全量方式处理 |

### 创建配置包
1. 进入 **出站配置包** 列表。
2. 点击 **创建**。
3. 填写名称、摘要、描述、出站配置包类型和配置版本。
4. 保存后进入详情页。

保存只会创建导出记录，不会立即生成可下载文件。管理员仍需在详情页执行生成操作。

### 版本号规则

配置包版本号用于标识配置基线。新配置包的版本号不能低于当前 Sphere 配置版本。

| 版本项 | 说明 |
|---------|------|
| 当前配置版本 | 当前 Sphere 已应用的配置版本，仅用于创建时参考，不可编辑 |
| 配置版本 | 本次配置包的版本号，保存后不建议再调整 |

版本号采用 4 段数字格式，每段取值范围为 `0-99999`，例如 `3.6.1.0`。

### 生成与下载
1. 在配置包详情页确认基本信息和包含范围。
2. 点击 **生成**。
3. 系统开始打包配置，并在完成后通知拥有者。
4. 生成成功后，在列表或详情页点击 **下载** 获取配置包文件。

生成期间，请不要重复创建相同范围的配置包。若生成失败，可查看详情页中的日志或错误信息，再修正配置后重新生成。

## 入站配置包

入站配置包用于将配置包导入到当前 Sphere，并在校验通过后执行部署。

### 列表页面

进入 **管理端 \> 部署管理 \> 入站配置包** 后，页面按导入时间倒序显示导入记录。管理员可通过关键词检索目标记录。

| 列 | 说明 |
|---|------|
| 名称 | 导入的配置包名称 |
| 版本号 | 配置包版本 |
| 摘要 | 配置包概要 |
| 描述 | 配置包详细说明 |
| 拥有者 | 导入配置包的用户 |
| 部署状态 | 显示未部署、部署中、已部署、失败等状态 |
| 更新时间 | 最近一次导入、校验或部署的更新时间 |

### 导入配置包
1. 进入 **入站配置包** 列表。
2. 点击 **导入**。
3. 选择本地配置包文件并上传。
4. 上传完成后，在列表中打开导入记录。

导入只会把配置包登记到目标 Sphere，不代表配置已经生效。配置生效必须经过校验和部署。

### 部署前校验

部署前校验会检查配置包完整性、程序版本兼容性、依赖关系、目标 Sphere 是否存在冲突，以及部分配置是否满足部署条件。

| 校验结果 | 管理员操作 |
|------------|---------------|
| 通过 | 可继续执行部署 |
| 警告 | 阅读提示，确认影响可接受后再部署 |
| 阻止 | 必须先修正问题，重新导入或重新生成配置包 |

常见阻止项包括：目标 Sphere 缺少依赖组件、配置包版本低于当前配置版本、对象或字段依赖不完整、工作流引用的状态或角色不存在。

### 执行部署
1. 打开入站配置包详情页。
2. 查看校验结果、变更范围和部署日志。
3. 确认当前处于允许部署的维护窗口。
4. 点击 **部署**。
5. 等待系统完成部署，并查看最终状态。

部署完成后，配置会在目标 Sphere 生效。涉及页面、权限或工作流的变更，建议重新登录或刷新页面后验证。
> \[!WARNING\]
部署期间系统会进入部署模式，部分业务端操作可能受限。建议在非业务高峰期执行部署，并提前通知受影响用户。   

### 部署失败处理

如果部署失败，请先查看入站配置包详情页的日志。日志通常包含失败阶段、失败组件和错误原因。

处理建议：
- 依赖缺失：在源 Sphere 补齐依赖后重新生成配置包，或先部署依赖配置包。
- 版本不兼容：确认源 Sphere 和目标 Sphere 程序版本，再重新生成匹配版本的配置包。
- 目标 Sphere 冲突：使用配置报告确认差异，再决定覆盖、合并或保留。
- 无法判断原因：保留配置包、部署日志和操作时间，联系技术支持处理。

## 部署检查清单

### 部署前
- 确认当前 Sphere、目标 Sphere 和配置包版本正确。
- 确认源 Sphere 已完成配置报告导出。
- 确认配置包摘要和描述清楚记录了变更范围。
- 确认验证 Sphere 和 UAT Sphere 已部署并验证通过。
- 确认生产部署窗口、通知范围和回退方案。
- 确认第三方集成地址、域名、流水号等 Sphere 参数不会被错误覆盖。
- 确认权限、工作流和生命周期属于本次预期变更。

### 部署后
- 查看入站配置包状态，确认部署完成且无阻止错误。
- 生成部署后的配置报告，并与部署前报告核对。
- 验证关键对象、字段、页面、权限和工作流。
- 检查业务端是否可以正常创建、编辑、审批和查看记录。
- 保存配置包、配置报告、部署日志和测试记录，供审计追溯。

## 常见问题

**Q：配置包导入后，为什么配置没有生效？** A：导入只会上传并登记配置包，配置生效需要在入站配置包详情页完成校验和部署。

**Q：生产 Sphere 是否可以直接修改配置？** A：不建议直接修改关键配置。生产配置变更应优先在低阶 Sphere 完成开发和验证，再通过配置包迁移到生产 Sphere。

**Q：哪些内容不应通过配置包覆盖？** A：业务配置应通过数据迁移迁移；第三方集成地址、域名、业务流水号、生产 Sphere 专用系统参数等 Sphere 相关配置通常应在各 Sphere 单独维护。

**Q：部署失败后是否可以继续业务操作？** A：需根据失败阶段判断。请先查看部署状态和日志，确认系统是否已退出部署模式，再执行关键业务操作。

**Q：如何确认部署内容与预期一致？** A：部署前后分别生成配置报告，并对照配置包摘要、需求清单和 UAT 结果核查关键差异。

**Q：配置包导入体验和以前不一样怎么办？** A：数据包 / 配置包在校验、导入体验上的优化以当前版本页面为准。若涉及对象实例数据的跨业务单元导入导出，请参阅 [数据迁移](18_%E6%95%B0%E6%8D%AE%E8%BF%81%E7%A7%BB.md)。

# 生命周期与工作流
> 本文解释 Gaia 平台中生命周期和工作流的概念、原理及其在 GxP 合规中的作用。   

---

## 概述

\*\*生命周期（Lifecycle）**和**工作流（Workflow）\*\*是 Gaia 平台实现业务流程自动化和合规管控的两大核心机制。

| 概念 | 定义 | 作用 |
|------|------|------|
| **生命周期** | 文档或对象记录从创建到归档经历的状态序列 | 控制状态流转和权限 |
| **工作流** | 完成特定业务目标的一系列步骤和任务 | 自动化审批和协作 |

---

## 生命周期

### 什么是生命周期？

生命周期定义了文档或对象记录可以处于的所有**状态（State）**，以及这些状态之间的**转换规则**。
```
┌─────────────────────────────────────────────────────────────────┐
│                    典型文档生命周期                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   ┌────────┐    ┌────────┐    ┌────────┐    ┌────────┐         │
│   │  草稿  │───►│ 审核中 │───►│ 已批准 │───►│ 已归档 │         │
│   │ Draft  │    │In Review│   │Approved│    │Archived│         │
│   └────────┘    └────────┘    └────────┘    └────────┘         │
│        │             │                                          │
│        │             ▼                                          │
│        │        ┌────────┐                                      │
│        └───────►│ 已拒绝 │                                      │
│                 │Rejected│                                      │
│                 └────────┘                                      │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

### 生命周期组件

| 组件 | 说明 |
|------|------|
| **状态（State）** | 文档/记录可以处于的一个阶段 |
| **状态类型** | 初始状态 / 稳态 / 终态 |
| **状态转换** | 从一个状态变更到另一个状态的规则 |
| **进入条件** | 进入某状态必须满足的条件 |
| **进入动作** | 进入状态时自动执行的操作 |
| **用户动作** | 用户可在该状态执行的操作 |
| **生命周期角色** | 与状态相关的权限角色 |

### 状态行为

不同状态可以配置不同的行为：

| 行为 | 说明 | 示例 |
|------|------|------|
| **编辑控制** | 控制是否允许编辑 | 已批准状态锁定编辑 |
| **版本行为** | 控制版本号变化 | 批准时升级主版本 |
| **权限变化** | 不同状态不同权限 | 草稿状态仅作者可见 |
| **用户动作** | 用户可执行的操作 | 草稿状态可提交审核 |
| **自动动作** | 进入状态触发操作 | 批准后自动发送通知 |

### 生命周期阶段

Gaia 支持将多个状态组织为**阶段（Stage）**，便于可视化进度：
```
┌────────────────────────────────────────────────────────────────┐
│   起草阶段        审批阶段         生效阶段        归档阶段     │
│  ───────────    ───────────     ───────────    ───────────    │
│   [草稿]         [审核中]         [已批准]        [已归档]     │
│                  [待签署]         [已发布]        [已作废]     │
│                  [已拒绝]         [已撤回]                    │
└────────────────────────────────────────────────────────────────┘
```

## 工作流

### 什么是工作流？

工作流是一系列\*\*步骤（Step）\*\*的有序集合，用于自动化业务流程，如文档审批、变更控制、培训分配等。

### 工作流类型

| 类型 | 说明 | 适用场景 |
|------|------|------------|
| **对象工作流** | 作用于单个或多个同类型对象记录 | CAPA 审批、变更控制 |
| **文档工作流** | 对象工作流的特殊形式，通过 Envelope 包装文档 | 文档审批、多文档批量审核 |

### 工作流步骤类型

| 步骤类型 | 说明 |
|------------|------|
| **开始步骤** | 工作流入口点，配置参与者和启动条件 |
| **任务步骤** | 分配任务给用户，支持裁决和电子签名 |
| **判断步骤** | 根据条件分支执行不同路径 |
| **动作步骤** | 自动化系统操作（更新字段、变更状态、发送通知等） |
| **合并步骤** | 汇合多条并行路径 |
| **更新共享设置步骤** | 更新权限 |
| **通知步骤** | 发送通知 |
| **结束步骤** | 工作流终止点 |
> 💡 **说明**："更新字段"、"变更状态"、"发送通知"等操作是**动作步骤**内可配置的**动作类型**，而非独立的步骤类型。   

## 电子签名

### 什么是电子签名？

电子签名是用户对文档或操作的**数字化确认**，等同于手写签名的法律效力。

### 电子签名要素

| 要素 | 说明 |
|------|------|
| **用户身份** | 签署者的系统账户 |
| **密码验证** | 签署时需重新输入密码 |
| **签名原因** | 说明签署的目的（可配置） |
| **时间戳** | 系统记录的精确签署时间 |
| **含义声明** | 签名代表的具体含义 |

### 签名类型

| 类型 | 使用场景 |
|------|------------|
| **单签名** | 一般文档审批 |
| **双签名** | 关键质量决策（操作者 \+ 复核者） |
| **多级签名** | 按序签署（起草 → 审核 → 批准） |

🔒 **合规要点**：Gaia 平台的电子签名功能符合 FDA 21 CFR Part 11 和 EU Annex 11 要求。

## 生命周期与工作流的关系

### 集成方式

生命周期和工作流通过以下方式协同工作：
```
┌─────────────────────────────────────────────────────────────┐
│                                                              │
│   用户发起     ┌──────────────┐                             │
│   状态变更 ───►│  工作流启动  │                             │
│                └──────────────┘                             │
│                       │                                      │
│                       ▼                                      │
│               ┌──────────────┐                              │
│               │   任务分配   │                              │
│               └──────────────┘                              │
│                       │                                      │
│                       ▼                                      │
│               ┌──────────────┐                              │
│               │  用户审批    │                              │
│               └──────────────┘                              │
│                       │                                      │
│          ┌───────────┴───────────┐                          │
│          ▼                       ▼                          │
│   ┌──────────────┐       ┌──────────────┐                   │
│   │    批准      │       │    拒绝      │                   │
│   └──────────────┘       └──────────────┘                   │
│          │                       │                          │
│          ▼                       ▼                          │
│   ┌──────────────┐       ┌──────────────┐                   │
│   │ 状态 → 已批准│       │ 状态 → 草稿  │                   │
│   └──────────────┘       └──────────────┘                   │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### 启动方式

| 方式 | 说明 | 配置位置 |
|------|------|------------|
| **手动发起** | 用户在记录上点击"启动工作流"手动触发 | 用户操作 |
| **生命周期入口动作** | 进入特定状态时自动启动工作流 | 生命周期配置 \> 状态 \> 入口动作 |
> 💡 **提示**：自动触发工作流不是独立配置，而是作为**生命周期状态的入口动作**来实现的。例如，配置"审核中"状态的入口动作为"启动审批工作流"。

## 最佳实践

### 生命周期设计
1. **保持简洁**：状态数量控制在 5-7 个
2. **明确语义**：状态名称清晰反映含义
3. **单向流动**：避免过多回退路径
4. **权限分离**：不同状态配置不同权限

### 工作流设计
1. **任务清晰**：每个任务目标明确
2. **适度并行**：可并行的任务同时进行
3. **超时处理**：配置任务超时提醒或升级
4. **异常处理**：考虑拒绝、取消等场景

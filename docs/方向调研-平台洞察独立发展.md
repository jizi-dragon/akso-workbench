# 方向调研 ③：平台洞察（insight）独立发展与优化 —— 准备清单 + 边缘规则

_2026-09-13 · 基于 `d0efa84`（v0.3.5）代码实测 + 真实数据目录勘查 + 三路并行代码深挖 · 接续《方向调研-公司级Agent平台.md》与《方向调研-钉钉MCP落地细节.md》_

> **结论先行**：quick-login 已经「完成」，因为它的正确性可以被肉眼验证（登录成功/失败、窗口有没有开）。
> 而 insight 的正确性**在当前代码库里没有任何东西能验证**——它只有 12 个跑在**假平台**（`tests/fakes.py`）上的测试，
> 而它 100% 的价值都来自「对**真实** eGMP 平台的**真实**语义理解是否准确」。
> 所以「发展 insight」的第一步不是加功能，是**先让它可被验证**。本文的 §1 是诊断，§2 是准备清单，§3 是边缘规则（可直接当验收清单用）。

## 1. 现状诊断：三个必须先承认的事实

### 1.1 事实一：insight 从未在真实数据上留下过任何记录

实测本机数据目录（`%APPDATA%\AksoWorkbench\workbench.db`）：

| 表 | 行数 | 含义 |
|---|---|---|
| `platform_env` | **4** | 示例租户 / 联邦 / 测试环境 / 培训（四个**不同的平台部署**） |
| `account` | **5** | 含同一环境两个账号（示例租户 `dev-user` + `T0901`） |
| `insight_runs` | **0** | 洞察**一次都没跑过** |
| `agent_audit` | **0** | Agent 工具层从未被调用 |
| `blueprint_jobs` | **0** | 配置工厂同样为零 |

磁盘上 `runtime/` 目录**不存在**：没有任何 `inventory.json` / `understanding` / `*.drawio` 产物。

> 已删除的原 `AGENT.md` §1 曾写「实测活跃数据：环境 3 / 账号 4 / 会话 2 / **洞察运行 4**」——与当前库不符。
> 无论原因是数据库被重装重置，还是当时用了另一份 `WORKBENCH_DATA`，**此刻不存在可复现的基线语料**，
> 而原 `AGENT.md` §7.5 记的「真机验收：understand（1.4 MB 模型）/ spider」是**历史通过项**，不是当前可回归的资产
> （该文档已于 2026-09-13 因整体滞后删除；可用 `git show d0efa84:AGENT.md` 取回）。

**为什么这条最重要**：这意味着下面 §1.2 里列的每一个平台耦合假设，**目前都只是「在假平台上成立」**。

### 1.2 事实二：平台耦合面完全靠「实证猜测」，且有一处文档承诺了但没实现

insight 是围绕 eGMP 私有接口写的一层**约定驱动**代码。这些约定**没有一处**被真实数据验证过：

| 约定 | 位置 | 风险 |
|---|---|---|
| 对象编码后缀 `__c` / `__ak` / `__sys` | `auth.py:26`、`crawler.py:19`、`annotate.py:20-25`（**三处各写一遍**） | 任何新后缀/夹在中间的后缀 → 对象静默不发现 |
| 布局编码后缀 `_table__ak` / `_base_layout__ak` | `crawler.py:18` | 同上 |
| 初始/完成状态编码 | `auth.py:31-32`（`init_status__c` / `complete_status__c`） | 拼错即整条 L3 判定失准 |
| 字段 `dataType` 数字语义 | `auth.py:17`（引用型 = 13/15/16/23） | `DATA_TYPE_NAMES`（`auth.py:12-15`）**全仓库无人引用**——是死资产 |
| 工作流 `stepType` / `behaviorType` / `dispatchMode` 枚举 | `auth.py:19-24` | 表外取值静默丢弃（`flowgraph.py:80-87`） |
| 平台全局固定 GUID | `endpoints.py:21` | 硬编码魔法值 |
| 状态相关指标正则 `修改状态为[［\[]([^\]］]+)` | `flowgraph.py:19`（**`spider.py:87` 重复一遍**） | 把自然语言描述当结构化事实 |
| 分页终止条件 `hasNext` | `client.py:160` | 用 `is True` **严格同一性**判断 |
| Token 缓存文件名 `token-{env_id or 'cli'}` | `client.py:48-53` | 见 §3.C |

**并且**：`crawler.py` 的模块 docstring（`:8`）声明发现链是 **5 步**（含「探测 `BasicObject/QueryList` / `GetPageList` / `Page`」），
但全仓库 `grep QueryList` 只命中 `MenuGroup/QueryList`（`crawler.py:151`）——**第 4 步根本没实现**。
一个接手的人读文档会以为有兜底探测，实际上没有。

### 1.3 事实三：产物会「看起来完整」，即使它其实是残缺的

这是最危险的一类：**当前代码在多个位置把「失败」渲染成「成功」**。

| 位置 | 行为 |
|---|---|
| `insight/__init__.py:67` | `run_inventory` **无条件** `return {"ok": True}`，哪怕 0 个对象 / 全部失败 |
| `insight/__init__.py:88` | `run_understand` 只要 `succeeded > 0` 就 `ok:True`——10 个对象成功 1 个也算「成功」 |
| `routes_insight.py:113` | job 状态直接取 `result["ok"]` → 上面两条直接污染 `insight_runs.status` |
| `crawler.py:71` | `discovery_via` **无条件**写成 `menu+workflow(N ids)`，即使两个调用都抛异常（谎报发现渠道） |
| `crawler.py:136-138` | 字段读取失败 → `[]` + 一条 `failures` 记录 → 报告里表现为 `fieldCount: 0`，**与「对象真的没有字段」无法区分** |
| `crawler.py:104-105` | 对象验证时**任何**异常 → `None` → **403（无权限）与 404（不存在）完全同义** |
| `assemble.py:30,61` | `summary.picklistCount` 初始化后**从未累加** → 恒为 `0` |
| `assemble.py:20,35,84` | `unresolvedObjectIds` 的入参**没有任何调用方传**（`__init__.py:51-54`）→ 恒为 0 → 报告恒打印「（无）」 |
| `spider.py:158-163` vs `:182` vs `:284` | `stats` 用原始边表计数、分析用剪枝后的图、JSON 存原始表 —— **三者互相矛盾** |
| `spider.py:152` | 运算符优先级 bug：`a or b if c else d` 实际解析为 `(a or b) if c else d` → `workflowStep` 类边的 `source` 可能是 `None` → drawio 里出现字面量 `None` 单元格引用 |
| `spider.py:264` | `crawled.extend(scoped)` 让相关对象**按每个主对象重复一次** → `model["nodes"]` 出现重复 `obj:{code}` → drawio 重复 `mxCell id` + `stats` 重复计数 |

**这就是本文 §3 的第一条边缘规则要解决的问题**：一个残缺的洞察报告比没有报告更糟——它会让实施工程师基于错误的理解去配置平台。

## 2. 准备清单（按依赖顺序，前 4 项是「不做就别谈优化」）

### P0 —— 建立可验证性（2-3 周，其他一切的前置）

#### P0-1. 真实基线语料 + 回放夹具（**最高优先级**）

**现状**：`tests/fakes.py` 造的是**想象中的**平台响应。于是「改 insight」= 盲改。

**做法**：你手上已经有**唯一正确的工具**——`Monitor`（`services/egmp/monitor/`，已真机验证过 248 请求捕获）。
它本来是为「解读请求」设计的，但它天然产出的就是**带时序的真实响应语料**。

1. 用 Monitor 在**每个真实环境**上跑一遍四个命令，把「请求 + 响应」全量落盘为夹具集
   （示例租户 / 联邦 / 测试环境 / 培训——这四个环境的 schema 差异是**真实存在的**，不是假想）；
2. 建一个 `ReplayClient`（实现 `EgmpClient` 同一接口，从夹具回放），让 insight 全链路可离线跑；
3. 夹具集覆盖**边界样本**：零字段对象、无工作流对象、被拒绝权限的对象、字段数 >1000 的对象、
   含自环/环的对象、多选引用（dataType 23）、非 ASCII 编码对象、树形自引用对象；
4. 建立**golden snapshot 回归**：`pytest` 跑回放 → 产物与基线逐字节 diff，差异必须人工确认后更新基线。

> 这一项做完，后面所有工作才有意义。**在这一项之前不要动 insight 的任何逻辑**——包括「顺手修一下」。

#### P0-2. 环境与身份模型修正（**当前的正确性已被污染**）

这三条是**bug，不是优化**，且会让 P0-1 的录制结果本身不可信：

| 编号 | 问题 | 证据 |
|---|---|---|
| C1 | Token 缓存**只按 `env_id` 分键**，且缺省 `""` → 回落 `token-cli.json`。**A 环境的 token 会交给 B 环境的 base_url 使用**；同环境两个账号（示例租户 `dev-user`/`T0901`）**共享一个 token**，第二个账号实际以第一个的身份运行 | `client.py:48-53,72,79-81`；`routes_insight.py:33`（`env_id` 由客户端任意传入且可空） |
| C2 | `QueryCache` 是**进程级全局单例**，键只有 `meta:{code}`，**不含环境**。四个环境若在同一个服务进程里查过同一个标准对象编码，后查的会拿到**前一个环境的元数据** | `cache.py:40`；`queries.py:24,28,33` |
| C3 | `_trim_base` 只做 `rstrip("/")`，**不校验也不剥离路径**。实测数据里示例租户的 `base_url` 就是 `https://example-config.example.com/login` → 登录 POST 会打到 `.../login/api/openapi/v1.0/Auth` | `client.py:44-45`；真实 `platform_env` 数据 |

**动作**：token 缓存改按 `(base_url, username)` 分键并在载入时校验归属；缓存键加环境命名空间；
`base_url` 在写入 `platform_env` 时就归一化为 origin 并校验 scheme（拒绝带路径、拒绝非 http(s)）。

#### P0-3. 端点契约单一事实来源

**现状**：`writers/endpoints.py` 自称「权威常量表」，但 **insight 完全没用它**——它把同样的字面量又硬编码了一遍，
约 **14 处重复**（`crawler.py:77,86,135,151`；`spider.py:208,223`；`client.py:182,186`；`queries.py:39,46` 等），
另有 **6 个 insight 在用但表里根本没有**的端点（`Menu/GetMenuList`、`UserAction/GetList`、`UserAction/GetActionBar`、
`Status/Detail`、`GetWorkflowSteps`、`GetWorkflowStepWithDetails`）。

**动作**：把读路径端点全部收进一张 `egmp/endpoints.py`，insight 只引用常量；补上缺失的 6 个；
标注每个端点属于哪个命名空间——**`/api/openapi/v1.0/*`（版本化）与 `/api/platform/*`、`/api/config/*`（私有、无版本）契约不同**，
后者是平台升级时最先断的地方。

#### P0-4. 错误分类 + 「完整/部分/降级」三态

**现状**：`ApiError` 携带结构化 `code`（`client.py:30-35`），但**全仓库没有任何地方 catch 它**——
所有消费方都是 `except Exception` 然后 `str(exc)`（`crawler.py:62,83,93,104`；`insight/__init__.py:46`），
平台返回的错误码在边界处就被销毁了。同时 4xx/5xx 走的是 `httpx.HTTPStatusError`（**不是** `ApiError`，与 `client.py:28` 的 docstring 矛盾），
401 / 429 / 503 在类型层面无法区分。

**动作**：建立 sealed 错误分类（`AuthError` / `EnvelopeError(code,message)` / `HttpStatusError(status)` /
`NonJsonBody(status,snippet)` / `TransportError(kind)` / `SchemaError`，各带 `retryable`），
从单一收口点抛出；**并且**把「完整 / 部分 / 降级」三态写进产物与 `insight_runs.status`——
**取代现在 `ok:True` 的布尔谎报**。

### P1 —— 契约化与工具化（P0 之后，约 1 个月）

- **P1-1. 产物契约 v1**：为 `inventory.json` / `<code>.json` / `spider-network.json` 写 JSON Schema，
  加 `schemaVersion`、`platformVersion`、`coverage{discovered,read,denied,failed}`、`failures[]` 与 **run manifest**。
  现在**没有任何 manifest**，产物之间也没有交叉引用。
- **P1-2. 工具层合一（MCP 前置）**：仓库里现在有**两套互不相通的工具层**——
  `harness/tools.py` 是**正确的做法**（Pydantic 声明参数 → 自动生成 JSON Schema → 调用前校验 → 错误转观测），
  但它内置的 3 个工具全是通用工具（时间/读文件/读网页），**一个 egmp 工具都没有**；
  而 `routes_agent.TOOLS` 有 egmp 工具但参数是**散文描述**（`"account_id": "string（必填）"`），且 `run_insight` **同步阻塞**。
  你《钉钉MCP落地细节》§4.2 定的三条军规（枚举锁死参数 / 统一 `{code,summary,data}` 信封 / 长任务返回 `job_id`）
  **当前一条都没实现**。动作：把 insight 四个命令迁到 `harness/tools.py` 的 schema-first 注册表，再由此生成 MCP 工具清单。
- **P1-3. 长任务化**：`/api/insight/run` 是同步阻塞（`routes_insight.py:140`），
  `run_insight` 工具直接内联调 `_run_job`（`routes_agent.py:81`）。必须改成「提交 → 返回 `job_id` → 查询进度」，
  否则钉钉助理会干等到超时。
- **P1-4. 并发与配额**：现在无锁、无队列、无上限、无取消。`crawler.py:107` 用 `ThreadPoolExecutor(max_workers=8)`
  对平台并发 8 路，两个 job 并行就是 16 路。公司级共享一个只读账号后会直接冒犯平台限流。
- **P1-5. 保留策略**：`runtime/insight/**` 与 `insight_runs` **永不清理**（全仓库无 `rmtree`/`unlink`/`DELETE`）。

### P2 —— 能力深化（可选，按业务价值排序）

- **入边/反向引用**：现在只有出边（`relations.py` 只扫本对象字段），所以「孤儿对象」判定**不可信**——
  一个被 10 个对象引用的对象，如果它自己不引用别人，会被报成孤儿。
- **多跳/传递闭包**：现在严格单跳，无法回答「改这个字段会影响哪些下游」。
- **对象级差异比对**：两个环境/两个时间点的配置 diff——这是实施工程师真正高频的需求，
  而且**只需要产物契约稳定**（P1-1）就能做，成本远低于新命令。
- **LLM 层的可控化**：现在 `understand --llm` 用 temperature 0.3 直出摘要（`routes_insight.py:61`），
  无 prompt 版本、无引用溯源、无确定性回退。

## 3. 边缘规则（Edge Rules）—— 可作为验收清单直接使用

> 写法：**规则 → 为什么 → 当前违反点**。凡标 ⛔ 的是当前代码**已经违反**的，应直接进 issue。

### A. 发现边界（Discovery）

| # | 规则 | 当前违反点 |
|---|---|---|
| A1 | **发现集必须可解释**：产物必须能回答「这个对象为什么在/不在集合里」。「发现 0 个对象」必须可从产物诊断出原因 | ⛔ 候选编码全部落空时**不记录任何东西**（`crawler.py:100-105`），0 对象无法解释 |
| A2 | **区分 403 / 404 / 5xx**，不得合并为同一个 `None` | ⛔ `crawler.py:104-105` 任何异常 → `None` |
| A3 | **「成功但空」不等于「失败」**：`Listlayout/List` 返回空列表时必须继续尝试降级渠道，而不是丢弃该 objectId | ⛔ 降级分支只在**抛异常**时触发（`crawler.py:85-88`） |
| A4 | **`discovery_via` 不得谎报**：只有真正成功的渠道才可写入 | ⛔ `crawler.py:71` 无条件写入 |
| A5 | **后缀/标准性判定必须有单一事实来源** | ⛔ `auth.py:26`、`crawler.py:19`、`annotate.py:20-25` 三处各写一遍，且 `annotate` 用 `elif` 链——**无后缀的对象拿不到任何 trait** |
| A6 | **文档承诺的探测步骤要么实现，要么从文档删除** | ⛔ `crawler.py:8` 声明的第 4 步未实现 |
| A7 | **重复编码必须去重并记录冲突**（`foo__c` 与 `foo__ak` 可能同时验证通过 → 同一布局产出两个「对象」） | ⛔ 无去重、无冲突记录 |

### B. 读取边界（Read / Pagination）

| # | 规则 | 当前违反点 |
|---|---|---|
| B1 | **`hasNext` 必须宽容强制转型**（`True` / `1` / `"true"` 都算真） | ⛔ `client.py:160` 用 `is True` → 平台返回 `1` 则**静默截断在第 1 页（1000 条）** |
| B2 | **分页必须有 `max_pages` / `max_rows` 上限，且触顶必须显式失败**，不得静默截断 | ⛔ 无任何上限（`client.py:151-164`），平台若忽略 `pageIndex` 会死循环 |
| B3 | **单页端点必须显式声明「假设单页」**，并在结果接近阈值时告警 | ⛔ `Menu/GetMenuList`、`Listlayout/List`、`GetWorkflowSteps` 都走非分页 `get`（`client.py:138-146`），默认无限大 |
| B4 | **401/403 必须触发一次 single-flight 重新登录**，不得让 token 过期表现为「部分对象失败」 | ⛔ token 在客户端构造时烧进 header（`client.py:117`），**无刷新、无重试**；`run_inventory` 逐对象吞异常 → **token 过期 = 静默截断的「成功」盘点** |
| B5 | **Token 有效期必须校验 JWT `exp`**，不能只信本地 55 分钟墙钟 | ⛔ `client.py:72` 只写 `expiresAt = now + 55min` |
| B6 | **非 2xx / 非 JSON（HTTP 200 的维护页）/ `code != 0` 必须映射到分类错误**，并保留响应片段 | ⛔ 维护页 → `JSONDecodeError`，body 与 Content-Type 均丢弃（`client.py:133`）；3xx 不跟随且丢 `Location` |
| B7 | **读操作可重试**（幂等），但只对 connect/timeout/429/502/503/504 重试，带退避 + jitter + 尊重 `Retry-After` | ⛔ `services/egmp/` 全包**零重试、零日志** |
| B8 | **字符集必须有回退**（Content-Type 缺失/错标时不得直接 `UnicodeDecodeError`） | ⛔ 仅信 Content-Type，否则 UTF-8，无回退、无 body 捕获 |

### C. 环境与身份边界（Environment / Identity）—— **当前最严重的正确性问题**

| # | 规则 | 当前违反点 |
|---|---|---|
| C1 ⛔ | **Token 缓存必须以 `(base_url, username)` 为键**，载入时必须校验归属；**绝不允许 `''`/`'cli'` 兜底键** | `client.py:48-53,72,79-81` —— 跨环境/跨账号 token 混用 |
| C2 ⛔ | **元数据缓存必须按环境命名空间** | `cache.py:40` + `queries.py:24,28,33` —— 进程内跨环境污染 |
| C3 ⛔ | **`base_url` 必须是纯 origin**：写入时校验 scheme + 拒绝路径成分 | 真实数据里示例租户就带 `/login`；`client.py:44-45` 只 `rstrip('/')` |

## 4. 建议的推进顺序

```
第 0 步  P0-2 环境与身份修正  ── 不修它，任何录制/验证结果都不可信
第 1 步  P0-1 真实语料 + 回放夹具 + golden snapshot 回归   ← 最大的单点收益
第 2 步  P0-3 端点契约统一 + P0-4 错误分类与三态
第 3 步  §3.F 输出边界（F1/F4/F5/F7/F8）── 全是已复现的缺陷，成本低、风险高
第 4 步  §3.C/§3.B 补齐（capability 探测、重试、JWT exp）
第 5 步  P1-1 产物契约 v1 + manifest → P1-2 工具层合一 → P1-3 长任务化
第 6 步  P1-4 并发配额 + P1-5 保留策略
第 7 步  P2 能力深化（入边 / 多跳 / 环境 diff）
```

**一句话**：先把 insight 从「能跑」变成「能被证明是对的」（第 1-2 步），
再把它从「本机工具」变成「可被 MCP 调用的确定性服务」（第 5 步）。
**在第 1 步完成之前，不建议新增任何 insight 命令或字段**——那只会扩大未被验证的耦合面。

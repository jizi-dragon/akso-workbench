# ADR-0018：蓝图里的对象在平台上不存在时，**不许静默新建**——先报"找不到"、列相近对象、问用户

- **状态**：已采纳
- **日期**：2026-09-22
- **决策人**：用户定稿（原话见 §1）
- **影响面**：`workbench/services/egmp/orchestrate.py`（预检 + 运行闸门）、`workbench/plugins/factory.py`（新增只读工具 `factory_resolve_object`）、`workbench/services/egmp/writers/spec.py`（给模型看的规则文本）；新增 1 个工具（22 → 23），`docs/TOOLS.md` 由 `gen_tools_doc.py --write` 重生成
- **取代**：无（这是新增约束，不改既有决策）

---

## 1. 背景：为什么现在需要这个决策

**用户原话**（2026-09-22）：

> 「当用户描述的对象不存在时，要给用户提出找不到该对象，并列举出相似对象给用户选择，
> 并询问用户若都不存在时，是否需要新建。」

触发场景：我在真机上跑蓝图之前，**手工**先只读核对了对象 `test_0903__c` 是否存在才敢执行。
用户看到这一步后说"这是你自己说的，我觉得很棒，但是我觉得应该加一条规则"。

**为什么手工核对是必需的**（也就是不决策的代价）：

| 事实 | 出处 |
|---|---|
| 对象步骤是**幂等**的：`with_idempotency(idem.object_exists(code), create_object)` —— code 存在→**复用**，不存在→**新建** | `orchestrate.py::_object` |
| 而 `object_exists` 把查询异常**吞成 None**（`except Exception: return None`） | `writers/idempotency.py:25-30` |
| ⇒ 用户把 code 打错一个字，后果**不是报错**，而是**静默多出一个空对象**；用户以为改的是他那个 | 2026-09-22 实测（本 ADR 的判据） |

## 2. 决策

### D-1 预检必须报"找不到"，并列出**确实存在**的相近对象

`precheck_blueprint` 对每个对象 code：存在 → 维持原样（提示会复用）；不存在 → 追加
`{"kind": "missing", "code": …, "candidates": [...], "message": …}`。
候选由 `similar_object_codes()` 机械生成并**逐个真机探测**（只保留确实存在的）：

- 后缀变体（`x` ↔ `x__c`）、下划线/大小写变体；
- **末位数字 ±1 / ±2**（实测这条最有用：`test_0905__c` 因此命中 `test_0903__c`）；
- 上限 5 个候选，探测数有界（一个错 code 不会放大成几十次请求）。

> **为什么不用平台的"对象列表"接口**：实测**没有可枚举对象的端点**——14 个候选路径
> （`BasicObject/{List,GetList,Query,Search,PageList,GetPageList,GetObjectList,…}`）GET/POST 全 404，
> openapi 那条 `/BasicObject/list` 回空。所以"相似"只能靠机械变体 + 逐个探测。

### D-2 有候选时，运行闸门**拒绝写入**

`run_full_workflow` 在预检之后、任何写入之前检查 `needsObjectChoice`：非空即
`{"success": False, "needsObjectChoice": [...], "message": "…本轮未写入任何东西…"}` 返回。
**没有候选时照旧执行**（那才是正常的"新建对象"用法）——这条闸门只拦"疑似打错字"。

### D-3 给 agent 一个只读工具，把话术交到它手里

新增 `factory_resolve_object`（`Risk.READ`，入参 `{account_id, query}`）：找到就回
`code/name/id`；找不到就回候选清单 + **明确的话术指引**（念候选 → 问选哪个 → 都不对再问是否新建）。
规格文本（`factory_blueprint_spec` 的 `how_to_use`）里也写进了这条规则，
所以模型**在写蓝图之前**就会看到它。

| 层 | 拦什么 | 强制手段 | 为什么必须有 |
|---|---|---|---|
| 规格文本 | 让模型**知道**要先确认 | 声明（**不是强制**） | 模型看不到规则就不会照做 |
| 工具 `factory_resolve_object` | 把"查存在性"变成一个**可调用的动词** | 无副作用（只读） | 没有这个动词，模型只能"问用户"，而它问不出候选 |
| 运行闸门 | **真的拦住写入** | 代码强制（返回 False，不进入执行） | 前两层都可能被绕过（直接 HTTP、模型忘了查） |

## 3. 本期做与不做

**做**：预检报 missing + 候选；运行闸门拒绝；新增只读工具；规格文本；回归测试
（`tests/test_native.py::test_missing_object_with_similar_candidate_blocks_the_run`）。

**不做（明确）**：

- ~~真机验证"新建对象"这条正常路径不受影响~~ —— 现状本来就是"没有候选 ⇒ 继续执行"，
  旧测试覆盖了这条路径；
- **不做**"平台对象列表"式的全局相似搜索：端点不存在（§2 D-1 的注），要做得先补采读面（见 §5）。

## 4. 后果

**好处**：把"打错 code ⇒ 静默多一个空对象"这条**不可见**的失败路径，变成一次**可见的提问**；
候选清单是机械产的、可复算的；平台的脏数据不再由"一个字母的笔误"产生。

**代价**：预检多几次探测请求（有界，≤ 约 10 次/对象）；"确实要新建一个字段名很像的对象"这种
真实场景会**多一次交互**（这是刻意的取舍：多问一句 vs 多一个空对象）。

**风险**：候选只能覆盖"形状相近"（数字/下划线/后缀），**语义相近但形状差得远**的找不到
（例如用户说"测试09-03"而平台上是 `qa_sample__c`）——那时闸门不会拦，只会在 `missing` 里
留一条"也没有找到相近的"，并靠工具话术让模型去问用户。

## 5. 诚实边界

**这条规则不保证"用户描述的对象一定被正确解析"**，它只保证三件事：
① 找不到时会说"找不到"；② 形状相近的会被列出来；③ 有候选时**不会**顺手建一个新的。

**它做不到**：中文名称 → code 的映射（平台没有"按名称查对象"的端点，实测 404）；
全局相似搜索（同上）；以及**绕过工具直接打 HTTP**时的行为（那时只有 `confirmed` 那道闸）。

## 6. 外部参照

| 参照对象 | 它的做法 | 与本决策的关系 | 我们的理由 |
|---|---|---|---|
| Terraform（`terraform plan` / `import`） | plan 只**声明**将要发生什么；对"已存在的资源"要么报错要么要求显式 `import`，**不会**因为"看起来像"就改别的资源 | **分歧**：我们没有 plan 的强约束，而是"预检 + 拒绝 + 问" | 我们的执行入口是**对话**（人在环里），不是 CI；把选择权交回人是这个产品的核心形态，所以选择"问"而不是"硬失败" |
| `kubectl apply` | 按名字**创建或更新**（upsert），打错名字就**创建出一个新对象**——与本仓旧行为一模一样 | 一致（这是被我们否掉的**反面**参照） | 实测代价：K8s 里打错名字会多一个 Deployment，人能 `kubectl get` 看见；而我们的平台里"多出来的空对象"**没有任何提示**，且删除要走界面 |
| Google Cloud CLI / `gcloud` 的 `--quiet` 与"资源不存在"提示 | 资源不存在时**明确报错**并给出候选（有的命令给相似资源建议） | 一致 | 行业共识：**"不存在"要出声**，不要静默创建 |
| AkSx（上游 `akso-auto` 的 `name-resolver.js` 口径） | 只做"名称/编码冲突"提示，**没有**"不存在 + 候选"这一半 | **分歧**：我们补了另一半 | 上游只防"重名"，不防"打错"；而我们的对象步骤是幂等的，"打错"才是主要风险 |

**由本次对照得出的结论**：

- **可以简化**：候选生成不必发明算法——"机械变体 + 逐个探测"与 `gcloud` 的做法同类，够用；
- **必须自己定**：**"有候选 ⇒ 拒绝写入"这个取舍是我们自己的**（Terraform 会硬失败、kubectl 会静默建、
  gcloud 会报错但不拦），我们选择"先问人"，因为本产品的执行者是对话里的 agent，而它**能把候选念给用户听**。

## 7. 重新评估的触发器

| 触发器 | 到时再考虑 |
|---|---|
| 平台补出"对象列表 / 按名称查对象"的端点（或我们补采到读面并证实存在） | §2 D-1 的候选生成改成**真的相似度搜索**（名称 + code 一起比），并放宽候选上限 |
| 出现"用户确实要新建一个与现有对象形状相近的对象"的真实需求 ≥ 2 次 | 给闸门加一个显式的"我确认要新建"信号（例如蓝图顶层 `createObject: true`），而不是靠"改 code 让它不像" |
| 对象步骤不再幂等（例如改成"必须显式指定复用哪个 id"） | 本 ADR 的前提消失，可整体重新评估 |

## 8. 补记：显式意图位 `createIfMissing`（**这段是后补的**，2026-09-22 晚，用户下达「方案1」）

> ⚠️ 本节是**事后追加**的，用来让"决策当时的认知"与"后来的认知"都能看见（体例同 ADR-0014）。
> 上面 §1–§7 **一字未改**。

### 8.1 触发它的现场（真机，n=1）

2026-09-22 15:07，用户在界面上说「我需要你建一个对象「测试09-04」」。模型**完全按本 ADR 执行**：
先 `factory_resolve_object` 查存在性 → 报告"找不到，相近的有 `test_0903__c` / `test_0902__c`" →
**问用户**「确认要新建吗」→ 用户答"确认" → 蓝图校验通过、暂存 → 调 `factory_create`。

**结果：仍然被拒**（`job 4b20a7b32fee` failed，平台侧零写入），而且**同一份蓝图重试多少次都回同一个拒绝**
——因为 §2 D-2 的闸门是**确定性**检查，它**看不见对话**："用户批准过"不是它能认的输入。
完整复盘见 [factory-tuning/reports/2026-09-22-会话复盘-测试09-04创建被拒.md](../factory-tuning/reports/2026-09-22-会话复盘-测试09-04创建被拒.md)。

### 8.2 为什么 n=1 就动手（§7 的触发器写的是 ≥2 次）

§7 假设这个场景"偶发"。实测下来它**结构性必然**：本平台的测试对象是**流水号命名**
（`测试09-01/02/03`），而候选生成里含"**末位数字 ±1/±2**" ⇒ **下一个编号必然被判成"像打错字"**。
也就是说，用户**按自己的命名习惯往下建**时，误报率是 100%（本次 n=1 全中）。
更关键的是：它问的那句「是否需要新建」（§2 D-3 的话术）**没有出口** ——
问了、答了，仍然建不了，这直接违背本 ADR 想买的东西（"把选择权交回人"）。

⇒ 因此把 §7 的触发器判定为**已命中**，并按它预告的方向实现（键名取 `createIfMissing`，
而不是当时草拟的 `createObject`，因为语义是"**这个对象不存在时按新建处理**"，
与"总是新建"不同）。

### 8.3 补的决策（新增 D-4，D-1/D-2/D-3 不变）

| # | 决策 | 强制点 |
|---|---|---|
| **D-4** | 蓝图对象上可写 **`createIfMissing: true`**：写了它，§2 D-2 的闸门**不再因"存在相近对象"拦截**；不写则行为与原来完全一致 | `orchestrate.precheck_blueprint`（`needsObjectChoice` 只收 `candidates and not createIfMissing`） |

配套（都属于 D-4 的"看得见"要求，不是新决策）：

- **放行要留痕**：被放过的相近对象进 `precheck.overridden`，并在运行日志里写一行
  `⚠ <code>：平台上有相近对象（…），但蓝图显式声明 createIfMissing=true ⇒ 按**新建**执行`
  —— **放行 ≠ 装作没看见**；
- **可机检**：`tests/test_native.py::test_explicit_create_if_missing_lets_the_run_through`
  （不写⇒拦 / 写了⇒放行且真的建出来 / 相近对象仍被记录）；
- **规格面**：`spec.py` 的 `how_to_use` 与 `_NOTES`、`factory_resolve_object` 的话术都改成
  "用户确认新建后 ⇒ 在该对象上写 `createIfMissing: true` 再重跑"。

### 8.4 诚实边界（这条补丁**没有**解决的）

1. **它不校验"模型是否真的问过用户"**：写这个键仍是模型自律（与 `needs_confirmation` 同一纪律，
   见 [ADR-0016](0016-model-initiated-confirmation.md) §5）。它买到的是"**用户确认之后有路可走**"，
   **不是**"没确认就走不了"。
2. **它没让闸门变聪明**：候选仍是"形状相近"，语义相近而形状差得远的照旧找不到（同 §5）。
3. 真机验证范围有限：本次放行路径跑通了一次（`test_0904__c` 建成并回读通过），
   **n=1**；而"不写它 ⇒ 仍拦"是单元判据（`FakeEgmpClient`），不是真机。

## 1. 背景：为什么需要这一组决策

> 三块独立的问题被放在一篇里，因为它们是**同一个系统的同一面**：浏览器是执行体，
> 扩展是执行面，而 `browser_pool` 是唯一能驱动浏览器的通道 —— 任何一条定错，
> 另外两条的结论都会跟着失真。三节的出处分别标在各自标题旁。

### 1.1 两种「在浏览器里以某账号身份动作」的能力并存（原 ADR-0002）

项目同时具备两种能力：

1. **扩展执行面**：Chrome MV3 扩展跑在**用户自己的 Chrome** 里，做六平面隔离与会话切换；
2. **托管浏览器**：`browser_pool` 用 Playwright（sync）驱动浏览器，做自动登录、免密持久化、
   状态墙、以及 Monitor 监听录制。

两者都能「打开某个账号」。若不定政策，会出现同一功能有两条实现路径、以及**同一账号被两处同时操作**
的风险。更早的形态（0.2.2 之前）确实存在这种混杂：pytest 与运行时夹具都曾各自起 chromium。

### 1.2 两套账号数据并存（原 ADR-0004）

> ★ **2026-10-09 后补（只追加，以下原文一字未改）**：这一节描述的是**已退役的形态**——
> `extensions/quick-login/` 与它带来的"两套账号数据"问题都已随扩展移出本仓库。
> **但这一节的核心结论仍然是本仓最有价值的决策之一**：**账号数据的真源只有一个（桌面端）**。
> 今天这条纪律的形态是"云端账号库（akso-vault）与桌面本机库的关系"：
> 桌面端登录云端后，真源的选择与切换语义需要同样明确——不要造出第二套能改账号的地方。
> 取回当时形态：`git show 34b5e94:extensions/quick-login/README.md`。

`extensions/quick-login/` 是上游 quick-login 项目的 fork。上游是**纯浏览器形态**：
扩展自带并行管理主页 `ui/parallel/`，用户在扩展里直接增删改账号，账号档案存在扩展的 IndexedDB。

本项目 fork 之后，账号数据的真源移到了桌面端（SQLite + Fernet），于是出现**两套账号数据**：

- 桌面 `account` 表（账号中心 UI 在改）；
- 扩展 IndexedDB `accounts`（上游 UI 在改，且本项目已把并行页隐藏）。

后果是双向的：两边都能改却没有对账协议，且上游那套「会话模型」——`session-manager.ts` /
`account-registry.ts` / `navigation.ts` + `session.*` 消息协议——与桌面端的 `par.open` 语义重叠，
留下来只会让人不知道该走哪条路。

### 1.3 Playwright sync 的三条硬约束（原 ADR-0006）

托管浏览器（`services/browser_pool.py`，624 行）需要同时满足三件事：

1. **多账号并行**：一张卡片一个账号，多个账号同时在线、互不干扰（用户明确要求「任务栏归组、
   同一浏览器应用内多窗口」）；
2. **Web 服务并发**：FastAPI 把并发请求派到线程池的不同线程；
3. **Playwright sync API 的硬约束**：**sync API 绑定创建它的线程，且非线程安全**。
   跨线程使用会抛 greenlet 错误（历史上的「浏览器启动失败」正是这个根因）。

另有一个更隐蔽的约束：**同一个线程里不能起第二个 `sync_playwright()` 实例**——会死锁。

### 1.4 一条"拿到即等于拿到口令"的路（原 ADR-0015）

`GET /extension/snapshot` 会**同时**下发：

- `fernetKey`（Fernet 密钥本体）；
- 每个账号的 `passwordEnc`（密文凭据）。

密钥与密文一起给出去，等于**明文口令**。而整条 `/extension/*` 此前**没有任何鉴权**，
唯一的屏障是"服务只监听 `127.0.0.1`"。这就是 `CODEBASE_OVERVIEW.md` §九 的 **R1**：

> 本机任意进程可拉快照（快照里**同时含 Fernet 密钥与全部密文口令**，等于直接拿到所有测试账号明文）
> —— `routes_extension.py:26`；`accounts.py:432-464`

#### 为什么"只监听回环"不够（原 ADR-0015 §1.1）

回环把**网络**攻击者挡在外面，但本机上的**任何**代码都能发这个请求：

| 敲门者 | 后果 |
|---|---|
| 用户浏览器里的**任意网页**（`fetch('http://127.0.0.1:18765/...')`） | 读不到响应（CORS 挡着），但**能造成副作用**——`POST /extension/commands` 可注入 `par.open`，触发扩展去打开页签并自动填口令 |
| 本机任意进程 / 脚本 | 一次 GET 拿到密钥 + 密文 = 全部账号明文 |
| 别的应用里的 WebView / 被安装器塞进来的辅助进程 | 同上，且**用户完全不知情** |

R1 在台账里挂了很久没修，原因是它**没有症状**：功能一切正常，注入的指令也能跑。

#### P0-4 的教训直接指向这里（原 ADR-0015 §1.2）

上一轮补 `/extension/*` 的 pytest 覆盖时发现：这一整块是**凭据下发口 + 指令队列宿主 +
"扩展是否需要重新加载"的判定源**，却**一条测试都没有**。C4（队列永不排空）能在仓库里
躺那么久，根因就是"暴露面最大、回归网最薄"。

所以原 ADR-0015 的目标不只是"加一个头"，而是**把这条通道纳入有测试、有机检的守备范围**。

## 2. 决策

### 2.1 浏览器分配政策（**原 ADR-0002**）

**按用途分配浏览器，而不是按功能模块分配：**

| 用途 | 浏览器 | 理由 |
|---|---|---|
| **快捷登录 / 打开账号**（用户手动切换到某身份去操作） | **用户自己的 Chrome**（经扩展 `par.open`） | 要的是「以该身份操作的真实效果」——真实 profile、真实代理、真实插件、真实书签。若用内置 Chromium，用户面对的是一个空 profile，很多站点体验不一致 |
| **监听 / 自动化 / 录制 / 批量动作** | **应用内置 Chromium**（`browser_pool`，CDP 模式即 Electron 壳的 Chromium） | 要的是可控、可录制、可复现、**不污染用户浏览器**。用户 Chrome 里塞自动化会污染其真实 profile，且扩展的隔离平面会干扰录制 |

配套硬性规定：

1. **Playwright sync 单线程单实例**：所有浏览器操作必须走 `BrowserPool` 专职工作线程队列；
   **测试不得另起 chromium 夹具**（见本文 §2.3）。
2. **`local` / `cdp` 双模式**：`WORKBENCH_SESSION_MODE=cdp` 时托管会话复用 Electron 壳的 Chromium
   （先 `:18767` 开户再 `connect_over_cdp(:18766)`）；否则本地 Playwright chromium。
   这样开发/无壳环境仍能跑全链路，测试也不依赖 Electron。
3. 快捷登录链路必须有 `launch-chrome` 前置：**Chrome 未运行时扩展 SW 不会轮询指令**，
   此时点击轮盘选人，指令只会滞留在队列里（所以桌面在派发前先探测/拉起 Chrome）。

#### 被放弃的方案（原 ADR-0002）

**方案 A：全部用用户 Chrome**

- ✗ 无法录制/回放：扩展不暴露网络录制能力，Monitor 的三级降噪（`dropped`/`trimmed`/`full`）
  需要 Playwright 的 `page.on("response")` 与 DOM 动作缓冲。
- ✗ 六平面隔离会**主动改写**请求（AUTH/CACHE 平面），录制到的流量不是平台的真实行为。
- ✗ 用户关闭浏览器即中断所有自动化。

**方案 B：全部用内置 Chromium**

- ✗ 失去「真实 profile 效果」——用户最常抱怨的正是「登录进去了但站点行为不对」。
- ✗ 凭据要经内置浏览器中转，扩大凭据暴露面。
- ✗ 平台的设备指纹/SSO 策略对全新 profile 未必友好。

**方案 C：按功能模块分（洞察走 A、工厂走 B）**

- ✗ 政策会随模块演进反复漂移，无法作为维护红线。
- ✗ 同一账号在两处并发操作的问题依然存在。

**代价（已接受）**

- 两套浏览器链路都要维护（扩展 TS + Playwright Python），且**两边的自动登录节奏门控参数各有一套**
  （扩展 `auto-login.ts` / Python `autologin.py`，见 [CONFIG.md](../CONFIG.md) §4）。
- 扩展侧必须保证「桌面不可达时静默跳过」（离线回退），否则用户不开桌面端时扩展会反复报错。

#### 后果（原 ADR-0002）

- 端口的职责被固化（[API.md](../API.md) §0）：`:18765` 服务、`:18766` CDP、`:18767` 壳控制服务。
  **CDP 端口必须在 Electron `app ready` 之前设置**（`app.commandLine.appendSwitch`），
  否则 Playwright 无法挂接。
- 「同一账号同时被扩展与托管会话操作」在语义上**未被禁止**——目前靠 UI 入口区分（卡片上的
  「打开」vs「快捷登录」/「开始监听」）。**这是一处仍待产品决策的边界。**
- 真机验收基线因此分两侧：托管侧 `tests/test_browser_parallel.py` / `test_browser_state.py`；
  扩展侧 `tools/verify_extension_*.py` / `acceptance_extension_e2e.py`。

### 2.2 扩展 = 执行面，数据面归桌面（**原 ADR-0004**）

**扩展 = 执行面（Execution Plane），数据面（Control/Data Plane）归桌面。**

| 归属 | 内容 |
|---|---|
| **扩展负责** | ① 六平面隔离（存储 / AUTH / COOKIE / CACHE / SW·CacheStorage / IndexedDB）；② 会话切换 `par.open`；③ 登录表单自动填表；④ 轮盘呼出 `wheel.toggle`；⑤ 状态上报；⑥ 在 `sync.ts` 里对账桌面快照 |
| **桌面负责** | 账号 / 盒子 / 站点的全部增删改；凭据 Fernet 加密存储；托管浏览器与监听录制；全部 UI 入口 |

具体动作（原 ADR-0004）：

1. **删**：死文件 `ui/parallel/*`（1,290+130+629 行）与 `ui/send.ts`；旧会话模型三件套 +
   `session.*` 协议 + `Session` 类型 + `sessionTabBindings`；并行页专用协议
   `par.create/update/delete/moveBox/renameBox/deleteBox/probeScheme` + `data.export/import`（SW 死分发约 275 行）。
   合计 **净删 2,849 行 / 18 文件**。
2. **留（别误删）**：`parallelStore` 的增删改（`sync.ts` 直接调用 = 活数据面）；
   `site-auth.ts` + `site.grants.*` + `par.grantChanged`（0.2.21 定稿保留的授权/停用核心，
   现状为**休眠源码**）；`ql.diag`（诊断）；`wheel.toggle`（桌面通道）。
3. **单一真源**：协议键只在 `shared/constants.ts` 定义；host/端口五函数收归 `background/core/host.ts`；
   `applyTitle` → `tabs/tab-title.ts`；待登录凭证 → `core/pending-login.ts`。

#### 换来什么（原 ADR-0004）

- **数据只有一个真源**（桌面 SQLite），消除「两边都能改」的分裂。
- 扩展的职责边界变得可验证：`sync.ts` 是唯一入口，实体是快照 + 映射表（`akso:acctMap`）。
- ~~上游同步的冲突面缩小：本项目只需维护一份「私有改造清单」~~
  （该清单原先记在 `extensions/quick-login/CHANGELOG.md`）。
  **2026-09-29 后补**：上游协作已终止，**"同步冲突面"这个收益随之消失** —— 改造清单仍然要维护，
  但它现在服务的读者是**本项目**（"哪些改动别误删"），不再是"下次同步上游要摘哪些"。
  **2026-10-09 后补**：浏览器扩展本身也已整体移出本仓库（用户决策：桌面端与扩展不耦合），
  连那份改造清单一起删除了。取回原文：`git show 34b5e94:extensions/quick-login/CHANGELOG.md`。

#### 代价（已接受）（原 ADR-0004）

- **扩展脱离桌面不可用**：账号数据不再能在扩展里自建。桌面不可达时扩展只能跑本地已有数据
  （「离线回退」：`getJson` 返回 `null` 即静默跳过，本地账号仍可用）。
- **跨进程协议成为关键路径**：快照幂等、指令游标、状态上报三件套一旦出问题就是**静默失效**
  （不报错、只是不动）。因此协议契约被写进 [SCHEMA.md](../SCHEMA.md) §5 与 [API.md](../API.md) §11/§12.3。
- **上游同步要反复摘除**：`ui/parallel` 与 Page Monitor 之类会在上游新版里回来，
  必须按清单再删一次（清单已落 CHANGELOG）。
- **休眠源码的技术债**：`site-auth.ts` 保留但不参与现行授权链路（0.2.21 改声明式全站权限后
  只剩「用户手动停用名单」语义），属于「保留以防回退」而非「正在使用」。

#### 后果（原 ADR-0004）

- 协议三面（数据/指令/状态）的语义与护栏成为扩展侧最需要读的代码路径。
- **四条实锤护栏**（都源于这次收敛之后暴露的问题，改动 `sync.ts` 前必读）：
  ① `snapshotId` 幂等；② 空快照护栏（否则桌面瞬时半量快照会删光本地账号）；
  ③ `consuming` 互斥（防同一 `par.open` 开两个页签）；④ `streaming` 幂等 + `longPoll` 退避（防热循环）。
- **关联决策**：扩展的凭据投递语义（密文 + 密钥经回环下发）见本文 §2.4 与
  [ADR-0007](0007-credentials-sandbox-and-trust.md)——注意它的**已知风险窗口**（明文凭据 60s 投递窗口读后不删）。

### 2.3 `browser_pool` 单专职线程串行化（**原 ADR-0006**）

**`BrowserPool` 持有唯一的专职工作线程，所有浏览器操作以 `Future` 提交、在该线程内串行执行。**
Playwright 与浏览器对象**只在该线程内存在**，线程外只拿到 `Future` 的结果（会话快照）。

```python
def _submit(self, job, timeout=None):
    future = Future()
    self._jobs.put((future, job))     # queue.Queue
    return future.result(timeout=timeout)   # 线程外阻塞等待

def _worker(self):
    # 打包态：先设 PLAYWRIGHT_BROWSERS_PATH 指向随包 chromium（必须在 sync_playwright 前）
    pw = None
    browsers: dict[bool, Any] = {}     # headful 标志 → browser（local 模式）
    sessions: dict[str, SessionEntry] = {}
    while True:
        future, job = self._jobs.get()
        try:
            result = job(pw, browsers, sessions)
            for entry in sessions.values():        # ← 关键：作业间隙统一 drain
                if entry.monitor is not None and getattr(entry.monitor, "_active", False):
                    entry.monitor.drain()
            future.set_result(result)
        except Exception as exc:
            future.set_exception(exc)
```

三条派生的硬性规则（原 ADR-0006）：

1. **事件回调内禁止任何连接调用**（`response.text()` / `page.evaluate` / `page.goto` 重入 = worker 死锁）。
   事件回调**只能入队**，在 worker 的作业间隙（上方的 `monitor.drain()`）统一处理。
   这是 0.2.2 修掉的严重缺陷，也是 `egmp/monitor/monitor.py` 三级降噪（`dropped`/`trimmed`/`full`）
   的存在原因——录制期间不能就地处理响应体。
2. **CDP 模式三律**：`remote-debugging-port` 必须在 Electron `app ready` **之前**用
   `app.commandLine.appendSwitch` 设置；**先 `:18767 /windows` 开户、再 `connect_over_cdp(:18766)`**
   （Electron 33 实测：窗口必须先于 connect 存在才可见）；
   Playwright 实例由 `_CdpState` **单一持有**（`browsers[True]` 是 `_CdpState`；同线程第二个
   `sync_playwright()` 会死锁）。
3. **CDP 连接按开户次数追加、旧连接保持存活**（`_CdpState.connections`），
   其会话句柄继续有效；`close_all()` 才统一清理。

#### 换来什么（原 ADR-0006）

- 彻底消除跨线程 greenlet 错误——这是历史上「启动失败」的根因。
- 多账号并行靠**同一 browser 多个 context** 实现（每账号一个独立窗口），
  既满足「任务栏归组」，又拿到 context 级原生隔离（cookie/storage 天然分开）。
- 状态与副作用集中在一处：`sessions: dict[account_id, SessionEntry]` 是唯一真源，
  自愈计数、监听句柄、token 捕获都挂在这个 dataclass 上。

#### 代价（已接受）（原 ADR-0006）

| 代价 | 表现与处置 |
|---|---|
| **全局串行**：一个慢操作阻塞所有账号的操作 | 这是有意换取正确性。缓解：多数作业无超时（见下）反而是隐患的另一面 |
| **无超时会挂死 HTTP 请求** | 只有 `monitor_start` 显式给了 `timeout=90`（因为可能要开户 + 等 CDP 定位）；`open_account` / `session` / `navigate` 等**无超时**——页面卡住时请求会一直挂着。见 `../CODEBASE_OVERVIEW.md` §九 的风险台账 |
| 事件回调纪律容易被违反 | 新增录制/监听能力时必须走「入队 + drain」，且**没有测试能拦住违规**（表现为运行期死锁，不是断言失败） |
| 测试必须复用该池 | **测试不得另起 chromium 夹具**（`tests/conftest.py` 只隔离数据目录；`test_browser_parallel.py` 用本地 `http.server` 模拟平台 + 池本身）。生命周期收尾靠 `pool.close_all()` |

#### 后果（原 ADR-0006）

- **`browser_pool` 是进程级单例**（`get_pool()` 持 `_pool_lock` 惰性创建），
  其工作线程随进程存活（daemon 线程）。
- **关窗 ≠ 停监听**：`_close_entry()` 落盘登录态、关 context、置 `stopped`，但**不清 `entry.monitor`**
  ——监听会话对象仍留在 `SessionEntry` 上直到 `sessions.clear()`。见 `../CODEBASE_OVERVIEW.md` §九 的风险台账。
- **`_close_entry` 的 finish 判定存在缺陷**：它在判定前就把 `entry.status` 置为 `"stopped"`，
  导致 `detail` 里的 `entry.status == "online"` 恒为假，首次登录的会话关窗会误报「已关闭」
  （应为「已关闭（登录态已保存）」）。见 `../CODEBASE_OVERVIEW.md` §九 的风险台账。
- **真机验收入口固定**：`GET /api/browser/check`（chromium 可执行文件体检）、
  `tests/test_browser_state.py`（storage_state 5 项）、`tests/test_browser_parallel.py`（双账号并行/免密/自愈 4 项）。

### 2.4 `/extension/*` 引入访问令牌（**原 ADR-0015**）

> ★★ **2026-10-09 后补：整节已随扩展一起退役（只追加，以下原文一字未改）**。
> 用户决策：**桌面端与浏览器扩展不耦合**——本仓只需账号库管理页来承接云端数据环境。
> 随之删除的是：`/extension/*` 整段蓝图（`workbench/api/routes_extension.py`）、
> 访问令牌中间件（`workbench/api/extension_auth.py`）、`extensions/quick-login/` 源码树、
> 随包携带扩展的打包步骤（`extraResources`）、桌面轮盘窗与「安装浏览器扩展…」引导。
>
> **本节记录的问题与教训仍然有效，不要删**：
> - **D-2 / D-6 的命名空间纪律**依然成立且更有价值——`/api/shell/*` 之所以独立成前缀，
>   正是这一节推出的结论。`routes_shell.py` 今天还在，只是少了 `setup-helper`。
> - **D-1 那张否决表**（为什么不信 `Origin`、不用 mTLS、不引 IPC）是**通用推理**，
>   将来若要给 `/api/*` 加认证，先读它，别重新踩一遍。
> - **D-5 的 grace 窗口**思路（新协议要求不能让旧客户端静默失灵）在**任何**客户端升级场景都适用。
>
> 取回本节所指代码的原文：
> `git show 34b5e94:workbench/api/extension_auth.py`、
> `git show 34b5e94:workbench/api/routes_extension.py`、
> `git show 34b5e94:tests/test_extension_auth.py`。

#### D-1 用**共享令牌**，而不是"来源校验"或"进程级 ACL"

| 方案 | 为什么否决 / 采纳 |
|---|---|
| **只校验 `Origin`** | ❌ **不可靠**：扩展 service worker 发跨源 `fetch` 时是否带 `Origin`，取决于浏览器实现与请求模式（简单请求 vs 预检）。本机无法实证，**不能把安全建立在没验证过的浏览器行为上** |
| **只信 `sender.frameId === 0`**（扩展侧） | ❌ 同族错误已在 P0-2 踩过：`auto-login.ts` 的**子 frame 也会各自索取**（跨域 SSO 登录框靠这条路径），按 frame 收口会打死合法路径 |
| **mTLS / 客户端证书** | ❌ 架构上没有载体：扩展与桌面之间只有 `fetch`，装不了客户端证书 |
| **命名管道 / 文件句柄** | ❌ MV3 扩展没有文件系统访问；且桌面壳与 Python 之间已有端口契约（[ADR-0011](0011-port-governance.md)），再引一条 IPC 通道是净增复杂度 |
| **共享令牌（采纳）** | ✅ 唯一在"扩展 ↔ 本机 HTTP"这一约束下能表达"持有者身份"的机制；且**浏览器侧的预检天然挡住网页**——自定义头会触发 CORS 预检，服务端不授予跨源许可，**浏览器根本不会发出那个请求** |

#### D-2 令牌**落库、跨重启稳定**

令牌存 `settings.extension_access_token`（`secrets.token_hex(32)`），**不是**进程内存态。

理由：装在用户 Chrome 里的扩展必须能长期持有它。若每次桌面重启都换令牌，扩展会拿旧令牌
狂刷 401 —— 而它看起来像"扩展坏了"，用户唯一的出路是重新加载扩展。
落库后 `WORKBENCH_AUTO_UPDATE` 类的"重启即变"问题不会出现在这里。

#### D-3 走**中间件按前缀守备**，不走逐路由 `Depends`

FastAPI 的依赖是**逐路由**声明的：漏加一条就静默开一个口子，而"新增路由忘了加依赖"
正是这类防护最常见的失效方式。中间件按**路径前缀**统一判定，于是
**"新加的路由自动被守住"是结构保证**，不是纪律。

代价：豁免面集中在 `EXEMPT_PATHS` **一处**（`/extension/hello` 与 `/extension/health`），
新增豁免必须显式登记。这是刻意的——豁免面越小，"整个前缀需要令牌"这句话才越接近真的。
`tests/test_extension_auth.py::test_exempt_surface_is_minimal` 钉住它。

#### D-4 自举端点 `/extension/hello`：免鉴权，但**必须保持最小**

扩展必须先拿到令牌才能访问需要令牌的端点 —— 这是死锁，所以自举端点必然免鉴权。

它**只回** `{format, version, token, desktopVersion, header}`，**不含任何账号数据**。
`test_hello_returns_only_bootstrap_fields` 按**字段集合**断言（不是"有没有 token"）：
往这里加一个便利字段，就等于把 R1 重新打开一部分。

#### D-5 **宽限期（默认 24h）**，而不是立刻硬失败

令牌是**新加的协议要求**。已装在用户 Chrome 里的**旧扩展不会带令牌**：

| 处置 | 后果 |
|---|---|
| 立刻硬失败 | "快捷登录静默失灵、且没有任何提示" —— 正是本仓反复踩的那类静默故障 |
| **宽限 24h（采纳）** | 旧扩展在这段时间照常可用；同时留 warning，并让桌面 UI 提示用户重新加载扩展 |

窗口起点**落库**（`settings.extension_auth_grace_started_at`）、**只记一次**：
放进程内存态会被每次重启重置，等于永久开着窗口。
`WORKBENCH_EXTENSION_AUTH_GRACE=0` 可切成严格模式——现场排障需要它来分诊"扩展连不上"。

#### D-6 把"壳协作面"迁出 `/extension/*` → `/api/shell/*`

这一步看起来与安全无关，实际是 D-3 能成立的前提。

原先 `/extension/*` 上挂着三条**给桌面 UI 用、且完全不碰凭据**的端点：
`/launch-chrome`（拉起 Chrome）、`/setup-helper`（请壳打开 `chrome://extensions`）、
`/update-state`（读壳落盘的更新状态）。调用方是账号中心与页内轮盘，**同源页面**
（`http://127.0.0.1:18765`）——而令牌只发给扩展，UI **拿不到也不该拿到**它
（页面里放令牌等于把它交给任何能读 DOM 的东西）。

于是只能给这三条开豁免。但**豁免一开，"整个前缀需要令牌"就退化成一份人工维护的清单**——
正是 D-3 想消灭的东西。

**所以按"碰不碰凭据"重新划边界**：

| 命名空间 | 内容 | 令牌 |
|---|---|---|
| `/extension/*` | 扩展 ↔ 桌面之间的**数据与指令**通道 | **必需**（豁免仅两条） |
| `/api/shell/*` | 桌面 UI 请**壳**干活（拉起浏览器 / 安装引导 / 读更新状态） | 不需要（也**不碰凭据**） |

这条边界有两条守护：`routes_shell.py` 的模块文档串写明判据（"新增端点前先问：它碰凭据吗？"），
以及 `test_extension_blueprint_has_no_ui_only_routes`。

#### D-7 **不**给 `/api/*`（95 个端点）加令牌

`/api/accounts/export`（导出备份，含密钥）与 `/api/browser/sessions/{id}/token` 同属敏感面，
但它们**同源**：桌面 UI 就是这个服务加载的页面，加令牌要么在页面里放令牌（等于没加），
要么改页面引导流程（净增复杂度、收益低于本 ADR）。

**如实记录这个取舍**：R1 的"零知识一次 GET"已经在 `/extension/*` 上关闭；
`/api/*` 仍依赖"只监听回环 + 无 CORS 授权"这一层。它是独立的后续项，不在本范围内。

#### 兼容性（原 ADR-0015 §4，沿用 ADR-0013 的"协议类标识"纪律）

改名/改协议的纪律是"**写出端发新名 + 读取端两个都收**"。这里是**新增**一个协议要求，
故兼容矩阵必须两侧都成立：

| 组合 | 行为 |
|---|---|
| 新桌面 + 新扩展 | 扩展 `POST /extension/hello` 自举令牌 → 全部请求带 `X-Workbench-Token` |
| **新桌面 + 旧扩展** | 宽限期（默认 24h）内照常放行；窗口过后 401，且 `authBlocked` 让桌面 UI 提示"重新加载扩展" |
| **旧桌面 + 新扩展** | `POST /extension/hello` 返回 404/405 → 扩展视为"不需要令牌"，照常发不带令牌的请求 |
| 桌面不可达 | 扩展离线回退，本地数据照常可用（与既有纪律一致） |

#### 防静默故障：401 必须是**可诊断**的（原 ADR-0015 §5）

grace 过后没重新加载扩展的用户会开始收 401，而扩展侧对失败是**静默吞掉**的
（`sync.ts` 的离线回退：桌面不可达是常态）。两条对策：

1. **401 带机器可读 code**（`extension_auth_required`）：扩展端据此"作废令牌 → 重新握手 →
   **重试一次**"（`desktop-auth.ts::authFetch`）。没有这一步，表现是"快捷登录莫名失灵"。
2. **无令牌访问对桌面 UI 可见**：中间件把"本该带令牌的端点被无令牌访问"记数，
   经**免鉴权的** `/extension/health` 暴露为 `authBlocked` / `tokenlessRequests`；
   账号中心复用既有的「扩展版本过旧」提示条（文案改成"需要重新加载"）。
   ⚠ 豁免路径（`/extension/health` 本身，UI 每 3s 打一次）**不计入**，
   否则 `authBlocked` 会被 UI 自己的轮询永久点亮、提示条再也关不掉。

#### 验收（原 ADR-0015 §6）

| 手段 | 覆盖 |
|---|---|
| `tests/test_extension_auth.py`（20 项） | 令牌稳定/落库、豁免面最小、**严格模式真拦**（GET/POST/错令牌）、宽限期语义与"起点只记一次"、401 的 `code`/`hello`/`action`、自举端点字段集合、来源允许清单、**静默故障可见性** |
| `tests/test_extension_blueprint.py` | R1 **哨兵已翻转**：原先"记录无鉴权"的断言改成守卫（中间件必须在 app 上、豁免面只允许 health） |
| `verify_packaging.py` **P10** | 机检：中间件已装 + 豁免面最小 + UI 端点已迁出该前缀 |
| 真机/脚本 | 严格模式（`GRACE=0`）起服务：无令牌 401（带 code）→ 自举领令牌 → 带令牌 200；`/api/shell/*` 不受影响 |
| 既有验收脚本 | `verify_extension_sync.mjs` / `verify_extension_version.py` / `verify_command_latency.py` / `acceptance_extension_e2e.py` / `diag_fernet_node.mjs` 全部改为**复刻扩展的自举流程**——于是它们验的与扩展真跑的是同一条协议 |

## 4. 后果

### 好处

- 浏览器分配政策让"同一账号被两处同时操作"从**默认行为**变成**需要显式入口**。
- 账号数据只剩一个真源（桌面 SQLite），消除"两边都能改"的分裂（原 ADR-0004）。
- 跨线程 greenlet 错误彻底消失，多账号并行靠 context 级隔离（原 ADR-0006）。
- R1 的"零知识一次 GET"在 `/extension/*` 上关闭；且这条通道第一次进入**有测试、有机检**的范围（原 ADR-0015）。

### 代价

- 两套浏览器链路 + 两套自动登录节奏门控参数都要维护（原 ADR-0002）。
- **跨进程协议成为关键路径**：快照幂等、指令游标、状态上报三件套出问题就是**静默失效**（原 ADR-0004）。
- **全局串行**：一个慢操作阻塞所有账号；且多数作业**无超时**（原 ADR-0006）。
- `/extension/*` 多一个协议要求，旧扩展要靠 24h 宽限期过渡（原 ADR-0015）。

### 风险

- 「同一账号同时被扩展与托管会话操作」**未被禁止**，只靠 UI 入口区分 —— 待产品决策（原 ADR-0002）。
- 事件回调纪律**没有测试能拦住违规**，表现为运行期死锁（原 ADR-0006）。
- 令牌把攻击面收窄了，但**没有消灭"本机已被攻陷"**（见 §5）（原 ADR-0015）。

## 5. 诚实边界（★ 四篇各自的「挡不住什么」原样保留）

> ★ **不要把这一节读成"我们做完了安全"**。四段边界是四篇原 ADR 各自**刻意写刺眼**的部分，
> 合并时**一句都没有软化**。

### 5.1 这一层**挡不住**什么（不要高估）（**原 ADR-0015** §3）

**本机同用户进程总能拿到令牌**——要么直接读 `%APPDATA%\Workbench\workbench.db`，
要么调一次 `POST /extension/hello`（它必须免鉴权）。而**能读库的进程本来就能拿到 Fernet 密钥**
（它就在同一张 `settings` 表里）。

所以令牌把攻击面从 **"任何能发 HTTP 的东西"** 收窄到
**"愿意读我们数据库或调我们自举端点的本机进程"**，后者与直接读库同级。
**它消灭的是"零知识的一次 GET"，不是"本机已被攻陷"。**

> 这是 PITFALLS #23 的同族判断：Fernet 密文挡的是**网络窃听**，不是本机实例串号；
> 令牌挡的是**零知识访问**，不是本机沦陷。**不要把这一层写成"凭据现在安全了"。**

可选加固（未做，留作触发器）：`WORKBENCH_EXTENSION_ORIGIN` 允许清单已实现并测过，
配好后可拒掉伪造来源的请求。默认空 = 不做来源校验，因为桌面壳目前不声明扩展 id
（用户手装的扩展 id 由 manifest 公钥决定、跨机一致，但不在本仓配置里）。

### 5.2 扩展侧的已知风险上限（**原 ADR-0002 / 0004 共同指向**）

- **「同一账号同时被扩展与托管会话操作」在语义上未被禁止** —— 目前靠 UI 入口区分，
  一处**仍待产品决策的边界**（原 ADR-0002）。
- **休眠源码 `site-auth.ts` 是"保留以防回退"，不是"正在使用"** —— 它不参与现行授权链路（原 ADR-0004）。
- **凭据投递的 60s 明文窗口读后不删**（原 ADR-0007 的 R1）是从本节这条链路上过的：
  扩展的凭据投递语义的完整风险登记见
  [ADR-0007](0007-credentials-sandbox-and-trust.md) §「已知风险（已登记，未修）」。

### 5.3 `browser_pool` 挡不住什么（**原 ADR-0006**）

- **「事件回调内禁止连接调用」没有机器守卫**：违反它的表现是**运行期死锁**，不是断言失败。
  新增录制/监听能力时只能靠纪律与 code review。行业内 async 派系天然没有这个问题，
  **所以没有现成教训可抄**（见 §6.2）。
- **"全局串行"是刻意的代价，不是缺陷**：一个慢操作阻塞所有账号；而多数作业**无超时**，
  页面卡住时 HTTP 请求会一直挂着（已登记在 `../CODEBASE_OVERVIEW.md` §九 风险台账）。
- **关窗 ≠ 停监听**，且 `_close_entry` 的 finish 判定存在缺陷（首次登录的会话关窗会误报「已关闭」）。
  两条都在风险台账里，**都还没修**。

### 5.4 令牌那一层**不是**"整个本机 API 都安全了"（**原 ADR-0015** D-7）

`/api/*` 的 95 个端点（含 `/api/accounts/export` 这种"含密钥的导出"）**仍然零认证**。
本 ADR 的取舍是**有意的**（同源页面无法安全地持有令牌），但它意味着：
**"给 `/extension/*` 加了令牌"不等于"本机 API 有认证"** —— 读到 §2.4 就以为整个服务被守住了，
是对这一节最常见的误读。

## 6. 外部参照

> **后补**的，标注一并保留；原 ADR-0002 写于模板建立之前，本栏为本次合并后补）。

### 6.1 扩展=执行面（**原 ADR-0004**，原文为 2026-09-20 后补）

> ⚠️ **本栏为后补**（ADR 正文其余部分保持决策当时的样子，不改写）。
> 补它的动机很直接：**这条决策的价值几乎全在"我们为何不同于别人"**，
> 而那部分在正文里只写了结论、没写对照对象。半年后没人能重建当时的权衡。

| 参照对象 | 它的做法 | 与本决策的关系 | 我们的理由 |
|---|---|---|---|
| [nanobrowser](https://github.com/nanobrowser/nanobrowser)（约 13,810 ★） | **MV3 扩展即全部**：agent 循环、工具、账号都在扩展里，**没有宿主后端**；不做多账号存储平面隔离 | **分歧** | 我们需要承载「业务写路径 + 审计 + 凭据库」，而扩展没有这些载体（无 SQLite、无 Fernet 密钥管理、无法跑平台 SDK）。**数据面放桌面不是为了架构好看，是因为扩展装不下** |
| [browser-use](https://github.com/browser-use/browser-use) / [Skyvern](https://github.com/Skyvern-AI/skyvern) / [Stagehand](https://github.com/browserbase/stagehand) | 一律用**受控的浏览器上下文**（可弃、无登录态），因此**不需要**存储平面隔离 | **分歧** | 我们的执行面是**用户自己已登录的真实 Chrome**——这是本项目的核心前提（真实登录态不复制、凭据不出本机）。隔离问题正是这个前提的**代价**，不是可选项 |
| [camoufox](https://github.com/daijro/camoufox) / [patchright](https://github.com/Kaliiiiiiiiii-Vinyzu/patchright) | 解决**跨站点指纹一致性 / 反检测** | **正交** | 我们要的是**同站点内多账号的存储平面隔离**，与指纹无关。且本项目的用户是合法持有这些账号的实施工程师——**刻意不做反检测**（合规取向） |
| Multilogin / AdsPower 一类商用多账号浏览器 | 商业闭源 | **无开源对应物** | 本次调研（`../OPENSOURCE-LANDSCAPE.md`，**该文件已于 2026-09-29 删除**）§2.7 **未找到**六个平面同时显式隔离 + 会话切换 + 回放的开源实现。⚠️ 该结论**限于检索范围，非穷尽性证明** |

**由本次对照得出的结论**：

- **这条决策没有现成共识可抄。** 行业里「扩展 = 执行面 + 桌面 = 数据面」没有同构体，
  六平面隔离也没有开源对应物。所以它不是"跟上行业"，而是**在自己的约束下自己定的**——
  这正是它值得被记成 ADR 的原因。
- **必须自己盯住的部分**：正文「代价」里那条"跨进程协议成为关键路径"。
  行业参照物都没有这条协议，因此**我们无法从别人那里学到它的坑**——
  只能靠自己的 PITFALLS #14 / #15 / #48 / #49 一条条攒。
- **可以放心的部分**：决策本身的形状（单一真源、职责二分）是通用的工程常识，不必自证。

### 6.2 sync vs async / 单线程队列（**原 ADR-0006**，原文为 2026-09-20 后补）

> ⚠️ **本栏为后补**（正文保持决策当时的样子，不改写）。

| 参照对象 | 它的做法 | 与本决策的关系 | 我们的理由 |
|---|---|---|---|
| **Playwright 官方文档**（sync API 章节） | 明确：sync API **非线程安全**、绑定创建它的线程；同线程不得起第二个 `sync_playwright()` | **一致（跟随）** | 这不是本仓的发明，是**上游的硬约束**。"专职单线程 + Future 提交"是满足该约束的标准解法，**无需自证** |
| [browser-use](https://github.com/browser-use/browser-use) / [Skyvern](https://github.com/Skyvern-AI/skyvern) / [Stagehand](https://github.com/browserbase/stagehand) | 一律用 **async API**（`async_playwright`），跑在自己的 asyncio 事件循环里，**因此不需要专职线程**——并发由事件循环提供 | **★ 分歧** | 这是一个**真实的权衡**，不是"我们落后"：本仓 `services/egmp/client`、`proc`、`sandbox.run` **都是同步的**，且 FastAPI 的同步依赖也走线程池。选 async 意味着把整条业务链改成 async（fork 存量大、改动面广），**而收益只是省掉一个线程**。我们选了 sync + 单线程队列，用 `asyncio.to_thread` 桥接 |
| 同上三者的"浏览器池" | 通常**每任务一个新上下文**，用完即弃，任务间无共享状态 | **分歧** | 我们的会话**必须长期存活**（登录态要复用、监听要持续），所以状态集中在 `sessions: dict[account_id, SessionEntry]`。代价就是正文里那条"**全局串行**：一个慢操作阻塞所有账号" |

**由本次对照得出的结论**：

- **可以放心的部分**：单线程串行化本身是上游约束下的标准解法，不必再论证。
- **必须自己盯住的部分**（也是本 ADR 最有价值的原创内容）：
  ① 正文那条「**事件回调内禁止连接调用**」——async 派系的框架天然没有这个问题（回调在事件循环里、
  它们本来就要 await），**所以行业里没有现成教训可抄**，这是 sync + 队列这个组合**独有**的坑；
  ② 正文承认的「**新增录制能力时没有测试能拦住违规**」——同上，只能靠纪律与 code review。
- **一个值得记住的推论**：本项目选了与主流相反的那条路（sync vs async），
  **代价集中体现在 ADR 的"代价（已接受）"表里，而收益是改动面小**。
  这正是"外部参照"栏存在的意义——**不是为了证明我们错了，是为了让代价可见**。

### 6.3 访问令牌（**原 ADR-0015** §8，原文为 2026-09-20 后补）

> ⚠️ **本栏为后补**（正文保持决策当时的样子，不改写）。

| 参照对象 | 它的做法 | 与本决策的关系 | 我们的理由 |
|---|---|---|---|
| **MCP**（Model Context Protocol，2025-12 捐入 Linux Foundation 旗下 AAIF） | 远程用 **OAuth**；**stdio 传输靠"本地进程 = 受信任"**，不带令牌 | **分歧（我们更严）** | MCP 的 stdio 假设"能起进程 = 可信"。本仓的威胁模型不同：**请求方是浏览器里的扩展**，而"本机任意进程"恰恰是我们要挡的（§1.4 的威胁表） |
| **MCP 规范对"人工介入"的态度** | 只到 **SHOULD** always be a human in the loop；机制上是 `Elicitation`。**没有令牌、没有 TTL、没有参数指纹** | **一致（同一立场）** | 两边都认为**不可信方不能自证安全**。分歧只在于"用什么手段表达持有人身份"——MCP 留给客户端自研，**本 ADR 就是那份自研** |
| **MCP `ToolAnnotations`**（`readOnlyHint` / `destructiveHint`…） | 是**提示**。规范原文明确：所有 annotations **不保证忠实描述工具行为**，且**客户端绝不应基于不可信服务端发来的 annotations 做工具使用决策** | **一致（强论据）** | 这条是 §2.4 D-1 否决"来源校验"的**外部背书**：本仓的 `Risk` 也是**宿主强制**而非对端声明。**行业共识是"分级不能由不可信方说了算"** |
| 常见的本机应用 token 做法 | 随机 token 落配置文件/DB，客户端**自举领取** + 宽限期兼容旧客户端 | **一致（跟随）** | §2.4 D-2 的自举端点 + 24h 宽限期就是这个标准形状；且已被 Claude Desktop / Cursor / VS Code 一类客户端反复验证 |
| 常见实现普遍会做的：**`Origin` 允许清单** | 直接按请求头判断来源 | **★ 分歧** | 我们**明确拒绝**——理由在 §2.4 D-1：扩展 service worker 的 `Origin` 行为**无法在本机实证**。这是有意选择"更严但更笨"的路径，代价是那张否决表里的复杂度 |

**由本次对照得出的结论**：

- **可以放心的部分**：令牌 + 自举 + 宽限期是本机应用的标准形状，不必自证。
- **必须自己盯住的部分**：§2.4「**401 必须是可诊断的**」。
  这是原 ADR-0015 最有原创价值的一节——**参照物都没有这个问题**，
  因为它们的客户端要么是浏览器（会弹登录框），要么是开发者工具（人看得懂 401）。
  **只有"扩展对失败静默吞掉"这个组合才会造出"功能莫名失灵"**，
  而它是本项目三面分工带来的**独有**后果（见 §2.2 的"跨进程协议成为关键路径"）。
- **一条可迁移的方法**：给任何客户端加鉴权时问一句「**失败会到达谁的眼前？**」——
  若答案是"被 catch 吞掉"，那就是又造了一条静默链。这条已写进本仓 PITFALLS #49 的"推广"。

### 6.4 浏览器分配政策（**原 ADR-0002**，本栏为本次合并后补）

> ⚠️ **本栏为后补**（2026-10-07 合并时补写；正文其余部分保持决策当时的样子，不改写）。
> 原 ADR-0002 写于 `0000-template.md` 建立之前，**没有这一栏**。

| 参照对象 | 它的做法 | 与本决策的关系 | 我们的理由 |
|---|---|---|---|
| [browser-use](https://github.com/browser-use/browser-use) / [Skyvern](https://github.com/Skyvern-AI/skyvern) / [Stagehand](https://github.com/browserbase/stagehand) | 只有**一种**浏览器：受控的、可弃的上下文。不存在"用户自己的浏览器"这个概念 | **★ 分歧** | 我们**刻意要两套**，因为两类任务的**成功判据不同**：快捷登录的判据是"以该身份操作的真实效果"（真实 profile/代理/插件），自动化的判据是"可控、可复现、不污染用户环境"。一套浏览器无法同时满足两个判据 |
| 商用多账号浏览器（Multilogin / AdsPower 一类） | 也做"多身份并行"，但用的是**自己托管的指纹浏览器实例** | **分歧** | 我们在快捷登录这条路上用的是**用户真实的 Chrome**（凭据不出本机、登录态不复制）。代价就是必须维护两套链路（§2.1 的"代价"） |
| Chrome MV3 扩展的既定形态 | 扩展只能跑在**用户浏览器的进程里**，无法托管一个浏览器 | **一致（约束）** | 这条约束直接决定了"扩展=执行面、桌面=数据面"的分工（§2.2）—— 不是我们选的，是 MV3 给的 |
| **Playwright 官方文档**（sync vs async） | 上游只保证 sync API 的单线程语义 | **一致（约束）** | §2.3 的专职线程是这条约束的标准解法 |

**由本次对照得出的结论**：

- **可以简化的**：单线程 + Future 提交的桥接形状（上游约束下的标准解法）。
- **必须自己定的**：① **按用途而非按模块分配浏览器** —— 行业里要么只有受控上下文、
  要么是商用指纹浏览器，**"用户真实 Chrome + 内置 Chromium 并存"没有同构体**；
  ② **"同一账号被两处同时操作"怎么办** —— 至今**未决**（§5.2 第一条第）。
- **未核实**：其他"桌面壳 + 浏览器扩展"组合如何在两者之间划分数据面，本次**没有取证**。
  本节的分工是在本项目三面约束（MV3、凭据不出本机、要有审计）下自己定的。

### 7.4 原 ADR-0015 §7（原文）

1. **有人能读 `%APPDATA%` 但仍被挡住**——说明令牌真的起了作用，值得考虑把来源允许清单设为默认开启；
2. **`/api/*` 出现远程可达场景**（不再只是本机 UI）——那时 §2.4 D-7 的取舍要重做；
3. **扩展 id 能被桌面壳稳定声明**（例如改用固定私钥签名）——把 `WORKBENCH_EXTENSION_ORIGIN`
   从"可选"升级为"默认开启"，并去掉宽限期；
4. **MCP / 脚本式 Skill 出现"以扩展身份访问"的需求**——那时令牌分发要重新设计（不能只是从 settings 读）。

# ADR-0012：端口固定（取代 ADR-0011 §D-1 的"壳当仲裁者、被占则顺延"）

- **状态**：已接受（2026-09-14），**取代** [ADR-0011](0011-port-and-session-negotiation.md) 的 §D-1 与 §D-6 的顺延部分
- **决策人**：用户（原话：「我建议还是固定端口号吧，别拿所谓的桌面壳引导去调整，就固定端口号」）
- **保留**：ADR-0011 的 §D-2（端口下发）/ §D-3（公布文件）/ §D-4（身份化就绪探测）/ §D-5（扩展发现）**继续有效**，
  本 ADR 只推翻"端口可以在运行时漂移"这一条。

---

## 1. 为什么推翻顺延

ADR-0011 的出发点是**对的**：它要治的是"旧实例占着端口，新壳却以为自己的服务起来了"。
两个真相来源（壳写 18765、Python 也默认 18765）确实必须收敛成一个。

**但它的解法选错了**：把"端口漂移"当成了常规能力，于是引入了一整套活动部件——

| 活动部件 | 引入的故障面（实测/可推演） |
|---|---|
| 协商窗口（每端口 +8） | 端口号不再是常量，任何"记下 18765"的地方都可能指错 |
| 实际端口公布 `desktop-ports.json` | 又一份需要判断"它是不是陈旧的"的状态（强杀后残留 → 误报，见 [PITFALLS](../PITFALLS.md) #25） |
| 扩展按窗口探测控制服务（18767…18770） | 探测期间打到别的实例上；探测超时又是一类静默失联 |
| 顺延后书签/收藏失效 | 用户"打开工作台"从固定动作变成"先查这次在哪口" |

而**顺延真正换来的收益接近于零**：本机出现端口冲突的唯一现实来源是**工作台自己的旧实例**
（还有极少数情况是别的程序恰好占了这一段）。前者用"说清楚是谁占的、让用户退出它"就能解决，
后者用"换个号偷偷跑起来"解决反而更糟——**用户不知道自己在 18768 上**。

一句话：**顺延把一个"应该报错并说清"的场景，变成了一个"看起来正常但地址变了"的场景。**

## 2. 决策

### D-1 三个端口是固定常量

```
18765  服务端业务面 + 静态页
18766  壳 Chromium 的 CDP 调试口
18767  壳控制服务（开户窗 / 聚焦 / 更新状态 / whoami）
```

- 唯一真相来源：壳侧 `desktop/ports.js` 的 `PORTS`；Python 侧 `workbench/config.py` 的默认值**必须与之一致**，
  由 `tests/test_ports_contract.py::test_python_defaults_match_shell_ports` 钉住（跨语言一致性，壳侧离线脚本验不了）。
- **不做顺延、不做随机**。`negotiate()` / `MAX_DRIFT` 已从壳的模块里删除，
  并由 `test_shell_exports_no_negotiation_api` 守住"不许加回来"。
- 环境变量下发（ADR-0011 §D-2）**保留**：它是"唯一真相来源"的手段，与是否顺延无关。

### D-2 端口被占 → 报错退出，并说清是谁占的

启动顺序（`desktop/main.js::bootstrapPorts`）：

```
① clearStale()           清掉"写它的进程已不是我们"的陈旧公布文件
② detectRunningInstance() 是不是我们自己的另一个实例（核对身份，见 §3）
③ unavailable()          三个固定端口是否都能绑
   └─ 有占用 → MessageBox（列出每个被占端口 + 占用者 + 处置办法）→ app.exit(1)
④ 写公布文件 → spawn 服务端 → 起控制服务
```

- 被占时的提示分两种，**不许混为一谈**：
  - 是我们自己的实例 → 报 PID / 版本 / 启动时间，让用户去托盘退出它；
  - 不是我们的实例 → 如实说明，并给出 `Get-NetTCPConnection -LocalPort <port>` 的排查命令。
- 报错文案**不再提"可以用 WORKBENCH_* 指定其它端口后重试"**——那等于教用户去制造漂移。

### D-3 结构上单实例（顺延撤销的连带收益）

端口固定后，"活着的实例必然占着 18765"，于是：

- 原来那个「另一个实例在运行 → 仍然启动 / 退出」的询问分支**成了永远走不到的死代码**，已删除；
- **同一时刻只可能有一个实例**。这顺带消灭了 ADR-0011 §6.2 记的两个待办与
  [PITFALLS](../PITFALLS.md) #23 的"两个实例共用同一份数据目录、凭据互相解密"那一族问题；
- `app.requestSingleInstanceLock()` 因此**不再必要**（端口占用已经把它挡住了），
  故本 ADR 明确**不做**——不是遗漏。

### D-4 扩展只做"确认身份 + 回退"，不再有探测窗口

`background/core/desktop-endpoint.ts`：端口固定后不必再挨个试控制端口。

- 打一次 `GET http://127.0.0.1:18767/whoami`，核对 `app === 'AksoWorkbench'`；
- 拿到就用它的 `serverPort`；拿不到回退固定 `18765`（保证旧桌面端仍可用、离线不炸）。

**为什么还留这一次请求**（而不是直接把 18765 写死）：它回答的是**身份**——
"18765 上坐着的是不是我们的服务端"。凭据（Fernet 密文 + 原始密钥）会经过这条通道，
而密钥就在本机数据库里，所以"发给了另一个实例"不是网络窃听问题。固定端口消除了
"顺延导致失联"，但没有消除"端口上是谁"。

## 3. 仍然保留的判据（与顺延无关，别一起删掉）

ADR-0011 的教训里，**真正值钱的是"必须核对身份"**这一条，本 ADR 原样继承并加强：

| 判据 | 拦住的故障 | 出处 |
|---|---|---|
| `/api/health` 必须回 `app === "AksoWorkbench"` | 旧实例占端口时新壳认错服务 | ADR-0011 §1 / PITFALLS #20 |
| "旧实例"必须核对**映像名**（`tasklist`），不能只看 pid 存活 | pid 回收复用 → 误报"另一个实例在跑" → 应用**再也起不来** | PITFALLS #25 |
| 启动时 `clearStale()` 清陈旧公布文件 | 强杀后 `will-quit` 不触发 → 文件残留 → 下次启动误报 | PITFALLS #25 |

> 判据演进史：`"端口有人回 200"` → `"公布文件里的 pid 还活着"` → `"活着 **且** 映像名是我们"`。
> 每一次升级都是因为**只问"有没有东西在"而不问"是不是我们"**而踩的坑。

## 4. 被否决的方案

| 方案 | 否决理由 |
|---|---|
| **继续顺延（ADR-0011 §D-1 原方案）** | 见 §1：把"该报错的场景"变成"地址悄悄变了"；活动部件多、故障面大、收益近零 |
| **每次启动随机端口** | 使用者要的是"打开工作台"，不是"先查这次端口"。扩展、书签、手输地址全部变复杂 |
| **固定端口 + 冲突时自动杀掉旧实例** | 危险且不可预期：可能杀掉用户正在用的实例，甚至误杀别的程序 |
| **固定端口 + 静默退到"仅服务端模式"** | 半死不活：窗口起来了却没有业务面，比明确报错更难排查 |
| **用 `app.requestSingleInstanceLock()` 独占** | 端口占用已经挡住了第二个实例（§D-3），加它只是多一层；且它**防不了**别的程序占端口 |
| **改成 Unix domain socket / 命名管道** | Windows 上 Chrome 扩展无法访问命名管道；扩展是执行面，必须走 HTTP 回环 |

## 5. 落地清单

- [x] 壳：`desktop/ports.js` 改为固定 `PORTS` + `unavailable()`；删除 `negotiate` / `MAX_DRIFT`
- [x] 壳：`bootstrapPorts()` 改为"清陈旧 → 判实例 → 探端口 → 报错退出"，删除顺延与询问分支
- [x] 壳：占用提示分"我们的实例 / 不是我们的实例"两种，均给出可执行动作
- [x] 扩展：`desktop-endpoint.ts` 取消探测窗口，只做一次 `whoami` 身份确认 + 回退
- [x] 测试：`tools/verify_port_broker.mjs` 改为固定端口语义（27 项）；`tests/test_ports_contract.py` 增 3 项（跨语言一致 / 固定值 / 无协商 API）
- [x] 文档：本 ADR + ADR-0011 加取代标注 + CONFIG / CODEBASE_OVERVIEW / PITFALLS / CHANGELOG 同步

## 6. 已知边界

1. **用户不能再同时跑两个实例**（原先"仍然启动"可以）。这是刻意的：数据目录只有一份，
   两个实例并存本来就只能靠"共用同一份库 + 各自一组端口"这种半吊子状态。
   要并行请用不同 `WORKBENCH_DATA`（此时**必须**同时覆盖三个端口，否则端口会撞）。
2. **固定端口被无关程序长期占用时，应用就是打不开**（只能先释放端口）。
   这是"可预测"换"总能起来"的取舍——报错里给了找占用者的命令。
3. **旧版本（含顺延的那版）留下的公布文件**可能记着 18770 之类的"实际端口"；
   `describeOccupant` 会**如实提示**该实例记录自己用的是哪个号，不会被掩盖。

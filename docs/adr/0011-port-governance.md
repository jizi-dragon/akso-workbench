## 1. 事故复盘（这就是本篇的存在理由）（**原 ADR-0011**）

**现象**：菜单里已经把 `inventory` / `understand` 两个命令删掉并推送了，但用户在桌面上打开
应用，下拉里还是四个命令。

**根因**：桌面上跑的是 **9/9 的旧打包副本**（`dist/Workbench/_internal/.../insight.html`，
静态页是打包那一刻的快照）。而当时端口 18765 上活着的正是那个旧实例。

**为什么壳没有察觉**（这才是真正的问题，不是"打包副本过期"这件小事）：

```js
// desktop/main.js:75-88（改造前）
function waitReady(timeoutMs = 40000) {
  const tick = () => {
    const req = http.get(serverUrl('/'), { timeout: 2000 }, (res) => {
      res.resume();
      resolve(res.statusCode === 200);   // ← 只看「有人应答」，不看「是不是我们」
    });
```

`waitReady()` 的判据是 **"这个端口上有个 HTTP 服务回了 200"**。它**不校验对方身份**。于是：

1. 旧实例先占住 18765（或另有任何程序占着并回 200）；
2. 新壳 spawn 自己的服务端 → 那个进程 `bind(18765)` **失败**（端口占用）；
3. 新壳去探 18765 → 旧实例回 200 → **判定"就绪"**；
4. 主窗打开的是**旧实例**的页面。

一个端口被占，表现成了"代码改动没生效"。这类故障的排查成本极高，因为所有组件都自认为正常。

## 2. 现状实证（改造前的三个真相来源）（**原 ADR-0011**）

| 端口 | 用途 | 硬编码处（实证） |
|---|---|---|
| 18765 | 服务端业务面 + 静态页 | `desktop/main.js:17` `SERVER_PORT`；`workbench/config.py:66` `WORKBENCH_PORT` 默认值；扩展 `background/sync.ts:20` `const DESKTOP = 'http://127.0.0.1:18765'`；`core/parallel-session.ts:74` 白名单 `127.0.0.1:18765` / `localhost:18765` |
| 18766 | 壳 Chromium 的 CDP 调试口 | `desktop/main.js:19`；`browser_pool.py:39` `WORKBENCH_CDP_PORT` |
| 18767 | 壳控制服务（开户窗 / 聚焦 / 更新状态） | `desktop/main.js:18`；`browser_pool.py:38`；`api/routes_extension.py`；`api/routes_update.py`（2 处） |

四个具体缺陷：

**D1｜壳不把端口告诉 Python，Python 也不告诉壳。**
打包态 `spawnServer()` 起 `WorkbenchServer.exe --server`，**不传端口、不设环境变量**；Python 侧
`config.PORT` 自己从环境变量读、默认 18765（`desktop/main.js:47` 与 `workbench/config.py:66`）。
两边各自默认到同一个数字，**没有一次握手**。更糟的是开发态反而传了 `--port`（`main.js:59`）——
"打包态与开发态走的不是同一条路径"，这类耦合只会在打包后才咬人。

**D2｜"端口被占"与"端口被自己占"分不清。** 见 §1 的 `waitReady`。

**D3｜扩展端口写死且没有下发通道。** 扩展能自动发现桌面端的**指令队列**
（长轮询 `/extension/commands`），却发现自己要访问的**业务面端口**只能靠猜同一个常量。
后果有二：桌面换端口 = 扩展静默失联；18765 上坐着别的实例 = 扩展把凭据
（Fernet 密文 + 原始密钥）发给**那一个**实例。

**D4｜壳与 Python 之间没有"配置下发"通道，端口只是第一个受害者。**
`WORKBENCH_SESSION_MODE` 全仓库只有 `browser_pool.py:37` 读它，`desktop/main.js` **从不设置**——
于是 `cdp` 模式永远不生效，托管会话实际跑的是原生 Playwright Chromium，而不是壳的 Chromium
（这正是 [ADR-0002](0002-browser-allocation-policy.md) §2.1 想要的）。**同一个病根，另一个症状。**

### 2.1 一个意外的纵深防御（值得记下来）（**原 ADR-0011**）

凭据是 **Fernet 密文**，而密钥存在**本机数据库** `settings.fernet_key`。所以"旧实例先占端口"
这种情形下，即使扩展被路由到了旧实例，旧实例**能**解密（同一个 `%APPDATA%` 数据库 → 同一把密钥）。
→ **不要把"密文"当作抵御错误路由的防线**，它抵御的是**网络窃听**，不是**本机实例串号**。

## 3. 决策

**原则：每个端口只有一个权威来源（壳），其余全部靠协商获得，禁止各自默认。**（**原 ADR-0011**）

### 3.2 ★ 端口是固定常量（**原 ADR-0012**，取代上面 §3.1）

#### 3.2.1 为什么推翻顺延

§3 开头那个出发点**是对的**：它要治的是"旧实例占着端口，新壳却以为自己的服务起来了"。
两个真相来源（壳写 18765、Python 也默认 18765）确实必须收敛成一个。

**但它的解法选错了**：把"端口漂移"当成了常规能力，于是引入了一整套活动部件——

| 活动部件 | 引入的故障面（实测/可推演） |
|---|---|
| 协商窗口（每端口 +8） | 端口号不再是常量，任何"记下 18765"的地方都可能指错 |
| 实际端口公布 `desktop-ports.json` | 又一份需要判断"它是不是陈旧的"的状态（强杀后残留 → 误报，见 [PITFALLS](../PITFALLS.md) #25） |
| 扩展按窗口探测控制服务（18767…18770） | 探测期间打到别的实例上；探测超时又是一类静默失联 |
| 顺延后书签/收藏失效 | 用户"打开工作台"从固定动作变成"先查这次在哪口" |

而**顺延真正换来的收益接近于零**：本机出现端口冲突的唯一现实来源是**工作台自己的旧实例**
（还有极少数情况是别的程序恰好占了这一段）。前者用"说清楚是谁占的、让用户退出它"就能解决，
后者用"换个号偷偷跑起来"解决反而更糟——**用户不知道自己在 18768 上**。

一句话：**顺延把一个"应该报错并说清"的场景，变成了一个"看起来正常但地址变了"的场景。**

#### 3.2.2 D-1 三个端口是固定常量

```
18765  服务端业务面 + 静态页
18766  壳 Chromium 的 CDP 调试口
18767  壳控制服务（开户窗 / 聚焦 / 更新状态 / whoami）
```

- 唯一真相来源：壳侧 `desktop/ports.js` 的 `PORTS`；Python 侧 `workbench/config.py` 的默认值**必须与之一致**，
  由 `tests/test_ports_contract.py::test_python_defaults_match_shell_ports` 钉住（跨语言一致性，壳侧离线脚本验不了）。
- **不做顺延、不做随机**。`negotiate()` / `MAX_DRIFT` 已从壳的模块里删除，
  并由 `test_shell_exports_no_negotiation_api` 守住"不许加回来"。
- 环境变量下发（§3.3）**保留**：它是"唯一真相来源"的手段，与是否顺延无关。

#### 3.2.3 D-2 端口被占 → 报错退出，并说清是谁占的

启动顺序（`desktop/main.js::bootstrapPorts`）：

```
① clearStale()           清掉"写它的进程已不是我们"的陈旧公布文件
② detectRunningInstance() 是不是我们自己的另一个实例（核对身份，见 §3.4）
③ unavailable()          三个固定端口是否都能绑
   └─ 有占用 → MessageBox（列出每个被占端口 + 占用者 + 处置办法）→ app.exit(1)
④ 写公布文件 → spawn 服务端 → 起控制服务
```

- 被占时的提示分两种，**不许混为一谈**：
  - 是我们自己的实例 → 报 PID / 版本 / 启动时间，让用户去托盘退出它；
  - 不是我们的实例 → 如实说明，并给出 `Get-NetTCPConnection -LocalPort <port>` 的排查命令。
- 报错文案**不再提"可以用 WORKBENCH_* 指定其它端口后重试"**——那等于教用户去制造漂移。
- ★ ~~§3.1 的"端口全部顺延失败 / 被别的实例占住 → 给出可执行 MessageBox"~~ 里的**顺延分支已不存在**；
  "失败要出声"这条**保留并加强**（文案改为"不是我们的实例"时如实说明 + 给命令）。

#### 3.2.4 D-3 结构上单实例（顺延撤销的连带收益）

端口固定后，"活着的实例必然占着 18765"，于是：

- 原来那个「另一个实例在运行 → 仍然启动 / 退出」的询问分支**成了永远走不到的死代码**，已删除；
- **同一时刻只可能有一个实例**。这顺带消灭了 §5.2（原 ADR-0011 §6.2）记的两个待办与
  [PITFALLS](../PITFALLS.md) #23 的"两个实例共用同一份数据目录、凭据互相解密"那一族问题；
- `app.requestSingleInstanceLock()` 因此**不再必要**（端口占用已经把它挡住了），
  故本 ADR 明确**不做**——不是遗漏。

#### 3.2.5 D-4 扩展只做"确认身份 + 回退"，不再有探测窗口

`background/core/desktop-endpoint.ts`：端口固定后不必再挨个试控制端口。

- 打一次 `GET http://127.0.0.1:18767/whoami`，核对 `app === 'Workbench'`；
- 拿到就用它的 `serverPort`；拿不到回退固定 `18765`（保证旧桌面端仍可用、离线不炸）。

**为什么还留这一次请求**（而不是直接把 18765 写死）：它回答的是**身份**——
"18765 上坐着的是不是我们的服务端"。凭据（Fernet 密文 + 原始密钥）会经过这条通道，
而密钥就在本机数据库里，所以"发给了另一个实例"不是网络窃听问题。固定端口消除了
"顺延导致失联"，但没有消除"端口上是谁"。

#### 3.2.6 ★ 仍然保留的判据（与顺延无关，别一起删掉）（**原 ADR-0012** §3 原文）

原 ADR-0011 的教训里，**真正值钱的是"必须核对身份"**这一条，本 ADR 原样继承并加强：

| 判据 | 拦住的故障 | 出处 |
|---|---|---|
| `/api/health` 必须回 `app === "Workbench"` | 旧实例占端口时新壳认错服务 | §1 / PITFALLS #20 |
| "旧实例"必须核对**映像名**（`tasklist`），不能只看 pid 存活 | pid 回收复用 → 误报"另一个实例在跑" → 应用**再也起不来** | PITFALLS #25 |
| 启动时 `clearStale()` 清陈旧公布文件 | 强杀后 `will-quit` 不触发 → 文件残留 → 下次启动误报 | PITFALLS #25 |

> 判据演进史：`"端口有人回 200"` → `"公布文件里的 pid 还活着"` → `"活着 **且** 映像名是我们"`。
> 每一次升级都是因为**只问"有没有东西在"而不问"是不是我们"**而踩的坑。

### 3.3 ~~D-2~~ 端口值经环境变量 + 显式参数下发给 Python（**原 ADR-0011**，**继续有效**）

> 编号说明：原 ADR-0011 的 §D-2；本合订本里它在 §3.3。原 ADR-0012 明确保留它
> （"它是唯一真相来源的手段，与是否顺延无关"）。

壳 spawn 服务端时同时：

- 设 `WORKBENCH_PORT` / `WORKBENCH_CDP_PORT` / `WORKBENCH_CONTROL_PORT` / `WORKBENCH_SESSION_MODE`
  环境变量（**Python 侧因此不再需要"默认值"这个第二真相来源**）；
- 继续传 `--port`（打包态 `server_entry.main()` 已支持解析），两者必须一致。

同时把 `WORKBENCH_SESSION_MODE=cdp` 一并下发 → 顺带修掉 §2 的 **D4**。

### 3.4 D-3 落一份端口公布文件 `desktop-ports.json`（权威事实）（**原 ADR-0011**，**继续有效**）

壳在 spawn 服务端**之前**原子写 `<数据目录>/runtime/desktop-ports.json`：

```jsonc
{
  "app": "Workbench",
  "schemaVersion": 1,
  "pid": 12345,              // 壳的 pid：用于判断「这个文件是不是当前活着那个实例写的」
  "version": "0.3.5",
  "startedAt": "2026-09-14T10:00:00+08:00",
  "ports": { "server": 18765, "cdp": 18766, "control": 18767 }
}
```

- 壳**退出时删除**该文件（正常退出路径；`before-quit` 已有清理动作）。
- 服务端与工具都能读它；读不到 = 只有服务端在跑（开发者手起场景），此时按传入参数/约定回落。
- **这份文件直接消灭 §1 的故障形态**：新壳启动时读到 `pid` 仍存活 + `version` 是别的版本 →
  立刻能给出"已有另一个实例（PID / 版本）在运行"这种**可执行**的提示，而不是静默等 200。
- ★ **它也是 §3.2.6 第二条判据的载体**：`clearStale()` 清的就是"写它的进程已不是我们"的陈旧文件。

### 3.5 D-4 就绪探测必须带身份（**原 ADR-0011**，**继续有效**）

服务端新增 `GET /api/health`（**无副作用**；它当年与 `/extension/health` 有明确分工，见下）：

```jsonc
{ "app": "Workbench", "service": "workbench-server", "version": "0.3.5",
  "pid": 4242, "ports": { "server": 18765, "cdp": 18766, "control": 18767 } }
```

壳的 `waitReady()` **必须核对 `app === "Workbench"`**：从"有人应答"升级为"是我们的服务在应答"。

> 分工：`GET /api/health` = **进程身份**（无副作用、供探测）；
> `GET /extension/health` = **执行面健康**（会写 `everConnected`，有副作用，供 UI）。
> 不要让探测去打一个会写库的端点。
>
> ★ **2026-10-09 后补（只追加，上文一字未改）**：`/extension/health` **已不存在**——
> 浏览器扩展整体移出本仓库（用户决策：桌面端与扩展不耦合）。
> 这条"不许打有副作用端点"的纪律**仍然有效**，只是今天本服务只剩 `/api/health` 这一个健康端点，
> **分工的两半只剩前半**。取回当时形态：`git show 34b5e94:workbench/api/routes_extension.py`。

### 3.6 D-5 扩展从壳的控制服务发现服务端口（回退固定值）（**原 ADR-0011**，**部分被 §3.2.5 收窄**）

- 壳控制服务新增 `GET /whoami`（无副作用）→ 返回 §3.4 的同一份信息（含 `serverPort`）。
  控制服务是**壳自己的**，因此它的回答天然比"18765 上是谁"可信。
- 扩展新增 `background/core/desktop-endpoint.ts`：把写死的 `DESKTOP` 换成
  `desktopBase()`——**先用上次成功发现的值**（`chrome.storage.local` 缓存），
  ~~**失败再按窗口探测** `18767` 起（`/whoami` 带 `app` 校验，短超时），~~
  **⇒ 按窗口探测已由 §3.2.5 取消**（端口固定后不必再挨个试），只剩**一次身份确认请求**；
  **全都失败则回退固定 `http://127.0.0.1:18765`**（保证旧桌面端仍可用）。
- `parallel-session.ts` 的同步宿主白名单改为**动态**：`127.0.0.1`/`localhost` + **端口 ∈ 已发现集合**
  （默认含 18765）。语义不变（仍然只信本机回环的桌面同步口），但不再绑死一个数字。
- 扩展已有 `host_permissions: ["<all_urls>"]`，**探测无需新增权限**（这是本方案可行的前提，
  若当初收窄过权限则必须先扩权限才能做发现）。

### 3.7 ~~D-6 失败要出声（含顺延失败分支）~~（**原 ADR-0011**，**顺延部分被取代**）

- ~~端口全部顺延失败 / 被别的实例占住 → 壳给出可执行 MessageBox：
  「端口 18765 被 PID 1234（Workbench v0.3.5，启动于 …）占用。请先退出那个实例再启动。」~~
  ⇒ **顺延分支已由 §3.2.3 取代**；"被别的实例占住"这一半**保留**，
  且提示分"我们的实例 / 不是我们的实例"两种（§3.2.3）。
- 探测超时不再只是"等 40 秒然后白屏"，而是把"我探到了什么"（对方 app 名 / 版本 / 无应答）写进
  `shell-state.json`，供排障。**这一半继续有效。**

## 4. 被否决的方案

### 4.1 原 ADR-0011 §4 的否决表（**继续有效**）

| 方案 | 否决理由 |
|---|---|
| **每次启动随机端口** | 使用者要的是"打开工作台"，不是"先查这次端口"。扩展、书签、手输地址全部变复杂；收益（避免冲突）用"顺延 + 公布"就能拿到（★ 而"顺延"本身也已被 §3.2 撤销 —— 随机端口被否决的理由**更强**了） |
| **改成 Unix domain socket / 命名管道** | Windows 上 Chrome 扩展**无法**访问命名管道；扩展是执行面，它必须走 HTTP 回环 |
| **用单实例锁（`app.requestSingleInstanceLock`）强行独占** | 好，但**不够**：它只能防"第二个我们的实例"，防不了"18765 被别的程序占"。★ §3.2.4 的结论是：端口占用**已经**把第二个实例挡住了，所以它**不再必要** |
| **扩展内置端口扫描整个 18700-18800** | 无谓放大攻击面与启动延迟；控制服务知道答案，问它就行 |
| **把 ports 文件放注册表** | 安装态/免安装态不一致；文件已有既定位置（`runtime/`），且 Python 侧读文件最自然 |

### 4.2 原 ADR-0012 §4 的否决表（**取代 §4.1 里的前两条与第三条**）

| 方案 | 否决理由 |
|---|---|
| **继续顺延（§3.1 原方案）** | 见 §3.2.1：把"该报错的场景"变成"地址悄悄变了"；活动部件多、故障面大、收益近零 |
| **每次启动随机端口** | 使用者要的是"打开工作台"，不是"先查这次端口"。扩展、书签、手输地址全部变复杂 |
| **固定端口 + 冲突时自动杀掉旧实例** | 危险且不可预期：可能杀掉用户正在用的实例，甚至误杀别的程序 |
| **固定端口 + 静默退到"仅服务端模式"** | 半死不活：窗口起来了却没有业务面，比明确报错更难排查 |
| **用 `app.requestSingleInstanceLock()` 独占** | 端口占用已经挡住了第二个实例（§3.2.4），加它只是多一层；且它**防不了**别的程序占端口 |
| **改成 Unix domain socket / 命名管道** | Windows 上 Chrome 扩展无法访问命名管道；扩展是执行面，必须走 HTTP 回环 |

## 6. 已知边界（本篇**没有**解决的）

> ★ **两个列表都保留**：§6.1 是原 ADR-0011 §6 的边界，其中**第 3 条已被 §3.2 消除**（划线保留）；
> §6.2 是原 ADR-0012 §6 的边界。**它们不重复**——前者讲"协商方案剩下的缺口"，
> 后者讲"固定端口换来的代价"。

### 6.1 原 ADR-0011 §6（**原方案时期**的边界）

1. **扩展没有"被通知"通道**：桌面端换了端口，扩展只能在下次轮询失败后重新发现（最长一个探测窗口的延迟）。
   要彻底解决得让扩展订阅，而 MV3 SW 没有稳定的常驻连接渠道。
   > ★ **端口固定后这条变了**：§3.2.5 已取消探测窗口，"换端口"这件事本身不再发生；
   > 但**"扩展没有被动通知通道"这个结构性缺口仍在** —— 只是它今天不再有触发场景。
2. **`app.requestSingleInstanceLock()` 仍未做**：两个我们的实例同时跑（不同端口）仍是可能的，
   只是不再互相误认。要做需连同"第二个实例应把主窗交给第一个"一起设计。
   > ★ **已被 §3.2.4 消除**：端口固定后"活着的实例必然占着 18765"，第二个实例起不来 ——
   > 这条待办**已不存在**（不是"做了"，是"前提没了"）。
3. ~~**端口顺延会改变"书签"**：固定端口失效时，写死的书签/收藏会失效——这是选择"可顺延"的代价，
   由 `desktop-ports.json` 与 `/api/health` 补偿（UI 可读它给出正确链接）。~~
   > ★ **已被 §3.2 取代**：这个**代价本身消失了**（不再顺延 ⇒ 书签永不失效）。
   > 保留了划线形态，因为它正是 §3.2.1 那张"活动部件"表里的最后一行。
4. **控制服务若也被占**：`/whoami` 的发现链断掉，扩展回退固定 18765。此时若服务端也顺延了，
   扩展就找不到——故顺序上**先用固定基准尝试**，顺延只作为兜底（与 §3.1 一致）。
   > ★ **顺延那半已被取代**：服务端不再顺延 ⇒ 回退固定 18765 **总是对的**。
   > 而"控制服务被占时发现链断掉"这一形态**仍在**（那时 `/whoami` 拿不到，扩展直接回退）。

### 6.2 原 ADR-0012 §6（**固定端口**的边界）

1. **用户不能再同时跑两个实例**（原先"仍然启动"可以）。这是刻意的：数据目录只有一份，
   两个实例并存本来就只能靠"共用同一份库 + 各自一组端口"这种半吊子状态。
   要并行请用不同 `WORKBENCH_DATA`（此时**必须**同时覆盖三个端口，否则端口会撞）。
2. **固定端口被无关程序长期占用时，应用就是打不开**（只能先释放端口）。
   这是"可预测"换"总能起来"的取舍——报错里给了找占用者的命令。
3. **旧版本（含顺延的那版）留下的公布文件**可能记着 18770 之类的"实际端口"；
   `describeOccupant` 会**如实提示**该实例记录自己用的是哪个号，不会被掩盖。

## 7. 诚实边界

- ★ **"端口固定"消灭的是"地址悄悄变了"，不是"端口上是谁"**。
  §3.2.5 把这一点写得很清楚：那一次 `whoami` 请求**必须留着**，
  因为凭据（Fernet 密文 + 原始密钥）会经过这条通道，而密钥就在本机数据库里。
  ⇒ **不要因为端口固定了就以为"路由到错误实例"的风险消失了。**
- ★ **固定端口的代价是"应用可能打不开"**（§6.2 第 2 条）——这是**刻意的**交换：
  用"可预测"换"总能起来"。任何"顺手加个顺延/回退端口"的改动都是在推翻这条决策。
- **"必须核对身份"这条纪律比端口方案本身更值钱**（§3.2.6）。判据演进史三跳
  （`有人回 200` → `pid 还活着` → `pid 活着且映像名是我们`）**每一次都是踩坑换来的** ——
  改这条链路前先读那一节。
- **"结构上单实例"是端口固定的副产品，不是设计目标**：§3.2.4 说得很明白 ——
  `requestSingleInstanceLock` 是"**不再必要**"，不是"已经做了"。

## 8. 外部参照

> ⚠️ **本栏为后补**（2026-10-07 合并时补写；两篇原文写于 `0000-template.md` 建立之前，
> **都没有这一栏**）。能给出处的写，给不出的写"未核实"，**不凭印象造共识**。

| 参照对象 | 它的做法 | 与本决策的关系 | 我们的理由 |
|---|---|---|---|
| 本机开发工具的通行做法（`vite` / `webpack-dev-server` / `jupyter` 等） | **默认固定端口 + 被占则自动 +1 顺延**，并把实际端口打印到终端 | **★ 分歧（且我们一开始抄了它）** | ★ **这正是 §3.1 原方案的来源形状**，而 §3.2 推翻了它。理由不是"顺延不好"，而是**语境不同**：那些工具的消费者是**坐在终端前的开发者**（会自动看到新端口），而我们的消费者是**装在 Chrome 里的扩展**与**用户书签** —— 它们**看不到**新端口。⇒ 同一条行业惯例在这里会静默失联 |
| 桌面应用的单实例端口惯例（VS Code / Slack / Docker Desktop 等） | 固定端口 / 命名管道 + **单实例锁**；第二个实例把请求转交给第一个 | **一致（方向）** | ★ 我们跟随"固定 + 单实例"，但**实现手段不同**：他们用 `requestSingleInstanceLock`（§3.2.4 明确**不做**，因为端口占用已经挡住了），我们用**端口占用本身**当单实例保证 |
| 常见的"就绪探测"实现（`wait-for-it` / `docker healthcheck` / k8s readiness probe） | 探"端口是否有应答"，或探一个**专用的健康端点** | **一致（且我们更严）** | §3.5 的 `/api/health` 是同一形状；★ 但我们**额外核对 `app` 字段** —— 这正是 §1 那次事故的教训（"有人回 200"不等于"是我们的服务"）。行业惯例里的 readiness probe 通常**不校验对端身份**，因为容器网络里"这个地址"只有一个可能的主人 |
| [Chrome 扩展的 host permissions 模型](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions) | 扩展需要显式声明它要访问的 host；`<all_urls>` 覆盖回环地址 | **一致（约束）** | §3.6 最后一条"探测无需新增权限"就是这个模型的结果 —— 而它同时是**一个前提**：若当初收窄过权限，整条发现链就做不了 |
| **命名管道 / Unix domain socket** 一类的本机 IPC | 比 HTTP 回环更"本机"，且天然免端口 | **★ 分歧** | §4.2 明确否决：**Windows 上 Chrome 扩展无法访问命名管道**。我们不是"选了更差的方案"，是**约束不允许** |

**由本次对照得出的结论**：

- **可以简化的**：固定端口 + 就绪探测端点 + 单实例 —— 桌面应用的通行形状，不必自证。
- **必须自己定的**：① ★ **"被占则顺延"到底要不要** —— 这是本合订本**最有价值的一条分歧**：
  行业默认顺延，而我们**推翻**了它，理由是**消费者变了**（扩展与书签看不到新端口）。
  这条没有可抄的答案，只能靠"我们的消费者是谁"来定；
  ② **就绪探测要不要校验对端身份** —— 行业通常不校验，我们**必须**校验（§1 的事故）。
- **未核实**：其他"桌面壳 + 浏览器扩展"组合在**端口变更时如何通知扩展**上的做法，本次**没有取证**。
  §6.1 第 1 条说得很直白：**扩展没有被动通知通道**，原因是 MV3 SW 没有稳定的常驻连接渠道 ——
  这是一个我们**没有解决**的结构性缺口（只是端口固定后它暂时没有触发场景）。

## 9. 重新评估的触发器

| 触发器 | 到时再考虑 |
|---|---|
| 三个固定端口之一被**无关程序长期占用**成为常态 | §6.2 第 2 条：那时"可预测换总能起来"这条取舍要重开（但**不要**顺手加顺延） |
| 需要**同时跑两个实例**（例如并行对比两个版本） | §6.2 第 1 条：必须用不同 `WORKBENCH_DATA` **且**同时覆盖三个端口，否则会撞 |
| 出现"路由到了错误的实例"的真实事故 | §7 第一条：身份核对（§3.2.6 / §3.5）不够 —— 那时升级的是**身份判据**，不是端口方案 |
| 桌面壳不再需要支持**旧版扩展** | §3.2.5 的"拿不到就回退固定 18765"可以去掉，`whoami` 失败即硬失败 |
| 出现 MV3 之外的扩展形态（有常驻连接） | §6.1 第 1 条的缺口可以补上（扩展可被动通知） |

# ADR-0010：Monitor 危险操作永不回放，解读须有实证来源

> **合订说明（2026-10-07）**：本文是**主题合订本**。仓库在 2026-10-07 把 22 篇 ADR
> 按主题合并成 8 篇（用户授权：「快速合并历史的 ADR」「未来的开发存在变更是正常的」）。
> 本组只吸收了 **原 ADR-0010** 一篇，内容除链接与标注同步外**未改写**。
> ★ **原有的「补记（这段是后补的）」标记原样保留**。
> 合并口径见 [AGENTS.md](../../AGENTS.md) §5。

- **状态**：已采纳（阶段 3D）
- **相关**：[ADR-0002](0002-browser-allocation-policy.md)、[API.md](../API.md) §13、[SCHEMA.md](../SCHEMA.md) §4

## 1. 背景

Monitor（`services/egmp/monitor/`）**录制**用户在平台上的操作，产出三样东西：

1. **录制日志**（`monitor-log.json`）——请求/响应/DOM 动作；
2. **解读**（`interpreter.py`）——把连续请求切成语义段，推断它在做什么；
3. **复现计划**（`reproduce_plan`）——把段映射成可重放的步骤，`API_MAP` 对位到 `egmp.writers` 的创建器。

它内化自 `akso-auto` 的 Puppeteer 版 Monitor。录制数据来自**真实生产/验证环境**，
里面必然包含真实的业务对象编码、字段值、以及**破坏性操作**（删除对象、批量改状态、
触发审批流、发通知……）。

危险点是显然的：**「录制 → 自动回放」在语义上等价于「在生产上重放用户当时的全部操作」**。
上游已确立安全边界，本项目内化时必须原样继承，不能因为「我们已经有了 writers 层」就放宽。

## 2. 决策

### D-1 危险操作永不回放（硬边界）

`interpreter.py` 对每个解读出的段做分类，**`DANGEROUS` 类永不进入可执行步骤**：
复现计划里保留它的位置与说明，但标记为不可执行，必须由人重新决策。

### D-2 `API_MAP` 必须对位到 `egmp/writers` 的实证常量

复现计划把录到的请求端点映射到 writers 的创建器/端点常量
（`egmp/writers/endpoints.py`，自原仓库只读提取并逐条标注来源）。
**不允许凭观察猜端点**：映射不上就不映射（宁可让人工处理），也不要写一个「看起来对」的端点。

> ★ **本条描述的东西已不在仓库里** —— 写路径（`egmp/writers/**` + `orchestrate.py`）随配置工厂
> 于 2026-09-22 一并删除，`API_MAP` 随之移除。**保留原文与划线形态是刻意的**，见 §5 补记。

### D-3 复现须逐步授权

复现不提供「一键全量回放」。执行由调用方按 `reproduce_plan` 的 `steps` **逐步确认**后调用对应 writers 函数。
这与配置工厂的「环境强制确认」原则同源（`confirmed=true` 才发起，见 [API.md](../API.md) §7）。

> ★ 同上：**"逐步确认后调用对应函数"这一步今天没有可调用的目标了**（写路径已移除），
> 而**安全边界原样保留** —— 见 §5 补记。

### D-4 三级降噪（录制侧的正确性约束，不是优化项）

录制引擎必须把事件分成三级，因为它跑在 [ADR-0002](0002-browser-allocation-policy.md) §2.3
的单线程约束下：

| 级别 | 含义 |
|---|---|
| `dropped` | 与本平台无关的流量（静态资源、埋点、第三方） |
| `trimmed` | 相关但只保留摘要（大响应体只留形状与关键字段） |
| `full` | 完整保留（平台的业务 API） |

**关键约束**：事件回调内**禁止**任何连接调用（`response.text()` / `page.evaluate` 重入 = worker 死锁）。
所以事件只入队，在 worker 的作业间隙由 `monitor.drain()` 统一处理——
这正是三级降噪必须存在的原因：**不能就地读响应体**。

真机验收基线：248 请求捕获 → `dropped 238 / trimmed 2 / full 8`。

### D-5 反馈闭环只写不自动改

`record_feedback` / `append_pitfall_record` / `append_error_record` / `mark_iterated`
把人工解读时发现的坑与错误记成记录（供后续改进解读规则）。
**它们只落盘，不自动修改 `API_MAP` 或复现计划**——规则的改动必须是显式的人工动作。

> ★ 同上：`API_MAP` 已不存在，但**"规则改动必须是显式人工动作"这条方向不变**；
> 今天它作用于解读规则本身。

## 3. 取舍

### 换来什么

- Monitor 可以放心在真环境录制，不会因为「某人点了一下自动回放」而造成生产事故。
- 解读的每一条映射都可追溯到 writers 里的实证常量，而不是模型的猜测。
  （★ 写路径移除后，"映射"不再存在；**"不许凭观察猜"这条纪律本身仍是活的**。）
- 录制本身对平台负载可控（三级降噪把 96% 的流量丢弃）。

### 代价（已接受）

| 代价 | 说明 |
|---|---|
| **复现的自动化程度低** | 每个计划都要人工逐步确认；不能用它做「无人值守的批量重放」 |
| 解读质量依赖人工核对 | `mark_iterated` / `record_feedback` 的价值取决于有人真的去标记 |
| 录制与复现是两套载体 | 录制走 Playwright（Python），最终执行走 httpx writers（Python）——中间靠 `API_MAP` 对齐，映射层是维护面。★ **复现那半已随写路径移除**（见 §5） |
| 长驻录制的资源占用 | 需要保持一个托管会话在线；`monitor_start` 因此可能触发开户（`_submit(timeout=90)`） |

### 明确排除的方案

- **「录制即脚本」**（把请求序列直接重放）：无法处理令牌/时序/条件分支，且必然包含危险操作。
- **让 LLM 直接生成复现计划**：无法保证端点真实性。LLM 只在 `understand` 的职责摘要
  （`_llm_summary_fn`，可选、且失败即回落确定性标注）与蓝图生成里出现——**不进入 Monitor 的映射判定**。

## 4. 后果

- **`DANGEROUS` 分类的正确性是安全关键路径**，但**目前没有自动化测试守住它**：
  `tests/test_native.py` 覆盖了 `monitor_classify_and_query` 与 `monitor_interpret_segment`，
  但它们验的是分类/解读的基本行为，**不是「危险操作不会被误放进可执行步骤」这一断言**。
  这是已知的测试缺口（见 `../CODEBASE_OVERVIEW.md` §九 的风险台账）。
- **监听的生命周期与托管会话耦合**：录制产物落 `runtime/monitor/<account_id8>-<stamp>/`；
  但关闭会话**不会自动停监听**（见 [API.md](../API.md) §13 与 `../CODEBASE_OVERVIEW.md` §九 的风险台账）。
- **另有一套同名但无关的东西**：上游扩展曾有 `page-monitor.ts`（Page Monitor，最近页面）。
  它已于 0.2.22 整块撤销，**与本文档的 Monitor 无关**——即使名字里都有 Monitor。
  `services/browser_pool.monitor_start/stop` + `runtime/monitor/` 才是本文档指的那套。

## 5. 诚实边界

> 本组只有一篇 ADR。它的诚实边界主要以「补记（这段是后补的）」的形态存在，**原样保留在 §6**；
> 下面三条取自 §4 与 §3，**未新增结论**。

- ★ **`DANGEROUS` 分类的正确性至今没有自动化断言守住它**。
  `tests/test_native.py` 验的是**分类/解读的基本行为**，不是"危险操作不会被误放进可执行步骤"。
  ⇒ **这是本 ADR 最要紧的一条边界**：整篇的安全承诺（"危险操作永不回放"）**没有判据**。
- **监听的生命周期与托管会话耦合**：关会话**不会自动停监听**（登记的待修项，不是"已处理"）。
- **"复现计划"这一半已不在仓库里**：见 §6 补记 —— 读到 §2 D-2/D-3 而不读补记的人，
  会以为仓库里有一条可以调用的回放执行链。

## 6. 补记（**这段是后补的**，2026-09-22）

**「复现计划」这一半已随配置工厂整体移除。** 本 ADR §2 第 3 条与上面「权衡」表里
API_MAP 对位 egmp.writers 创建器的说法，**描述的是一个已经不在仓库里的东西**：
写路径（egmp/writers/** + orchestrate.py）连同配置工厂一并删除，API_MAP 随之移除。

现状（**决策的方向没变，只是执行侧不再存在**）：

- `reproduce-plan.json` **只承载平台侧事实**（method / path / params / `reproducible`，
  外加显式的 `"executor": null`）；
- **本仓库不再提供任何回放执行器**——「逐步确认后调用对应函数」这一步没有可调用的目标了；
- **安全边界原样保留**：DANGEROUS 类**永不入计划**（这条是本 ADR 的核心，未受影响）；
- 录制侧（Playwright 三级降噪 / 查询层 / 段解读）**全部保留**，坑与口径见
  [factory-tuning/README.md](../../factory-tuning/README.md) 与
  [PITFALLS.md](../PITFALLS.md) 的 #64 / #74 / #76 / #80。

**§4 里那条测试缺口仍然成立**：DANGEROUS 分类的正确性依旧没有自动化断言守住它。

> ★ 补记里那两处 `reproduce-plan.json` 的原文在**记录当时就带着一处渲染/替换损伤**
> （行首少了 `r`、`reproducible` 少了一个 `p`）—— **合并时未擅自"修好"**，

## 7. 外部参照

> ⚠️ **本栏为后补**（2026-10-07 合并时补写；正文其余部分保持决策当时的样子，不改写）。
> 原 ADR-0010 写于 `0000-template.md` 建立之前，**没有这一栏**。
> 能给出处的写，给不出的写"未核实"，**不凭印象造共识**。

| 参照对象 | 它的做法 | 与本决策的关系 | 我们的理由 |
|---|---|---|---|
| **Playwright 官方 · `codegen`** | 录下用户操作并**生成脚本**；官方文档明确把它定位为"**起点**，生成的代码要人工修改" | **★ 分歧（关键）** | §3 的「**录制即脚本**」正是它这条路线，而我们**明确排除**：生成脚本无法处理令牌/时序/条件分支，且**必然包含危险操作**。⇒ 我们改成"录制 → 解读 → **分类** → 只有非 DANGEROUS 的段才可能进计划" |
| Chrome DevTools 的 **HAR 导出** / 各家"录制 HTTP 流量"工具 | 录下请求序列，**原样可重放** | **★ 分歧（同一族）** | 与上一条同一个理由：**"能重放"本身不是目标**。我们的产品边界是"帮人**理解**平台上发生了什么"（解读），不是"自动重做一遍" |
| [HAR 规范](http://www.softwareishard.com/blog/har-archives/) | 请求/响应的**记录格式**（无重放语义） | **一致（方向）** | 我们的 `monitor-log.json` 与它同类：**只记录，不承诺可重放**。三级降噪对应它的"大响应体只留形状"的常见处置 |
| 各家的"工作流录制/回放"产品（RPA 类） | 以**能重放**为核心卖点，通常配"确认步骤"或"生产环境保护开关" | **分歧** | 我们的结论更保守：**危险操作永不入计划**，而且**今天的计划里连执行器都没有**（§6 补记）。RPA 类产品的重放能力对我们**不是收益而是风险源**（录制数据来自真实生产环境） |
| 本仓 [ADR-0002](0002-browser-allocation-policy.md) §2.3（`browser_pool` 单线程） | 事件回调内禁止连接调用，只能入队 + drain | **一致（约束）** | §2 D-4 的三级降噪**不是优化项**，它就是这条约束的产物：**不能就地读响应体**，所以必须分级决定"留多少" |

**由本次对照得出的结论**：

- **可以简化的**：记录格式（HAR 一类的形状）与"大响应体只留摘要"的降噪思路 ——
  行业已有共识，不必自证。
- **必须自己定的**：★ **"危险操作"怎么分类、由谁分类** —— 行业里 RPA 类产品把这件事
  交给"用户开保护开关"，而我们的答案是**分类器 + 永不入计划**。
  这个取舍取决于"录制数据来自真实生产环境"这一语境，**没有可抄的答案**。
- **未核实**：其他"录制 + 解读"型工具在**解读正确性**上如何设判据，本次**没有取证**。
  ★ 而本仓在这一块**恰好是最弱的**：§5 第一条说得很清楚 ——
  `DANGEROUS` 分类的正确性**至今没有自动化断言**。

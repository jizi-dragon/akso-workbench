# ADR-0023：整批只读调用的并发——口径从「整批 READ」收窄为「逐工具举证」

- **状态**：已采纳
- **日期**：2026-09-24
- **决策人**：维护者（依据 `CORE-AGENT-PLAN.md` §7.4 执行时的实测）
- **影响面**：`plugin_api.py`（新增 `ToolSpec.parallel_safe`）；`harness/loop.py`（`_parallel_eligible`
  ＋ `_run_parallel_batch` ＋ 抽出 `_observation_event`/`_tool_message` 唯一构造处）；
  `harness/safety.py`（新增 `SafetyGate.would_loop`）；`plugins/builtins.py`（只标一个工具）
- **取代**：**收窄**（不废除）`CORE-AGENT-PLAN.md` §7.4 的设计口径。并**收窄** §5.6 的停止检查点
  在"显式标了并发的批次"上的粒度（见 §5 第 2 条）
- **外部参照**：OpenAI / Anthropic 的并行工具调用（见 §6）

---

## 1. 背景：计划原文的口径是「整批都是 `Risk.READ` 且都不需确认」

那个口径看起来无懈可击 —— 只读的东西并发跑，不会互相影响。

**按它实现完之后，三条已批准的判据当场变红：**

| 变红的判据 | 它属于 |
|---|---|
| `test_stop_before_a_tool_call_backfills_every_unexecuted_call` | 计划 §5.6（可中止 stop） |
| `test_the_action_event_is_not_emitted_for_a_call_we_will_not_make` | 计划 §5.6 |
| 评测用例 `stop_mid_batch` | 计划 §6.3（离线评测集） |

红的原因**不是实现写错了**，而是并发**必然**带来一个后果：它把"停止"的检查点从
**每次调用之间**退到**每批之间** —— 而那是 §5.6 明确买下的性质。

★ **本仓的默认假设：新功能让已批准的判据变红时，是新功能错了，不是判据该改。**
（改判据是允许的，但那要走一篇 ADR 把被取代的决策写清楚 —— 而不是顺手把断言改绿。）

---

## 2. 决策：★ 逐工具举证（`ToolSpec.parallel_safe`，缺省 `False`）

**只并发"整批都显式声明了 `parallel_safe=True`"的调用。** 今天全仓只有**一个**工具标了它：
`get_current_time`（纯计算：读一次系统时钟，没有 IO、没有共享状态、没有 `to_thread`）。

其余 17 个**一律保持 `False`**。这不是判定它们不安全，而是**还没有逐个核实**。

### 为什么「只读」不足以支撑并发

"只读"说的是**不改变我们关心的状态**，而并发要问的是**另一件事**：
**两个实例同时在跑时，会不会碰同一份可变状态？** 至少三类东西"只读但会碰"：

| 东西 | 并发时会发生什么 |
|---|---|
| HTTP 会话（`requests.Session` 不是线程安全的） | 可能出错，也可能静默串味（连接复用/重定向状态） |
| 浏览器那条**单工作线程队列**（铁律 23） | 并发只会**排队**，一点不加速，白白让事件形状变复杂 |
| sqlite 连接（跨线程用会直接抛） | 在 `to_thread` 里用同一个连接 = 报错；而报错点离原因很远 |

★ 三类里有两类**不会报错**。这正是本仓最防的形态：**没有任何症状，只是不变快或者偶尔怪一下**。

### 标注之前必须回答的那一句

> **「这个工具并发跑两个，会不会碰同一份可变状态？」**

与 `trust` 同一种纪律（那一条问的是"它的返回值是谁写的"）：**举证一个，标一个**。
按"它看起来只是读"批量放行，正是本 ADR 要防的那个直觉。

## 3. 两条实现纪律

### D-1 资格判定必须是**纯**的 —— `SafetyGate.would_loop`

重复检测（`is_loop`）是**有状态**的：它把调用记进一个滑动窗口，第 3 次相同调用触发。

所以资格预检**不能**用它 —— 预检失败时要**原封不动地**退回串行路径，
而预检一旦改了 `_history`，同一次调用在串行路径上会被记**第二遍**，
重复检测就**提前一轮误报**（本该第 3 次，变成第 2 次）。

⇒ 新增 `would_loop`：只回答"假如现在记下这一条，会不会触发"，**不改任何状态**。

### D-2 资格判定**不问** `should_stop`

第一版在预检里调了一次 `_stopped(should_stop)`，结果 §5.6 的两条判据红得**很奇怪**：
"该只执行第 0 个，实际 **`[]`**" —— 一个都没执行。

根因：**那句询问消耗了一个检查点**。"用户在第 N 个检查点按了停止"是用**计数器**模拟的，
多问一次就把整个时序**往前挪了一位**。

生产里 `StopToken.__call__` 只读一个 bool（无副作用），所以这不是线上缺陷 ——
但它说明：**"问是否停止"这个动作本身是可观测的**，而资格判定是**关于批次的纯谓词**，
不该消费停止通道。⇒ 预检里不问；停止仍由串行路径那三个检查点负责。

## 4. 事件顺序：按 `index`，不按完成顺序

完成顺序取决于网络与平台，**不确定**。所以：**先按 index 发完全部 `action`，
`gather`，再按 index 发完全部 `observation`**。

⇒ 并发批次的事件形状是 `action, action, observation, observation`（**分组**），
而不是串行路径的 `action, observation, action, observation`（**交替**）。

前端**本来就能处理**：`chat-tools.js` 按 `auditId` 配对卡片，注释里逐字写着
「优先按 auditId 配对（**同轮可以并发多次调用**）」，并且有一条"乱序/重放"的兜底分支。

（这一条是动手**之前**核实的第一件事 —— 如果前端是按顺序配对的，整个 §7.4 都要重新设计。）

## 5. 诚实边界

1. ★ **并发今天几乎不会触发。** 全仓只有一个工具标了 `parallel_safe`，
   而模型要一次发出 2–4 个 `get_current_time` 才会走到快路径。
   **这一节交付的是"机制 + 纪律"，不是"今天能省多少延迟"** ——
   谁想拿到收益，得去逐个核实工具并标上它。**这是刻意的**：
   宁可收益来得慢，也不要一次批量放行换来一堆"偶尔怪一下"。
2. ★ **对显式标了并发的批次，停止的粒度是"每批"而不是"每次调用"。**
   §5.6 的检查点②在串行路径上仍是每次调用前；标并发的批次在**派发之前**查一次。
   为什么可接受：那类批次**只含无副作用、且经核实的**调用，所以"少跑两个"省不下什么，
   也不会留下半完成状态。**凡可能改状态的批次一律走串行路径**，
   "每个动作要么完整发生、要么完全没发生"的保证**原样保留**。
3. **批大小超过 `PARALLEL_READ_MAX = 4` 时整批退回串行**（不切波）。
   切波要引入"波与波之间要不要重新查停止/预算"的额外语义，
   而那正是这条快路径最该保持简单的地方。放宽它的前置是回答那个问题。
4. **`gather` 在 `execute` 抛异常时不做特殊处理。** `execute` 按 I13 **从不抛**；
   万一它抛了，快路径把已经拿到的结果发完（不让做过的工作变成看不见的），最后再抛出。
   更复杂的补偿逻辑（取消其余、合成观测）**刻意没写** ——
   为一个"按设计不可能发生"的分支加复杂度，换来的是更难懂的失败路径。
5. **量化的收益没有测。** 今天只有一个工具能并发，测出来的数字没有代表性。
   触发条件：标的工具多到能构造出真实的多调用批次时再测。

## 6. 外部参照

| 参照对象 | 它的做法 | 与本决策的关系 | 我们的理由 |
|---|---|---|---|
| OpenAI 的 parallel function calling | 模型一次返回多个 `tool_calls`，**由调用方决定**并发还是串行；官方文档只讲"怎么发多个"，不讲调度 | **方向一致** | 我们采纳"模型一次发多个、由我们决定怎么跑"；**调度策略自己做**：它们没有"只读/有副作用"的分层，而我们有 `Risk` —— 那是本仓自己长出来的、恰好能用在这里的东西 |
| Anthropic 的 tool use | 同样支持一次多个 `tool_use`，并建议**读类**工具可并发 | **口径与计划原文接近** | ★ **没有采纳它的粗口径**：它的上下文是"工具由你（开发者）自己写、你知道它们会不会打架"；而本仓有**用户装的 Skill**（第三方代码），"它看起来是 read" 不足以证明它并发安全。这正是 `parallel_safe` 要显式举证的原因 |
| 本仓铁律 23（`browser_pool` 单线程队列） | 浏览器操作**必须**串行过一条队列 | ★ **正是本决策的依据之一** | 它说明"只读但会碰同一份状态"在本仓**不是一个假设，而是一个已经存在的事实**（Playwright sync API 就是这么要求的）。所以"只读 ⇒ 可并发"在本仓**从前提上**就不成立 |
| 计划 §7.4 原文 | 「只并发整批都是 `Risk.READ` 且都不需确认的调用」 | **收窄** | 按它实现会让 §5.6 的两条判据 + 一条评测用例变红。见 §1 |

**由本次对照得出的结论**：

- **可以照抄的**：模型一次发多个调用、我们把它们并发跑、事件按 index 回填 —— 这三件事各家一致。
- **必须自己定的**：★ **"哪些工具能并发"没有可抄的答案。** 别家的工具都是自己写的，
  而我们有一个**第三方代码入口**（Skill）。那意味着"安全"不能由**代码分类**（只读/写）推出，
  只能由**逐个举证**得到。这条差异只在本仓成立。
- **未核实**：各家在**并发 + 用户中断**同时发生时怎么处理（取消已派发的调用？等它们跑完？），
  我没有读到明确说法。我们选了"等它们跑完"（§5 第 2 条），理由写在上面 —— 但那是我们的取舍，
  不是抄来的。

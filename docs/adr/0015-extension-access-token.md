# ADR-0015：`/extension/*` 引入访问令牌，并把"壳协作面"迁出该命名空间

- **状态**：已接受（2026-09-17）
- **决策人**：用户（原话：「接着做 p0-1」——承接上一轮体检里列为唯一的 P0 安全项）
- **影响面**：`workbench/api/extension_auth.py`（新）、`routes_shell.py`（新）、
  `routes_extension.py`（瘦身）、`api/__init__.py`（装中间件 + 注册新路由）、
  扩展 `background/core/desktop-auth.ts`（新）+ `sync.ts` / `constants.ts`、
  桌面 UI `accounts.js` / `wheel-picker.html`（改路径）、`workbench/static`、
  `verify_packaging.py` 的 **P10**、5 个 `tools/verify_*` 脚本
- **取代**：无。本 ADR **修的是** [ADR-0011](0011-port-and-session-negotiation.md) §D-4
  里那句"仅靠 127.0.0.1 回环 + `/api/health` 的 `app` 字段自证身份"的**安全前提**——
  它当时回答的是"端口上坐的是不是我们的服务端"，**没有**回答"敲门的是不是我们的扩展"

---

## 1. 背景：一条"拿到即等于拿到口令"的路

`GET /extension/snapshot` 会**同时**下发：

- `fernetKey`（Fernet 密钥本体）；
- 每个账号的 `passwordEnc`（密文凭据）。

密钥与密文一起给出去，等于**明文口令**。而整条 `/extension/*` 此前**没有任何鉴权**，
唯一的屏障是"服务只监听 `127.0.0.1`"。这就是 CODEBASE_OVERVIEW 的 **R1**：

> 本机任意进程可拉快照（快照里**同时含 Fernet 密钥与全部密文口令**，等于直接拿到所有测试账号明文）
> —— `routes_extension.py:26`；`accounts.py:432-464`

### 1.1 为什么"只监听回环"不够

回环把**网络**攻击者挡在外面，但本机上的**任何**代码都能发这个请求：

| 敲门者 | 后果 |
|---|---|
| 用户浏览器里的**任意网页**（`fetch('http://127.0.0.1:18765/...')`） | 读不到响应（CORS 挡着），但**能造成副作用**——`POST /extension/commands` 可注入 `par.open`，触发扩展去打开页签并自动填口令 |
| 本机任意进程 / 脚本 | 一次 GET 拿到密钥 + 密文 = 全部账号明文 |
| 别的应用里的 WebView / 被安装器塞进来的辅助进程 | 同上，且**用户完全不知情** |

R1 在台账里挂了很久没修，原因是它**没有症状**：功能一切正常，注入的指令也能跑。

### 1.2 P0-4 的教训直接指向这里

上一轮补 `/extension/*` 的 pytest 覆盖时发现：这一整块是**凭据下发口 + 指令队列宿主 +
"扩展是否需要重新加载"的判定源**，却**一条测试都没有**。C4（队列永不排空）能在仓库里
躺那么久，根因就是"暴露面最大、回归网最薄"。

所以本 ADR 的目标不只是"加一个头"，而是**把这条通道纳入有测试、有机检的守备范围**。

## 2. 决策

### D-1 用**共享令牌**，而不是"来源校验"或"进程级 ACL"

| 方案 | 为什么否决 / 采纳 |
|---|---|
| **只校验 `Origin`** | ❌ **不可靠**：扩展 service worker 发跨源 `fetch` 时是否带 `Origin`，取决于浏览器实现与请求模式（简单请求 vs 预检）。本机无法实证，**不能把安全建立在没验证过的浏览器行为上** |
| **只信 `sender.frameId === 0`**（扩展侧） | ❌ 同族错误已在 P0-2 踩过：`auto-login.ts` 的**子 frame 也会各自索取**（跨域 SSO 登录框靠这条路径），按 frame 收口会打死合法路径 |
| **mTLS / 客户端证书** | ❌ 架构上没有载体：扩展与桌面之间只有 `fetch`，装不了客户端证书 |
| **命名管道 / 文件句柄** | ❌ MV3 扩展没有文件系统访问；且桌面壳与 Python 之间已有端口契约（ADR-0012），再引一条 IPC 通道是净增复杂度 |
| **共享令牌（采纳）** | ✅ 唯一在"扩展 ↔ 本机 HTTP"这一约束下能表达"持有者身份"的机制；且**浏览器侧的预检天然挡住网页**——自定义头会触发 CORS 预检，服务端不授予跨源许可，**浏览器根本不会发出那个请求** |

### D-2 令牌**落库、跨重启稳定**

令牌存 `settings.extension_access_token`（`secrets.token_hex(32)`），**不是**进程内存态。

理由：装在用户 Chrome 里的扩展必须能长期持有它。若每次桌面重启都换令牌，扩展会拿旧令牌
狂刷 401 —— 而它看起来像"扩展坏了"，用户唯一的出路是重新加载扩展。
落库后 `WORKBENCH_AUTO_UPDATE` 类的"重启即变"问题不会出现在这里。

### D-3 走**中间件按前缀守备**，不走逐路由 `Depends`

FastAPI 的依赖是**逐路由**声明的：漏加一条就静默开一个口子，而"新增路由忘了加依赖"
正是这类防护最常见的失效方式。中间件按**路径前缀**统一判定，于是
**"新加的路由自动被守住"是结构保证**，不是纪律。

代价：豁免面集中在 `EXEMPT_PATHS` **一处**（`/extension/hello` 与 `/extension/health`），
新增豁免必须显式登记。这是刻意的——豁免面越小，"整个前缀需要令牌"这句话才越接近真的。
`tests/test_extension_auth.py::test_exempt_surface_is_minimal` 钉住它。

### D-4 自举端点 `/extension/hello`：免鉴权，但**必须保持最小**

扩展必须先拿到令牌才能访问需要令牌的端点 —— 这是死锁，所以自举端点必然免鉴权。

它**只回** `{format, version, token, desktopVersion, header}`，**不含任何账号数据**。
`test_hello_returns_only_bootstrap_fields` 按**字段集合**断言（不是"有没有 token"）：
往这里加一个便利字段，就等于把 R1 重新打开一部分。

### D-5 **宽限期（默认 24h）**，而不是立刻硬失败

令牌是**新加的协议要求**。已装在用户 Chrome 里的**旧扩展不会带令牌**：

| 处置 | 后果 |
|---|---|
| 立刻硬失败 | "快捷登录静默失灵、且没有任何提示" —— 正是本仓反复踩的那类静默故障 |
| **宽限 24h（采纳）** | 旧扩展在这段时间照常可用；同时留 warning，并让桌面 UI 提示用户重新加载扩展 |

窗口起点**落库**（`settings.extension_auth_grace_started_at`）、**只记一次**：
放进程内存态会被每次重启重置，等于永久开着窗口。
`WORKBENCH_EXTENSION_AUTH_GRACE=0` 可切成严格模式——现场排障需要它来分诊"扩展连不上"。

### D-6 把"壳协作面"迁出 `/extension/*` → `/api/shell/*`

这一步看起来与安全无关，实际是 D-3 能成立的前提。

原先 `/extension/*` 上挂着三条**给桌面 UI 用、且完全不碰凭据**的端点：
`/launch-chrome`（拉起 Chrome）、`/setup-helper`（请壳打开 `chrome://extensions`）、
`/update-state`（读壳落盘的更新状态）。调用方是账号中心与页内轮盘，**同源页面**
（`http://127.0.0.1:18765`）——而令牌只发给扩展，UI **拿不到也不该拿到**它
（页面里放令牌等于把它交给任何能读 DOM 的东西）。

于是只能给这三条开豁免。但**豁免一开，"整个前缀需要令牌"就退化成一份人工维护的清单**——
正是 D-3 想消灭的东西。

**所以按"碰不碰凭据"重新划边界**：

| 命名空间 | 内容 | 令牌 |
|---|---|---|
| `/extension/*` | 扩展 ↔ 桌面之间的**数据与指令**通道 | **必需**（豁免仅两条） |
| `/api/shell/*` | 桌面 UI 请**壳**干活（拉起浏览器 / 安装引导 / 读更新状态） | 不需要（也**不碰凭据**） |

这条边界有两条守护：`routes_shell.py` 的模块文档串写明判据（"新增端点前先问：它碰凭据吗？"），
以及 `test_extension_blueprint_has_no_ui_only_routes`。

### D-7 **不**给 `/api/*`（95 个端点）加令牌

`/api/accounts/export`（导出备份，含密钥）与 `/api/browser/sessions/{id}/token` 同属敏感面，
但它们**同源**：桌面 UI 就是从这个服务加载的页面，加令牌要么在页面里放令牌（等于没加），
要么改页面引导流程（净增复杂度、收益低于本 ADR）。

**如实记录这个取舍**：R1 的"零知识一次 GET"已经在 `/extension/*` 上关闭；
`/api/*` 仍依赖"只监听回环 + 无 CORS 授权"这一层。它是独立的后续项，不在本 ADR 范围内。

## 3. 这一层**挡不住**什么（不要高估）

**本机同用户进程总能拿到令牌**——要么直接读 `%APPDATA%\Workbench\workbench.db`，
要么调一次 `POST /extension/hello`（它必须免鉴权）。而**能读库的进程本来就能拿到 Fernet 密钥**
（它就在同一张 `settings` 表里）。

所以令牌把攻击面从 **"任何能发 HTTP 的东西"** 收窄到
**"愿意读我们数据库或调我们自举端点的本机进程"**，后者与直接读库同级。
**它消灭的是"零知识的一次 GET"，不是"本机已被攻陷"。**

> 这是 PITFALLS #23 的同族判断：Fernet 密文挡的是**网络窃听**，不是本机实例串号；
> 令牌挡的是**零知识访问**，不是本机沦陷。**不要把这一层写成"凭据现在安全了"。**

可选加固（未做，留作触发器）：`WORKBENCH_EXTENSION_ORIGIN` 允许清单已实现并测过，
配好后可拒掉伪造来源的请求。默认空 = 不做来源校验，因为桌面壳目前不声明扩展 id
（用户手装的扩展 id 由 manifest 公钥决定、跨机一致，但不在本仓配置里）。

## 4. 兼容性（ADR-0013 的"协议类标识"纪律）

改名/改协议的纪律是"**写出端发新名 + 读取端两个都收**"。这里是**新增**一个协议要求，
故兼容矩阵必须两侧都成立：

| 组合 | 行为 |
|---|---|
| 新桌面 + 新扩展 | 扩展 `POST /extension/hello` 自举令牌 → 全部请求带 `X-Workbench-Token` |
| **新桌面 + 旧扩展** | 宽限期（默认 24h）内照常放行；窗口过后 401，且 `authBlocked` 让桌面 UI 提示"重新加载扩展" |
| **旧桌面 + 新扩展** | `POST /extension/hello` 返回 404/405 → 扩展视为"不需要令牌"，照常发不带令牌的请求 |
| 桌面不可达 | 扩展离线回退，本地数据照常可用（与既有纪律一致） |

## 5. 防静默故障：401 必须是**可诊断**的

grace 过后没重新加载扩展的用户会开始收 401，而扩展侧对失败是**静默吞掉**的
（`sync.ts` 的离线回退：桌面不可达是常态）。两条对策：

1. **401 带机器可读 code**（`extension_auth_required`）：扩展端据此"作废令牌 → 重新握手 →
   **重试一次**"（`desktop-auth.ts::authFetch`）。没有这一步，表现是"快捷登录莫名失灵"。
2. **无令牌访问对桌面 UI 可见**：中间件把"本该带令牌的端点被无令牌访问"记数，
   经**免鉴权的** `/extension/health` 暴露为 `authBlocked` / `tokenlessRequests`；
   账号中心复用既有的「扩展版本过旧」提示条（文案改成"需要重新加载"）。
   ⚠ 豁免路径（`/extension/health` 本身，UI 每 3s 打一次）**不计入**，
   否则 `authBlocked` 会被 UI 自己的轮询永久点亮、提示条再也关不掉。

## 6. 验收

| 手段 | 覆盖 |
|---|---|
| `tests/test_extension_auth.py`（20 项） | 令牌稳定/落库、豁免面最小、**严格模式真拦**（GET/POST/错令牌）、宽限期语义与"起点只记一次"、401 的 `code`/`hello`/`action`、自举端点字段集合、来源允许清单、**静默故障可见性** |
| `tests/test_extension_blueprint.py` | R1 **哨兵已翻转**：原先"记录无鉴权"的断言改成守卫（中间件必须在 app 上、豁免面只允许 health） |
| `verify_packaging.py` **P10** | 机检：中间件已装 + 豁免面最小 + UI 端点已迁出该前缀 |
| 真机/脚本 | 严格模式（`GRACE=0`）起服务：无令牌 401（带 code）→ 自举领令牌 → 带令牌 200；`/api/shell/*` 不受影响 |
| 既有验收脚本 | `verify_extension_sync.mjs` / `verify_extension_version.py` / `verify_command_latency.py` / `acceptance_extension_e2e.py` / `diag_fernet_node.mjs` 全部改为**复刻扩展的自举流程**——于是它们验的与扩展真跑的是同一条协议 |

## 7. 重新评估的触发器

1. **有人能读 `%APPDATA%` 但仍被挡住**——说明令牌真的起了作用，值得考虑把来源允许清单设为默认开启；
2. **`/api/*` 出现远程可达场景**（不再只是本机 UI）——那时 D-7 的取舍要重做；
3. **扩展 id 能被桌面壳稳定声明**（例如改用固定私钥签名）——把 `WORKBENCH_EXTENSION_ORIGIN`
   从"可选"升级为"默认开启"，并去掉宽限期；
4. **MCP / 脚本式 Skill 出现"以扩展身份访问"的需求**——那时令牌分发要重新设计（不能只是从 settings 读）。

## 8. 外部参照（2026-09-20 后补）

> ⚠️ **本栏为后补**（正文保持决策当时的样子，不改写）。上方 §7 即本模板所说的"触发器"栏。

| 参照对象 | 它的做法 | 与本决策的关系 | 我们的理由 |
|---|---|---|---|
| **MCP**（Model Context Protocol，2025-12 捐入 Linux Foundation 旗下 AAIF） | 远程用 **OAuth**；**stdio 传输靠"本地进程 = 受信任"**，不带令牌 | **分歧（我们更严）** | MCP 的 stdio 假设"能起进程 = 可信"。本仓的威胁模型不同：**请求方是浏览器里的扩展**，而"本机任意进程"恰恰是我们要挡的（§1.1 的威胁表） |
| **MCP 规范对"人工介入"的态度** | 只到 **SHOULD** always be a human in the loop；机制上是 `Elicitation`。**没有令牌、没有 TTL、没有参数指纹** | **一致（同一立场）** | 两边都认为**不可信方不能自证安全**。分歧只在于"用什么手段表达持有人身份"——MCP 留给客户端自研，**本 ADR 就是那份自研** |
| **MCP `ToolAnnotations`**（`readOnlyHint` / `destructiveHint`…） | 是**提示**。规范原文明确：所有 annotations **不保证忠实描述工具行为**，且**客户端绝不应基于不可信服务端发来的 annotations 做工具使用决策** | **一致（强论据）** | 这条是 §D-1 否决"来源校验"的**外部背书**：本仓的 `Risk` 也是**宿主强制**而非对端声明。**行业共识是"分级不能由不可信方说了算"** |
| 常见的本机应用 token 做法 | 随机 token 落配置文件/DB，客户端**自举领取** + 宽限期兼容旧客户端 | **一致（跟随）** | §D-2 的自举端点 + 24h 宽限期就是这个标准形状；且已被 Claude Desktop / Cursor / VS Code 一类客户端反复验证 |
| 常见实现普遍会做的：**`Origin` 允许清单** | 直接按请求头判断来源 | **★ 分歧** | 我们**明确拒绝**——理由在 §D-1：扩展 service worker 的 `Origin` 行为**无法在本机实证**。这是有意选择"更严但更笨"的路径，代价是 §D-1 那张否决表里的复杂度 |

**由本次对照得出的结论**：

- **可以放心的部分**：令牌 + 自举 + 宽限期是本机应用的标准形状，不必自证。
- **必须自己盯住的部分**：§5「**401 必须是可诊断的**」。
  这是本 ADR 最有原创价值的一节——**参照物都没有这个问题**，
  因为它们的客户端要么是浏览器（会弹登录框），要么是开发者工具（人看得懂 401）。
  **只有"扩展对失败静默吞掉"这个组合才会造出"功能莫名失灵"**，
  而它是本项目三面分工带来的**独有**后果（见 [ADR-0004](0004-extension-as-execution-plane.md) 的"跨进程协议成为关键路径"）。
- **一条可迁移的方法**：给任何客户端加鉴权时问一句「**失败会到达谁的眼前？**」——
  若答案是"被 catch 吞掉"，那就是又造了一条静默链。这条已写进本仓 PITFALLS #49 的"推广"。

## 1. 背景

### 1.1 三个互不相关、且都不报错的缺陷（**原 ADR-0019**）

2026-09-24 对核心 Agent 做了一次逐行核查，在"上下文与预算"这一小块里查出**三个缺陷**。
三者共同的特征是：**请求仍然合法、接口仍然 200、测试仍然全绿**，只是行为静默变差。

#### 缺陷① 折叠一旦发生，系统提示词就永久消失

`harness.context.split_turns` 只按 `role == "user"` 切轮，而首条 `system` 后面紧跟着
`user` ⇒ **`system` 自成一个 turn** ⇒ `cache._split_keep` 把它算进 `older` ⇒ 进
`plan.truncated` ⇒ 被并进摘要。而 `_with_summary` 补回来的那条 system 正文是
`"历史对话摘要：…"`——**原始提示词被替换成了一段有损摘要**。

`loop.py:17` 的模块契约白纸黑字写着 `[system] + [冻结摘要] + [原文历史] + [新消息]`，
实现违反了它。**没有任何断言读那句话。**

#### 缺陷② 上下文预算整轮只算一次

`_build_context` 在整个 `while True` **之前**只调一次，之后工具轮次只往同一个 list
`append`（一条 `read_web_page` 正文上限 12,000 字符）。实测探针：

> 预算 1000 token，**第 5 次请求已达 12,059**，而折叠发生 **0** 次。

超窗后是**平台**拒回来的，而那句话用户与模型都无法据以行动。

#### 缺陷③ 步数预算只在两次模型轮次之间检查

`safety.exhausted` 只在外层 `while` 开头检查一次，而工具批次是
`for call in assistant["tool_calls"]:`——**循环体内一次预算检查都没有**。
于是 `max_steps` 的实际语义退化成"N 次调用之后不再发起新的一轮"，
超出量由"模型一轮里发了几个调用"决定（实测：`max_steps=2` + 首轮 5 个调用 ⇒ **5 个全跑**）。

★ 而这个语义**当时就写在 `safety.SafetyGate` 的文档串里**（"只在两次模型轮次之间检查"）
——**文档是对的，代码是错的**。

次生缺陷更隐蔽：三条早退路径**直接 `return`**，于是 `assistant` 带着 N 个 `tool_call`
却只有前几个有配对的 `tool` 响应 ⇒ 这段历史**对平台非法**（`tool_call_id not found`），
且"对话级断点续跑"永远做不成。

### 1.2 「一次用户回合」在数据里**不是一个实体**（**原 ADR-0021**）

三条各自独立的证据：

1. `agent_audit` 记的是**单次工具调用**，`deepseek_usage` 记的是**一次回答的用量** ——
   两者只能靠**时间戳猜**关联。于是"这一回合失败了"这件事**没有任何载体**。
2. **"这次为什么慢"只能翻日志** —— 而日志是给人看的文本，不是可聚合的数据。
   一个真实的场景："最近几次洞察任务越来越慢" —— 在现有数据上**无法回答**
   是模型慢了、还是某个工具慢了、还是等待用户确认的时间变长了。
3. **跨步的因果表达不了** —— "第 3 步的超时导致第 5 步重试"在审计表里是两行无关的记录。

#### OTel GenAI 语义约定是行业共识，而本仓**零**（**原 ADR-0021**）

核查结论：**"行业标准是 OTel GenAI 语义约定 + Langfuse/Phoenix/LangSmith 三选一"**；
而本仓现状是 **"零"**（`grep` 全仓无 `opentelemetry` / `langfuse` / `trace_id` / `span(`）。

`CORE-ARCHITECTURE.md` §7.5 早就把它列为缺口，并给了一个关键约束：
**"不动现有表（它是审计事实源，且有合规含义），额外导出一层"** —— 采纳它。

### 1.3 计划原文的口径是「整批都是 `Risk.READ` 且都不需确认」（**原 ADR-0023**）

那个口径看起来无懈可击 —— 只读的东西并发跑，不会互相影响。

**按它实现完之后，三条已批准的判据当场变红：**

| 变红的判据 | 它属于 |
|---|---|
| `test_stop_before_a_tool_call_backfills_every_unexecuted_call` | 计划 §5.6（可中止 stop） |
| `test_the_action_event_is_not_emitted_for_a_call_we_will_not_make` | 计划 §5.6 |
| 评测用例 `stop_mid_batch` | 计划 §6.3（离线评测集） |

红的原因**不是实现写错了**，而是并发**必然**带来一个后果：它把"停止"的检查点从
**每次调用之间**退到**每批之间** —— 而那是 §5.6 明确买下的性质。

★ **本仓的默认假设：新功能让已批准的判据变红时，是新功能错了，不是判据该改。**
（改判据是允许的，但那要走一篇 ADR 把被取代的决策写清楚 —— 而不是顺手把断言改绿。）

### 1.4 计划把"token 估算"拆成两半，而 (b) 长期"受阻"（**原 ADR-0024**）

| 半 | 内容 | 状态 |
|---|---|---|
| (a) | 估算的**统计范围**（`tool_calls` / `tool_call_id` / 工具 schema 都要算进去） | ✅ 已完成 |
| (b) | **精确**计数：`tiktoken cl100k_base` + 1.1 系数 | ⬜ 长期"受阻" |

(b) 受阻的**表面**原因很实在：本机没装 `tiktoken`，而它首次使用要**联网下载 BPE 文件**
（`.venv` 是 uv 管理的、离线环境）。

★ **而真正的转折是重新读了一遍那个方案本身**：

> `cl100k_base` 是 **OpenAI 的分词器**。

我们发请求的对象是 **DeepSeek**（`deepseek-flash` ＝ DeepSeek-V4.1-Flash）。
拿 OpenAI 的分词器去数 DeepSeek 的 token，**是另一种近似** ——
它不比"数 CJK 字 + 词"更有依据，只是**看起来更精确**，代价是多一个依赖、
多一份要下载的资产、以及一个**永远对不准**的数字被当成真值使用。

★ **而真值一直在手上**：API 每次响应都在 `usage.prompt_tokens` 里回报它。
更关键的是，§7.1(a) 那一轮已经把它和**估算值**记在了**同一条 span** 上：

```python
"estimatedTokens": estimate_request_tokens(messages, tools),   # 估的
"usage": self.last_usage,                                      # 其中含 prompt_tokens（真值）
```

⇒ **两个数在同一条记录上**，比较不需要 join，也不存在"配错了一次请求"的余地。
`tools/compare_token_estimators.py` 就是靠这一对算偏差表的 ——
**而它只被用来"看偏差"，没被用来"修估算"**。

不决策的代价：估算与真值之间那个**已知会漂的偏差**会一直留着，
而折叠判定是按估算值做的 —— 估偏低就会**该折的时候不折**（直到平台把请求拒回来），
估偏高就会**过早折叠**（白丢上下文、还多花一次摘要的钱）。

### 1.5 一个**活的**不变量违规，两重看不见（**原 ADR-0025**）

`CORE-ARCHITECTURE.md` §5 的 **I4** 与 `AGENTS.md` 铁律 7 逐字写着：

> 依赖方向 `plugins → plugin_api`，**永不反向**。
> `plugin_api.py` 里出现平台术语、import 插件、或 import `db` 都是错的
> （它连审计与确认门都靠注入）。

★ 而 `plugin_api.py` 的 `get_hub()` 一直在做这件事：

```python
_hub = ToolHub()
from . import approvals as approvals_mod  # 本地导入：避免模块循环
from . import plugins as plugins_pkg

approvals_mod.install(_hub)
plugins_pkg.load_all(_hub)
```

★★ **它为什么能活这么久 —— 两重看不见：**

| 重 | 机制 |
|---|---|
| ① | 那两行是**局部导入**（函数体内）。注释写着「避免模块循环」—— 作者**知道**这是反向依赖，用局部导入把环绕开了 |
| ② | I4 的判据 `_imports()` **对 `from . import plugins` 这种形态算出来是空模块名** —— 它只取 `node.module`（这里是 `None`），**完全没看 `node.names`**。而那是本仓最常见的写法之一（`from .. import db` / `config` / `cache` 在 `workbench/api/` 下有十几处） |

★★★ **它是被反证翻出来的**。给 I4 补反证时，往 `plugin_api.py` 加一行
`from . import db` —— **判据照样绿**。修好 `_imports` 的解析之后，`get_hub()` 那两行
**当场变红**。

> 那正是反证存在的理由：**"全绿"与"判据瞎了"在输出上长得一模一样。**
> （本会话第三次撞到同一件事 —— PITFALLS #112 / #117 / #119。）

## 2. 决策

### 2.1 上下文窗口的**轮内**治理（**原 ADR-0019**）

#### D-1 `system` 提示词移出折叠域，永不参与摘要

`cache._pin_system()` 把首条 system 从折叠域里摘出来；`summarized_upto` 改为**只索引正文体**
（`body`）；`_compose(pinned, body, summarized)` 按契约拼 `[system][摘要?][正文]`。
**装配期断言** `assert plan.messages[0] is pinned` 放在 `plan_prefix` 里 —— 它每次请求都经过，
坏掉立刻炸，而不是静默降级。

**迁移 22** 把历史数据整体减 1：旧值 `k` 折叠的是 `{system} ∪ conversation[1:k]`，
新值 `k-1` 折叠 `conversation[1:k]` ⇒ **被折叠的正文逐条不变**。这是**精确平移，不是近似**。

#### D-2 上下文预算**每次模型调用前**复检，且分两档处置

| 档 | 条件 | 处置 |
|---|---|---|
| 过门槛 | 估算 > `context_threshold × window` | **折叠**历史后继续（原有行为） |
| 过硬上限 | 估算 > `context_hard_limit_tokens`（`None` = 用 `context_window_tokens`） | **根本不发这次请求**，以可行动文案终止 |

两档必须分开：混成一句"太大了"会让用户既不知道能不能继续、也不知道该做什么。
终止文案要说清三件事 —— 发生了什么、怎么接着做、去哪儿调大。

**估算刻意用偏低的那一个**（只算 `content`，不算 `tool_calls` 与工具 schema）：
宁可漏判（少一次保护）也不要误判（把正常请求掐掉）。

#### D-3 步数预算**逐调用**检查，且未执行的调用必须回填

- 预算检查移进 `for call in …` 内 —— **"预算"这类横切约束必须钉在"每次消费"的那一行旁边**，
  钉在循环外就等于把粒度交给了对方的批次大小。
- 未执行的每一条经 `loop._fill_unexecuted`（**一处实现**，后续取消 / 超时复用）补一条
  `tool` 观测，并各发一条 `status="skipped"` 的 `observation`（前端据此把卡画成"已跳过"
  而不是一直转圈）。
- **重复调用检测那条早退路径一并回填** —— 它此前同样直接 `return`。

#### D-4 三个新不变量写进 `CORE-ARCHITECTURE.md` §5

**I15**（system 永不被折叠）、**I16**（`tool_calls` 与 `tool` 成对）、
**I17**（预算每次调用前复检）。原计划里它们只写在方案文档中，
**不写进 §5 就等于引用了一个不存在的不变量**。

#### 本期做与不做（原 ADR-0019 §3）

**做**：D-1 / D-2 / D-3 / D-4 全部落地，判据见 `tests/test_cache.py`（新增 4 条）与
`tests/test_agent_contract.py`（**8 条**契约：C1–C5）。
反证：三处修复都做了 `git stash` 反证，确认新断言真的会红（不是"恰好绿着"）。

**不做（明确）**：

- ~~**轮内折叠**（超 `context_threshold` 时把中段并进摘要）~~ —— 本轮**只做了硬上限终止**。
  轮内折叠需要把 `loop` 的 `source`（原始会话）与 `context`（`plan_prefix` 的输出）**拆开**，
  而 `_one_model_turn` 目前只持有后者并就地 append。**到那时判据要从"能终止"
  升级为"能折叠后继续"。**
- ~~精确 token 计数~~（仍是 `harness/context.py` 的粗估）—— 见计划 §7.1。
  ★ **这一条后来由 §2.4 部分接续**（按 API 自报用量校准），但**仍不是精确计数** ——
  见 §5.4。
- ~~会话级断点续跑~~ —— I16 只保证历史**合法**（可回放），
  真正重放还需要 transcript 落库（计划 §7.3）。

#### 后果（原 ADR-0019 §4）

**好处**：

- 长会话不再"越用越不听话"（缺陷① 是它的唯一成因）。
- 长任务不再以"平台拒回来的一句话"收场，而是以**我们**给的、用户能据以行动的文案收场。
- 成本上限重新可控：`max_steps` 恢复成它字面的意思。
- 历史对平台合法 ⇒ 后续所有"回放/续跑/评测"能力第一次有了地基。

**代价**：

- 摘要边界多一层间接（`body` 与 `conversation` 的索引差 1），
  这是**每一次读 `summarized_upto` 的人都要知道**的事 —— 靠 `SummaryState` 的文档串与断言守。
- 硬上限终止是**新的失败形态**：以前是"平台拒"，现在是"我们主动不发"。
  两者的用户可见文案必须不同，否则用户会以为是我们坏了。

**风险**：

- 迁移 22 是**减法**且不可逆（没有 down 迁移）。若平移前提（旧值 `k` 的语义）判断有误，
  历史会话的摘要边界会整体偏 1 条 —— 表现为"某条消息偶尔重复或缺失"。
  缓解：迁移只改 `summarized_upto`，不动任何消息正文；且新装配路径有 `assert` 兜底。

### 2.2 Agent 运行记录（`agent_run` / `agent_span`）与 OTel 导出层（**原 ADR-0021**）

#### D-1 新增两张表，**不合并**进审计

```sql
agent_run(id, conversation_id, started_at, ended_at, status, error, steps, model,
          prompt_tokens, cache_hit_tokens, cache_miss_tokens, completion_tokens,
          summary_calls, latency_ms)
agent_span(id, run_id, step, span_kind, name, started_at, duration_ms, status, error,
           attrs_json)   -- span_kind: model | tool | sandbox | confirm
```

**三张表的分工（不要合并）**：

| 表 | 它是什么 | 权威性 |
|---|---|---|
| `agent_audit` | **审计**：谁对哪个对象做了什么 | 有合规含义，只增不改 |
| `deepseek_usage` | **计费**：token 与缓存命中 | 成本口径的唯一事实源 |
| `agent_run` / `agent_span` | **轨迹**：一次回合里每一步的耗时/状态/用量 | 只为"把一次回合当成整体看" |

★ 三者是"同一个事件的三份投影"，**权威各自独立**（铁律 28：两处都写全量 =
第二个会漂的事实源）。所以 `attrs_json` **只放指针**（`auditId` / 插件 / 风险 / 状态），
**不复制参数与账号** —— 判据见 `tests/test_agent_spans.py::test_tool_span_does_not_copy_the_arguments`。

**为什么不与 `agent_audit` 合并**：粒度不同。一次回合里的**多次模型调用没有审计记录**
（审计只覆盖工具），而工具调用在时间线上需要"它属于哪一步"的父子关系 —— 那是 span 的职责。
合并会让审计表被写入大量非审计行，而它的合规含义依赖于"**一行 = 一次有副作用的操作**"。

#### D-2 写入点只有两处，且**都在循环层**（对计划的一处偏离）

计划写的是"`loop._one_model_turn` 前后、`ToolHub.execute` 前后"。实际实现**两处都在
`harness/loop.py`**：

- 模型调用：包一层 `_SpanClient`（含摘要那次 `chat()` —— 它也是真实开销）；
- 工具调用：在 `await registry.execute(...)` 之后记，耗时取
  `ToolInvocation.duration_ms`（`ToolHub` 自己测的，**不含**用户等待）。

**偏离的理由**：`plugin_api.py` **不许 import `db`**（AGENTS.md 规则 7 / I4 的同一族），
所以 `ToolHub` 要写 span 就必须再走一次注入（像 `set_audit_writer` 那样）。
而 `ToolHub.execute` 目前的唯一调用方就是循环，注入带来的收益是零、成本是一个新的
注入面与一处启动期装配。**等真的出现第二个调用方时再加注入**（§7.2 的触发器）。

#### D-3 **任何出口都收尾**，且区分「失败」与「被中止」

`RunRecorder` 由 `_accounted`（既有的用量收尾上下文管理器）在 `finally` 里收 ——
同一条理由：循环有多个出口（final / error / 预算耗尽 / 上下文超限 /
抛异常 / 消费方断开），收尾交给调用方记得就会重演那两个缺陷。

★ **`failed` 与 `aborted` 刻意分开**：前者是"它真的坏了"，后者是
"用户关掉了页面"（`GeneratorExit`）。两者对用户的含义完全不同 ——
与「（已中止）」vs「错误：…」是同一条区分。

#### D-4 OTel 对齐靠**导出层**，不靠改表；**只做 OTLP**

`tools/export_otel.py` 把三张表映射到 `gen_ai.*`，输出 OTLP/JSON。
**零运行时依赖** —— 不为一个导出功能把 otel-sdk 拖进 sidecar（那是几 MB 与一棵依赖树）。

**不做 Langfuse 的私有导入格式**：OTLP/JSON 是**标准**（有公开 wire format），
而 Langfuse / Phoenix 的**导入格式我没有核实过** —— 不凭印象造第二份 schema。
接它们应当走各自的 OTLP 入口。

`AssertionError: 写失败没有被计数`）。

#### 后果（原 ADR-0021 §4）

**好处**：

- 失败回合**第一次有了载体**（`status='failed'` + `error`），而"卡在 `running`"
  与"跑完了"在界面上不再长得一样。

**代价**：

  判据见 `test_trace_write_failure_is_counted_not_swallowed_silently`。

### 2.3 整批只读调用的并发：逐工具举证（**原 ADR-0023**）

**只并发"整批都显式声明了 `parallel_safe=True`"的调用。** 今天全仓只有**一个**工具标了它：
`get_current_time`（纯计算：读一次系统时钟，没有 IO、没有共享状态、没有 `to_thread`）。

其余 17 个**一律保持 `False`**。这不是判定它们不安全，而是**还没有逐个核实**。

#### 为什么「只读」不足以支撑并发

"只读"说的是**不改变我们关心的状态**，而并发要问的是**另一件事**：
**两个实例同时在跑时，会不会碰同一份可变状态？** 至少三类东西"只读但会碰"：

| 东西 | 并发时会发生什么 |
|---|---|
| HTTP 会话（`requests.Session` 不是线程安全的） | 可能出错，也可能静默串味（连接复用/重定向状态） |
| 浏览器那条**单工作线程队列**（铁律 23） | 并发只会**排队**，一点不加速，白白让事件形状变复杂 |
| sqlite 连接（跨线程用会直接抛） | 在 `to_thread` 里用同一个连接 = 报错；而报错点离原因很远 |

★ 三类里有两类**不会报错**。这正是本仓最防的形态：**没有任何症状，只是不变快或者偶尔怪一下**。

#### 标注之前必须回答的那一句

> **「这个工具并发跑两个，会不会碰同一份可变状态？」**

与 `trust` 同一种纪律（那一条问的是"它的返回值是谁写的"）：**举证一个，标一个**。
按"它看起来只是读"批量放行，正是本节要防的那个直觉。

#### D-1 资格判定必须是**纯**的 —— `SafetyGate.would_loop`

重复检测（`is_loop`）是**有状态**的：它把调用记进一个滑动窗口，第 3 次相同调用触发。

所以资格预检**不能**用它 —— 预检失败时要**原封不动地**退回串行路径，
而预检一旦改了 `_history`，同一次调用在串行路径上会被记**第二遍**，
重复检测就**提前一轮误报**（本该第 3 次，变成第 2 次）。

⇒ 新增 `would_loop`：只回答"假如现在记下这一条，会不会触发"，**不改任何状态**。

#### D-2 资格判定**不问** `should_stop`

第一版在预检里调了一次 `_stopped(should_stop)`，结果 §5.6 的两条判据红得**很奇怪**：
"该只执行第 0 个，实际 **`[]`**" —— 一个都没执行。

根因：**那句询问消耗了一个检查点**。"用户在第 N 个检查点按了停止"是用**计数器**模拟的，
多问一次就把整个时序**往前挪了一位**。

生产里 `StopToken.__call__` 只读一个 bool（无副作用），所以这不是线上缺陷 ——
但它说明：**"问是否停止"这个动作本身是可观测的**，而资格判定是**关于批次的纯谓词**，
不该消费停止通道。⇒ 预检里不问；停止仍由串行路径那三个检查点负责。

#### D-3 事件顺序：按 `index`，不按完成顺序

完成顺序取决于网络与平台，**不确定**。所以：**先按 index 发完全部 `action`，
`gather`，再按 index 发完全部 `observation`**。

⇒ 并发批次的事件形状是 `action, action, observation, observation`（**分组**），
而不是串行路径的 `action, observation, action, observation`（**交替**）。

前端**本来就能处理**：`chat-tools.js` 按 `auditId` 配对卡片，注释里逐字写着
「优先按 auditId 配对（**同轮可以并发多次调用**）」，并且有一条"乱序/重放"的兜底分支。

（这一条是动手**之前**核实的第一件事 —— 如果前端是按顺序配对的，整个设计都要重新做。）

### 2.4 token 估算用 **API 自报的用量**校准，不用 tiktoken（**原 ADR-0024**）

#### D-1 用 API 自报的 `prompt_tokens` 校准估算，不引入 tiktoken

`harness/context.calibration_factor(pairs)` 从「(估算, 真实)」配对里算一个**系数**，
折叠判定按它缩放：

```
estimate = (estimate_messages_tokens(messages) + tools_tokens) * factor
超预算 ⇔ estimate > window_tokens * threshold
```

`factor` 缺省 **1.0** ⇒ **没有样本时行为与从前逐字相同**，
不接线的调用方不需要知道这个参数存在。

#### D-2 用**中位数**，不是平均值

校准系数是**要拿去乘一个阈值**的。一次异常样本（服务端截断、某条 span 写坏）
会把平均值拽走 —— 而那等于**那一轮悄悄换了折叠策略**。中位数对少量离群点稳定。

判据里刻意构造了「平均值与中位数分道扬镳」的输入
（8 个比值 1.2 ＋ 1 个比值 10 ⇒ 平均值 ≈2.18 被夹住，中位数 1.2）。

#### D-3 三道闸门，全部朝向"宁可不校准"

| 闸门 | 阈值 | 为什么 |
|---|---|---|
| 样本数不足 ⇒ 1.0 | `< 5` | 两三个样本算出来的系数**比不校准更坏**，而"我按数据校准过"这个说法让人更不敢质疑它 |
| 夹住范围 | `[0.5, 2.0]` | 防止一串坏样本把阈值放大数倍 ⇒ 请求**真的**超窗 |
| 丢掉非正配对 | `估算 ≤ 0` 或 `真实 ≤ 0` | `prompt_tokens = 0`（回放夹具就是这样）**不是**"0 个 token"，是**没有这个数据** |

#### D-4 一次运行算一次，且**必须留痕**

- **一次运行一次**（不是每次模型调用）：它读库，而且**同一轮里不该变** ——
  一轮之内换折算系数会让"这一轮到底按哪个阈值折"变得说不清。
- 系数 ≠ 1.0 时写一条 `logger.info`（带原因字符串）。
  ★ **这是承重的**：不留痕的话，"这一轮的折叠阈值被悄悄改过"没有任何痕迹
  （与铁律 28 同一条推理）。
- 读样本失败**一律回落 1.0**：**校准是优化，不是前提** —— 它坏掉不该让对话跑不起来。

#### 本期做与不做（原 ADR-0024 §3）

**做**：

- `calibration_factor(pairs)` 纯函数（中位数 / 闸门 / 夹范围 / 非正丢弃）
- `trace.recent_token_pairs(limit)` —— 从 `agent_span` 读配对，跳过数据不全的
- `_over_budget` / `plan_prefix` 各多一个缺省 `factor=1.0`
- `run_agent_loop` 开头读一次、写日志、透传
- `tests/test_token_calibration.py`（**12 条**，含一条端到端与一条"系数真的改变了判定"）

**不做（明确）**：

- ~~引入 `tiktoken`~~ —— 见 §1.4：它数的是**别人的**分词器
- ~~把系数做成**每次调用**都重算~~ —— 一轮之内不该变（D-4）
- ~~拿系数去改 `_over_hard_limit`~~ —— 那个函数的文档串写着「宁可漏判也不要误判」，
  而**校准是让估得更准**，不是让它更激进。★ 那是**已决策**，改它要另开一篇 ADR
- ~~把偏差表接成自动告警~~ —— 那是可观测性的另一件事，本轮不做

#### 后果（原 ADR-0024 §4）

**好处**：

- 折叠判定按**真值**校准过，而不是按一个"看起来精确"的近似
- **零新依赖、零联网、零下载**；样本从已有的 span 表里读
- 样本不足 / 读库失败 / 全是坏样本 —— **三种情况都回落到与从前逐字相同的行为**

**代价**：

- 校准的**精度受样本量限制**：冷启动（前 5 次模型调用）不校准
- 它读一次库（每次运行一次，可忽略）
- ★ **校准是滞后的**：它用**过去**的样本校准**现在**的请求。
  对话内容分布突变时（比如突然贴进来一份长文档），系数会慢一拍

**风险**：

- ★ **一条坏样本不会毁掉结果，一串坏样本会** —— 中位数与夹范围各自挡一层，
  但两者都挡不住"最近 60 条样本整体偏了"。⇒ 触发器里写了样本数下限的复查。

## 5. 诚实边界

> ★★ **这一节是本文的核心。** 五篇原 ADR 各自写下的"做不到什么"**逐条保留、一句未软化**。

### 5.1 上下文治理这一层做不到什么（**原 ADR-0019** §5 原文）

- **D-2 的估算偏低**，所以"没触发硬上限"**不等于**"这次请求一定不超窗"。
  它是限损，不是保证。真正的保证要等精确 token 计数（计划 §7.1）。
- **硬上限只在"每次模型调用前"检查**，不在请求**发出时**检查 ——
  两次检查之间如果有别的写入路径，仍可能超。当前只有工具结果会写，已覆盖。
- **I16 的回填让历史"合法"，但不让历史"完整"**：被回填的调用正文是
  `[未执行] <原因>`，模型看到的是"这件事没做"，而不是"这件事做了什么"。
  不要把它读成"任务被保存下来了"。
- **D-1 保证的是 system 恒在 `messages[0]` 且是原文**；它**不保证** system 内容本身
  不随版本变化 —— 系统提示词一改，整个前缀缓存照样全 miss（那是 I1 的领域）。

### 5.2 运行记录与 OTel 做不到什么（**原 ADR-0021** §5 原文）

1. **本决策不保证"时间线完整"**：消费方在流中途断开时，`_SpanClient` 会记一条
   `status="aborted"` 的模型 span，但**工具批次里正在执行的那一步**不会被补记。
   完整的中断语义要等可中止 stop。
2. ★ **OTel 属性名没有逐条核实**。写这份映射时（2026-09-24）网络不可达
   （`github.com` / `raw.githubusercontent.com` 均 DNS 失败）。本仓此前也明记着
   这条边界（`CORE-ARCHITECTURE.md` §7.5："具体属性名未逐条核"）。
   **处置**：把映射集中成一张表（`export_otel.OTEL_ATTRS`），每条带核实状态，
   `--list-attributes` 打出来逐条核 —— 于是"未核实"从一句空泛提醒变成
   **一条可执行的检查**。**不要**因为"看起来对"就把 `verify` 改成 `ok`：
   那会让"这个属性名对不对"从**已知的未知**变成**未知的未知**。
3. **`duration_ms` 的口径不统一**：模型 span 是墙钟（含网络），工具 span 是
   `ToolInvocation.duration_ms`（不含用户等待）。这是**刻意的** ——
   把用户思考时间算进"工具慢"会让那个问题的答案完全失真；
   但它意味着**两条 span 的 `duration_ms` 不能直接相加**来解释总时长。

### 5.3 并发这一层做不到什么（**原 ADR-0023** §5 原文）

1. ★ **并发今天几乎不会触发。** 全仓只有一个工具标了 `parallel_safe`，
   而模型要一次发出 2–4 个 `get_current_time` 才会走到快路径。
   **这一节交付的是"机制 + 纪律"，不是"今天能省多少延迟"** ——
   谁想拿到收益，得去逐个核实工具并标上它。**这是刻意的**：
   宁可收益来得慢，也不要一次批量放行换来一堆"偶尔怪一下"。
2. ★ **对显式标了并发的批次，停止的粒度是"每批"而不是"每次调用"。**
   检查点②在串行路径上仍是每次调用前；标并发的批次在**派发之前**查一次。
   为什么可接受：那类批次**只含无副作用、且经核实的**调用，所以"少跑两个"省不下什么，
   也不会留下半完成状态。**凡可能改状态的批次一律走串行路径**，
   "每个动作要么完整发生、要么完全没发生"的保证**原样保留**。
3. **批大小超过 `PARALLEL_READ_MAX = 4` 时整批退回串行**（不切波）。
   切波要引入"波与波之间要不要重新查停止/预算"的额外语义，
   而那正是这条快路径最该保持简单的地方。放宽它的前置是回答那个问题。
4. **`gather` 在 `execute` 抛异常时不做特殊处理。** `execute` 按 I13 **从不抛**；
   万一它抛了，快路径把已经拿到的结果发完（不让做过的工作变成看不见的），最后再抛出。
   更复杂的补偿逻辑（取消其余、合成观测）**刻意没写** ——
   为一个"按设计不可能发生"的分支加复杂度，换来的是更难懂的失败路径。
5. **量化的收益没有测。** 今天只有一个工具能并发，测出来的数字没有代表性。
   触发条件：标的工具多到能构造出真实的多调用批次时再测。

### 5.4 token 校准做不到什么（**原 ADR-0024** §5 原文）

**★ 这个决策做到的**：让折叠判定按**该模型自己回报的 token 数**校准，
而不是按一个字面估算。

**★ 它做不到的**：

1. **它不是"精确计数"。** 计划 §7.1(b) 的标题是"精确"，而本决策给的是
   **更准的估算** —— 系数是从**历史**样本推出来的，对**当前**这一条请求
   仍然可能偏。★ **不要把这里说成"精确计数了"**。
2. **它校准的是"总量"，不是"每一段"。** 一个系数同时作用在 `messages` 与
   `tools_tokens` 上。若真实的偏差主要来自其中一段（比如中文正文比英文更费 token，
   而 schema 是英文的），单一系数就是**两段共用一把尺**。
3. **它依赖 `estimatedTokens` 与 `usage` 同时存在。** 回放夹具（`prompt_tokens = 0`）
   贡献不了样本；`tests/eval` 产生的 `eval-*` 会话同理。
   ⇒ **样本要靠真实对话积累**，这决定了它上线初期基本不起作用。
4. **它没有消除"估算器本身的偏差"。** 若 `estimate_tokens` 对某类内容系统性低估，
   校准只是在总量上补一个常数倍 —— 换个内容分布就又要重新学。

### 5.5 hub 搬迁做不到什么（**原 ADR-0025** §5 原文）

- ★ **这个决策做到的**：`plugin_api` 对宿主的依赖**清零**，"插件整体拆除而不碰宿主"这句话
  现在有机器守卫撑着。
- ★ **它做不到的**：

1. **`plugin_api` 里仍有两处宿主导入**（`logging_setup` / `approvals`，都是局部导入）。
   ⇒ **不要从这里读出"`plugin_api` 已经与宿主解耦"** —— 它只是**不再 import 插件**。
2. **修好的 `_imports()` 只覆盖"静态可解析"的导入。** `importlib.import_module("workbench.plugins")`
   这类**字符串导入**它看不到。★ 全仓今天没有这种写法，但**没有守卫**。
3. **`hub.py` 自身不在任何"依赖方向"判据的覆盖里** —— 那三条判据分别管
   `plugins/`、`services/`、`harness/`、`plugin_api.py`。`hub.py` 是新的，
   它**允许**依赖宿主（那正是它的职责），但这条"允许"**没有被写进任何判据**。

### 5.6 三条边界的共同形态（本次合并时归拢，**不新增结论**）

| 面 | 它做到的 | 它**不**做到的 |
|---|---|---|
| 上下文治理（§2.1） | 历史合法 / 系统提示词不被折叠 / 预算逐调用复检 | **估算偏低** ⇒ "没触发"≠"不会超窗"；回填 ≠ 完整 |
| 运行记录（§2.2） | 失败有载体 / 慢可查询 / 跨步因果可表达 | **时间线不完整**；**OTel 属性名未核实**；两种 `duration_ms` 不可相加 |
| 并发（§2.3） | 机制 + 纪律就位 | **今天几乎不触发**；标的批次停止粒度退到"每批" |
| token 校准（§2.4） | 按模型自报真值校准 | **不是精确计数**；只校准总量；上线初期不起作用 |
| hub 搬迁（§2.5） | I4 真的成立 | `plugin_api` **仍有两处宿主导入**；`hub.py` 自己**不在任何判据覆盖里** |

> **"全绿"与"判据瞎了"在输出上长得一模一样** —— 这是本篇五个面的共同教训
> （§1.5 那句原话）。读到任何一条"已实现"，都该顺手问一句"**它的反证是什么**"。

### 6.1 上下文治理（**原 ADR-0019** §6 原文）

| 参照对象 | 它的做法 | 与本决策的关系 | 我们的理由 |
|---|---|---|---|
| [DeepSeek 上下文硬盘缓存](https://api-docs.deepseek.com/zh-cn/guides/kv_cache) | 前缀缓存要求**完整匹配一个缓存前缀单元** | 一致 | 缺陷① 正是"前缀的第一个字节被换掉"⇒ 每轮全 miss（成本 ×50）。我们跟随 |
| [DeepSeek 模型 & 价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing) | `deepseek-flash` 上下文 **1M**、输出上限 384K | 参考 | 硬上限的默认值取自这里（按 2²⁰ 读作 1,048,576，判据见 `harness/types.py` 的字段文档串） |
| LangChain `ConversationSummaryBufferMemory` 一类的摘要记忆 | 摘要**只覆盖对话历史**，system 单独持有 | 一致 | 我们跟随。这是行业默认形状，不必自己发明 |
| 各家的 "context window management" 实践（按窗口占用百分比触发压缩） | 用**比例阈值**触发压缩，而不是绝对上限 | **分歧** | 我们**两个都要**：比例阈值决定"该折叠了"，绝对上限决定"不许再发"。只有比例阈值时，"折叠救不回来"的情形没有任何出口 |
| MCP 规范中关于"列表结果需可缓存、顺序需确定以保持上游 prompt cache 稳定"的要求 | 把"前缀稳定"当作**协议级**要求 | 一致 | 我们的 I1/I2 与它同向；缺陷① 属于同一类错误（改动已发出的前缀） |

**由本次对照得出的结论**：

- **可以简化的**：摘要记忆的形状（system 独立于摘要）行业已统一，直接跟随，不必论证。
- **必须自己定的**：**"折叠救不回来"时的处置**。行业普遍只谈"压缩"，不谈"压缩失败怎么办" ——
  而我们的实测探针证明"单条工具结果 > 窗口"是真实可达的（12k 字符的网页正文）。
  这一条取决于我们的语境（工具结果不可信、长度不可控），没有可抄的答案。
- **未核实**：其他 Agent 框架是否也把"未执行的工具调用必须回填"当作硬契约。
  我们这条是从**平台 API 的硬要求**（`tool_call_id` 必须成对）反推出来的，不是抄来的。

### 6.2 Agent 运行记录 / OTel（**原 ADR-0021** §6 原文）

| 参照对象 | 它的做法 | 与本决策的关系 | 我们的理由 |
|---|---|---|---|
| [OpenTelemetry GenAI 语义约定](https://opentelemetry.io/docs/specs/semconv/gen-ai/) | 为 LLM/agent/tool 调用定义 `gen_ai.*` 属性与 span 结构 | **一致（方向）／未核实（细节）** | 方向采纳：span 分层、属性化、OTLP 输出。**具体属性名未逐条核** —— 见 §5.2 第 2 条。★ 这一栏刻意把"方向"与"细节"分开写：前者可信，后者**此刻不可信** |
| [OTLP/JSON 协议](https://opentelemetry.io/docs/specs/otlp/) | 公开的 wire format：`resourceSpans` → `scopeSpans` → `spans`，纳秒时间戳为**字符串**，属性值显式标注类型 | 一致 | 直接跟随。判据落在**形状**上（`test_otel_export_produces_a_structurally_valid_payload`），因为形状错了通用工具就读不进去 |
| 本仓既有的 `agent_audit` / `sandbox_run` / `skill_audit` | 自建审计表，可 SQL 查询、零依赖 | **分歧（部分）** | 我们**保留**它们并**额外**加一层导出，而不是改用 OTel SDK 做事实源。理由：审计有**合规含义**（一行 = 一次有副作用的操作），而这个语义 OTel 的 span 模型不承载 |
| Langfuse / Phoenix / LangSmith | 各自有导入格式，也各自宣称支持 OTLP | **分歧** | 只做 OTLP。它们的**导入格式我没核实过**，不凭印象造第二份 schema —— 那会是一条没人敢质疑的假共识 |

**由本次对照得出的结论**：

- **可以简化的**：span 的分层（agent → model / tool）与 OTLP 的输出形状 —— 行业已统一，直接采用，不必自己发明。
- **必须自己定的**：**"审计"与"轨迹"要不要分家**。行业（OTel）只有 span，
  而我们有合规驱动的审计表。本案的答案是"分家 + 导出层桥接"，
  这个取舍取决于**我们的合规语境**，没有可抄的答案。
- **未核实**：`gen_ai.*` 的**具体属性名**（11 个，全部标着 `verify`）。
  这是本 ADR 最重要的一条待办，而它现在**有一条命令可以推进**。

### 6.3 并发（**原 ADR-0023** §6 原文）

| 参照对象 | 它的做法 | 与本决策的关系 | 我们的理由 |
|---|---|---|---|
| OpenAI 的 parallel function calling | 模型一次返回多个 `tool_calls`，**由调用方决定**并发还是串行；官方文档只讲"怎么发多个"，不讲调度 | **方向一致** | 我们采纳"模型一次发多个、由我们决定怎么跑"；**调度策略自己做**：它们没有"只读/有副作用"的分层，而我们有 `Risk` —— 那是本仓自己长出来的、恰好能用在这里的东西 |
| Anthropic 的 tool use | 同样支持一次多个 `tool_use`，并建议**读类**工具可并发 | **口径与计划原文接近** | ★ **没有采纳它的粗口径**：它的上下文是"工具由你（开发者）自己写、你知道它们会不会打架"；而本仓有**用户装的 Skill**（第三方代码），"它看起来是 read" 不足以证明它并发安全。这正是 `parallel_safe` 要显式举证的原因 |
| 本仓铁律 23（`browser_pool` 单线程队列） | 浏览器操作**必须**串行过一条队列 | ★ **正是本决策的依据之一** | 它说明"只读但会碰同一份状态"在本仓**不是一个假设，而是一个已经存在的事实**（Playwright sync API 就是这么要求的）。所以"只读 ⇒ 可并发"在本仓**从前提上**就不成立 |
| 计划 §7.4 原文 | 「只并发整批都是 `Risk.READ` 且都不需确认的调用」 | **收窄** | 按它实现会让 §5.6 的两条判据 + 一条评测用例变红。见 §1.3 |

**由本次对照得出的结论**：

- **可以照抄的**：模型一次发多个调用、我们把它们并发跑、事件按 index 回填 —— 这三件事各家一致。
- **必须自己定的**：★ **"哪些工具能并发"没有可抄的答案。** 别家的工具都是自己写的，
  而我们有一个**第三方代码入口**（Skill）。那意味着"安全"不能由**代码分类**（只读/写）推出，
  只能由**逐个举证**得到。这条差异只在本仓成立。
- **未核实**：各家在**并发 + 用户中断**同时发生时怎么处理（取消已派发的调用？等它们跑完？），
  我没有读到明确说法。我们选了"等它们跑完"（§5.3 第 2 条），理由写在上面 —— 但那是我们的取舍，
  不是抄来的。

### 6.4 token 校准（**原 ADR-0024** §6 原文）

| 参照对象 | 它的做法 | 与本决策的关系 | 我们的理由 |
|---|---|---|---|
| [OpenAI `tiktoken`](https://github.com/openai/tiktoken) | 提供 `cl100k_base` / `o200k_base` 等 BPE；**是 OpenAI 模型的分词器** | **分歧**（本决策**不采用**） | 它数的不是我们模型的 token。用它计数等于把"另一个模型的词表"当真值 —— **看起来精确，实际是另一种近似**，还多一个联网依赖 |
| [Anthropic token counting API](https://docs.anthropic.com/en/docs/build-with-claude/token-counting) | 提供**独立的**计数端点（服务端按**自己**的分词器数） | 参考 | ★ 它印证了正确的方向：**计数要用服务提供方自己的口径**。我们没有那个端点，但**每次响应的 `usage` 就是同一个口径的真值** |
| [OpenTelemetry GenAI 语义约定](https://opentelemetry.io/docs/specs/semconv/gen-ai/) | `gen_ai.usage.input_tokens` / `output_tokens` 是标准属性；语义约定**建议**用提供方回报的用量，而不是客户端估算 | **一致**（我们跟随） | 本仓的 span 已经按这套约定记 `gen_ai.*`，估算与真值成对落在同一条上正好顺这条路 |
| [DeepSeek API 文档](https://api-docs.deepseek.com/) —— `usage.prompt_tokens` / `prompt_cache_hit_tokens` | 每次响应回报用量，且**区分命中与未命中** | **一致** | 我们已经在用它的缓存字段算成本（价差 50×）；同一个对象里的 `prompt_tokens` 拿来校准是顺手的 |
| 各家 agent 框架的"上下文预算"实现（LangChain `get_num_tokens` 等） | 多数走**客户端分词器**，并附一句"可能不精确" | **分歧** | 那句话正是问题所在：一个**已知不准**的数被当成预算依据，而**服务端每次都在回报真值** |
| 控制论里的**闭环校准**（用观测量修正模型参数） | —— | 参考 | 本决策的形状就是它：估算器是模型，`prompt_tokens` 是观测，系数是那一个待修参数。**刻意只留一个自由度**（一个标量），因为样本少 |

**由本次对照得出的结论**：

- ★ **可以简化的**：不需要自己实现或引入分词器 —— 行业里"用提供方口径计数"这条路
  有 Anthropic 的计数端点作先例，而我们连端点都不需要（`usage` 里就有）。
- ★ **必须自己定的**：**用哪种统计量**（中位数而非平均值）、**闸门多严**
  （5 个样本 / `[0.5, 2.0]`）、**多久算一次**（一次运行一次）。
  这三条行业里没有共识，取决于我们的样本量与成本结构 —— 所以它们写进了本 ADR，
  且各自有判据。

### 6.5 hub 装配器（**原 ADR-0025** §6 原文）

| 参照对象 | 它的做法 | 与本决策的关系 | 我们的理由 |
|---|---|---|---|
| 依赖倒置（[Martin, DIP](https://en.wikipedia.org/wiki/Dependency_inversion_principle)） | 高层与低层都依赖抽象；**装配**由第三方（composition root）负责 | **一致**（我们跟随） | `plugin_api` ＝ 抽象侧；`hub.py` ＝ composition root。★ 我们此前把 composition root 放进了抽象侧，那是 DIP 的教科书反例 |
| [Cosmic Python](https://www.cosmicpython.com/book/chapter_13_dependency_injection.html) 的 "composition root" 一节 | 明确要求装配**只在入口处发生一次**，业务代码不自己 new 依赖 | **一致** | `hub.get_hub()` 就是那个唯一入口；它的文档串写着"进程级工具中枢（唯一装配点）" |
| Python 的循环导入惯例 | 常见处置是**函数内局部 import**（我们原先就是） | **分歧** | ★ 局部 import 能解**循环**，但**解不了方向** —— 它把一条架构违规变成一行看不见的代码。**能 import 成功 ≠ 方向对** |
| `pytest` 的 `monkeypatch` 与全局单例 | 官方建议避免模块级可变全局 | 参考 | 16 个测试文件在打桩 `_hub`。★ 这暴露的是**单例本身**的味道，不是搬迁造成的 —— 搬迁只是把桩点换了个模块 |

**由本次对照得出的结论**：

- ★ **可以简化的**：composition root 的位置行业里没有争议 —— 放宿主侧、放一个**不认识业务**
  的模块。不需要自己发明。
- ★ **必须自己定的**：**它住哪个文件**（D-3 那一段：三条判据各禁一部分，交集很窄），
  以及**要不要留兼容再导出**（D-2：不留，因为那是违规最容易复活的方式）。

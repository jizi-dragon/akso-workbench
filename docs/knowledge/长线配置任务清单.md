# 长线配置任务清单（8 步 · 可复用执行手册）

> 用途：验证 akso-workbench「长线配置」能力时反复用同一套流程。
> 用法：把文末「§0 直接粘贴的指令」发给 agent；agent 按本手册 §1–§9 执行。
> 版本依据：`0.2.26`（2026-11-27 实测：设备维修申请、设备巡检两轮，均一次跑通到发布）。

---

## §1 任务边界

必须完成的 8 步，缺一不算完成：

| # | 步骤 | 判据（必须能回读出来） |
|---|---|---|
| 1 | 创建对象 | `query.object.get` 有 id，`enableLifeCycle`、`enableSignatures` 均为 true |
| 2 | 创建字段 | 至少一个**选项类型**（`dataType: 4` + 选项集）、一个**对象类型**（`dataType: 15` + 被关联对象）；其余用文本 `dataType: 1`；全部非必填 |
| 3 | 调整表单布局 | `layout.detail` 回读到新分区与控件，控件 `fieldId`/`sectionId` 都对得上，关联控件 `attrs` 三项齐 |
| 4 | 调整列表布局 | `listlayout.columns.get` 里字段列齐全，且 `status_id__sys` 仍在 |
| 5 | 调整生命周期 | 状态按流转顺序排出（`lifecycle.status.sort` 后回读顺序一致），首尾是「开启/关闭」改名的状态 |
| 6 | 生成审批工作流 | `workflow.get` 的 `status = 20`，`workflow.steps.list` 首尾闭合，判断分支两边都落到动作 |
| 7 | 挂用户动作 | `lifecycle.useraction.list` 能看到按钮，`behaviorTypes: [7]`、`workflowId` = workflowBasicId |
| 8 | 业务菜单 | `menu.list` 按 code 找到母/子菜单，子菜单 `objectId`/`layoutId`/`listLayoutId` 三个 id 都非空 |

## §2 环境与前置

- 写入账号只来自底部账号条（`akso_workbench_accounts`，`section` 只传 `accounts`；传 `all`/`sites` 会报 `value is not lossless JSON`）。
- 环境固定 `standard-val`（`https://standard-val.aksoegmp.com`），账号 `liyulong`。
- 审批：`config_plan` → `config_apply({prepareOnly: true})` 出审核文档 → 把摘要+链接发给用户 → `config_apply({reviewPath})` 弹窗。**整条任务只弹一次窗**。
- 只读计划（`writes = 0`）不弹窗、可直接 `config_apply` 执行，用来当查询用。

## §3 命名与编码约束

- 自定义元数据一律 `__c` 后缀：对象 `xxx__c`、字段 `xxx__c`、菜单 `xxx__c`、流程 `xxx_approval_YYYYMMDD__c`。
- 布局 code 由平台生成：`<对象code 去掉 __c>_base_layout__ak`；列表布局 `<去掉 __c>_table__ak`。
- 动作按钮 code：`submit_xxx` / `resubmit_xxx`；工作流节点 code：`action_set_<状态>`、`task_xxx`、`decision_xxx`。
- 节点命名：任务 `【任务】：X`、判断 `【判断】：X`、动作 `【动作】：修改状态为‘X’`（“为”不能漏）；开始/结束保留平台默认名。

## §4 施工顺序（一次审批版：3 阶段一条任务）

> 一条任务 = 一个 `taskId` = 一次审批窗。阶段在执行时**现算**，所以阶段 2/3 能用阶段 1 刚建出来的 id。
> 跨阶段引用写法：`{"$ref": "stages.<阶段号>.steps.<步骤号>.after.<路径>"}`（阶段 1-based）。

### 阶段 1「对象与主数据」
1. `object.save` ×2：先建**被引用对象**（如设备台账 `asset_ledger__c`），再建**主对象**（如巡检记录 `inspection_record__c`）。两个都 `enableLifeCycle: true` + `enableSignatures: true`（缺一引擎直接拒）。
2. `picklist.save` ×N（每个选项字段一个选项集，code 与字段同名即可）。
3. `field.save` ×M：
   - 文本：`{"name":"巡检编号","code":"inspection_no__c","dataType":1}`
   - 选项：`{"name":"巡检类型","code":"inspection_type__c","dataType":4,"extras":{"picklist":"inspection_type__c"}}`
   - 对象：`{"name":"所属设备","code":"asset_ref__c","dataType":15,"extras":{"referenceObject":"asset_ledger__c","objectRelation":{"controlField":null}}}`
   - 一律不带 `isRequired: true`（必填在表单布局里控制）。
4. `kind: listLayout`：`{object: 主对象code, columns: [{fieldCode: 各字段}]}`（引擎自动解析 fieldId，并保留 `status_id__sys`）。
5. 菜单（同一阶段用 `$ref` 串，母→子）：
   - 先 `query.object.get` 拿主对象 objectId → `layout.list` 拿 layoutId → `listlayout.list` 拿 listLayoutId；
   - 母菜单 `menu.submit {menuActionType: 3, backgroundColor: "#366EF4"}`；
   - 子菜单 `menu.submit {menuActionType: 1, parentMenuId: {"$ref":"steps.sN.after.Id"}, objectId/layoutId/listLayoutId 全部 $ref, createType: 4}`。
6. `kind: lifecycle`：建 3 个中间态（待审批 / 已通过 / 已退回）。

### 阶段 2「表单布局」
1. `layout.list` 拿主对象 layoutId / code / objectTypeId。
2. `layout.detail` 拿现有 `sections`/`controls`/`pages`（**原样留作回传**，尤其 `workflow_time__cs` 这类 type 4 分区不能删）。
3. `query.field.get` ×N：每个要进表单的字段取一次（`{"objectCode","fieldCode"}`）→ 后面当 `fieldId`。
4. `layout.stable.ids`：把自己指定的**临时 uuid** 当键，换稳定 id；分区和每个控件都要换。
   - `componentIds: {"<临时uuid>": {objectId, layoutCode, componentType: "layout_section"|"layout_control", componentCode}}`
   - 之后 `{"$ref":"steps.sN.after.stableComponentIds.<临时uuid>"}` 就是稳定 id。
5. `layout.save` 整份回写：旧分区原样 + 新分区**追加在数组末尾**（`sort` = 现有最大 + 1）；新控件 `{id, sectionId, code, name, fieldId, type, gridSpan, attrs}`；`pages` 用 detail 原值；`rules: []`。
   - 关联控件 `attrs` 必须三项齐：`objectId`、`listLayoutId`（**被关联对象**的列表布局）、`createRecordMode: "3"`。

### 阶段 3「生命周期顺序 + 审批流 + 挂载」
1. `lifecycle.status.update` ×2：把「开启」改成首状态、把「关闭」改成末状态（**提交的 `sort` 必须等于平台现值**，否则预检直接拦）。
2. `lifecycle.status.sort`：带全部状态、`sort` 从 0 连续（顺序 = 期望流转顺序）。
3. 审批流（同一阶段内 `steps.<id>.after.step.id` 串联）：
   `workflow.create`（`status: 10`、`isAllowTrigger: false`）→ `workflow.steps.list` → 两个 `workflow.action.add`（已通过/已退回，`nextStepId` 指结束节点）→ `workflow.decision.add`（`rules: []`，`nextStepId` = 已退回动作）→ `workflow.task.add`（`nextStepId` = 判断；审批按钮两个都 `isHaveSign/isRequireSign: true`，同意 `isRequiredResons: false`、拒绝 `true`；`stepTaskConfig.userControlIds` 指向开始节点参与者控件 id）→ `workflow.decision.update`（规则 `targetId` = 任务、`logicValue` = `"\"<同意按钮id>\""`，`stepDecision.nextStepId` = 已退回动作）→ `workflow.action.add`（待审批，`nextStepId` = 任务）→ `workflow.start.update`（参与者 = `created_by__sys` `selectUserType: 40` + `ctrlType: 60` 电子签名控件；`nextStepId` = 待审批动作）→ `workflow.status.change`（`status: 20`）。
   - **`task.add` 之后不要补 `workflow.task.update`**：平台在 add 时已填好 `stepTaskConfig.workflowConfigId/stepId`，再 update 要全量体，最小体重放 400。
4. `lifecycle.useraction.create` ×2：待提交状态「提交」、已退回状态「重新提交」，`belongType: 2`、`enableSignatures: true`、`actions[0].configs[0] = {behaviorType: 7, behaviorValue: {workflowId: workflowBasicId, isBeforeWorkflowCompleteReminderTask: true}}`。

## §5 已知平台限制（不要试图硬修）

| 现象 | 结论 |
|---|---|
| `lifecycle.status.update` 提交 `sort` | 平台不落库；要改顺序只能用 `lifecycle.status.sort`（裸数组 `[{id,sort}]`，0 起连续、必须带全部状态）。预检会拦 |
| 列表里 `status_id__sys` 与第一列 `sort` 都是 1 | 平台默认行为，外观问题，不必修 |
| 建对象每个约 14 s | 平台侧固定开销，串行即可 |
| `query.picklist.get` 查不存在的 code | 返回 HTTP 500 `Object reference not set to an instance of an object.`，按「查不到」处理，不是 `data: null` |
| `*.add` 写成功但紧接着回读 `steps.list` 报 HTTP 400 | 瞬时；只读回读已内置 300 ms 重试一次。**写成功就不要再重放 add** |
| 布局控件看起来「列表布局/创建记录方式为空」 | 抓包核对过：保存体里三项都在（2026-11-27 现场反馈，记为可能发生）；先抓包比对，不要急着重写布局 |
| 预览/分析报告说「工作流 0 条」 | 状态按钮拉起的流程不回写 `lifecycleStatusIds`；已修（`analysis-workflow.ts` 会合并按钮绑定） |

## §6 每步回读（不可省）

- 每步写入**立刻**回读；不符先就地修一次，仍不符就停在该步，后面的包不发。
- 只读回读走 `invokeReadCapability`（400/408/409/425/429/5xx 与网络抖动等 300 ms 重试一次）；**写入路径绝不重试**。
- 预检硬拦（出计划就报错）：`WORKFLOW_DUPLICATE`、`USER_ACTION_DUPLICATE`、`TASK_SIGNATURE_MISSING`、`STATUS_SORT_NOT_PERSISTED`、`USER_ACTION_ID_IS_ACTION_ID`、`LAYOUT_FIELD_UNKNOWN`、`LAYOUT_SECTION_UNKNOWN`、`LAYOUT_OBJECT_CONTROL_ATTRS_MISSING`、`LAYOUT_OBJECT_CONTROL_LAYOUT_UNKNOWN`。

## §7 收尾（缺一不算交付）

1. `akso_workbench_config_verify({taskId})` → 报告写到 `akso-workbench-data/verifications/`。
2. 再跑一个**只读终验计划**（不弹窗）：`layout.detail` / `listlayout.columns.get` / `query.lifecycle.status.config.list` / `workflow.steps.list` / `lifecycle.useraction.list` / `menu.list`，逐项对照 §1 的判据。
3. `akso_workbench_object_analysis`（主对象）→ 确认报告里 `workflows` 有这条流程、`statuses` 数量对、`userActions` 两个。
4. 给用户一张表：8 步 × 判据 × 证据（id / 回读值），外加「已知限制」清单。

## §8 交付物位置

- 审核文档：`<工作区>/akso-workbench-data/reviews/`
- 计划/任务：`config-plans/`、`config-tasks/`（`results[].after` 就是每步响应 `data`）
- 验证报告：`verifications/`
- 对象分析：`analysis/<对象名>-<时间戳>/`（md + drawio + png）

> 读大 payload 的坑：不要 `console.log` 整个 `results[].after`（菜单 1000+ 条会刷爆输出）；用 node 脚本在 plan 文件上做过滤。
> PowerShell 的 `ConvertFrom-Json` 遇到 `language`/`Language` 这类仅大小写不同的键会报错，解析 JSON 用 node。

## §9 本次实例参考（可换成别的业务）

## §10 需求词 → 配置决策对照表

用户只说业务语言，不写接口。下表是「听到什么词 → 落成什么配置」的固定判断，**不要每次自定义**。

### §10.1 字段类型只有三条路

| 用户说 | 落成 | 说明 |
|---|---|---|
| 编号、单号、名称、数量、金额、日期、结论、描述、备注 | **文本** `dataType: 1` | 项目规则：一律文本；长文本 17 / 富文本 18 已禁用。数量/金额也不做数字类型 |
| 类别、类型、状态性质、等级、方式（带括号枚举，或「A/B/C」） | **选项集 + 选项字段** `dataType: 4` + `extras.picklist` | 选项顺序按用户括号里的顺序；选项集 code 与字段同名 |
| 「取自 X」「关联 X」「引用 X 的记录」 | **对象字段** `dataType: 15` + `extras.referenceObject`（`objectRelation.controlField: null`） | X 必须是**已存在的对象**；先 `query.object.get` 拿它的 id，再 `listlayout.list` 拿它的列表布局给布局控件用 |
| 是否、启用/禁用 | 优先**选项集**（是/否）；用户明确要勾选框时再议 | 不新造布尔类型 |

**必填**：字段建时一律 `isRequired: false`，必填只在表单布局里控制。

**待实测（遇到先问，不要猜）**：人员/用户、部门/组织、附件、多选、子表。这四类的 `dataType` 还没实测过；现行做法是——审批人先用系统字段 `created_by__sys`（已验证），部门先用对象字段指向组织对象，附件/多选遇到就说明"这轮先不做，下一轮补实测"。

### §10.2 生命周期词

| 用户说 | 落成 |
|---|---|
| 「待提交 → 待评审 → 通过 → 完成」「A→B→C」 | 首尾复用平台自带的「开启/关闭」两个状态改名；中间态 `lifecycle.status.create` |
| 「被拒后回到 X」「可以退回」 | 多一个「已退回」状态 + 该状态上的「重新提交」按钮；工作流判断的 else 分支落到它 |
| 「作废/关闭/终止」 | 再建一个终止态，**排在排序末尾**；不重命名「已完成」 |
| 用户没说状态顺序 | 按业务叙述的先后排，`lifecycle.status.sort` 用 **0 起连续**顺序，最后回读顺序一致 |

### §10.3 工作流词

| 用户说 | 落成 |
|---|---|
| 「提交后由 X 审批」 | 审批流：开始 →【动作】改状态为「待X」→【任务】→【判断】→ 同意【动作】/拒绝【动作】→ 结束 |
| 「审批人取自『质量负责人』字段」 | 参与者只能用**字段取人**（`selectUserType: 40`）或**审批矩阵**（`50`）；字段取人要求该字段是人员类型，若不是就先问用户「改成审批矩阵，还是先按创建人审批」 |
| 「两级审批」「先主管后经理」 | 任务节点串两个（每级一个任务节点），不要塞进同一个任务的多人审批 |
| 「超过 N 天自动提醒」 | 提醒流（`isNotifyTaskType`）+ 进入动作 + `isAllowTrigger: true`（开启后**不可逆**，必须先跟用户确认） |
| 用户没说拒绝后去哪 | 默认落到「已退回」，并在汇报里标注这是默认值 |

### §10.4 布局与菜单词

| 用户说 | 落成 |
|---|---|
| 「表单上分块」「基本信息/处理信息」 | 每个块一个分区（`type: 1`、`columnsNum: 2`），**追加在原分区之后**；「工作流时间线」分区原样保留 |
| 「这个字段要整行」 | `gridSpan: 2`（或按 `columnsNum` 取满） |
| 用户没说布局 | 一个「基本信息」分区 + 全部字段按 §10.1 顺序、除「描述/结论」整行外都是 `gridSpan: 1` |
| 「挂在 X 菜单下」 | 母菜单 `menuActionType: 3`（X 不在就建），子菜单 `menuActionType: 1` + `createType: 4` + 三个绑定 id |
| 用户没说列表要哪些列 | 全部业务字段都进列表，`status_id__sys` 必须保留 |

### §10.5 命名自动规则（不问用户）

- 对象 `xxx__c`（业务名直译拼音/英文，如 `nonconforming_disposal__c`）
- 字段 `xxx__c`；选项集与字段同名；对象字段加 `_ref__c` 后缀
- 布局/列表布局 code 由平台生成，不自己造
- 流程 `xxx_approval_YYYYMMDD__c`，名称 `X审批流（YYYY-MM-DD）`
- 按钮 `submit_xxx` / `resubmit_xxx`；节点 code `action_set_<状态>` / `task_xxx` / `decision_xxx`

## §11 澄清协议（最多一轮，一次问全）

原则：**能默认的不问，不能猜的才问，且只问一轮。**

### §11.1 必问项（需求里没写就必须问，不能猜）

1. **审批人从哪来**：字段取人（哪个字段）/ 审批矩阵（哪张矩阵）/ 先用创建人。猜错整条流程没人能审。
2. **退回后回到哪个状态**：「已退回」是新状态还是回到「待提交」。
3. **有没有终止态**：作废/关闭/取消，以及从哪些状态可以进。
4. **菜单挂在哪一级**：现有母菜单名，或新建一个。
5. **哪些字段必填**（表单布局里控）；用户不说就全部非必填并标注。

### §11.2 可默认项（不问，直接定，汇报时标「默认」）

状态顺序、字段类型（按 §10.1）、布局分区与跨度、列表列、按钮命名、所有 code、选项集顺序。

### §11.3 提问格式

- 一次把 3–5 条列完，每条给**默认值 + 影响一句话**，例如：
  > 「已退回」放流转顺序第几位？默认排在「评审通过」之后（即 待提交 → 待评审 → 评审通过 → 已退回 → 处置中 → 已完成），改的话告诉我顺序。
- 用户答「随便/你定/按默认」→ 直接用默认，不再追问。
- **审批一旦发起，不再补问第二轮**；只有预检报错（§6 的错误码）需要用户裁决时才提一次，且只提报错本身。

### §11.4 触发不可逆项时单独确认

`enableLifeCycle`（开生命周期）、流程发布、`isAllowTrigger: true`、改 code、停用对象/字段——这几件事在审核文档里**单独点名**，不要混在 checklist 里。

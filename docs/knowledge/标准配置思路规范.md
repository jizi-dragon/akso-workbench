# 标准配置思路规范

> 状态：v1.1，2026-11-10。相对 v1 的变化：补 §1.3 存量对照表、§3.3 审核稿规范、§4.1 规模判断表，
> 并删掉"错了就重来"的说法（改为"先判规模，选最小动作"）。
>
> 这份文档管**动手之前的思路**：一个业务对象要配成什么样（蓝图）、按什么顺序施工、
> 什么时候找人审核、配错了怎么收场。
>
> 它不教接口怎么调（→ `基础API使用指南.md`），不抄成文步骤（→ `标准配置使用规范.md`），
> 不重复平台硬约束与实测证据（→ `EGMP-CONFIG-BASICS.md`）。三者冲突时以实测为准，
> 并回来改这份文档。

## 0. 一句话与四条铁律

配置不是「把一列接口按顺序调一遍」，而是**先查存量、再交蓝图、一次审核、按序施工；出错先判规模，能局部修就绝不推倒重来**。

1. **一张蓝图一次审**：蓝图（对象 / 字段 / 两套布局 / 菜单 / 状态 / 工作流 / 挂载）整体给人看一遍；
   范围内的写入不再逐条问——施工分段是执行细节，不是重新审批的理由。审核稿写业务语言，不贴 JSON（§3.3）。
2. **顺序不跳步**：对象 → 字段 → 表单布局 → 列表布局 → 菜单 → 状态 → 工作流 → 挂载。
   后一步要前一步的 id，跳步只会返工。
3. **先查存量，再动手**：对象 code / 对象名 / 字段名 / 状态名 / 流程名 / 菜单名 / 按钮名，逐个查过再写进蓝图（§1.3）。
   撞名的代价往往不是一句报错，而是 `object.save` 按 code 改写别人的对象，或系统里留下两套同义资源。
4. **每步回读**：`code: 0` 不等于生效；平台会静默忽略（工作流回退草稿就是典型）。

事故复盘：错在字段或布局，停用 + 新建 + 换控件就够了；错在对象或生命周期，东西已经建进系统、删不掉，
推倒重来只会留一堆脏数据——**先判规模，再选最小动作**（§4.1）。

## 1. 先出蓝图，再碰接口

### 1.1 蓝图要回答的 8 个问题

动手前把这 8 个问题答全，缺一个就会在施工中途返工。

| # | 问题 | 答案落到哪 | 答不上来的后果 |
| --- | --- | --- | --- |
| 1 | 一条记录代表什么业务？ | 对象名、`code`、记录粒度 | code 定了就改不了，只能新建对象重挂一遍 |
| 2 | 要录哪些信息？ | 字段表（名称 / code / 类型 / 必填 / 选项集） | `dataType` 建完不可改，选错只能停用重建 |
| 3 | 打开表单先看什么、按什么分组？ | 表单布局：分区、控件、`gridSpan` | 布局控件是独立对象，字段改了布局不会自动跟着改 |
| 4 | 列表里要扫哪几列、怎么筛？ | 列表列、顺序、筛选 | `columns.set` 是整份替换，漏 `status_id__sys` 直接 500 |
| 5 | 业务怎么流转，谁在什么状态下做什么？ | 状态表：状态 / `sort` / 出口动作 | 状态不能删，建错只能停用，还会留下「同义重复」 |
| 6 | 谁来审、审几步、要不要提醒？ | 工作流表：审批流 / 提醒流 + 骨架 | 发布单向，20 回不到 10，配漏了只能新建一条 |
| 7 | 流程从哪触发、挂在哪个状态上？ | 挂载表：状态按钮 / 进入动作 | 按钮和进入动作引用 `workflowBasicId`，必须最后挂 |
| 8 | 用户从哪里点进来？ | 菜单：父级、`code`、对象 / 布局 / 列表 id | 菜单 `code` 必须 `__c`，且它是入口的身份证，改了就等于换一个入口 |

**第 8 个问题不是"顺手加个菜单"。** 一个对象没人点得进来，等于没配。

### 1.3 蓝图自检（过不了别拿去给人看）

**第一步是存量对照，不是自检格式。** 表 0 的「同 code 对象是否已存在」必须是一次真实调用的结果，不能凭记忆、
也不能等建完再看——所有有唯一性的名字（对象 / 字段 / 选项集 / 状态 / 流程 / 布局 / 菜单 / 动作）都先查一遍：

| 要建的东西 | 用什么查 | 查到同名 / 同 code 时怎么办 |
| --- | --- | --- |
| 对象（`code` / 中文名） | `query.object.get` | `object.save` 按 code **upsert**，会改写现有对象——先看清它挂了哪些字段、布局、流程、菜单 |
| 字段（名称 / `code`） | `query.fields.list` | 同名字段会让新建报「字段名称重复」；决定复用、改名停用、还是换个语义 |
| 选项集 | `query.picklist.get`（只能按 code 查，列不出全部） | 用候选 code 先查一次：有就拿它的 `objectPicklistId` 复用，没有才 `picklist.save` |
| 状态（名称 / `sort`） | `query.lifecycle.status.list` | 同义状态已存在就复用或「改名 + 停用」，不要再建第三个 |
| 流程（名称 / 骨架） | `workflow.page.list` | 同名先确认是不是同一条业务，别把提醒流和审批流混名 |
| 布局 / 列表 | `layout.list`、`listlayout.list` | 默认布局能改就改，不新建 |
| 菜单（入口名 / 分组） | `menu.group.list`（只看得到分组，看不到新建菜单） | 同名入口以控制台实际为准，查不到就在蓝图里注明「未确认」 |
| 状态按钮 / 进入动作 | `lifecycle.useraction.list`、`lifecycle.enteraction.list` | 同 `code` 动作已存在就复用，别叠第二个 |

查到的东西原样贴进蓝图（带 id 和"复用 / 改名 / 停用 / 新建"的结论），这张对照表就是后面 §4 判规模的事实依据。

- **每个字段有下落**：表 2 的「进表单 / 进列表」至少一个为「是」；两个都否的字段等于白建。
- **每个状态有出口**：除终态外，每个状态都要写清"谁把它推到哪"——按钮、进入动作、流程里的动作节点都算；
  一项都写不出来的状态，记录进去就卡死。
- **每条流程有触发点**：表 4 的每条流程都能在表 5 找到挂载；建了没人调的流程是废配置。
- **引用的 id 都先建**：挂载表的每条都指向表 4 里已存在的流程；菜单的三个 id 都在表 1/6 里。
- **没有重复造轮子**：系统自带字段（名称、创建人、创建时间、状态）、默认首尾状态、默认布局，
  能复用就复用，不要新建同义资源——平台不会帮你合并，只会留下两套。
- **code 一次定对**：对象 / 字段的 `code` 是 upsert 键，改了就是另一个资源；菜单 `code` 是入口的身份证。
  七张表里把 code 逐个核对拼写，比事后停用重建便宜一个数量级。
- **能被第三个人照着做**：把七张表交给另一个人，他不需要问你就能施工——这是蓝图的验收标准。

## 2. 施工顺序

### 2.1 八个阶段

**蓝图里资源的排列顺序，就是执行顺序。** 计划生成时按蓝图 `resources` 数组逐个生成步骤
（`plugin/src/config/engine.ts` 的 `for (const resource of input.resources)`），只自动补两类硬依赖
（字段依赖对象、列表列依赖字段），菜单与 `call` 不补；跨阶段的顺序没有任何兜底，全靠蓝图排序。

蓝图能直接表达的 kind：`picklist` / `object` / `field` / `lifecycle` / `listLayout` / `menu` / `call`。
`formLayout` 会被引擎直接拒绝（全量替换风险，提示改用 `call` + `layout.save`）；工作流与挂载也没有专用 kind，
一律写 `call`。而 `call` 的参数是静态的、引用不了前一步的返回值——所以凡是要用 `configId` /
`workflowBasicId` / `stepId` 的链路（工作流、挂载），天生要分段施工，每段一次审批。

| # | 阶段 | 主要能力 | 先读什么 | 记下什么 | 收工判据 |
| --- | --- | --- | --- | --- | --- |
| 1 | 对象 | `object.save` | `query.object.get`（按 code） | `objectId`、`lifeCycleId` | 回读 code / 中文名 / `enableLifeCycle: true` |
| 2 | 字段 | `picklist.save`（先）、`field.save` ×N | `query.fields.list` | 每个 `fieldId` | 每个字段 `status: 1`、`dataType` 与表 2 一致 |
| 3 | 表单布局 | `layout.list` → `layout.detail` → `layout.stable.ids` → `call` + `layout.save` | `layout.detail` 全量 | `layoutId` | 分区 / 控件数量 +N，`sectionId` 对得上，无 `belongId` |
| 4 | 列表布局 | 默认列表直接 `listlayout.columns.set`；要单独列表才 `listlayout.save` → `columns.set` → `filter.save` | `listlayout.list`、`listlayout.columns.get` | `listLayoutId` | 列顺序正确、含 `status_id__sys`、筛选 `relationId` 是 GUID |
| 5 | 菜单 | `menu.submit`（父 → 子） | —（`menu.group.list` 看不到新建菜单） | 四 id 回填 | 控制台能看到入口，点进去是这张表单 |
| 6 | 生命周期状态 | `lifecycle.status.update`（改名首尾）→ `create`（中间态）→ `update`（排 `sort`） | `query.lifecycle.status.list` | `statusId` ×N | 状态数与 `sort` 符合表 3，无同义重复 |
| 7 | 工作流 | `workflow.create` → `steps.list` → `task` / `decision` / `action` → `workflow.start.update` 接线 → 验完再 `status.change` | `workflow.get` | `configId`、`workflowBasicId` | 节点链完整不断、`status` 到 30（已发布） |
| 8 | 挂载 | `lifecycle.useraction.create`、`lifecycle.enteraction.create` | `lifecycle.useraction.list`、`lifecycle.enteraction.list` 查重 | 动作 id | 回读 `code` / `workflowId` / `belongType` 与表 5 一致 |

### 2.2 为什么是这个顺序

- **对象第一**：后面所有资源都挂 `objectId`；`code` 进了库就改不了。
- **字段第二**：布局、列表、流程字段都引用 `fieldId`；`dataType` 建完不可改，所以必须在这一步就定对。
- **布局第三**：字段刚建完，语义最清楚，一次排完；布局可以反复改，早排能早发现「字段不够 / 字段该拆」——
  此时改字段比流程配完再改便宜得多。
- **列表第四**：引用字段 id；`columns.set` 整份替换，必须一次给全。
- **菜单第五**：要同时给 `objectId` + `layoutId` + `listLayoutId`，前四步不齐就给不全。
- **状态第六**：状态只被按钮和工作流引用，布局 / 列表 / 菜单都不需要它；先建好状态，下一步才有得挂。
- **工作流第七**：引用对象 / 字段 / 状态；发布是单向的（20 回不到 10），必须等节点全配完再发。
- **挂载第八**：按钮和进入动作要填 `workflowBasicId`，而 `workflowBasicId` 在流程创建后才存在；
  绑到草稿流程上不会报错，但点了没反应——所以放在发布之后。

### 2.3 和 EGMP-CONFIG-BASICS §1 的顺序为什么不一样

那边写的是**依赖顺序**（谁引用谁），这边写的是**施工顺序**（一次把一类资源做完）。两处刻意调换：

| 资源 | 那边 | 这边 | 理由 |
| --- | --- | --- | --- |
| 表单布局 | 最后（"只能改，不能加"） | 字段之后 | 该结论已被推翻：`layout.save` 能加分区和控件（错在自造 `belongId`）。布局是软的、可反复改，早排早暴露字段问题 |
| 生命周期状态 | 列表 / 菜单之前 | 菜单之后 | 状态不被布局 / 列表 / 菜单引用；列表的状态列在 `enableLifeCycle` 时就由平台加好 |
| 状态按钮 | 状态之后 | 单独一段第 8 位 | 按钮要给 `workflowBasicId`，必须等流程发布；「进入动作」同理 |

两套顺序不冲突：**按施工顺序做，天然满足依赖顺序**。唯一要盯的是跨阶段引用——
任何一步只要用到前面阶段的 id，就必须等前面阶段回读通过，不能"先把请求发了再说"。

### 2.4 哪一步可以批量、哪一步不能并

- 同一阶段内的同类资源可以一个计划批量写：N 个字段、N 个状态、N 个菜单项。
- 不同阶段不要并行：后一阶段要前一阶段的返回值（`objectId` / `fieldId` / `layoutId` / `workflowBasicId`）。
- 唯一的前置特例：`dataType: 4`（单选）的字段要先 `picklist.save`，选项集排在该字段之前。
- 布局和列表都依赖字段，但彼此不依赖；如果字段已全部回读通过，这两步可以同批。

## 3. 一次审批，而不是一个接口一次

### 3.1 审批的真实粒度

- 一个计划（plan）= 一组有序步骤；**一次 apply = 一次弹窗 = 一张审批**。
- 审批绑定计划指纹 `planHash`，**一次性**：执行前就标记已用，中途失败不能拿同一张审批重试。
- 计划 **30 分钟**过期；弹窗 **8 分钟**无人处理判超时（超时 = 不写）；同一时间只挂**一条**审批。
- 结论：**审批次数 ≈ 计划个数**。计划切得碎，用户就被迫点很多次；所以计划粒度应当是**蓝图里能一次写完的一段**
  （对象 → 菜单通常可以合成一个计划），而不是「一两个接口」。
- 但别指望「一次审批写完全部」：`call` 的参数是静态的、引用不了上一步返回值，工作流要拿 `configId` / `stepId`
  接线、挂载要拿 `workflowBasicId`，这些必须分段。**分段可以，碎成单个接口不行**。

### 3.2 蓝图层审批的七步

1. **存量自检**（§1.3 的表）：`query.object.get` / `query.fields.list` / `query.lifecycle.status.list` /
   `workflow.page.list` / `lifecycle.useraction.list` 逐个查；结果连 id 一起贴进蓝图。
   查到同名资源时的动作是「复用 / 改名停用 / 新建」，不是"照建"。
2. **出蓝图**：填 §1.2 的七张表 + §1.3 的存量对照，含「本次不改的东西」。
3. **给人审蓝图**：按 §3.3 写审核稿——业务语言、一屏结论、待拍板项做成选择题；**不贴 JSON**，
   也不列 method / path / params。
4. **按回复改蓝图**：同意 → 下一步；补充 → 改表重贴；拒绝 → 停，不要偷偷改名再来。
5. **按蓝图分段、每段一个计划**：`resources` 按 §2.1 的顺序排。对象 / 字段 / 布局 / 列表 / 菜单 / 状态
   通常能合成一个计划；工作流与挂载按「创建流程 → 批量建节点 → 接线 → 发布 → 挂载」分段，
   每段一次审批，不要每加一个节点问一次。
6. **一次弹窗同意**，逐步骤执行、每步回读。弹窗展示的是「这一步要写什么」（method / path / params），
   不是设计图——所以设计评审必须发生在弹窗之前，弹窗只回答"这批写入能不能发"。
7. **交施工报告**：实际写入清单 + 回读结果 + 与蓝图的差异 + 遗留项（如需要控制台补的）。

### 3.3 审核稿：给人看的，不是给机器看的

审核稿是人**做设计判断**的唯一环节（审批弹窗只回答"这批写入能不能发"），所以它要回答
"这东西建出来是什么样、谁会怎么用"，而不是"要发哪些请求"。

- **不贴 JSON、不列参数**。JSON 是施工细节：用户审不了 `params` 拼写，也发现不了业务缺口，
  一屏 40 行参数只会让人闭眼点同意。请求体只出现在施工后的回读报告里；要给接口依据时，
  写「能力名 + 一句作用」就够（如 `workflow.task.add`：加审批任务节点）。
- **一屏看完全貌**：先一段结论（建几个对象 / 几条流程 / 动哪几处），再按业务分段。七张表是工作稿，
  给人看时压成「建什么 / 怎么流转 / 谁从哪里进来」三段；细节表要附就折叠，别当正文。
- **三态标出"这次到底动什么"**：新增 / 修改 / 不动（复用现有）。用户最怕的是"不知道你会不会顺手改别的"，
  所以「本次不改的东西」必须写在审核稿里，而不是只留在工作稿里。
- **不可逆点单独点名**：对象 `enableLifeCycle`、流程发布（10→30）、`isAllowTrigger`、任何改 `code` 的念头——
  放在「风险」一小段，不埋在表格里。
- **要拍板的做成选择题**：字段进不进列表、要不要「已撤回」状态、审批人从字段取还是固定、提醒走策略还是模板——
  每条给 2–3 个选项 + 推荐 + 影响，不要开放式发问，也不要在稿子里替用户决定。
- **存量对照带结论**：每个名字后面标「系统里没有 / 已有（id xxx，复用 or 改名停用）」，见 §1.3。
- 反例：把能力目录的 `example` 原样倒出来；只贴字段表就让人确认；审核稿里塞满参数，让人在「同意」里找业务。

审核稿骨架（照抄改字即可）：

```
【作业提交】新建 1 个对象、4 个字段、3 个状态、2 条流程、1 个菜单入口

- 谁在用：生产部班组长，从「教学管理 → 作业提交」进入
- 一条记录 = 一次作业提交（学员 × 作业）
- 字段：标题（必填，平台自带改名）、内容（必填，文本）、截止时间、附件
        列表显示：标题、截止时间、状态；表单两列，标题与内容通栏
- 流转：待提交 --提交--> 待审核 --通过--> 已通过
                           └--退回--> 已退回 --重新提交--> 待审核
- 审批人：生产部主管（固定角色）。备选：按记录从字段取人，需在字段表加「审核人」，本次未含
- 提醒：退回时提醒提交人（提醒流，靠「已退回」上的进入动作拉起）
- 不可逆：对象开启生命周期；审批流发布后回不到草稿
- 存量对照：homework__c 不存在；「作业提交」菜单与流程名均未占用
- 本次不改：课程对象、已有菜单分组

请确认：A 照此执行 ｜ B 字段清单要改 ｜ C 先只建对象和字段，流程下次再配
```

### 3.4 什么情况必须在蓝图之外再问一次

- 蓝图里没有的新资源（临时想加字段、加状态、加流程）。
- 不可逆动作：工作流发布（10→30）、`isAllowTrigger` 置 true、对象 `enableLifeCycle`、
  删流程（`workflow.delete`）、任何改 `code` 的念头。
- 目标环境或账号与蓝图不一致（计划会以 `TARGET_CHANGED` 拒绝，别绕过）。
- 计划执行到一半失败：审批已用掉，**重新出计划、重新审批**；不要拿旧计划"再试一次"。

### 3.5 反模式

| 做法 | 后果 | 正确做法 |
| --- | --- | --- |
| 一个字段一个计划、一个按钮一个计划 | 用户点十几次「同意」，还会漏看 | 按蓝图分段，一段一个计划 |
| 先写后补蓝图 | 顺序错、id 对不上，返工比想清楚更慢 | 蓝图先行 |
| 用审批弹窗做设计评审 | 弹窗只有步骤，没有全局图，用户看不出缺什么 | 蓝图表贴对话里审 |
| 用户说"你看着办"就跳过蓝图 | 出问题时没有对照物，责任与范围都说不清 | 蓝图照样贴出来，一句话确认即可 |
| 把 JSON / 请求体丢给用户审 | 看不懂参数，只能闭眼点「同意」，业务缺口全漏 | 按 §3.3 写业务语言审核稿 |
| 不查存量就出蓝图，建的时候才发现同名 | 轻则报错返工，重则 `object.save` 覆盖别人的对象 | 出蓝图前先跑 §1.3 的存量对照 |
| 一出错就推倒重来 | 对象 / 状态删不掉，系统里留下两套资源，脏数据越积越多 | 先判规模（§4.1），选最小动作 |
| 界面上一处不对就再发一个计划 | 又一个弹窗，且可能与上一个计划的写入打架 | 攒成一批，或明确说"这是修正计划" |

## 4. 出错之后：先判规模，再选最小动作

**「错了就重来」是错的。** 对象、生命周期、字段一旦建进系统，工具侧没有删除能力；推倒重来不会回到干净状态，
只会在系统里多出一套停用资源、留下一堆没人维护的脏数据。正确顺序是：**先判断错在哪一层，再选能解决问题的最小动作。**

### 4.1 先判规模：错在哪一层，决定用多重的手段

| 错在哪一层 | 已经写进系统的 | 最小动作 | 绝对不要 |
| --- | --- | --- | --- |
| 对象（`code` 或业务边界选错） | 对象 + 2 个默认状态 + 默认布局 / 列表 | 先停手评估：能复用就复用（改中文名、补字段）；确认必须换对象时，旧对象改名「xxx(停用)」+ `status: 2` 停用（`object.save` 的参数注释只写了 `status: 1 = 启用`，2 未实测 → 先单步验证回读）、把入口从菜单摘掉，新对象另建；旧对象登记进 §4.6 废弃清单 | 建第二个同名对象并存；指望删掉旧对象 |
| 生命周期 / 状态建错 | 状态（不能删）、挂在状态上的按钮 | 改名 + 停用 + 新建 + 在新状态上重建按钮（§4.4） | 改 `sort` 把重复状态藏起来 |
| 字段类型 / 名称错 | 字段、布局控件、列表列 | 改名（停用）→ 停用 → 新建 → 换控件（§4.2） | 改 `dataType`、删字段 |
| 布局 / 列表排错 | 布局本身 | 直接整份回写覆盖（`layout.save` / `columns.set`） | 重建对象 |
| 流程配错（还在草稿） | 流程草稿（没被任何审批实例引用） | `workflow.delete` 删掉重建（不可逆，只对草稿用），或 `workflow.task.update` 改节点 | 带着问题发布 |
| 流程配错（已发布） | 已发布流程 + 状态按钮 + 进入动作 + 历史审批记录 | 新建一条修正流程，旧的 `status: 30` 禁用，挂载改指新流程；**不要删已发布的流程** | 指望 20→10 回草稿 |
| 菜单错 | 菜单（无删除 / 停用能力） | 新建正确菜单，旧入口去控制台处理 | 臆造删除接口 |

判规模只需要问三个问题：**① 错的东西能不能删？② 有没有别的资源指着它？③ 修它比"在它旁边再建一个"便宜吗？**
三个都答完，动作基本就定了。规模判错的典型后果：字段级错误被当成对象级错误处理 → 新对象 + 新字段 + 新流程，
旧的全留在系统里，两套都得维护。

**顺带认清三条不可逆**（它们决定了为什么有些错只能停用、不能修）：

| 不可逆 | 表现 | 唯一的出路 |
| --- | --- | --- |
| 字段 `dataType` 建完不可改 | 改类型请求被拒 | 停用旧字段 + 新建 |
| 字段 / 状态不能删 | 没有删除接口 | 停用（`status: 2` / `isEnabled: false`） |
| 工作流发布后回不到草稿 | 20→10 被静默忽略（`code` 仍 0） | 新建一条流程 |

推论：**能在蓝图阶段定对的东西，不要留到施工后改。**

### 4.2 字段类型选错了（作业内容被建成"长文本"）

标准动作是五步，顺序不能反：

| # | 动作 | 具体做什么 | 为什么 |
| --- | --- | --- | --- |
| 1 | 先把旧字段**改名** | `field.save`：`name` 改「作业内容(停用)」，其余键按原值回传 | 对象内字段**名称唯一**；不先改名，第 3 步会报「字段名称重复」 |
| 2 | 再**停用**旧字段 | 同一请求里 `status: 2`、`disabled: true` | 停用只是隐藏；历史数据仍留在旧字段，不会丢 |
| 3 | 新建正确字段 | `field.save`：`content_text__c`、`dataType: 1`、`status: 1` | code 不能与旧的重复 |
| 4 | 同步布局 | `layout.detail` 读全量 → 把旧控件换成新控件 → `layout.save` 整份写回 | 控件是独立对象，字段停用**不会**自动摘掉控件 |
| 5 | 同步列表与引用 | `columns.set` 换列；工作流 `taskFields` / 判断规则里引用旧字段的，一并换 | 列表整份替换；审批页挂旧字段会让人看到停用值 |

回读三件事：旧字段 `status: 2`、新字段 `status: 1`、表单上只剩新控件。

反面做法（都踩过）：直接改 `dataType`（被拒）、先建新字段再想名字（撞名）、
只停用不改名（新字段建不出来）、字段停了但布局没动（表单上留着旧控件）。

### 4.3 停用之后要收拾的连锁反应

停用不会「自动传播」。一个字段 / 状态停用后，逐项回查：

- **表单布局**：`layout.save` 里换掉或删掉旧控件，否则表单还显示停用字段。
- **列表**：`columns.set` 整份替换时把旧列去掉；注意别把 `status_id__sys` 一起删了。
- **工作流**：任务节点 `taskFields`、判断规则、动作节点的 `statusId`，引用旧资源的都要换。
- **状态按钮 / 进入动作**：挂在停用状态上的按钮不再可达。`lifecycle.useraction` 只有
  `create` / `get` / `list`，**没有 update 和删除**——旧按钮改不了、也删不掉，只能在新状态上新建按钮，
  旧按钮随旧状态一起失效。所以状态一旦建错，代价是把挂在上面的动作重建一遍。
- **菜单**：引用了被替换布局 / 列表的，`menu.submit` 回传新 id。

### 4.4 状态建错了（同义重复、顺序错）

状态不能删，处理方式与字段同构，但多一步「迁移动作」：

1. `lifecycle.status.update`：旧状态改名「待提交(停用)」+ `isEnabled: false`（`code` 不变）。
2. `lifecycle.status.create`：新建正确状态，`sort` 按流转顺序重排（停用状态排最后，别插中间）。
3. 重建挂载：在新状态上 `useraction.create` / `enteraction.create`（旧按钮无法改，见 4.3）。
4. 回查工作流动作节点的 `statusId`，必须是**启用中**的状态 id。
5. 回读 `query.lifecycle.status.list`：启用状态的数量与顺序符合蓝图，停用项排在末尾。

### 4.5 code 写错了

对象 / 字段的 `code` 是 upsert 键，菜单 `code` 是入口的「身份证」；无论哪种，**改 code 都等于换一个资源重来**，旧资源甩不掉：

- 对象 `code` 错：最贵。旧对象删不掉（工具没有删除对象的能力，平台上删除是否级联也未验证），
  字段 / 布局 / 菜单 / 流程都要在新对象上重挂。所以对象 `code` 视为**一次写入、永久不可逆**，蓝图阶段逐字核对。
- 字段 `code` 错：按 4.2 停用旧字段 + 新建，历史数据留在旧字段。
- 菜单 `code` 错：新建菜单；工具没有菜单删除 / 停用能力，旧菜单只能进控制台处理，别臆造接口。

### 4.6 蓝图是活文档：留一张废弃清单

每次停用 / 重建，都在蓝图末尾追加一行：

| 废弃资源 | 类型 | 停用日期 | 替身 | 原因 |
| --- | --- | --- | --- | --- |
| 作业内容(停用) `content__c` | 字段 | 2026-11-10 | `content_text__c` | 误建为长文本（17），已禁用 |

这张表是下一次配置的输入：看到「同义重复」的候选，先查废弃清单，别又建一个。

## 5. 命名与 code（工作约定，待组织拍板）

`EGMP-CONFIG-BASICS.md` §5 把命名列为待定项。在拍板前按下面这套做，别每次自创：

- `code`：小写 + 下划线 + `__c` 后缀（菜单已实测必须 `__c`）；对象 / 字段 / 菜单同一套规则。
- 中文名：写业务语义，不带技术词（「作业内容」不是「content 字段」）。
- 停用项：中文名追加「(停用)」，让表单、列表、控制台一眼能分辨。
- 按钮 / 动作 `code`：稳定业务码（`submit_homework`），不用演示值或时间戳。
- 同一蓝图内，一个资源只出现一次；重名先当成建错处理。

## 6. 分工、维护与检查单

### 6.1 四份文档各管一段

| 文档 | 管什么 | 什么时候读 | 进不进能力卡片 |
| --- | --- | --- | --- |
| `标准配置思路规范.md`（本文） | 存量自检、蓝图、施工顺序、审核稿怎么写、审批粒度、出错判规模 | **接到配置任务的第一分钟** | 否 |
| `基础API使用指南.md` | 单条接口是什么、要点、一条案例 | 写某个请求体之前 | 是 |
| `标准配置使用规范.md` | 一类配置的成文步骤 | 照某个方案施工时 | 是 |
| `EGMP-CONFIG-BASICS.md` | 平台硬约束与实测证据 | 怀疑"为什么不能这么干"时 | 否 |

一句话：本文给次序和判据，`基础API使用指南` 与 `标准配置使用规范` 给具体写法，`EGMP-CONFIG-BASICS` 给硬边界和实测证据。

### 6.2 检查单

**开工前**

- 七张表填完，自检 7 条全过。
- 存量对照（§1.3）查完并贴进蓝图：对象 code / 对象名 / 字段名 / 状态名 / 流程名 / 菜单名 / 动作名，逐个有结论。
- 审核稿（§3.3）是业务语言：没有 JSON、没有 method / path / params，待拍板的是选择题。
- 账号条已选账号，环境是测试还是生产说清楚。
- 本次「不改的东西」列出来了。

**每个阶段**

- 先读后写；写完立刻回读该阶段产物。
- 记下返回的 id（`objectId` / `fieldId` / `layoutId` / `listLayoutId` / `statusId` / `workflowBasicId`）。
- 不可逆点（发布、`isAllowTrigger`、`enableLifeCycle`）留到最后，且单独在报告里点名。

**收工**

- 控制台逐项验收：对象、字段、表单、列表、菜单、状态、流程、按钮。
- 交施工报告：写入清单、回读结果、与蓝图差异、废弃清单新增项。
- 有新的坑，回填本文件或 `EGMP-CONFIG-BASICS.md`；有新的成文步骤，回填 `标准配置使用规范.md`。

### 6.3 本文怎么维护

- 顺序变了（比如平台新增强约束）：改 §2，并同步 `EGMP-CONFIG-BASICS.md` §1 的对照说明。
- 又出现一次「多个小计划」的返工：把案例补进 §3.5。
- 又出现一次「出错就推倒重来、留下脏数据」：把规模判断和止损动作补进 §4.1。
- 又出现一次「改错重建」：把连锁反应补进 §4.4 / §4.5。
- 修订时同步 `AGENTS.md` 的硬规则一节——那里是入口，本文是细节。

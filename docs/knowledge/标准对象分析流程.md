# 标准对象分析流程

> 目标：只给一个**对象 ID** 或**对象 code**，稳定地产出这个对象的生命周期分析：
> 状态、启用/停用、每个状态上的进入动作和用户动作、动作类型、关联工作流、进入条件，以及可选的 drawio 图。
>
> 适用范围：eGMP 配置环境（standard-val / 生产）的只读分析。本文所有接口都已在 `homework2__c`、`audit_plan__c`、`change_control__c` 上实测过；未实测的字段会明确标注「未验证」。
>
> 配套文档：
> - 数字 → 中文：`docs/knowledge/系统常用映射表.md`
> - 完整 behaviorType 221 项：`docs/analysis/lifecycle-action-types.md`
> - 样例：`docs/analysis/homework2__c-lifecycle.md`

## 0. 输入、输出与前置条件

### 输入

| 输入 | 是否必需 | 说明 |
|---|---|---|
| 对象 ID | 二选一 | 如 `7bb8b0ef-57ad-13f9-0ede-73dfb2d9be9b` |
| 对象 code | 二选一 | 如 `homework2__c` |
| 多对象 | 可选 | 一次最多 3 个；用中英文逗号、空格或换行分隔，如 `homework2__c, audit_plan__c` |
| 环境地址 | 自动 | **必须取自底部账号条的当前账号**；不接受手填，也不复用旧账号的会话 |
| eGMP 令牌 | 必需 | 按 `prefs.currentAccountId` 换票，不落盘、不打日志；换票失败直接报错，不回落旧会话 |

### 多对象分析

- 页面会先给一张「对比总览」，按对象列出生命周期、状态数、用户动作数、进入动作数、进入条件状态和警告数。
- 每个对象下面是一块可展开的明细；单对象默认展开，多对象默认收起，避免三份状态和动作表把页面拉得很长。
- 各对象独立请求、独立报错：一个对象 id 写错不会让另外两个结果消失；失败对象在对比卡和明细里显示错误原因。
- 多对象只解决“并排看”的问题，**不会**把两个对象的生命周期合并；跨对象比较时仍以对象自己的 `lifeCycleId` 为准。

### 输出

1. 对象元数据：id、code、名称、`lifeCycleId`、`enableLifeCycle`
2. 状态表：`sort`、名称、code、是否启用
3. 动作表：所属状态、进入/用户动作、动作 code、`behaviorType`、效果、关联工作流
4. 工作流表：名称、code、`workflowBasicId`、`workflowConfigId`、状态、`isAllowTrigger`
5. 进入条件：已配置 / 未配置
6. 结论与阅读边界
7. 可下载产物：Markdown 详细文档、drawio 生命周期 / 工作流图

### 产物下载

- 每个对象明细和「对比总览」卡片都提供「下载文档」「下载 drawio」「下载 PNG」三个按钮；多对象可逐个下载，不打包。
- Markdown 文档包含环境/账号、对象概览、逐状态动作表、工作流解析、自动观察与风险、读取告警，并注明“生命周期总览列出全部状态，已知变更才画实线，不按 `status.sort` 推测迁移边”。
- drawio 是真正的 `.drawio` XML：第 1 页是生命周期状态总览，后续每条工作流一页。总览页列出全部状态；能确认的本对象状态变更画实线；工作流改状态但触发源未读到的，放在右侧“待确认触发源”清单里，**不画箭头、不猜源状态**。工作流页画任务、判断、动作节点和分支，`behaviorType=46` 的关联对象动作单独标注，不画成本对象边。
- PNG 是同一张生命周期总览的栅格图，便于直接插入文档；完整工作流仍以 `.drawio` 为准。
- 文件名形如 `code-analysis-YYYY-MM-DD.md` / `.drawio` / `.png`；`code` 会做字符白名单处理。
- 总览页状态按 `status.sort` 排列，但**不画 sort 连线**；判断“主流程怎么走”要看工作流页和文档的工作流解析，不能只看总览页的箭头。

### 前置条件

- 读取账号必须来自 akso-workbench 底部账号条；不要回落到旧会话。
- 只读流程不触发审批；但**不要**调用任何 `Create/Update/Delete/Sort/UpdateStatus`。
- 令牌只放在请求头，不写文件、不打印。

## 1. 总流程

```text
输入 objectId / objectCode
  │
  ├─ 1. 解析对象：拿到 code、id、lifeCycleId、enableLifeCycle
  ├─ 2. 读状态：基础状态列表 + 配置状态列表（isEnabled / sort）
  ├─ 3. 读动作：每个启用状态 → UserAction/EnterAction list
  │       └─ 每个动作再 GetById，拿 configs / behaviorType
  ├─ 4. 类型翻译：behaviorType → 中文
  ├─ 5. 读进入条件：StatusEnterRule/GetList
  ├─ 6. 读工作流：basicId → configId → 详情 / 步骤
  ├─ 7. 判断流程性质：审批流 / 提醒流
  ├─ 8. 汇总：状态表 + 动作表 + 工作流表 + 边界
  └─ 9. 可选：生成 drawio / Markdown
```

## 2. 第一步：解析对象

### 2.1 输入是 code

```http
GET /api/openapi/v1.0/BasicObject/{objectCode}
```

返回 `data`：

```json
{
  "id": "7bb8b0ef-57ad-13f9-0ede-73dfb2d9be9b",
  "code": "homework2__c",
  "name": "作业提交2.0",
  "lifeCycleId": "70e6973c-c1e1-bed3-3d41-4fb2b75e093d",
  "enableLifeCycle": true
}
```

要点：

- 对象不存在时是业务错误（`code != 0`），不是 HTTP 404。
- `enableLifeCycle=false` 表示对象没启用生命周期，后续状态/动作分析应直接停止并说明。

### 2.2 输入是 ID

当前 OpenAPI 没有按 ID 取对象的路径；用配置侧对象清单反查 code：

```http
GET /api/platform/BasicObject/AllObjectWithType
```

返回 `data[]`，每项含 `id`、`code`、`name`、`objectTypes[]`。在客户端按 `id` 精确匹配，拿到 `code` 后再走 2.1。

要点：

- 这是全量对象清单，数据量可能较大；只做一次，按 id 过滤，不要逐页翻。
- `AllObjectWithType` 是**配置接口**，与 OpenAPI 的对象详情字段不完全一样；以 2.1 的返回为准确认 `lifeCycleId`。

### 2.3 解析结果

至少记录：

```text
objectId, objectCode, objectName, lifecycleId, enableLifeCycle
```

## 3. 第二步：读状态

状态有两个来源，必须合并：

### 3.1 基础状态列表（名称、id、code）

```http
GET /api/openapi/v1.0/BasicObject/lifecycleStatus/{objectCode}
```

返回每项：

```json
{
  "id": "46e3ce00-c78e-f5a3-17cd-096ba7343175",
  "code": "init_status__c",
  "name": "待提交",
  "lifecycleId": "70e6973c-c1e1-bed3-3d41-4fb2b75e093d",
  "lifecycleCode": "homework2_lifecycle__c",
  "lifecycleName": "作业提交2.0生命周期",
  "belongType": 1
}
```

**没有** `isEnabled`、**没有** `sort`。不要拿它判断启停或排序。

### 3.2 配置状态列表（isEnabled、sort）

```http
GET /api/config/lifecycle/Status/GetList
```

返回 `data[]`，每项：

```json
{
  "id": "a39a6182-b0c0-c9e4-544b-244231c34c65",
  "name": "待提交（停用）",
  "code": "status_draft__c",
  "lifecycleId": "70e6973c-c1e1-bed3-3d41-4fb2b75e093d",
  "sort": 4,
  "isEnabled": false,
  "description": "",
  "workflowCancelStatus": null,
  "isRecordDeactivate": false,
  "dmsStatusMapping": null,
  "isDeleted": false
}
```

关键坑：

- 这个接口一次返回**全环境 4000+ 条状态**（2026-11-12 实测 `count: 4016`），`lifecycleId` 查询参数会被忽略；
- 返回是**分页对象**，不是裸数组：

```json
{
  "count": 4016,
  "hasUp": false,
  "hasNext": false,
  "datas": [ ... ]
}
```

- 兼容写法：`const rows = Array.isArray(data) ? data : data.datas`；
- GET 可用，POST 405；
- 必须在客户端按 `lifecycleId` 过滤，再按 `sort` 升序；
- 合并时以 `id` 为主键，不要按名称合并（停用状态会带“（停用）”后缀）。

### 3.3 合并规则

| 场景 | 处理 |
|---|---|
| 基础列表有、配置列表无 | 保留，`isEnabled` 未知，标注待确认 |
| 配置列表有、基础列表无 | 保留，名称以配置列表为准，标注“基础列表缺失” |
| 两边都有 | 合并，`isEnabled` / `sort` 取配置列表 |
| `isEnabled=false` | 默认**不展示**，只计入“停用状态数”；分析报告可单列一张停用表 |

输出示例：

| sort | 状态 | code | 启用 | 进入动作 | 用户动作 |
|---:|---|---|---:|---:|---:|
| 0 | 待提交 | `init_status__c` | 是 | 0 | 1 |
| 1 | 待审核 | `status_pending__c` | 是 | 0 | 0 |
| 2 | 已通过 | `complete_status__c` | 是 | 0 | 0 |
| 3 | 已退回 | `status_rejected__c` | 是 | 1 | 1 |

## 4. 第三步：读每个状态的动作

对每个 **启用状态**，分别读用户动作和进入动作。

### 4.1 用户动作（状态按钮）

```http
GET /api/config/lifecycle/UserAction/GetListByStatusId?statusId={statusId}
```

返回动作数组，常见字段：

```text
id, code, name, description, lifecycleStatusId, lifecycleStatusName,
group, behaviorTypes[], icon, isCommonly, isNotMetHide, isNotShowOperation,
preConfigDto, configs[]
```

用户动作的 `configs[]` 通常已带 `behaviorType` / `behaviorValue`；但仍建议对每个动作再调一次详情。

### 4.2 进入动作

```http
GET /api/config/lifecycle/EnterAction/GetListByStatusId?statusId={statusId}
```

返回的是**动作壳**，只有：

```text
id, sort, belongId, name, isEnabled, description,
modifiedTime, belongType, executeType
```

**没有 `code`，没有 `configs`**。直接看这里会误判成“未配置动作”。

### 4.3 必须再读详情（关键）

进入动作：

```http
GET /api/config/lifecycle/EnterAction/GetById?id={actionId}
```

返回：

```json
{
  "id": "84908509-0d00-be66-284e-fdd867a78756",
  "code": "dd__c",
  "sort": 1,
  "belongId": "a077aead-6ad2-6631-b939-815db1378a14",
  "description": "asdf",
  "failPrompt": null,
  "conditionStr": null,
  "condition": null,
  "configs": [
    {
      "id": "34d10e67-4572-4b1f-a0f8-cfa7c346b5c5",
      "tempId": "00000000-0000-0000-0000-000000000000",
      "behaviorValue": {
        "workflowId": "d3cd2559-2f43-d5a0-2063-3a24d1ee2875",
        "isBeforeWorkflowCompleteReminderTask": false
      },
      "sort": 0,
      "behaviorType": 7
    }
  ],
  "belongType": 1,
  "executeType": 1
}
```

用户动作：

```http
GET /api/config/lifecycle/UserAction/GetById?id={actionId}
```

返回完整对象，动作配置在 `actions[].configs[]`（注意不是顶层 `configs`）。

### 4.4 动作读取规则

1. **list 只用来拿 id / 名称 / 排序**；
2. **类型一律以 GetById 的 `configs[]` 为准**；
3. 一个动作可能有**多个 configs**，逐条列出，不要只取第一条；
4. `configs: []` 才是真“未配置具体动作”，不能从名称/描述反推；
5. `name` 可能为 `null` 或空串；显示时回落到 `description`，再回落到 `code`，最后显示“未命名”；
6. `UserAction/GetById` 个别动作会返回 `data:null`（实测 `a1b3dd9d-...`），此时回落到 list 里的 `configs`，并把“详情缺失”写进边界。

### 4.5 动作类型翻译

`configs[].behaviorType` 是数字。常用值：

| 值 | 含义 |
|---:|---|
| 5 | 修改记录字段 |
| 7 | 发起工作流 |
| 9 | 修改生命周期状态 |
| 10 | 启动检查表（异步） |
| 17 | 创建相关对象记录 |
| 46 | 修改相关对象生命周期状态 |
| 48 | 启动检查表 |
| 68 | 运行报告生成到附件字段 |
| 89 | 权限共享复制到 |
| 576 | 修改相关文档的文件 |
| 600 | 使电子签名记录作废 |
| 800 | 活跃工作流 |
| 811 | 催办 |

完整 221 项见 `docs/analysis/lifecycle-action-types.md`。映射不到时显示 `behaviorType: <数字>（未登记）`，不要猜中文。

## 5. 第四步：读生命周期进入条件

```http
GET /api/config/lifecycle/StatusEnterRule/GetList?lifecycleId={lifecycleId}
```

实测：

- `homework2__c` 返回 `data: []`；
- `audit_plan__c` 返回 `data: []`；
- 不带参数、只带 `objectId`、只带 `statusId` 也都是空；
- `Get` / `GetByLifecycleId` 是 404。

结论写法：

- `data.length === 0` → **当前生命周期未配置进入条件**；
- 非空样例尚未取得 → 不要编造字段结构，标“已配置，结构待验证”。

> 进入条件与“进入动作”是两回事：进入动作是状态上的动作；进入条件挂在生命周期上，用于控制记录能否进入该生命周期。

## 6. 第五步：读关联工作流

对每个动作的 `behaviorValue.workflowId`（即 `workflowBasicId`）去重，逐个解析。

### 6.1 basicId → 工作流基本信息

```http
POST /api/platform/Workflow/GetWorkflowBasicPageViewList
Content-Type: application/json

{"pageIndex":1,"pageSize":1000,"filters":[]}
```

实测 941 条；`pageSize:1000` 可用。返回项关键字段：

```text
workflowBasicId, name, code, status, isAllowTrigger,
objectId, objectCode, lifecycleId,
workflowType, versionNo, id (workflowConfigId)
```

按 `workflowBasicId` 精确匹配。

### 6.2 工作流详情

```http
GET /api/platform/Workflow/GetWorkflowBasic?id={workflowConfigId}
```

注意：

- 参数是 **workflowConfigId**（列表项里的 `id`），不是 `workflowBasicId`；
- 传 `workflowBasicId` 会返回 `data:null`。

### 6.3 工作流步骤

```http
GET /api/platform/Workflow/GetWorkflowSteps?workflowConfigId={workflowConfigId}
```

返回步骤数组，关键字段：

```text
id, name, code, stepType, sort, isEnable, nextStepId, stepDetail
```

**不要直接按 `sort` 展示**：部分流程的 70/90 节点 `sort=0`，会排到“开始”前面。展示时按 `stepType` 的逻辑顺序排：

```text
10 开始 → 30 任务 → 70 判断 → 90 动作 → 20 结束
```

同类型内再按 `sort` 升序；`sort` 相同的保留接口返回顺序。

`stepType`：

| 值 | 含义 |
|---:|---|
| 10 | 开始 |
| 20 | 结束 |
| 30 | 任务（审批或提醒） |
| 70 | 判断 |
| 90 | 动作 |

### 6.4 判断审批流还是提醒流

看任务节点的 `stepDetail.stepTaskConfig`：

| 配置 | 含义 |
|---|---|
| `isNotifyTaskType: true` | 提醒任务 |
| `isRequireApproval: false` | 不要求审批 |
| `stepTaskApprovals: []` | 没有审批按钮 |
| `taskRequireType: 20` | 提醒任务类型 |
| `notifyType: -10` | 使用提醒策略 |

满足以上组合 → **提醒型待办**，不是审批流。

### 6.5 `isEnable=false` 的正确含义（重要）

任务节点上的步骤级 `isEnable=false` **不是“停用”**，而是表示：

> 该任务仅作为**提醒型待办**，不需要用户点击“完成”。

不要因为 `isEnable=false` 就过滤掉这个任务，也不要写成“任务停用/不执行”。状态上的 `isEnabled` 才是启用/停用；两者不是一回事。

### 6.6 工作流动作节点也会改状态（重要）

生命周期上的进入动作 `behaviorType=7` 只是“启动工作流”；真正改状态的，往往是工作流里的**动作节点**（`stepType=90`）。

读法：

1. `GET /api/platform/Workflow/GetWorkflowSteps?workflowConfigId=...`；
2. 每个步骤的 `stepDetail` 是 **JSON 字符串**，先 `JSON.parse`；
3. 动作节点看 `stepDetail.stepAction.actions[].configs[]`：
   - `behaviorType=9` → `behaviorValue.statusId` 是目标状态；
   - `behaviorType=7` → `behaviorValue.workflowId` 是再拉起另一条工作流；
   - `behaviorType=5/10/48` → 改字段/启动检查表，不改状态。
4. 判断节点看 `stepDetail.stepDecision.rules[]`：`nextStepId` + `condition`（通常是审批按钮结果）；默认出口是 `stepDecision.nextStepId`。

因此一条完整边应写成：

```text
源状态 --进入动作/用户动作--> 工作流启动
工作流 --审批通过--> 动作节点 behaviorType=9 --> 目标状态
工作流 --审批退回--> 另一个动作节点 --> 另一个目标状态
```

典型例子（偏差管理）：

| 工作流 | 启动于 | 分支 | 目标状态 |
|---|---|---|---|
| 偏差申请审核流程 | 偏差申请审核 | 审核通过 | 初步评估 |
| 偏差申请审核流程 | 偏差申请审核 | 审核退回 | 报告与识别 |
| 初步评估审核流程 | 初步评估审核 | 通过 | 偏差调查 |
| 初步评估审核流程 | 初步评估审核 | 退回 | 初步评估 |
| 偏差调查审核流程 | 偏差调查审核 | 通过 | CAPA路径判断 |
| 偏差调查审核流程 | 偏差调查审核 | 退回 | 偏差分级 |

必须额外检查：

- **自环**：工作流动作把状态改回“启动它的那个状态”，而该状态又挂了同一个进入动作 → 可能重复启动；
- **同状态多进入动作**：都无 `condition` 时可能同时执行，最终状态取决于顺序；
- **链式工作流**：动作节点 `behaviorType=7` 会再拉一条流程，要把链继续展开；
- 不要把工作流内部节点画成生命周期状态；它们是“宏动作”的内部步骤。

## 7. 第六步：流转关系（当前不可靠）

已尝试：

| 接口 | 结果 |
|---|---|
| `GET /api/config/lifecycle/StatusRelation/GetList?lifecycleId=...` | 404 |
| `GET /api/config/lifecycle/Flowchart/GetConfig?lifecycleId=...` | HTTP 200，`code:500` |
| `StatusRelation/Create` / `Delete` / `UpdateStatus` | 只在前端 bundle 里见到写接口，没有稳定读接口 |

因此当前**不要声称画出了“完整运行时状态机”**。但可以画**配置级流转图**，边分两类：

| 边类型 | 来源 | 标签写法 |
|---|---|---|
| 动作直改 | 状态上的用户/进入动作，`behaviorType=9` | `用户动作：提交审核` / `进入动作：若需要CAPA` |
| 工作流改 | 进入动作 `behaviorType=7` → 工作流动作节点 `behaviorType=9` | `工作流：审核通过` / `工作流：审核退回` |

这类图要标清：

- 哪些边是用户点击触发，哪些是进入状态自动触发；
- 哪些边经过工作流、经过哪个审批结果；
- 哪些是配置目标但无 `condition`、可能同时执行；
- 自环、重复进入动作、链式工作流必须单独列异常。

分析报告至少列：状态、动作、工作流、两类边、异常；如果必须画“平台运行时真实流转”，先在前端页面抓 `Flowchart` 的实际读接口，或让用户提供流转关系。

## 8. 第七步：汇总输出

### 8.1 Markdown 报告结构

```text
1. 概览（状态数、启用/停用、动作数、工作流数、进入条件）
2. 状态表（sort / 名称 / code / 启用 / 动作数）
3. 启用状态的动作明细（按状态分组）
4. 动作类型说明
5. 关联工作流（审批流 / 提醒流分开）
6. 生命周期进入条件
7. 阅读边界
8. 数据来源
```

### 8.2 动作行格式

| 类型 | 动作名称 | code | behaviorType | 触发效果 | 含义 |
|---|---|---|---:|---|---|
| 用户动作 | 提交 | `cc__c` | 7 | 启动《作业提交-标准审核工作流》 | 人工发起审批 |
| 进入动作 | 未命名 | `dd__c` | 7 | 启动《作业提交》提醒流 | 进入状态时生成提醒待办 |

### 8.3 先选图的语义

生命周期图不是只有一种画法，先定语义再动笔：

| 图类型 | 画什么 | 适合回答 | 风险 |
|---|---|---|---|
| 状态图 | 只画启用状态 + 状态间箭头 | 主流程怎么走、有没有断头/回环 | 看不到动作和工作流 |
| 动作图 | 状态 + 用户动作 + 进入动作 | 谁在推状态、动作触发什么 | 动作多时线会挤 |
| 全量图 | 状态 + 用户动作 + 工作流任务/判断 | 评审配置、看审批分支 | 信息最多，最容易乱 |

原则：

- 一张图只表达一种语义；不要把“运行轨迹”和“配置明细”混在一张图里。
- 本流程画的是**配置视图**：箭头表示“配置上会改到哪个状态”，不是运行记录。
- 全量图优先保证主链可读；分支、异常、测试动作可以放侧栏或报告，不要都塞进主轴。

### 8.4 节点与连线映射

| 平台对象 | 图形 | 便笺本模块 | 说明 |
|---|---|---|---|
| 生命周期状态 | 矩形 | `生命周期状态` | 浅蓝 `#bdd7ee`；只画 `isEnabled=true` |
| 用户动作 | 胶囊 | `用户动作` | 橙色 `#ed7d31`；放在状态旁边或状态之间 |
| 工作流任务 | 矩形 | `用户任务` | 橙色；标注“（任务）” |
| 判断/审批结果 | 菱形 | `判断` | 橙色；通过向下、退回向上/侧向 |
| 开始/结束 | 圆形 | `开始/结束` | 绿色 `#70ad47`；需要时再加 |
| 泳道 | 大框 | `泳道图` | 多角色/多阶段时用，单对象流程可不加 |

连线来源只有两类：

1. **动作直改**：`behaviorType=9` + `behaviorValue.statusId`；
2. **工作流动作节点改状态**：`stepType=90` 的 `stepAction.actions[].configs[]` 里的 `behaviorType=9`。

边标签只写“动作名 / 通过 / 退回”，不要把 workflowId 写在线上的标签里；id 放报告表格，图上只保留可读信息。

### 8.5 布局与连线规则（本次实测）

#### 1. 方向与主轴

- 生命周期状态**竖向排列**，主轴居中；状态按 `sort` 升序。
- 侧向状态（已取消、制定CAPA、偏差关闭、关闭、等待行动项完成）放主轴左侧或右侧，不要打断主链。
- 主链上状态之间至少留 **60 px 净间距**（约 3 行字）；这是“线要够长”的硬下限。

#### 2. 一个节点多条线时，先分端口

同一个状态/判断上有多条线时，按边分配端口，不要都挤在中心：

```text
顶部：通过 / 主入边
底部：下一状态 / 主出边
左侧：退回、取消、侧向动作
右侧：长回环、自环、次要动作
```

- 同一侧两条线，端口至少错开 **40–60 px**；箭头之间不能压在一起。
- 例：`报告与识别` 底部“退回”进 x=660，“发起审核”在 x=720；`初步评估` 顶部“退回”进 x=660，“通过”在 x=720。
- 同一条边不要先横再竖再横反复拐；能一条直线就一条直线，侧分支最多一个弯。

#### 3. 退回/长回环各用独立通道

- 退回线走**左侧专用通道**（如 x=500/520），长回环走**右侧专用通道**（如 x=1080）。
- **一条通道只给一条边用**。两条边共用同一 x 会看起来像一条线穿过了中间的节点/菱形，评审时会被误判为“连线与节点重合”。
- 本次踩坑：`CAPA路径判断 → 制定CAPA` 曾借用左侧 x=500，和“审批结果 → 偏差分级”的退回线同通道，视觉上像一条线从菱形穿下去。改为正下方直连、目标节点下移后消失。
- 如果两条边必须靠近，至少错开 20–30 px，或在节点边缘换一个端口。

#### 4. 箭头必须“进边”，不能“贴边”

- 最后一段要**垂直于目标边**进入：从上边进就竖直向下，从左边进就水平向右，从右边进就水平向左。
- 不要出现“竖直向下、落在胶囊右边缘”这种箭头：看起来像没连上。
- 本次踩坑：`报告与识别 → 取消` 原来终点在“取消”胶囊右边缘，箭头方向却是向下的。改为进入胶囊**顶部中心**，箭头向下，才叫连到位。
- 箭头尖端与节点边缘留 0–2 px，不要穿进节点，也不要在节点外悬空。

#### 5. 少拐弯，优先对齐

- 两个节点中心对齐时，直接一条竖线；例如 `取消 → 已取消` 改成同 x 的竖线，去掉了原来的“下—左—下”三次拐弯。
- 侧分支能用一个弯解决，就不要用三个弯；画完先删掉“为了绕而绕”的折点。
- 交叉不可避免时，让线在空白区交叉，不要让线穿过节点文字或动作胶囊。

#### 6. 自环与测试动作

- 自环放在节点**外侧**（底部或右侧），离节点和相邻动作至少 30 px。
- 测试动作（如 `sdfsdf`）可以保留，但要在报告里标注“测试数据”；不要让它占据主通道。
- 空配置的进入动作要标“未配置具体动作”，不要凭名字猜效果。

#### 7. 底部发散分支

- 主目标（如“制定CAPA”）放在判断正下方，直线向下；
- 次目标（如“偏差关闭”）从右侧出一个弯，再向下；
- 底部两个目标节点要留足高度，箭头长度不要小于 60 px，否则会显得“贴在一起”。

### 8.6 生成与校验

- 用 drawio XML 生成，PNG 由同一份总览的 SVG 栅格化；**最终以 `.drawio` 能正常打开为准**。
- 预览画布高度必须覆盖最底部节点：本次 `制定CAPA` 在 y=2600、高 76，画布 2620 会截断，改为 2720 才完整。
- 生成后校验：
  - 顶点数 = 状态 + 动作 + 任务 + 判断；
  - 边数 = 直改边 + 工作流边 + 待确认侧栏边；
  - 无重复 id、无悬空 source/target；
  - 每条边都有 `marker-end`；
  - PNG 只覆盖生命周期总览，检查状态列、右侧清单和文字没有重叠；工作流页的分支、自环、退回通道在 `.drawio` 里检查。

## 9. 完整样例：`homework2__c`

```text
对象：作业提交2.0（homework2__c）
对象 id：7bb8b0ef-57ad-13f9-0ede-73dfb2d9be9b
生命周期：作业提交2.0生命周期（70e6973c-c1e1-bed3-3d41-4fb2b75e093d）
状态：6 个（4 启用 / 2 停用）
动作：3 个（2 用户 + 1 进入）
进入条件：未配置
工作流：2 条
  - aa__c 作业提交-标准审核工作流（审批流，两个用户动作使用）
  - df__c 作业提交（提醒流，进入动作用）
```

`已退回` 的进入动作：

```text
list: id 84908509-0d00-be66-284e-fdd867a78756, description "asdf", configs []
GetById: code dd__c, behaviorType 7,
         workflowId d3cd2559-2f43-d5a0-2063-3a24d1ee2875
```

`df__c` 结构：

```text
开始（10）
  └─ 任务：请修改作业后重新提交（30，isEnable=false，提醒型待办）
       └─ 结束（20）
```

结论：进入“已退回”时发起提醒流，给创建人生成“请修改作业后重新提交”的提醒待办；它不是审批流。

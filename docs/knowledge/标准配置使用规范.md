# 标准配置使用规范

> 记录「一类配置怎么用接口一步步做出来」的成文方案：一个需要同意 / 驳回的审批节点该怎么配、一个只提醒不要求完成的任务节点该怎么配，等等。
>
> 这份文档**由人指定补写**——只有已经定稿的配置类型才写成方案，不是每个接口都有方案。工具卡片上的「标准配置用法」一栏就从这里读，改完**刷新页面**即生效，不用重新构建。

## 怎么写

- `### <capability id>` —— 方案挂在哪个接口的卡片下，id 用能力目录里的那个（如 `workflow.task.add`）。
- `#### 方案 · <名字>` —— 一个方案一块，同一个接口可以有多块。
- `>` 开头的引用块 —— 一句话说明这个方案解决什么。
- `**步骤**` —— 有序列表，每一步开头用反引号写接口 id，后面写这一步做什么。
- `**校验**` —— 列表，写回读 / 核对的方法。
- `**示例**` —— 一个 json 代码块，写主请求体（可省；示意为主，字段以先读后写为准）。
- `**预期**` —— 一两句话写跑完应该看到什么。

## 已收录

### layout.save 保存对象布局

#### 方案 · 新增一个分区并放置控件

> 已有布局要加一块「基本信息」，把两个字段放进新分区，不动原有分区。

**步骤**
1. `layout.detail` —— 读回当前布局，拿到 sections 与 controls 的 id 与顺序。
2. `layout.save` —— 在原 sections 后面追加新 section（只需 `id` / `code` / `name` / `type` / `columnsNum`，**不要**带 `belongId` / `fullPath`），再追加 control（`sectionId` 指向新分区）。
3. `layout.detail` —— 回读，确认分区与控件都在、顺序符合预期。

**校验**
- 回读 sections 数量 +1、controls 数量 +N。
- 新控件的 `sectionId` 指向新分区，没有被并到旧分区里。

**示例**
```json
{
  "id": "<layoutId>",
  "sections": [
    { "id": "<existingSectionId>", "code": "base", "name": "基本信息", "type": 1, "columnsNum": 1 },
    { "id": "<newSectionId>", "code": "attach", "name": "附件", "type": 1, "columnsNum": 1 }
  ],
  "controls": [
    { "id": "<newControlId>", "sectionId": "<newSectionId>", "code": "attach_file", "name": "附件", "fieldId": "<fieldId>", "type": 1, "gridSpan": 1, "attrs": {} }
  ]
}
```

**预期**
- 返回 `data` 是布局 id 字符串；回读的 sections / controls 与提交一致。

### object.save 新建对象

#### 方案 · 建对象时默认开生命周期与电子签名

> 新建业务对象时把状态机与电子签名一起打开：生命周期一旦开启就不可逆，所以这两个开关要在**建对象那一次**定下来，事后补要另走更新接口。

**步骤**
1. `object.save` —— `source: 3`、`objectClass: 1`、`status: 1`，同时带 `enableLifeCycle: true` 与 `enableSignatures: true`。
2. `query.object.get` —— 按 `code` 反查，确认两个开关都是 `true`（这个接口不回 objectId）。
3. `lifecycle.status.create` —— 需要自定义状态时接在后面建（平台自带「开启」「关闭」两态）。

**校验**
- 回读 `enableLifeCycle === true` 且 `enableSignatures === true`。
- 电子签名开了之后，审批 / 动作类节点才能配签批。

**示例**
```json
{ "name": "作业提交", "code": "homework__c", "source": 3, "status": 1, "objectClass": 1, "enableLifeCycle": true, "enableSignatures": true, "summaryFields": [] }
```

**预期**
对象建出来即带状态机与电子签名；后续加字段、布局、工作流都基于它。

### field.save 新建 / 更新字段

#### 方案 · 唯一字段用 name__ak 承载

> 每个对象自带一个 `name__ak`（名称）字段，它是配置字段里唯一特殊的一个：对象内的唯一性交给它。已经建了同义的自建字段（比如 `no__c`），先把自建字段停用，再把 `name__ak` 的名字改过来——同一对象内字段 name 与 code 都不能重复，所以必须改名，光停用不够。
> 平台 UI 停用/启用字段走的是 `POST /api/platform/BasicObject/EnableField`，体是 `{ id, status }`（`status: 1` 启用、`2` 停用）。

**步骤**
1. `query.fields.list` —— 先看对象下现有 name / code，确认没有同名字段，顺便拿到 `name__ak` 的 id。
2. `field.save` —— 更新 `name__ak`：回传整份字段（`id`、`code: "name__ak"`、`source: 2`、`status: 1`、`disabled: false` 等），只把 `name` 改成业务名（例：作业编号）；`code` 保持 `name__ak` 不动。
3. `field.save` —— 若已有自建唯一字段（例 `no__c`）：改名为 `作业编号(停用)`，并置 `disabled: true`、`status: 2`，既避免与 `name__ak` 撞名，也让人一眼看出废弃。
4. `query.fields.list` —— 回读确认 `name__ak.name` 已是业务名、自建字段 `status: 2`。

**校验**
- 对象内不存在两个同 `name` 或同 `code` 的字段。
- 唯一性由 `name__ak` 承担，不再给自建字段设 `isUnique`。

**示例**
```json
{ "id": "8b062e08-c65d-2e23-cd69-7d5c265869d0", "name": "作业编号", "code": "name__ak", "source": 2, "status": 1, "disabled": false, "dataType": 1 }
```

**预期**
表单、列表、关联选择器里显示的都是「作业编号」，唯一性由平台名称字段保证；自建重复字段保留但停用，不再出现在表单上。

### listlayout.save 保存列表布局

#### 方案 · 在原有列表布局上改字段，不新建

> 除非明确要求「给这个对象建一个新的列表布局」，否则都改对象已有的那条列表布局（通常只有一条默认布局）。新建会多出一个入口、默认列表反而没变，用户看到的信息和不改一样。

**步骤**
1. `listlayout.list` —— 传 `basicObjectId`，取已有布局（一般就一条，记下 `id`）。
2. `listlayout.columns.get` —— 读当前列，确认要加 / 删哪几个字段。
3. `listlayout.columns.set` —— `POST /api/platform/Listlayout/AddColumns`，体为 `{ listlayoutId, listlayoutColumns: [{ fieldId, fieldPath, sort }] }`，**整组给全量列**（不是增量），`sort` 从 1 递增，系统状态列 `status_id__sys` 放第 1。
4. `listlayout.columns.get` —— 回读列与顺序。

**校验**
- 布局数量没变（没有多出记录）。
- 回读的 `fieldPath` 顺序 = 期望顺序，且首列是 `status_id__sys`。

**示例**
```json
{"listlayoutId":"e1aa392d-1a17-b342-db82-19c4e2a132b8","listlayoutColumns":[{"fieldId":"0166c9db-1be3-9078-194b-907e85ebc0f5","fieldPath":"status_id__sys","sort":1},{"fieldId":"8b062e08-c65d-2e23-cd69-7d5c265869d0","fieldPath":"name__ak","sort":2},{"fieldId":"07b252e0-ab3a-4da1-96f9-dfc170fe80db","fieldPath":"content__c","sort":3}]}
```

**预期**
对象列表页直接显示配置的字段与顺序，不用切视图；布局清单仍然只有原来那一条。

#### 方案 · 开了生命周期的对象，列表必须带 status_id__sys

> 对象一旦 `enableLifeCycle: true`，列表布局里**必须**有系统状态列 `status_id__sys`，否则列表看不出记录走到哪一步。这条在改列时最容易踩：整组覆盖时把它漏掉，页面不报错但状态列就没了。

**步骤**
1. `query.object.get` —— 看 `enableLifeCycle` 是否为 `true`。
2. `listlayout.columns.get` —— 读现有列，检查 `fieldPath === "status_id__sys"` 是否存在。
3. `listlayout.columns.set` —— 缺了就补进整组列里，`sort: 1`，`fieldId` 用字段详情里的 id（`0166c9db-1be3-9078-194b-907e85ebc0f5` 是 homework__c 的）。

**校验**
- 开了生命周期的对象，`Columns` 回读第一列就是 `status_id__sys`。
- 没开生命周期的对象不加这一列（该对象没有这个系统字段）。

**预期**
列表每行都能看到当前状态，配合生命周期流转使用；改列时也不会把它顺手删掉。

### layout.save 保存表单布局

#### 方案 · 在默认布局上改：先建分区，再放字段

> 没指定「新建布局」时一律改对象的默认布局（`isMain: true`）。改表单的第一步不是放字段，而是**先建一个分区**：默认布局自带「工作流时间线」分区（`workflow_time__cs`，type 4），业务字段要放进自己新建的分区（type 1 基本信息）。
> 新分区不能随手编一个 uuid：平台用 `GetStableComponentIds` 把「对象 + 布局 + 组件类型 + 组件 code」映射成稳定 id，本地生成的临时 id 只是用来换这个稳定 id 的。

**步骤**
1. `layout.list` —— 传 `basicObjectId`，取 `isMain` 的那条默认布局（例 `homework_base_layout__ak`）。
2. `layout.detail` —— 读回整份布局，记下已有分区（工作流时间线那份要带全部键原样回传，缺键会报 400）。
3. `layout.stable.ids` —— `POST /api/platform/Layout/GetStableComponentIds`，体 `{ componentIds: { "<临时uuid>": { objectId, layoutCode, componentType: "layout_section", componentCode: "basic_info__cs" } } }`，从 `data.stableComponentIds` 取稳定 id。
4. `layout.save` —— 已有分区整份 + 新分区 `{ id: 稳定id, code: "basic_info__cs", name: "基本信息", type: 1, columnsNum: 2 }`；顶层带 `pages: []`、`rules: []`、`formEditStatus: 0`、`labelCol: 0`、`source: 2`、`status: 1`。
5. `layout.detail` —— 回读确认分区在、控件在。

**校验**
- 回读 `sections` 里新分区 id = `GetStableComponentIds` 返回的稳定 id。
- 默认布局仍 `isMain: true`，布局清单没有多一条。
- 「工作流时间线」分区还在（自带，别删）。

**示例**
```json
{"id":"c85911fc-e302-8187-485b-22eff84f8d81","objectId":"70a49df0-a5b9-2ac8-ff9c-f37758df3381","code":"homework_base_layout__ak","name":"默认布局","labelCol":0,"source":2,"status":1,"objectTypeId":"7dce2368-b02b-a60a-359b-9bfb73ae040e","sections":[{"id":"e19d6af1-ea1c-9f81-8b9d-409d6b95bdbb","code":"workflow_time__cs","name":"工作流时间线","type":4,"sort":1,"hidden":false,"visible":null,"relationId":"00000000-0000-0000-0000-000000000000","relationFilter":[],"listlayoutId":"00000000-0000-0000-0000-000000000000","selectListlayoutId":"00000000-0000-0000-0000-000000000000","selectObjectId":"00000000-0000-0000-0000-000000000000","referenceType":0,"isSimpleRelation":false,"isAssociatedMultipleRecords":false},{"id":"1f117d6f-38ec-db8e-9a0f-3ebf47e08885","code":"basic_info__cs","name":"基本信息","type":1,"columnsNum":2}],"controls":[],"pages":[],"isMain":true,"formEditStatus":0,"rules":[]}
```

**预期**
表单上出现「基本信息」分区，可以把字段控件放进去；默认布局仍是那一条，工作流时间线照常显示。

#### 方案 · 往分区里放字段控件

> 分区建好后再放控件。控件 id 同样要先用 `GetStableComponentIds` 换（`componentType: "layout_control"`、`componentCode` 填字段 code），**`sectionId` 要填分区换出来的稳定 id**，不是建分区时的临时 id。一个分区的控件一次整组提交。

**步骤**
1. 对每个要放的字段用临时 uuid 调 `GetStableComponentIds`（可一次批量传多个），拿回稳定 id。
2. `layout.save` —— `controls` 里每项 `{ id: 稳定id, sectionId: 分区稳定id, code: 字段code, name: 字段名, fieldId, type, gridSpan: 1, attrs }`。
3. `layout.detail` —— 回读 `controls`，确认 `sectionId` 落在新分区下、`type` 对了。

**控件类型对照（实测）**：文本→`AKInput`、多行文本→`AKTextArea`、数字→`AKInputNumber`、日期/日期时间→`AKDateTime`、单选→`AKSelectorSingle`、是否→`AKSelectorYesNo`、关联→`AKSelectorObject`。

**关联控件的 attrs**：`objectId` 与 `listLayoutId` 都要写成**带引号的字符串**（值本身是 json 字符串，序列化后形如 `"\"3a09ccdd-…\""`），`createRecordMode: "3"` 表示可新建关联记录；另可带 `readPrettyShowType: "1"`。

**`listLayoutId` 必须填「被关联对象」的列表布局**，不能图省事填 `00000000-0000-0000-0000-000000000000` 占位——选择器打开时就是按这个列表布局取列的，填错/填零会取不到列，弹窗里一片空白或列全乱。取法：`GET /api/platform/Listlayout/List?objectId=<被关联对象 objectId>`，挑该对象的主列表布局（名字一般是「所有的<对象名>」，如用户对象 = `plat_org_user_table__ak` / `3a175857-27e1-ac0f-14f0-adbfa9724e95`；部门对象同理选部门自己的列表布局）。**自关联**（如「关联上一次作业」指向本对象）则填本对象自己的列表布局。

**示例**
```json
{"controls":[{"id":"cc4c6465-796f-e33f-7733-87cd19bcfc42","sectionId":"1f117d6f-38ec-db8e-9a0f-3ebf47e08885","code":"name__ak","name":"作业编号","fieldId":"8b062e08-c65d-2e23-cd69-7d5c265869d0","type":"AKInput","gridSpan":1,"attrs":{"readPrettyShowType":"1"}},{"id":"458f5b9d-bb83-dff0-d26e-2cacc6c374e2","sectionId":"1f117d6f-38ec-db8e-9a0f-3ebf47e08885","code":"teacher__c","name":"老师","fieldId":"f0b50d24-6405-0cc5-13f2-4fdf87b55d58","type":"AKSelectorObject","gridSpan":1,"attrs":{"readPrettyShowType":"1","objectId":"\"3a09ccdd-2d7a-dfac-4a59-07a50cb8a2a5\"","listLayoutId":"\"3a175857-27e1-ac0f-14f0-adbfa9724e95\"","createRecordMode":"3"}}]}
```

**预期**
分区下按 `gridSpan` 栅格排列控件，表单能录入这些字段；关联控件点开能选已有记录或新建。

#### 方案 · 字段类型怎么选：默认且只用文本（长文本 / 富文本已禁用）

> **一律用文本（1）。长文本（17）、富文本（18）已禁用（2026-11-09 管理员规则）：不再新建、不再使用。** 内容再长也先按文本建；确实需要多行/排版时先跟需求方确认，不要自行改用 17 / 18。公式（14）仅当字段值由其它字段计算得出时才用。
> 平台字段类型枚举（实测）：1 文本 / 2 数字 / 3 布尔 / 4 单选 / 5 日期 / 7 日期时间 / 8 附件 / 10 ID / 11 链接 / 12 邮箱 / 13 查找 / 14 公式 / 15 对象 / 16 父对象 / 17 长文本（禁用） / 18 富文本（禁用） / 19 组件 / 20 统计 / 21 加密文本 / 22 只读文本 / 23 对象多选。

**步骤**
1. `query.fields.list` —— 先看对象下有没有同义字段，避免重复建。
2. `field.save` —— 固定 `dataType: 1`（文本）；`maxLength` 按需（默认即可）。
3. `query.fields.list` —— 回读 `dataType` 确认是 1。

**校验**
- `dataType` 不能是 17 / 18（违例，需停用重建）。
- `dataType === 14` 必须有真实的计算公式，否则就是选错了。

**示例**
```json
{ "name": "作业内容", "code": "content__c", "dataType": 1, "source": 3, "status": 1, "statisticsArrange": { "id": 1 } }
```

**预期**
表单上是普通单行输入框。

#### 方案 · 字段建完就改不了：错了只能停用 + 新建

> **平台没有删字段的接口，字段的 `dataType` 建完也不能改**。类型选错、或建了语义重复的字段，唯一出路是「停用旧的 + 新建一个」：旧字段改名带「(停用)」并置 `status: 2`、`disabled: true`，让它在表单/列表里消失。
> 布局里如果已经放了旧字段的控件，还要同步改 `layout.save` 的 `controls`（控件是独立于字段的，字段停用不会自动摘掉控件）。

**步骤**
1. `field.save` —— **先把旧字段改名停用**：`name` 改成「作业内容(停用)」，`status: 2`、`disabled: true`（其它键按原值回传）。对象内字段**名称也唯一**，不先改名，新字段会报「字段名称重复」。
2. `field.save` —— 再新建正确类型的字段，code 不能与旧的重复（例：`content__c` 选错公式，新建 `content_text__c`、`dataType: 1`）。
3. `query.fields.list` —— 回读：新字段 `status: 1`、旧字段 `status: 2`。
4. `layout.save` —— 旧字段已进布局时，把对应控件从 `controls` 里换掉或删掉。

**校验**
- **不要试图改 `dataType`**，平台会拒绝；也不要想删字段。
- 新旧字段 code 不能重复；改名后的旧字段名也要唯一。
- 停用只是隐藏，历史数据仍挂在旧字段上。

**示例**
```json
{"name":"作业内容","code":"content_text__c","dataType":1,"source":3,"status":1,"statisticsArrange":{"id":1}}
```

**预期**
表单上只剩普通文本框；旧字段留在后台可查历史值，但不再出现。

### lifecycle.status.create 新建生命周期状态

#### 方案 · 复用默认的首尾状态，中间态按流转顺序排

> 生命周期一建出来就自带两个状态：**开启** `init_status__c`（头）和**关闭** `complete_status__c`（尾）。这两个就是状态机的起点和终点，**先把它们改名成业务语义**（作业提交里就是「待提交」和「已通过」），再按需往中间加状态——不要另建两个同义状态，否则会出现「待提交 / 待提交（停用）」这种重复，状态机也读不懂。状态建完**不能删**，只能停用；显示顺序由 `sort` 决定，**按流转顺序排**。

**步骤**
1. `query.lifecycle.status.list` —— 建完对象先看默认两态：`init_status__c`（开启）、`complete_status__c`（关闭），记下 id。
2. `lifecycle.status.update` —— 把这两个**改名**成首尾业务名（作业提交：开启→待提交、关闭→已通过）；`code` 保持不变，`isEnabled: true`，`sort` 给最小/最大值（0 和最后一位）。
3. `lifecycle.status.create` —— 只补中间态（待审核 / 已退回），`workflowCancelStatus` 固定 `11515107-dce6-4ef1-8d51-b1ffed22040f`。
4. `lifecycle.status.update` —— 给每个中间态设 `sort`，按「待提交 → 待审核 → 已退回 → 已通过」这类实际流转顺序递增。
5. `query.lifecycle.status.list` —— 回读名称与顺序，确认没有语义重复的状态。

**校验**
- 状态总数 = 默认 2 个 + 真正需要的中间态；出现同义重复就是建错了（只能停用，不能删）。
- 停用用 `lifecycle.status.update` 的 `isEnabled: false`，**没有删除接口**。
- `sort` 递增且与实际流转顺序一致；停用状态排在最后，别插在中间。
- 工作流动作节点里引用的 `statusId` 必须是**启用中**的状态 id——状态改过名/停用后要回查动作节点。

**示例**
```json
{"name":"待审核","code":"status_pending__c","lifecycleId":"<lifecycleId>","isEnabled":true,"isRecordDeactivate":false,"description":"","source":3,"workflowCancelStatus":"11515107-dce6-4ef1-8d51-b1ffed22040f"}
```

**预期**
状态机是「待提交 → 待审核 → 已退回 / 已通过」四条，按顺序排列；界面上看不出平台默认的两态痕迹，但起点终点仍是那两个系统状态。

### menu.submit 新建 / 更新菜单

#### 方案 · 给对象建入口菜单：母菜单 + 子菜单

> 对象建完、布局配好后，用户要在侧边栏点进去。菜单是两级的：先建**母菜单**（`menuActionType: 3`，相当于分组），再建**子菜单**（`menuActionType: 1`）挂到母菜单下。子菜单必须挂齐对象、列表布局、表单布局三样，用户点进去才是「能看列表、能新建、表单字段正确」的入口。
> 顶层母菜单的 `parentMenuId` 留空；它出现在「所有菜单」分组下，权限再按角色放开。

**步骤**
1. `menu.submit` —— 建母菜单：`{ name, code, menuActionType: 3, source: 2, menuType: 1, status: 1, backgroundColor: "#366EF4", childShowType: null }`，返回 `data.Id`。
2. `menu.submit` —— 建子菜单：`{ name, code, menuActionType: 1, parentMenuId: <第 1 步的 id>, source: 2, menuType: 1, status: 1, objectId, listLayoutId, layoutId, createType: 4, childShowType: null }`。
3. `menu.group.list` —— 读分组清单确认母菜单挂在哪组；或用 `GET /api/platform/Menu/GetMenuList` 按 code 读回两级记录。

**校验**
- 子菜单回读的 `objectId` / `listLayoutId` / `layoutId` 三样都不为空，`createType = 4`。
- 子菜单的 `parentMenuId` 等于母菜单 id；母菜单 `parentMenuId` 为空。
- 侧边栏能看到「母菜单 → 子菜单」，点开是对象列表页。

**示例**
```json
{"name":"作业提交","code":"homework_submit__c","menuActionType":1,"parentMenuId":"6c7ad784-002a-67cc-d934-3c48870e98cc","source":2,"menuType":1,"status":1,"objectId":"70a49df0-a5b9-2ac8-ff9c-f37758df3381","listLayoutId":"e1aa392d-1a17-b342-db82-19c4e2a132b8","layoutId":"c85911fc-e302-8187-485b-22eff84f8d81","createType":4,"childShowType":null}
```

**预期**
侧边栏出现「作业管理 → 作业提交」，点进去是作业列表，右上角能新建作业提交单，表单里是基本信息分区 + 配置好的字段。新菜单默认只对管理员可见，普通角色要去角色/菜单权限里授权。

### workflow.create 新建工作流

#### 方案 · 标准审核工作流：开始 → 老师审核 → 判断 → 双动作 → 结束

> 一条「提交后交给某人审核、通过/拒绝各回写一个状态」的流程，标准骨架就是六个节点：开始（stepType 10）→ 任务（30）→ 判断（70）→ 两个动作（90）→ 结束（20）。2026-11-09 管理员演示的「作业提交-标准审核工作流」（`aa__c`，config `6ab05534-1e0c-576e-34cb-3a24d1d916aa`）就是这个形状，下面按它记录。
> **重要前提**：工作流发布后**不会自己触发**，必须在对象/状态上挂「动作」把它拉起（动作类型 `behaviorType: 7` 触发工作流，`behaviorValue.workflowId` 填 workflowBasicId）。同一个对象可以同时存在多条已发布流程，互不冲突，谁被动作挂上谁才跑。

**步骤**
1. `workflow.create` —— 建编辑态流程：`status: 40`、`workflowType: 10`、`isSingleRecord: true`、`objectId`、`lifecycleId`；返回 `workflowConfigId`（同时记住 `workflowBasicId`，挂动作要用）。
2. `workflow.start.update` —— 开始节点：参与者控件用「从对象字段取人」，`selectUserType: 40`、`fielsObjectIds: [{ id: <字段id>, objectId, name, code }]`，发起时按该字段解析审批人，发起人不用手选。（开始节点参与者还有其它形式，管理员后续补充。）
3. `workflow.task.add` —— 任务节点（stepType 30）：16 键 `stepTaskConfig`，`dispatchMode: 10`（系统指派）、`taskRequireType: 20`（必须完成）、`isRequireApproval: true`、`userControlIds` 填开始节点那个参与者控件的 id（**字符串**，不是数组）、`taskFields` 挂审批时可见的对象字段（不挂的话老师看不到作业内容）。
   - **任务提醒**：「任务提醒方式」下拉里选「使用提醒策略」，对应 `notifyType: -10`（按 `aa__c` 流程回读的值核对；其它选项的值等遇到再补）。
4. `workflow.task.add` 的 `stepTaskApprovals` —— 两个按钮：`同意`（sort 0）、`拒绝`（sort 1）。**审批意见里必须带电子签名，签名栏由下面这组开关控制**（对应界面「审批意见 → 需要电子签名 / 需要填写签名备注 / 需要填写签名含义 / 需要选择职位」）：
   - `isRequireSign: true` + `isHaveSign: true` —— 需要电子签名；`isRequireUserName: false`、`enableDigitalIdentityAuth: false`（用户名、数字身份认证不勾）。
   - `isShowResons: true` —— 需要填写签名备注；`resonTitle: "签名备注"`；`reasonInputType: 20`（输入类型：填写）；`isRequiredResons`（备注必填）：同意 `false`、拒绝 `true`。
   - `isShowResponsibilities: true` + `isRequireResponsibilities: true` —— 需要填写签名含义；`responsibieTitle: "签名含义"`；含义选项写进 `responsibleOptions[0].value`（同意「同意提交的作业」/ 拒绝「拒绝本次作业」）。
   - **`isRequirePosition: true` —— 需要选择职位**（标准审批意见签名必须勾这一项）。
   - 任务级签名（`stepTaskConfig.isRequireSign`）保持 `false`，签名只在审批意见上做。
5. `workflow.decision.add` —— 判断节点（stepType 70）：`rules[0]` 的条件 `targetType: 7`、`targetId` 指**任务节点** id、`logicType: 40`、`logicValue` 是**带引号的「同意」按钮 id**（形如 `"\"0d86903b-…\""`，序列化后是 38 字符带引号串）；`rules[0].nextStepId` 指「已通过」动作，`stepDecision.nextStepId`（else）指「已退回」动作。
6. `workflow.action.add` —— 两个动作节点（stepType 90）：`stepAction.actions[0].configs[0] = { behaviorType: 9, behaviorValue: { statusId } }`，`statusId` 必须是**启用中**的状态 id（作业提交里：已通过 `5ff2f178…`、已退回 `a077aead…`），`nextStepId` 都指结束节点。
7. `workflow.status.change` —— 发布：`{ ids: [workflowConfigId], status: 20, workflowBasicId }`。

**校验**
- `workflow.steps.list` 回读六节点，`nextStepId` 首尾串通：开始→任务→判断，判断 `rules[0]`→已通过、else→已退回，两个动作→结束。
- 任务节点回读 `userControlIds` 不为空；按钮回读 `isRequireSign: true`、`isShowResons: true`、`isShowResponsibilities: true`、`isRequirePosition: true`。
- 审批意见签名四件套齐全：电子签名、签名备注（拒绝必填）、签名含义（必填）、选择职位。
- 任务提醒方式回读 `notifyType: -10`（使用提醒策略）。
- 动作节点 `statusId` 指向的状态 `isEnabled: true`。
- 发布后 `status = 20`；再去挂触发动作（`behaviorType: 7`），否则流程永远不会跑。

**示例**
```json
{"stepAction":{"belongType":3,"actions":[{"code":"","name":"","isEnabled":true,"belongType":3,"configs":[{"behaviorType":9,"behaviorValue":{"statusId":"5ff2f178-fec4-3144-dcf5-eedacd4aa22f"},"sort":0}],"sort":0,"executeType":1,"description":"","lifecycleId":"","lifecycleStatusId":""}]}}
```

**预期**
对象上出现一条可被动作触发的审批流程：提交后系统按字段指派老师，老师收到待办提醒，点同意/拒绝时填审批意见并电子签名，通过置「已通过」、拒绝置「已退回」。

#### 方案 · 提醒工作流：只提醒、不审批，由进入动作触发

> 除了审批工作流，还有一类**提醒工作流**：不设审批、不阻断流程，只在某个时点给参与人推一条提醒任务。典型场景：作业提交生命周期里老师「退回」，系统给提交作业的学生推一条提醒，告诉他作业被退回了、要重新提交。
> 触发方式与审批流不同：提醒流一般由**进入动作**触发，因此必须勾选「允许从进入动作和事件动作自动启动」。

**步骤**
1. `workflow.create` —— 建编辑态流程（`status: 40`），对象、生命周期按要挂的入口选；工作流级 `isAllowTrigger: true` 就是「允许从进入动作和事件动作自动启动」这个开关（不勾默认 false）。
2. `workflow.start.update` —— 开始节点：参与者用「从对象字段取人」，`selectUserType: 40` + `fielsObjectIds`（示例取 `created_by__sys` 创建人，控件的 `code` 起个可读名如 `sf__c`），这样提醒对象自动是发起人，不用手选。
3. `workflow.task.add` —— 任务节点（stepType 30）配成**提醒任务**：`isNotifyTaskType: true`、`isRequireApproval: false`、`stepTaskApprovals: []`（不配任何审批按钮）；`userControlIds` 填开始节点参与者控件 id（字符串）、`dispatchMode: 10`（系统指派）、`taskRequireType: 20`、`notifyType: -10`（任务提醒方式：使用提醒策略）。任务名直接写提醒语，如「请修改作业后重新提交」。
4. 链路只保留「开始 → 提醒任务 → 结束」，不配判断、不配动作（不改变状态）。
5. `workflow.status.change` —— 发布（`status: 20`）。
6. 到「生命周期 → 进入动作」里挂 `behaviorType: 7` 的动作，`behaviorValue.workflowId` 填 workflowBasicId。

**校验**
- 工作流回读 `isAllowTrigger: true`（「允许从进入动作和事件动作自动启动」已勾）。
- **该开关一旦勾选并启用，后续无法取消** —— 这是不可逆项，上线前确认清楚。
- 提醒任务回读 `isNotifyTaskType: true`、`isRequireApproval: false`、`stepTaskApprovals` 为空。
- 发布后在对应生命周期的进入动作里能看到这条流程；触发后当事人收到提醒任务。

**示例**
```json
{"stepTaskConfig":{"taskNodeType":0,"dispatchMode":10,"taskRequireType":20,"isNotifyTaskType":true,"isRequireApproval":false,"userControlIds":"<开始节点参与者控件id>","notifyType":-10,"taskFields":[]}}
```

**预期**
老师退回作业后，学生收到一条「请修改作业后重新提交」的提醒任务，流程本身不改变状态、不需要任何人审批。实例：`作业提交` / `df__c`（config `2d6aac69-4a54-d69c-548e-3a24d1f0d7dd`，basic `d3cd2559-2f43-d5a0-2063-3a24d1ee2875`，三个节点：`df_Start__c` → `sadfasdf__c`「任务：请修改作业后重新提交」→ `df_End__c`）。

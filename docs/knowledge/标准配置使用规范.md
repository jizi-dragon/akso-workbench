# 标准配置使用规范

> 记录「一类配置怎么用接口一步步做出来」的成文方案：一个需要同意 / 驳回的审批节点该怎么配、一个只提醒不要求完成的任务节点该怎么配，等等。
>
> 这份文档**由人指定补写**——只有已经定稿的配置类型才写成方案，不是每个接口都有方案。工具卡片上的「标准配置用法」一栏就从这里读，改完**刷新页面**即生效，不用重新构建。
>
> 方案是「照做」的步骤；至于一套配置该先配什么、蓝图怎么画、什么时候找人审一次，看 `标准配置思路规范.md`。

## 怎么写

- `### <capability id>` —— 方案挂在哪个接口的卡片下，id 用能力目录里的那个（如 `workflow.task.add`）。
- `#### 方案 · <名字>` —— 一个方案一块，同一个接口可以有多块。
- `>` 开头的引用块 —— 一句话说明这个方案解决什么。
- `**步骤**` —— 有序列表，每一步开头用反引号写接口 id，后面写这一步做什么。
- `**校验**` —— 列表，写回读 / 核对的方法。
- `**示例**` —— 一个 json 代码块，写主请求体（可省；示意为主，字段以先读后写为准）。
- `**预期**` —— 一两句话写跑完应该看到什么。

## 已收录

### layout.save 保存对象布局

#### 方案 · 新增一个分区并放置控件

> 已有布局要加一块「基本信息」，把两个字段放进新分区，不动原有分区。

**步骤**
1. `layout.detail` —— 读回当前布局，拿到 sections 与 controls 的 id 与顺序。
2. `layout.save` —— 在原 sections **数组末尾**追加新 section，`sort` 取现有最大 `sort + 1`（平台按数组顺序归一化 sort，不能插到第一位）；只需 `id` / `code` / `name` / `type` / `columnsNum`，**不要**带 `belongId` / `fullPath`；再追加 control（`sectionId` 指向新分区）。
3. `layout.detail` —— 回读，确认分区与控件都在、顺序符合预期。

**校验**
- 回读 sections 数量 +1、controls 数量 +N。
- 新分区在 sections 数组末尾，旧分区顺序不变（2026-11-21 实测：插到第一位会导致「基础信息」跑到「工作流时间线」前面）。
- 新控件的 `sectionId` 指向新分区，没有被并到旧分区里。

**示例**
```json
{
  "id": "<layoutId>",
  "sections": [
    { "id": "<existingSectionId>", "code": "base", "name": "基本信息", "type": 1, "columnsNum": 1 },
    { "id": "<newSectionId>", "code": "attach", "name": "附件", "type": 1, "columnsNum": 1 }
  ],
  "controls": [
    { "id": "<newControlId>", "sectionId": "<newSectionId>", "code": "attach_file", "name": "附件", "fieldId": "<fieldId>", "type": 1, "gridSpan": 1, "attrs": {} }
  ]
}
```

**预期**
- 返回 `data` 是布局 id 字符串；回读的 sections / controls 与提交一致。

### object.save 新建对象

#### 方案 · 建对象时默认开生命周期与电子签名

> 新建业务对象时把状态机与电子签名一起打开：生命周期一旦开启就不可逆，所以这两个开关要在**建对象那一次**定下来，事后补要另走更新接口。

**步骤**
1. `object.save` —— `source: 3`、`objectClass: 1`、`status: 1`，同时带 `enableLifeCycle: true` 与 `enableSignatures: true`。
2. `query.object.get` —— 按 `code` 反查，确认两个开关都是 `true`（这个接口不回 objectId）。
3. `lifecycle.status.create` —— 需要自定义状态时接在后面建（平台自带「开启」「关闭」两态）。

**校验**
- 回读 `enableLifeCycle === true` 且 `enableSignatures === true`。
- 电子签名开了之后，审批 / 动作类节点才能配签批。

**示例**
```json
{ "name": "作业提交", "code": "homework__c", "source": 3, "status": 1, "objectClass": 1, "enableLifeCycle": true, "enableSignatures": true, "summaryFields": [] }
```

**预期**
对象建出来即带状态机与电子签名；后续加字段、布局、工作流都基于它。

### field.save 新建 / 更新字段

#### 方案 · 唯一字段用 name__ak 承载

> 每个对象自带一个 `name__ak`（名称）字段，它是配置字段里唯一特殊的一个：对象内的唯一性交给它。已经建了同义的自建字段（比如 `no__c`），先把自建字段停用，再把 `name__ak` 的名字改过来——同一对象内字段 name 与 code 都不能重复，所以必须改名，光停用不够。
> 平台 UI 停用/启用字段走的是 `POST /api/platform/BasicObject/EnableField`，体是 `{ id, status }`（`status: 1` 启用、`2` 停用）。

**步骤**
1. `query.fields.list` —— 先看对象下现有 name / code，确认没有同名字段，顺便拿到 `name__ak` 的 id。
2. `field.save` —— 更新 `name__ak`：回传整份字段（`id`、`code: "name__ak"`、`source: 2`、`status: 1`、`disabled: false` 等），只把 `name` 改成业务名（例：作业编号）；`code` 保持 `name__ak` 不动。
3. `field.save` —— 若已有自建唯一字段（例 `no__c`）：改名为 `作业编号(停用)`，并置 `disabled: true`、`status: 2`，既避免与 `name__ak` 撞名，也让人一眼看出废弃。
4. `query.fields.list` —— 回读确认 `name__ak.name` 已是业务名、自建字段 `status: 2`。

**校验**
- 对象内不存在两个同 `name` 或同 `code` 的字段。
- 唯一性由 `name__ak` 承担，不再给自建字段设 `isUnique`。
- 新建字段时除 `name__ak` 外，`isRequired` 必须为 false；是否必填在表单布局里控制（2026-11-21 用户规则）。

**示例**
```json
{ "id": "8b062e08-c65d-2e23-cd69-7d5c265869d0", "name": "作业编号", "code": "name__ak", "source": 2, "status": 1, "disabled": false, "dataType": 1 }
```

**预期**
表单、列表、关联选择器里显示的都是「作业编号」，唯一性由平台名称字段保证；自建重复字段保留但停用，不再出现在表单上。

### listlayout.save 保存列表布局

#### 方案 · 在原有列表布局上改字段，不新建

> 除非明确要求「给这个对象建一个新的列表布局」，否则都改对象已有的那条列表布局（通常只有一条默认布局）。新建会多出一个入口、默认列表反而没变，用户看到的信息和不改一样。

**步骤**
1. `listlayout.list` —— 传 `basicObjectId`，取已有布局（一般就一条，记下 `id`）。
2. `listlayout.columns.get` —— 读当前列，确认要加 / 删哪几个字段。
3. `listlayout.columns.set` —— `POST /api/platform/Listlayout/AddColumns`，体为 `{ listlayoutId, listlayoutColumns: [{ fieldId, fieldPath, sort }] }`，**整组给全量列**（不是增量），`sort` 从 1 递增，系统状态列 `status_id__sys` 放第 1。
4. `listlayout.columns.get` —— 回读列与顺序。

**校验**
- 布局数量没变（没有多出记录）。
- 回读的 `fieldPath` 顺序 = 期望顺序，且首列是 `status_id__sys`。

**示例**
```json
{"listlayoutId":"e1aa392d-1a17-b342-db82-19c4e2a132b8","listlayoutColumns":[{"fieldId":"0166c9db-1be3-9078-194b-907e85ebc0f5","fieldPath":"status_id__sys","sort":1},{"fieldId":"8b062e08-c65d-2e23-cd69-7d5c265869d0","fieldPath":"name__ak","sort":2},{"fieldId":"07b252e0-ab3a-4da1-96f9-dfc170fe80db","fieldPath":"content__c","sort":3}]}
```

**预期**
对象列表页直接显示配置的字段与顺序，不用切视图；布局清单仍然只有原来那一条。

#### 方案 · 开了生命周期的对象，列表必须带 status_id__sys

> 对象一旦 `enableLifeCycle: true`，列表布局里**必须**有系统状态列 `status_id__sys`，否则列表看不出记录走到哪一步。这条在改列时最容易踩：整组覆盖时把它漏掉，页面不报错但状态列就没了。

**步骤**
1. `query.object.get` —— 看 `enableLifeCycle` 是否为 `true`。
2. `listlayout.columns.get` —— 读现有列，检查 `fieldPath === "status_id__sys"` 是否存在。
3. `listlayout.columns.set` —— 缺了就补进整组列里，`sort: 1`，`fieldId` 用字段详情里的 id（`0166c9db-1be3-9078-194b-907e85ebc0f5` 是 homework__c 的）。

**校验**
- 开了生命周期的对象，`Columns` 回读第一列就是 `status_id__sys`。
- 没开生命周期的对象不加这一列（该对象没有这个系统字段）。

**预期**
列表每行都能看到当前状态，配合生命周期流转使用；改列时也不会把它顺手删掉。

### layout.save 保存表单布局

#### 方案 · 在默认布局上改：先建分区，再放字段

> 没指定「新建布局」时一律改对象的默认布局（`isMain: true`）。改表单的第一步不是放字段，而是**先建一个分区**：默认布局自带「工作流时间线」分区（`workflow_time__cs`，type 4），业务字段要放进自己新建的分区（type 1 基本信息）。
> 新分区不能随手编一个 uuid：平台用 `GetStableComponentIds` 把「对象 + 布局 + 组件类型 + 组件 code」映射成稳定 id，本地生成的临时 id 只是用来换这个稳定 id 的。

**步骤**
1. `layout.list` —— 传 `basicObjectId`，取 `isMain` 的那条默认布局（例 `homework_base_layout__ak`）。
2. `layout.detail` —— 读回整份布局，记下已有分区（工作流时间线那份要带全部键原样回传，缺键会报 400）。
3. `layout.stable.ids` —— `POST /api/platform/Layout/GetStableComponentIds`，体 `{ componentIds: { "<临时uuid>": { objectId, layoutCode, componentType: "layout_section", componentCode: "basic_info__cs" } } }`，从 `data.stableComponentIds` 取稳定 id。
4. `layout.save` —— 已有分区整份 + 新分区放在 `sections` **数组末尾**，`sort` 取现有最大 `sort + 1`；新分区 `{ id: 稳定id, code: "basic_info__cs", name: "基本信息", type: 1, columnsNum: 2 }`；顶层带 `pages: []`、`rules: []`、`formEditStatus: 0`、`labelCol: 0`、`source: 2`、`status: 1`。
5. `layout.detail` —— 回读确认分区在、控件在、顺序正确。

**校验**
- 回读 `sections` 里新分区 id = `GetStableComponentIds` 返回的稳定 id。
- 默认布局仍 `isMain: true`，布局清单没有多一条。
- 「工作流时间线」分区还在（自带，别删），且仍是第一块；新分区在它之后（2026-11-21 实测）。

**示例**
```json
{"id":"c85911fc-e302-8187-485b-22eff84f8d81","objectId":"70a49df0-a5b9-2ac8-ff9c-f37758df3381","code":"homework_base_layout__ak","name":"默认布局","labelCol":0,"source":2,"status":1,"objectTypeId":"7dce2368-b02b-a60a-359b-9bfb73ae040e","sections":[{"id":"e19d6af1-ea1c-9f81-8b9d-409d6b95bdbb","code":"workflow_time__cs","name":"工作流时间线","type":4,"sort":1,"hidden":false,"visible":null,"relationId":"00000000-0000-0000-0000-000000000000","relationFilter":[],"listlayoutId":"00000000-0000-0000-0000-000000000000","selectListlayoutId":"00000000-0000-0000-0000-000000000000","selectObjectId":"00000000-0000-0000-0000-000000000000","referenceType":0,"isSimpleRelation":false,"isAssociatedMultipleRecords":false},{"id":"1f117d6f-38ec-db8e-9a0f-3ebf47e08885","code":"basic_info__cs","name":"基本信息","type":1,"columnsNum":2}],"controls":[],"pages":[],"isMain":true,"formEditStatus":0,"rules":[]}
```

**预期**
表单上出现「基本信息」分区，可以把字段控件放进去；默认布局仍是那一条，工作流时间线照常显示。

#### 方案 · 往分区里放字段控件

> 分区建好后再放控件。控件 id 同样要先用 `GetStableComponentIds` 换（`componentType: "layout_control"`、`componentCode` 填字段 code），**`sectionId` 要填分区换出来的稳定 id**，不是建分区时的临时 id。一个分区的控件一次整组提交。

**步骤**
1. 对每个要放的字段用临时 uuid 调 `GetStableComponentIds`（可一次批量传多个），拿回稳定 id。
2. `layout.save` —— `controls` 里每项 `{ id: 稳定id, sectionId: 分区稳定id, code: 字段code, name: 字段名, fieldId, type, gridSpan: 1, attrs }`。
3. `layout.detail` —— 回读 `controls`，确认 `sectionId` 落在新分区下、`type` 对了。

**控件类型对照（实测）**：文本→`AKInput`、多行文本→`AKTextArea`、数字→`AKInputNumber`、日期/日期时间→`AKDateTime`、单选→`AKSelectorSingle`、是否→`AKSelectorYesNo`、关联→`AKSelectorObject`。

**关联控件的 attrs**：`objectId` 与 `listLayoutId` 都要写成**带引号的字符串**（值本身是 json 字符串，序列化后形如 `"\"3a09ccdd-…\""`），`createRecordMode: "3"` 表示可新建关联记录；另可带 `readPrettyShowType: "1"`。

**`listLayoutId` 必须填「被关联对象」的列表布局**，不能图省事填 `00000000-0000-0000-0000-000000000000` 占位——选择器打开时就是按这个列表布局取列的，填错/填零会取不到列，弹窗里一片空白或列全乱。取法：`GET /api/platform/Listlayout/List?objectId=<被关联对象 objectId>`，挑该对象的主列表布局（名字一般是「所有的<对象名>」，如用户对象 = `plat_org_user_table__ak` / `3a175857-27e1-ac0f-14f0-adbfa9724e95`；部门对象同理选部门自己的列表布局）。**自关联**（如「关联上一次作业」指向本对象）则填本对象自己的列表布局。

**三项必须齐、否则只保存不生效**：`objectId`、`listLayoutId`、`createRecordMode` 缺任一，`layout.save` 仍返回成功，但界面上「列表布局 / 创建记录方式」是空的，等于配置没配。引擎出计划时就拦：缺项 `LAYOUT_OBJECT_CONTROL_ATTRS_MISSING`，`listLayoutId` 不属于该对象 `LAYOUT_OBJECT_CONTROL_LAYOUT_UNKNOWN`（2026-11-27）。

**记录为可能发生的情况（2026-11-27 现场反馈）**：用户打开该控件设置时看到这三项是空的；抓包核对 3 次 `Layout/SaveLayoutDetail` 请求体，三项一直都在且三次语义完全一致（只有 attrs 键顺序变化），与平台 UI 建的同类控件写法也一致。暂按「偶发显示问题」记录，不认定为写入丢失；再遇到先抓包比对请求体，不要急着重写布局。

**示例**
```json
{"controls":[{"id":"cc4c6465-796f-e33f-7733-87cd19bcfc42","sectionId":"1f117d6f-38ec-db8e-9a0f-3ebf47e08885","code":"name__ak","name":"作业编号","fieldId":"8b062e08-c65d-2e23-cd69-7d5c265869d0","type":"AKInput","gridSpan":1,"attrs":{"readPrettyShowType":"1"}},{"id":"458f5b9d-bb83-dff0-d26e-2cacc6c374e2","sectionId":"1f117d6f-38ec-db8e-9a0f-3ebf47e08885","code":"teacher__c","name":"老师","fieldId":"f0b50d24-6405-0cc5-13f2-4fdf87b55d58","type":"AKSelectorObject","gridSpan":1,"attrs":{"readPrettyShowType":"1","objectId":"\"3a09ccdd-2d7a-dfac-4a59-07a50cb8a2a5\"","listLayoutId":"\"3a175857-27e1-ac0f-14f0-adbfa9724e95\"","createRecordMode":"3"}}]}
```

**预期**
分区下按 `gridSpan` 栅格排列控件，表单能录入这些字段；关联控件点开能选已有记录或新建。

#### 方案 · 字段类型怎么选：默认且只用文本（长文本 / 富文本已禁用）

> **一律用文本（1）。长文本（17）、富文本（18）已禁用（2026-11-09 管理员规则）：不再新建、不再使用。** 内容再长也先按文本建；确实需要多行/排版时先跟需求方确认，不要自行改用 17 / 18。公式（14）仅当字段值由其它字段计算得出时才用。
> 平台字段类型枚举（实测）：1 文本 / 2 数字 / 3 布尔 / 4 单选 / 5 日期 / 7 日期时间 / 8 附件 / 10 ID / 11 链接 / 12 邮箱 / 13 查找 / 14 公式 / 15 对象 / 16 父对象 / 17 长文本（禁用） / 18 富文本（禁用） / 19 组件 / 20 统计 / 21 加密文本 / 22 只读文本 / 23 对象多选。

**步骤**
1. `query.fields.list` —— 先看对象下有没有同义字段，避免重复建。
2. `field.save` —— 固定 `dataType: 1`（文本）；`maxLength` 按需（默认即可）。
3. `query.fields.list` —— 回读 `dataType` 确认是 1。

**校验**
- `dataType` 不能是 17 / 18（违例，需停用重建）。
- `dataType === 14` 必须有真实的计算公式，否则就是选错了。

**示例**
```json
{ "name": "作业内容", "code": "content__c", "dataType": 1, "source": 3, "status": 1, "statisticsArrange": { "id": 1 } }
```

**预期**
表单上是普通单行输入框。

#### 方案 · 字段建完就改不了：错了只能停用 + 新建

> **平台没有删字段的接口，字段的 `dataType` 建完也不能改**。类型选错、或建了语义重复的字段，唯一出路是「停用旧的 + 新建一个」：旧字段改名带「(停用)」并置 `status: 2`、`disabled: true`，让它在表单/列表里消失。
> 布局里如果已经放了旧字段的控件，还要同步改 `layout.save` 的 `controls`（控件是独立于字段的，字段停用不会自动摘掉控件）。

**步骤**
1. `field.save` —— **先把旧字段改名停用**：`name` 改成「作业内容(停用)」，`status: 2`、`disabled: true`（其它键按原值回传）。对象内字段**名称也唯一**，不先改名，新字段会报「字段名称重复」。
2. `field.save` —— 再新建正确类型的字段，code 不能与旧的重复（例：`content__c` 选错公式，新建 `content_text__c`、`dataType: 1`）。
3. `query.fields.list` —— 回读：新字段 `status: 1`、旧字段 `status: 2`。
4. `layout.save` —— 旧字段已进布局时，把对应控件从 `controls` 里换掉或删掉。

**校验**
- **不要试图改 `dataType`**，平台会拒绝；也不要想删字段。
- 新旧字段 code 不能重复；改名后的旧字段名也要唯一。
- 停用只是隐藏，历史数据仍挂在旧字段上。

**示例**
```json
{"name":"作业内容","code":"content_text__c","dataType":1,"source":3,"status":1,"statisticsArrange":{"id":1}}
```

**预期**
表单上只剩普通文本框；旧字段留在后台可查历史值，但不再出现。

### lifecycle.status.create 新建生命周期状态

#### 方案 · 复用默认的首尾状态，中间态按流转顺序排

> 生命周期一建出来就自带两个状态：**开启** `init_status__c`（头）和**关闭** `complete_status__c`（尾）。这两个就是状态机的起点和终点，**先把它们改名成业务语义**（作业提交里就是「待提交」和「已通过」），再按需往中间加状态——不要另建两个同义状态，否则会出现「待提交 / 待提交（停用）」这种重复，状态机也读不懂。状态建完**不能删**，只能停用；显示顺序由 `sort` 决定，**按流转顺序排**。

**步骤**
1. `query.lifecycle.status.list` —— 建完对象先看默认两态：`init_status__c`（开启）、`complete_status__c`（关闭），记下 id。
2. `lifecycle.status.update` —— 把这两个**改名**成首尾业务名（作业提交：开启→待提交、关闭→已通过）；`code` 保持不变，`isEnabled: true`，`sort` 给最小/最大值（0 和最后一位）。
3. `lifecycle.status.create` —— 只补中间态（待审核 / 已退回），`workflowCancelStatus` 固定 `11515107-dce6-4ef1-8d51-b1ffed22040f`。
4. `lifecycle.status.update` —— 给每个中间态设 `sort`，按「待提交 → 待审核 → 已退回 → 已通过」这类实际流转顺序递增。
5. `query.lifecycle.status.list` —— 回读名称与顺序，确认没有语义重复的状态。

**校验**
- 状态总数 = 默认 2 个 + 真正需要的中间态；出现同义重复就是建错了（只能停用，不能删）。
- 停用用 `lifecycle.status.update` 的 `isEnabled: false`，**没有删除接口**。
- `sort` 递增且与实际流转顺序一致；停用状态排在最后，别插在中间。
- 工作流动作节点里引用的 `statusId` 必须是**启用中**的状态 id——状态改过名/停用后要回查动作节点。

**示例**
```json
{"name":"待审核","code":"status_pending__c","lifecycleId":"<lifecycleId>","isEnabled":true,"isRecordDeactivate":false,"description":"","source":3,"workflowCancelStatus":"11515107-dce6-4ef1-8d51-b1ffed22040f"}
```

**预期**
状态机是「待提交 → 待审核 → 已退回 / 已通过」四条，按顺序排列；界面上看不出平台默认的两态痕迹，但起点终点仍是那两个系统状态。

### lifecycle.status.sort 调整生命周期状态顺序

#### 方案 · 状态建完/改名后按流转顺序收口

> 平台只按 `sort` 显示状态，而 `lifecycle.status.update` 的 `sort` **不落库**（2026-11-26 三次实测、2026-11-27 复核）；顺序必须在所有状态都建好之后，用这条接口一次性收口——尤其「关闭」`complete_status__c` 这类默认尾态，建对象时就占了第二个槽位。

**步骤**
1. `query.lifecycle.status.config.list` —— 读全量状态，客户端按 lifecycleId 过滤，得到每个状态的 id / name / code / sort。
2. 按业务流转顺序排出目标顺序（如 待提交 → 待审批 → 已通过 → 已退回 → 已完成），`sort` 从 0 递增；**该生命周期下全部状态都要带上**，包含停用态。
3. `lifecycle.status.sort` —— 提交裸数组 `[{id, sort}]`。
4. `query.lifecycle.status.config.list` —— 回读按 sort 排好序的名字序列，必须与目标顺序一致。

**校验**
- 回读顺序 = 目标顺序；漏带的状态会被平台挤到后面，重排一次即可。
- 初始状态 `init_status__c` 排第一、终止态排最后，中间态按实际流转顺序排。
- 已发布工作流动作节点里的 `statusId` 不受排序影响，但界面上的按钮会跟着状态位置移动。

**示例**
```json
{"statuses":[{"id":"<init>","sort":0},{"id":"<pending>","sort":1},{"id":"<approved>","sort":2},{"id":"<returned>","sort":3},{"id":"<complete>","sort":4}]}
```

**预期**
状态机在界面上按业务顺序排列，不再出现「已完成」夹在「待提交」后面这种默认布局。

### lifecycle.useraction.create 新建状态按钮（含动作）

#### 方案 · 作业提交 2.0：三处挂载闭环（提交 / 退回提醒 / 重新提交）

> 对象 `homework__c`，生命周期「待提交 → 待审核 → 已退回 / 已通过」。三处动作各管一段：待提交的用户动作拉起审核流；已退回的进入动作拉起提醒流；已退回的用户动作再次拉起审核流。两个 Create 都不合并，先查重再建，建完回读。
> 关键边界：按钮上的 `enableSignatures` 只是入口，**发起人电子签名在审核流的开始节点控件**；`isAllowTrigger` 是工作流级「允许从进入动作/事件动作自动启动」，审批流保持 false，不要为了签名误开。

**步骤**
1. `lifecycle.useraction.list` —— 按待提交、已退回的状态 id 查已有按钮；再 `lifecycle.enteraction.list` 查已退回的进入动作，按 `code` 查重。
2. `lifecycle.useraction.create` —— 待提交「提交」：`belongType: 2`，`configs[0].behaviorType: 7`，`workflowId` 填审核流 workflowBasicId。
3. `lifecycle.enteraction.create` —— 已退回进入动作：`belongType: 1`，`behaviorType: 7`，`workflowId` 填提醒流 basicId；提醒流必须已发布且 `isAllowTrigger: true`。
4. `lifecycle.useraction.create` —— 已退回「重新提交」：同待提交按钮，仍绑审核流；`code` 用稳定业务码，别用演示值。
5. `lifecycle.useraction.list` / `lifecycle.enteraction.list` —— 回读两状态上的按钮与进入动作，确认 `code`、`workflowId`、`belongType` 对得上。

**校验**
- 待提交按钮 `belongType: 2`、`behaviorType: 7`，`workflowId` = 审核流 basicId。
- 已退回进入动作 `belongType: 1`、`behaviorType: 7`，`workflowId` = 提醒流 basicId；该流程 `isAllowTrigger: true`。
- 已退回重新提交按钮 `belongType: 2`、`behaviorType: 7`，仍指向审核流。
- 审核流开始节点有电子签名控件；`enableSignatures` 不作为“必签”判据。
- 三个 Create 都返回 id；回读无重复 code。

**示例**
```json
{"isEnabled":true,"belongId":"<statusId>","belongType":2,"sort":1,"executeType":1,"description":"学生提交作业","lifecycleId":"<lifecycleId>","lifecycleStatusId":"<statusId>","executionConditionGroups":[],"basicObjectId":"<objectId>","objectCode":"homework__c","enableSignatures":true,"actions":[{"name":"提交","code":"submit_homework","sort":0,"configs":[{"behaviorType":7,"behaviorValue":{"isBeforeWorkflowCompleteReminderTask":true,"workflowId":"<workflowBasicId>"},"sort":0}]}]}
```

**预期**
待提交出现「提交」，已退回出现「重新提交」；学生点提交进审核流并签发起人签名，老师通过/退回后状态回到已通过/已退回；退回时进入动作自动拉起提醒流。

### lifecycle.enteraction.create 新建进入动作（触发流程）

#### 方案 · 已退回：进入动作拉起提醒流

> 提醒流只发提醒、不审批，工作流级必须 `isAllowTrigger: true`（启用后不可逆）；进入动作本身 `belongType: 1`，和状态按钮的 `2` 区分开。

**步骤**
1. `lifecycle.enteraction.list` —— 按已退回状态 id 查已有进入动作，按 `code` 查重。
2. `lifecycle.enteraction.create` —— 建进入动作：`belongId` 填已退回状态 id，`belongType: 1`，`actions[0].configs[0].behaviorType: 7`，`workflowId` 填提醒流 basicId。
3. `lifecycle.enteraction.list` —— 回读 `belongType`、`configs[0].behaviorValue.workflowId` 与 `code`。

**校验**
- 进入动作 `belongType: 1`，状态按钮是 `2`。
- `workflowId` 是提醒流 workflowBasicId，不是 configId。
- 提醒流 `status: 20` 且 `isAllowTrigger: true`；否则进入动作选不到/不触发。
- 回读 `name` 可能为 null，用 `code` 识别。

**示例**
```json
{"code":"return_reminder","belongId":"<statusId>","belongType":1,"actions":[{"code":"return_reminder","name":"","isEnabled":true,"belongType":1,"configs":[{"id":"<actionConfigId>","uid":"<actionConfigId>","behaviorType":7,"behaviorValue":{"workflowId":"<workflowBasicId>"},"belongId":"<statusId>","sort":0}],"sort":1,"executeType":1,"description":"已退回触发提醒","lifecycleId":"<lifecycleId>","lifecycleStatusId":"<statusId>","basicObjectId":"<objectId>","objectCode":"homework__c","enableSignatures":true}]}
```

**预期**
作业被退回时，进入动作自动启动提醒流，给提交人发「请修改作业后重新提交」提醒；不会写状态、不会产生审批任务。

### menu.submit 新建 / 更新菜单

#### 方案 · 给对象建入口菜单：母菜单 + 子菜单

> 对象建完、布局配好后，用户要在侧边栏点进去。菜单是两级的：先建**母菜单**（`menuActionType: 3`，相当于分组），再建**子菜单**（`menuActionType: 1`）挂到母菜单下。子菜单必须挂齐对象、列表布局、表单布局三样，用户点进去才是「能看列表、能新建、表单字段正确」的入口。
> 顶层母菜单的 `parentMenuId` 留空；它出现在「所有菜单」分组下，权限再按角色放开。

**步骤**
1. `menu.submit` —— 建母菜单：`{ name, code, menuActionType: 3, source: 2, menuType: 1, status: 1, backgroundColor: "#366EF4", childShowType: null }`，返回 `data.Id`。
2. `menu.submit` —— 建子菜单：`{ name, code, menuActionType: 1, parentMenuId: <第 1 步的 id>, source: 2, menuType: 1, status: 1, objectId, listLayoutId, layoutId, createType: 4, childShowType: null }`。
3. `menu.group.list` —— 读分组清单确认母菜单挂在哪组；或用 `GET /api/platform/Menu/GetMenuList` 按 code 读回两级记录。

**校验**
- 子菜单回读的 `objectId` / `listLayoutId` / `layoutId` 三样都不为空，`createType = 4`。
- 子菜单的 `parentMenuId` 等于母菜单 id；母菜单 `parentMenuId` 为空。
- 侧边栏能看到「母菜单 → 子菜单」，点开是对象列表页。
- 用 `call` 跑 `menu.submit` 时，引擎会自动调 `menu.list` 按 `code` 回读，比 `name` / `parentMenuId` / `objectId` / `listLayoutId` / `layoutId`；日志里看到「回读菜单「…」：层级与对象/两套布局 id 都对得上」才算验过，报「回读未找到」就是没建成（2026-11-26 standard-val 实测：`GetMenuList` 1050 条、按 `menuType=1` 1041 条，含新建的两级菜单）。

**示例**
```json
{"name":"作业提交","code":"homework_submit__c","menuActionType":1,"parentMenuId":"6c7ad784-002a-67cc-d934-3c48870e98cc","source":2,"menuType":1,"status":1,"objectId":"70a49df0-a5b9-2ac8-ff9c-f37758df3381","listLayoutId":"e1aa392d-1a17-b342-db82-19c4e2a132b8","layoutId":"c85911fc-e302-8187-485b-22eff84f8d81","createType":4,"childShowType":null}
```

**预期**
侧边栏出现「作业管理 → 作业提交」，点进去是作业列表，右上角能新建作业提交单，表单里是基本信息分区 + 配置好的字段。新菜单默认只对管理员可见，普通角色要去角色/菜单权限里授权。

### workflow.create 新建工作流

#### 方案 · 标准审核工作流：开始 → 状态：待审核 → 老师审核 → 判断 → 双动作 → 结束

> 一条「提交后先落待审核，再交给老师审核，通过/拒绝各回写一个状态」的流程。2026-11-09 管理员演示的「作业提交-标准审核工作流」（`aa__c`，basic `ef355b4e-b46a-c0a3-1f6d-3a24d1d916aa`，v4）就是这个形状：开始 → 状态：待审核 → 任务：老师审核 → 判断 → 已通过/已退回两个动作 → 结束。
> **重要前提**：工作流发布后**不会自己触发**，必须在对象/状态上挂「动作」把它拉起（动作类型 `behaviorType: 7` 触发工作流，`behaviorValue.workflowId` 填 workflowBasicId）。审批流由用户动作触发，工作流级 `isAllowTrigger` 保持 **false**；该开关只给进入动作/事件动作触发的提醒流用。
> **发起人签名**：用户动作上的 `enableSignatures: true` 只是按钮入口，真正的发起人电子签名在**开始节点的电子签名控件**（`startUpControls`，如 `ccc__c`）里配；不要回读 `isNeedSignature: false` 就判断“不必签”。

> **节点命名（2026-11-26 用户实测）**：中间节点统一 `【类型】：名称`；动作用 `【动作】：修改状态为‘X’`（“为”不能漏），任务用 `【任务】：X`，判断用 `【判断】：X`。本次开始/结束保留平台默认“开始”“结束”，没有强制加前缀；若平台允许改名再统一，不要假设所有节点都能改名。

**步骤**
1. `workflow.create` —— 建草稿：`status: 10`、`workflowType: 10`、`isSingleRecord: true`、`objectId`、`lifecycleId`、`objectLayoutCode`（从零建时 UI 必传）；返回 `workflowConfigId`（同时记住 `workflowBasicId`，挂动作要用）。**新建出来就是草稿，不需要先切 40**；审批流 `isAllowTrigger` 保持 false。
2. `workflow.start.update` —— 开始节点：用户动作挂载的审批流**必须**加发起人电子签名控件；实测 `ctrlType: 60`，`signatureConfig` 含 `isRequirePosition: true`、`isShowSignatureMean: true`、`isRequiredMean: true`、`isShowSignatureRemark: true`、`reasonInputType: 20`、`signatureMeanName: "签名含义"`、`signatureRemarkName: "签名备注"`，并用 `signatureMeanOptions: [{ value: "提交授权账号处理结果" }]` 给含义选项（文案按业务改；回读会补 optionType/sort/id，更新时保留原 option id）。本次回读 `isRequiredSignature: false`，但**只要开始节点存在电子签名控件，实际执行即按必填处理**（用户 2026-11-26 口径），不能因参数回读 false 判断为“可选”；`isShowSignatureRemark: true` 只显示备注，备注不必填。参与者控件可用「从对象字段取人」，`selectUserType: 40`、`fielsObjectIds: [{ id, objectId, name, code }]`；`nextStepId` 指「状态：待审核」。
3. `workflow.action.add` —— 状态节点（stepType 90）：`behaviorType: 9`、`behaviorValue.statusId` 填**待审核**状态 id；`nextStepId` 指老师审核任务。这个节点是提交后真正把状态从待提交推到待审核的地方。
4. `workflow.task.add` —— 任务节点（stepType 30）：`dispatchMode: 10`（系统指派）、`taskRequireType: 20`（必须完成）、`isRequireApproval: true`、`userControlIds` 填开始节点参与者控件的 id（**字符串**，不是数组）、`taskFields` 挂审批时可见的对象字段（不挂的话老师看不到作业内容）；`nextStepId` 指判断节点。
   - **任务提醒**：「任务提醒方式」下拉里选「使用提醒策略」，对应 `notifyType: -10`（按 `aa__c` 流程回读的值核对；其它选项的值等遇到再补）。
5. `workflow.task.add` 的 `stepTaskApprovals` —— 两个按钮：`同意`（sort 0）、`拒绝`（sort 1）。**审核任务两个按钮都要显示电子签名**（对应界面「审批意见 → 需要电子签名 / 需要填写签名备注 / 需要填写签名含义 / 需要选择职位」）：
   - `isHaveSign: true` 两个按钮都设；`isRequireSign`：两个按钮都 `true`（**都必填电子签名**）。`isRequireUserName: false`、`enableDigitalIdentityAuth: false`（用户名、数字身份认证不勾）。
   - `isShowResons: true` —— 显示签名备注；`resonTitle: "签名备注"`；`reasonInputType: 20`（输入类型：填写）；`isRequiredResons`：同意 `false`、拒绝 `true`（拒绝时备注必填）。
   - `isShowResponsibilities: true` + `isRequireResponsibilities: true` —— 显示并必填签名含义；`responsibieTitle: "签名含义"`；含义选项写进 `responsibleOptions[0].value`（文案按业务，如同意「复核处理后的账号信息」/ 拒绝「拒绝本次复核」）。
   - **`isRequirePosition: true` —— 需要选择职位**（标准审批意见签名必须勾这一项）。
   - 任务级签名（`stepTaskConfig.isRequireSign`）保持 `false`，签名只在审批意见上做。
   - 2026-11-26 v3 实测：两个按钮都 `isRequireSign:true`；同意 `isRequiredResons:false`（签名备注可选）、拒绝 `isRequiredResons:true`（签名备注必填）；两个按钮 `isHaveSign:true`、`isShowResons:true`、`isShowResponsibilities:true`、`isRequireResponsibilities:true`、`isRequirePosition:true`。
6. `workflow.decision.add` —— 判断节点（stepType 70）：`rules[0]` 的条件 `targetType: 7`、`targetId` 指**任务节点** id、`logicType: 40`、`logicValue` 是**带引号的「同意」按钮 id**（形如 `"\"0d86903b-…\""`，序列化后是 38 字符带引号串）；`rules[0].nextStepId` 指「已通过」动作，`stepDecision.nextStepId`（else）指「已退回」动作。
7. `workflow.action.add` —— 两个动作节点（stepType 90）：`stepAction.actions[0].configs[0] = { behaviorType: 9, behaviorValue: { statusId } }`，`statusId` 必须是**启用中**的状态 id（作业提交里：已通过 `5ff2f178…`、已退回 `a077aead…`），`nextStepId` 都指结束节点。
8. `workflow.status.change` —— 发布：`{ ids: [workflowConfigId], status: 20, workflowBasicId }`。发布后 `isEnable` 可能仍是 false，以 status=20 为准。
9. `lifecycle.useraction.create` —— 到待提交状态挂「提交」按钮，`belongType: 2`、`behaviorType: 7`、`workflowId` 填审核流 basicId；到已退回状态挂「重新提交」按钮，同样绑审核流。用户动作才是审批流的触发器。

**校验**
- `workflow.steps.list` 回读七节点，`nextStepId` 首尾串通：开始→状态：待审核→任务→判断，判断 `rules[0]`→已通过、else→已退回，两个动作→结束。
- 开始节点有电子签名控件（`ctrlType:60`，`signatureConfig` 含 `isRequirePosition/isShowSignatureMean/isRequiredMean/isShowSignatureRemark`，本次 `isRequiredSignature:false`；**控件存在即实际必填，不能按参数 false 判为可选**；备注只显示、不必填）；`stepTaskApprovals` 回读：两个按钮 `isHaveSign:true`、`isRequireSign:true`；同意 `isRequiredResons:false`、拒绝 `isRequiredResons:true`；两者 `isShowResons:true`、`isShowResponsibilities:true`、`isRequireResponsibilities:true`、`isRequirePosition:true`。
- 状态：待审核节点的 `behaviorValue.statusId` 是启用中的待审核状态 id。
- 任务提醒方式回读 `notifyType: -10`（使用提醒策略）。
- 动作节点 `statusId` 指向的状态 `isEnabled: true`。
- 发布后 `status = 20`；`isEnable: false` 不一定是失败。审批流 `isAllowTrigger` 为 false。
- 发布后必须挂用户动作（`behaviorType: 7`），否则流程永远不会跑；只挂进入动作不够。
- **节点「读回→改→写回」的形状**（2026-11-26 实测，踩过 NRE）：`workflow.step.get` 返回的控件是**摊平**形态（`ctrlType`/`value`/`stepId` 都在控件对象顶层），四个 `*Step.update` 要的是 UI 的包裹形态 `{id, sort, name, controlConfig:{…}, participantConfig, signatureConfig}`。把 Get 结果原样回传，服务端会抛 `Object reference not set to an instance of an object.`（保存阶段就崩，不是运行时）。

#### 方案 · 提醒工作流：只提醒、不审批，由进入动作触发

> 除了审批工作流，还有一类**提醒工作流**：不设审批、不阻断流程，只在某个时点给参与人推一条提醒任务。典型场景：作业提交生命周期里老师「退回」，系统给提交作业的学生推一条提醒，告诉他作业被退回了、要重新提交。
> 触发方式与审批流不同：提醒流一般由**进入动作**触发，因此必须勾选「允许从进入动作和事件动作自动启动」。

**步骤**
1. `workflow.create` —— 建草稿（`status: 10`，新建出来就是草稿，不用先切 40），对象、生命周期按要挂的入口选；工作流级 `isAllowTrigger: true` 就是「允许从进入动作和事件动作自动启动」这个开关（不勾默认 false）。
2. `workflow.start.update` —— 开始节点：参与者用「从对象字段取人」，`selectUserType: 40` + `fielsObjectIds`（示例取 `created_by__sys` 创建人，控件的 `code` 起个可读名如 `sf__c`），这样提醒对象自动是发起人，不用手选。
3. `workflow.task.add` —— 任务节点（stepType 30）配成**提醒任务**：`isNotifyTaskType: true`、`isRequireApproval: false`、`stepTaskApprovals: []`（不配任何审批按钮）；`userControlIds` 填开始节点参与者控件 id（字符串）、`dispatchMode: 10`（系统指派）、`taskRequireType: 20`、`notifyType: -10`（任务提醒方式：使用提醒策略）。任务名直接写提醒语，如「请修改作业后重新提交」。
4. 链路只保留「开始 → 提醒任务 → 结束」，不配判断、不配动作（不改变状态）。
5. `workflow.status.change` —— 发布（`status: 20`）。
6. 到「生命周期 → 进入动作」里挂 `behaviorType: 7` 的动作，`behaviorValue.workflowId` 填 workflowBasicId。

**校验**
- 工作流回读 `isAllowTrigger: true`（「允许从进入动作和事件动作自动启动」已勾）。
- **该开关一旦勾选并启用，后续无法取消** —— 这是不可逆项，上线前确认清楚。
- 提醒任务回读 `isNotifyTaskType: true`、`isRequireApproval: false`、`stepTaskApprovals` 为空。
- 发布后在对应生命周期的进入动作里能看到这条流程；触发后当事人收到提醒任务。

**示例**

**预期**

#### 方案 · 给对象建一条待办通知模板，再挂到提醒/审批任务节点

## 工作流配置知识（2026-11-22 沉淀，非方案）

**改已发布流程：先开草稿，再改节点（2026-11-25 用户口径 + 通桥抓包）**

工作流一旦发布（`status: 20` 启用），要改节点必须先切到「编辑中（40）」。切法不是调 `ChangeWorkflowBasicStatus`，而是对 `UpdateWorkflowBasic` 原样保存一次基本配置：服务端会新建一个草稿版本——`workflowConfigId` 换新、`status` 变 40、`versionNo` 加 1、`workflowBasicId` 不变。改节点与发布都用这个新 id，发布用 `ChangeWorkflowBasicStatus { ids: [新 id], status: 20, workflowBasicId }`。页面上「编辑 → 改节点 → 发布」这三步对应的就是这三个调用。

**开始节点：参与者 + 电子签名**

开始节点不是空入口，通常配置“参与者”和“电子签名”。参与者表示**谁能够参与**这条流程，不是“谁能够发起”；谁能发起由状态上的用户动作/进入动作和入口权限决定，不能从开始节点参与者推断。

**发起入口单独检查**

`isAllowTrigger` 只控制是否允许「进入动作/事件动作自动启动」。审批流仍必须在状态上挂用户动作（`behaviorType: 7`，`behaviorValue.workflowId` 填 workflowBasicId）作为触发器；初始状态绑定 `lifecycleStatusIds` 不等于触发器。

**创建任务节点前：只检查开始节点有无对应参与者**

创建任务节点前，只判断开始节点中有没有对应的参与者控件；有就把任务的 `userControlIds` 指向它，没有就回开始节点补。矩阵规则、角色成员、通知接收人是否齐全，放到发布前检查，不要把它们当成创建任务节点的前置条件。

**参与者控件只允许两种（2026-11-22 用户口径）**

- `使用字段作为参与者`：`selectUserType: 40`，配 `fielsObjectIds`，从当前记录字段取人；
- `使用审批矩阵作为参与者`：`selectUserType: 50`，配审批矩阵。

不得使用指定用户、指定用户组、指定用户+用户组、使用角色、使用自定义动作等其它类型；已有流程如用了其它类型，另行评估迁移，不在新建/调整时继续使用。

**配置前分析与执行顺序（2026-11-22 用户口径）**

- 配置前先出三张清单：参与者清单（只能是字段/审批矩阵）、节点清单（开始/状态/任务/判断/动作/结束）、节点关系图（含判断分支与拒绝回退）；
- 执行顺序固定为「先建参与者 → 再建节点 → 最后收口节点关系」；
- 当前 `workflow.*.add/update` 的 `nextStepId` 是必填，节点可先带临时指向占位，节点全部建完后再用 `workflow.*.update` 统一收口；最终必须回读 `nextStepId/nextStepList` 与判断分支，不能把临时指向留在发布版本里。

**审批矩阵两组配置不要混**

- `constraintRoleIds`：应用角色约束，限制哪些角色可以参与；
- `constraintsCondition`：使用的条件，特殊情况下的更原始字段/角色过滤。

两者不是互相替代关系。矩阵类型创建后会自动生成 `<code>_mgt__ak` / `<code>_role__ak` 两个对象，但创建响应只返回 `matrixConfigId`，后续要按 code 反查对象。

**分析与创建顺序**

对象/生命周期/状态/字段 → 审批矩阵及其角色/条件 → 开始节点参与者（字段或审批矩阵）/签名 → 任务节点参与者 → 状态/任务/判断/动作步骤 → 发布 → 触发绑定。

分析工作流时按同一顺序做“六遍”：参与者与签名 → 对象/状态 → 工作流身份 → 步骤图 → 语义（任务/判断/动作）→ 可执行性校验。

**典型分支示例**

变更申请审核这类流程，常见结构是：开始 → 设置“审核中” → 判断类型 → 通用变更走部门负责人/部门评估/管理者代表 → 分配责任部门；设计变更走设计评估/研发负责人/企业负责人 → 按影响注册申报、是否需要验证确认三选一进入后续状态。所有拒绝分支回到申请状态，恢复关联对象状态并生成退回通知。流程结束在中间业务状态时，不代表对象已完成，后续执行/关闭要单独承接。

**`else` 的语义要写清**

不要把“非通用变更”默认当设计变更；新增第三种类型前先复核 `else` 兜底，否则新类型会被误送入设计变更链路。

**签名含义：开始节点和审批按钮是两套字段（2026-11-23 实测）**

「签名含义」在两个地方出现，字段名完全不同，不要混用：

- 开始节点：`startUpControls[].signatureConfig`（电子签名控件）。`isShowSignatureMean` 是否显示「签名含义」、`isRequiredMean` 含义是否必填、`signatureMeanName` 标题（默认「签名含义」）、`signatureMeanOptions[].value` 含义选项、`isShowSignatureRemark` + `signatureRemarkName` + `reasonInputType: 20` 备注栏、`isRequirePosition` 需要选择职位、`isRequireUserName` 需要填写用户名、`isRequiredSignature` 签名必填参数。开始节点只要存在签名控件，实际执行即按必填处理，`isRequiredSignature:false` 不能判为可选。实测：`isShowSignatureMean: true`、`isRequiredMean: true`、`isRequirePosition: true`、含义「发起计算机化授权申请」。服务端回读会补 `optionType: 0`、`sort`、`isAllowedNotes: false`、`isRemarkRequired: false` 与全零归属 id，更新时保留原 option 的 `id`。
- 审批按钮：`stepTaskApprovals[]`。任务级 `stepTaskConfig.isHaveSign: true` 表示该节点带签名栏，`isRequireSign: false` 表示任务级签名不必填（签名落在按钮上），`externalSignatureInfoFrom: 1`。每个按钮上：`isRequireSign`（本按钮要电子签名）、`isShowResons` + `isRequiredResons` + `resonTitle`（签名备注；同意可不填、拒绝必填）、`isShowResponsibilities` + `isRequireResponsibilities` + `responsibieTitle`（签名含义标题，**拼写原样少一个 l**）+ `responsibleOptions[].value`（该按钮的含义文案，实测同意「同意授权申请」、拒绝「拒绝授权申请」）、`isRequirePosition`（选职位）。
- 含义选项没有独立字典接口，随节点/按钮一起内联保存；改文案就是改 `value` 再整份写回。

**拒绝分支：判断的默认分支指「修改状态：已驳回」**

审批流的判断节点，`rules[].nextStepId` 是「断言命中」分支（同意→下一任务），`stepDecision.nextStepId` 是默认/否则分支（拒绝）。默认分支必须指向一个「修改状态：已驳回」的动作节点，再由它连结束；直接指结束会让拒绝后状态停在待审核。

```text
任务：上级审批 ──判断：上级审核结果
   ├─ 规则1：step_dept_approve__c 断言=同意(按钮 id) → 任务：系统授权人审批
   └─ 默认 → 动作：修改状态已驳回(behaviorType 9) → 结束
```

条件写法：`targetType: 7`、`targetId` 填任务节点 id、`targetCode` 填任务 code、`logicType: 40`（单条件也用 40）、`logicValue` 是带引号的按钮 id JSON 字符串、`relations[].logicalOperator: 1`。

**发布与版本：发布后再编辑会生成新草稿**

`workflow.status.change`（ChangeWorkflowBasicStatus）用 `status: 20` 发布当前草稿。在已发布版本上继续编辑，平台会生成新草稿版本：`versionNo + 1`、`status: 40`、换新 id（2026-11-23 实例：v2 于 18:17:18 发布，18:19:19 生成 v3 草稿 id `2bc51743-…`）。改完必须再发布一次，并按 `GetWorkflowBasic` 回读的 `status`/`versionNo`/`id` 判断当前版本，不要沿用旧 id。

**`isEnable` 不是配置项**

步骤对象里的 `isEnable`（与 `name`/`code`/`stepType`/`sort`/`nextStepId` 同级）是平台内部字段，不在任何表单里，保存时原样回传，分布没有规律（开始/结束为 true，中间节点多为 false），发布成功后它也不会变。不要把它当节点启停开关或发布失败的判据。

# 对象分析经验与模板

> 面向：使用 akso-workbench 做对象分析的人，以及维护对象分析实现的开发者。
> 定位：把 2026-11 的对象分析实战经验、矩阵/菜单/业务数据检查方法、可复用模板收在一起；具体接口细节仍以 `基础API使用指南.md` 为准。

## 0. 先记住一条边界

对象分析是**只读**能力。它读对象、字段、生命周期、动作、工作流、审批矩阵、菜单和业务数据，不写平台。

从 2026-11-23 起，报告口径固定为：

1. **只分析启用状态**。停用状态及其上的进入动作/用户动作不进入报告；停用状态数量只在概览里作为背景信息，不展开。
2. **工作流必须挂到至少一个启用状态**。只挂停用状态、或没有 `lifecycleStatusIds` 绑定的流程，不进入报告。
3. **不要求每个状态都有用户动作/进入动作**。没有动作的状态不是异常，可能由工作流、事件或后续流程承接。
4. 工作流里的步骤、判断分支、动作节点必须写**名称**，不能只写 id。
5. 审批矩阵必须用列表呈现，不能只给数量；每行至少包括矩阵名称、关联工作流、参与者控件、控件应用到的任务节点、菜单、业务数据、异常。

## 1. 一次分析的最小闭环

### 1.1 输入

- 对象 id 或对象 code；页面一次最多 3 个对象，agent 一次一个。
- 当前环境来自底部账号条 `prefs.currentAccountId`，不接受手填；账号条为空时返回 `needs-account`，不回落旧会话。

### 1.2 读取顺序

1. 对象元数据：`BasicObject/{code}`，拿到 objectId、lifeCycleId、是否启用生命周期。
2. 字段：`BasicObject/field/{code}`，按 `sort` 排；注意 `dataType` 映射和 `objectRelation`。
3. 状态：`Status/GetList`，按 `lifecycleId` 过滤；只保留 `isEnabled !== false`。
4. 状态动作：用户动作/进入动作的 list + 每个 `GetById`；解析 `configs[]` 的 `behaviorType`、`behaviorValue`。
5. 工作流：`GetWorkflowBasicPageViewList` 按 objectId 过滤；只保留 `statusBindings` 命中启用状态的工作流。
6. 步骤：`GetWorkflowSteps` 取外壳，逐步骤 `GetWorkflowStepWithDetails` 取详情；先回填步骤名称，再解析任务/判断/动作。
7. 开始控件：`startUpControls[].participantConfig`；`selectUserType=50` 取 `approveMatrix`，`40` 取字段参与者。
8. 矩阵：只分析保留工作流里实际出现的开始控件矩阵；用任务节点 `userControlIds` 反查“控件应用在哪一个任务”。
9. 菜单：`Menu/GetUserMenuPermission` 返回扁平行；按 `parentMenuId` 还原祖先链，在“审批矩阵”父菜单下找矩阵管理菜单。
10. 业务数据：菜单行 `objectId` → `Listlayout/List?objectId=` 取列表布局 id → `Record/GetViewDataCount?viewId=` 取条数。
11. 汇总：矩阵表、触发缺口、无菜单矩阵、无数据菜单、状态/动作/工作流统计，最后写产物。

### 1.3 产物

- agent 路径：`akso_workbench_object_analysis` 直接写 `<工作区>/akso-workbench-data/analysis/<对象名>-YYYYMMDD-HHmmss/`，含 md/drawio/png，返回 `artifacts.folder/files/warnings`。
- 页面路径：页面生成 zip 包，包内根路径也是 `akso-workbench-data/analysis/<对象名>-时间戳/`，解压后得到同样的三件套。
- 每次成功/失败都留分析历史；失败不能只留临时目录里的 JSON。

## 2. 审批矩阵：最容易出错的部分

### 2.1 三个对象别混

| 概念 | 位置 | 用途 |
|---|---|---|
| 矩阵配置 | `ApproveMatrix/GetConfigApproveMatrixPagedList` 的 `id` | 规则、匹配字段的配置 id |
| 矩阵管理对象 | 矩阵菜单行的 `objectId` | 业务数据（管理记录）所在对象 |
| 矩阵角色对象 | 自动生成的 `_role__ak` | 规则角色记录，通常由平台维护 |

`CreateConfigApproveMatrix` 的响应只返回 `matrixConfigId`，不返回自动创建的两个对象 id；要按 code/菜单再查，不能假设响应里有。

### 2.2 矩阵与工作流的对应

- 开始节点的参与者控件：`participantConfig.selectUserType === 50` 时，`approveMatrix` 是矩阵 id。
- 任务节点不直接存矩阵 id，只存 `userControlIds`；必须回到开始节点控件表反查。
- 同一矩阵可能被多条工作流、多个任务使用；报告按 usage 展开，不要合并成一行丢掉节点信息。
- `statusBindings` 只说明流程挂在哪，不等于触发器；触发器仍要看状态动作的 `workflowIds`。

### 2.3 菜单与业务数据

- 菜单接口是扁平数组，不能假设 `children` 树；用 `parentMenuId` 自己建链。
- 矩阵管理菜单名通常包含“矩阵”，但要限定在“审批矩阵”父菜单下，否则会把业务菜单误认成矩阵菜单。
- 菜单行的 `objectId` 是管理对象，不是矩阵配置 id；用 `Listlayout/List` 查该对象的列表布局，再拿布局 id 当 `viewId`。
- `Record/GetViewDataCount?viewId=` 是 GET + query；不要把 query 塞进 POST body。
- 一个矩阵可能同时有“配置菜单”和“数据菜单”，逐个尝试，别只读第一个就判无数据。
- 找不到菜单、菜单无数据、矩阵停用、工作流引用矩阵但开始节点无控件，都要在异常列写清楚。

## 3. 常见坑

| 现象 | 根因 | 做法 |
|---|---|---|
| 任务/判断只显示 id | 没做步骤 id→名称回填 | 先建 `stepId → name` 映射，再写 `nextStepName`、分支名、else 名 |
| 矩阵列表为空 | 用 `triggeredBy` 过滤，审核流只有状态绑定 | 按“挂启用状态”过滤，矩阵从开始控件取 |
| 矩阵菜单全空 | 把扁平菜单当树 | 用 `parentMenuId` 还原祖先链 |
| 业务数据全是 null | 把 `menu.id` 当 `viewId`，或 query 放错位置 | `Listlayout/List?objectId=` → `viewId` → `GetViewDataCount?viewId=` |
| 停用状态出现在报告 | 用了全部 `statuses` | 只取启用状态，停用状态不展开 |
| 新对象没有生命周期/签名 | 旧版本允许不传 | 新建对象必须同时 `enableLifeCycle:true`、`enableSignatures:true` |
| 布局 section/control 保存报 `BelongId` | 新 section/control 缺 `layoutId` | 随机 UUID 可以，但必须带 `layoutId`；`GetStableComponentIds` 不可用时不硬等 |
| 字段被停用 | `field.save` 更新没带 `status:1` | 更新现有字段必须显式 `status:1` |
| 报告落到了 profile | 没拿到工作区根 | 从 `exec.agent.id` 找 session id，再查 workspace.json；不要回落 profile |
| 工具改了但结果没变 | 当前 session 固定旧插件 revision | 重启 DSH 或开新会话再验证 |

## 4. 模板

### 4.1 发起对象分析

```text
分析对象 <code 或 id>。
要求：
1. 只分析启用状态；停用状态及其动作不要写进报告。
2. 工作流只分析挂到启用状态的流程；步骤写名称，不要只写 id。
3. 审批矩阵用列表：矩阵名称 / 关联工作流 / 参与者控件 / 应用节点 / 菜单 / 业务数据 / 异常。
4. 产物写到工作区 akso-workbench-data/analysis。
5. 只读，不写平台。
```

### 4.2 报告结构

```text
# <对象名>（<code>）对象分析

## 1. 概览
- 环境 / 账号
- 生命周期 / 启用状态数 / 字段数 / 工作流数 / 矩阵数

## 2. 生命周期
| sort | 状态 | code | 启用 | 用户动作 | 进入动作 |
...

## 3. 用户动作 / 进入动作
按状态分组；每个动作写 code、behaviorType、效果、关联工作流。

## 4. 字段表
| # | 字段名 | code | 类型 | 必填 | 唯一 | 来源 | 引用/选项集 | 状态 |

## 5. 工作流解析
每条工作流：目的、触发、步骤表、判断分支、动作效果、拒绝回退、风险。

## 6. 审批矩阵分析
| 审批矩阵 | 状态 | 关联工作流 | 参与者控件 | 应用节点 | 菜单 | 业务数据 | 异常 |

## 7. 自动观察与风险
只写有证据的：缺菜单、缺数据、停用矩阵、无触发、无最终状态、跨对象写入等。

## 8. 读取告警与边界
未读到的接口、未验证的字段、host/账号限制。
```

### 4.3 矩阵表最小列

至少保留这 8 列，不要只写“矩阵 N 个”：

`审批矩阵 | 状态 | 关联工作流 | 参与者控件 | 应用节点 | 菜单 | 业务数据 | 异常`

### 4.4 审核文档

创建/大调整用完整文档，小范围更新用短文档；三节固定：

1. 本次任务需要解决什么问题
2. 本次任务计划怎么执行
3. 本次任务完成后预期结果是什么（checklist）

文档执行成功后才标记“已结束/作废”；已执行文档禁止修改，后续调整另建更新文档。文件放 `<工作区>/akso-workbench-data/reviews/`。

## 5. 交付前检查

- [ ] 账号来自底部账号条，环境没有串
- [ ] 只分析启用状态；停用状态及动作没有进报告
- [ ] 工作流都挂了启用状态
- [ ] 步骤/判断/动作都显示名称
- [ ] 矩阵表含矩阵/工作流/控件/应用节点/菜单/业务数据
- [ ] 菜单祖先链正确，没有把业务菜单当矩阵菜单
- [ ] `viewId` 来自 `Listlayout/List`，不是 `menu.id`
- [ ] 产物在 `akso-workbench-data/analysis/<对象名>-时间戳/`
- [ ] 报告末尾有字段表
- [ ] 只读分析没有产生平台写入

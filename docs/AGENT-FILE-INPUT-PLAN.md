所以：**DB 只存"文本 + 附件引用"，附件在请求构建那一刻（唯一扼流点）展开成 content parts**。

## 2. 设计（三条硬约束推出来的唯一形状）

```
用户 ── 附件按钮 / 粘贴 / 拖拽 ──► POST /api/attachments (multipart)
                                      │  白名单 + 大小/数量上限 + 落盘 + sha256
                                      ▼
                        runtime/attachments/<会话id>/<att_id>__<安全文件名>
                                      │  解析（按类型）→ 文本 + 定位表 + 摘要
                                      ▼
                        附件表（attachments）：id / 会话 / 名字 / mime / 字节 / sha256
                                              / 解析状态 / 页数或表数 / 文本长度
                                      │
   用户在输入框里引用 ────────────────┘
                                      ▼
   messages.content 仍存**文本**：`…请看这份表 [附件 att-3f2a：培训记录.xlsx]`
                                      │
                          _model_history()（**唯一扼流点**）在**请求构建时**展开：
                                      │   · 图片 → image_url（data URL）
                                      │   · 文档 → 「文件名 + 摘要 + 定位目录 + 前 N 行」
                                      │   · **只有最新一轮**的附件展开，历史轮只留那句文本引用
                                      ▼
                         Agent 循环（工具面加三个只读动词）：
                           attachment_list()                    看得见手上有哪些文件
                           attachment_read(id, page/sheet/range) 按需取，不爆上下文
                           attachment_search(id, pattern)         大文件里定位
```

### 2.1 为什么"只有最新一轮展开"（这条是成本与正确性的分界）

把图片或整份文档**每一轮都重发**，会造成三件事同时发生：token 账单线性膨胀、
上下文被同一份文件挤满、以及**前缀缓存失效**（每轮前缀都在变，命中率归零 ⇒ 成本 ×50，
`cache.py:143` 有明确警告）。所以：**展开只发生在"用户这一轮刚交上来的附件"上**，
历史轮保留文本引用（`[附件 att-3f2a：…]`）——模型仍然知道自己"看过它"，
需要细节时用工具回去取。

### 2.2 为什么解析产物要带**定位信息**

G3 的"正确"不是"答得像"，而是"**答得出处**"。所以解析器不只要文本，
还要 `{page: 7, sheet: "明细", range: "B4:F12", heading: "3.2 培训记录"}` 这类**可复算的坐标**，
工具按同一个坐标系取值。这样"模型说第 7 页"与"工具读第 7 页"是同一件事。

### 2.3 安全与留痕（沿用既有红线，不新造）

| 面 | 规则 |
|---|---|
| 落盘位置 | 只在 `config.RUNTIME_DIR/attachments/`（不碰用户任意路径；不写 `docs/`、不写仓库） |
| 文件名 | **不接受用户提供的路径**：`<att_id>__<slug(原名)>`，`Path.is_relative_to` 复查（规则 22） |
| 大小/数量 | 单文件 ≤ **20 MB**、单轮 ≤ **5 个**、会话累计 ≤ **200 MB**（超限 413/400 并说清哪个超了） |
| 类型 | 白名单：`.docx .xlsx .pdf .md .txt .csv .png .jpg .jpeg .webp`；**按内容嗅探复核**扩展名（后缀能骗人） |
| 凭据 | 附件正文**不进日志**；解析文本进模型前照旧过 `RedactionFilter` 的规矩；上传只记 `att_id/名字/字节/sha256`（规则 19/20/26） |
| 可信度 | 外部内容一律带**不可信标签**（`CORE-AGENT-PLAN` I18）：注入上下文的文本块前面加机器可读前缀，确认卡上显示"内容来自附件" |
| 审计 | 上传/解析/读取各写一行（`agent_audit` 已有工具面 + 新增上传端点自己的留痕） |

## 5. 风险与诚实边界（先写下来，免得以后当成"已支持"）

1. **"传进来的内容"是攻击面**：文档里可以写"忽略你之前的指令"。I18 的可信度标签是结构防线，
   但**它不保证模型不被说服**——真正的强制点在"附件内容不能单独触发高风险工具"（确认门仍在）。
2. **表格类图像/扫描件**：直连多模态能"看图说话"，但**精确读数（几十行数字）不可靠**；
   这一类要靠 OCR 或让用户给原始 xlsx（A1-②/③ 才解决）。
3. **PDF 版式**：`pypdf` 抽的是文本流，双栏/表格会串行；要"版式级"正确得另换引擎（本方案不承诺）。
4. **体积**：20MB 上限是"上传体验"与"解析耗时"的折中；更大的文件建议用户切分或走 CSV。
5. **附件与会话生命周期**：删会话是否删附件、附件是否随导出带走 —— A3 定了之后要写进 `SCHEMA.md`。

### 6.1 真机联调抓到、而单元测试**看不见**的两个缺陷（值得单独记一笔）

| # | 现象 | 根因 | 为什么单测没抓到 |
|---|---|---|---|
| 1 | 模型回"该附件属于另一段会话，读取被拒绝" | `_pending`（"还没开会话"的落点）是**真值**，而绑定条件写的是 `if not conversation_id` ⇒ 永远不绑 | 单测直接用真实会话 id，从不经过"先上传后开会话"这条真实时序 |
| 2 | 模型回"没有把像素送过来"（图片只有一个文件名） | 真实路径是"先取历史 → 过硬点 → **再把这一轮的消息原样追加**" ⇒ **恰好是这一轮的附件**绕过了展开 | 单测直接喂的就是扼流点，天然绕过了"谁来调它"这一步 |

两个都补了判据：`test_pending_upload_is_bound_on_first_send`（含**文件必须跟着搬**）与
`test_the_newest_message_goes_through_the_choke_point`（走真路径 `_request_history`）。
**教训写在这里**：附件这条链路上，"函数对不对"与"链路通不通"是两件事——
真机联调不是可选项（同族：PITFALLS #53 / #62）。

### 6.2 已知限制（**不是缺陷，是取舍**，但用户会撞到）
1. **旧轮次的图片后续看不见**：A4 只展开最新一轮 ⇒ 用户隔一轮再问"刚才那张图"，模型会
   （正确地）说"我已经看不到它的像素了，请重新贴一次"。实测确认它会**如实说**，不会硬答。
   ⚠️ 但它差一点连"如实说"都做不到：2026-09-22 的真机联调里，模型读到的旧轮提示是
   「已交过你、**正文**没有重复发送、要看内容用 `attachment_read`」——图片没有正文，
   而 `attachment_read` 也给不了像素 ⇒ 它据此**撤回了自己刚答对的内容**（"前面是瞎猜的"）。
   话术已按类型分开写，判据见 **PITFALLS #89**。
   要改的话有两条路：① 保留"最近 N 轮"的图片；② 给工具加"把图片重新内联"的能力
   （今天工具结果只能是文本 ⇒ 需要新机制）。**这条等你定**（见 §7）。
2. **极小图会被读错**：8×8 的纯蓝被读成"紫色"（64×64 就对了）。→ 这不是链路问题，
   是"图太小"的感知边界；记在这里，免得下次被当成"图片功能坏了"。
   （2026-09-22 又量了一次：`tmp\probe_color.py` 直连 API、64×64 与 256×256 的纯蓝/纯红各 2 次
   ⇒ **8/8 全对**；所以"读不准"要先怀疑提示话术，再怀疑尺寸，最后才怀疑模型能力。）
3. **扫描件 PDF** 读不出文字（不做 OCR，A1 选的是直连多模态）：解析器会明确说"可能是扫描件"，
   模型也照此如实回答；用户改传截图即可走多模态。

### 6.3 发给模型的**提示文案**是链路的一部分（2026-09-22 新增的一条教训）

同一份图片、同一套请求体，**只改我们写给模型的那句话**，行为可以完全不同：

| 写法 | 实测结果 |
|---|---|
| 旧轮：「已交过你、**正文**没有重复发送、要看内容用 `attachment_read`」 | 模型**撤回自己刚答对的答案**：「前两轮……我并没有真的读取附件内容，回答是瞎猜的」（n=2 次都出现） |
| 内联（长版）：「不要用 `attachment_list` 的 `textChars` 判断它能不能读」 | 模型**拒绝看图**：「看不出颜色——只有 168 字节、textChars=0，像是空文件或损坏的图」（同一次运行的下一问又答对了"正方形"） |
| 内联（现在的短版）：「用户交上来的图片，见图」 + 旧轮按类型分写 | **连续 3 次运行五问全绿**（颜色/形状/表格/不撤回/负样本） |

⚠️ **样本量都很小**（n=2 vs n=3），所以这条的结论不是"新话术一定对"，而是两条**规则**：
① 别在提示里提起失败模式（那等于给模型一个可选项）；② 旧轮引用**必须按类型分写**。
判据：`tests\test_attachments.py` 的两条措辞断言 + `tools\verify_attachments_live.py` 的 2b。

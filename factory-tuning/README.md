## 这个目录是干什么的

配置工厂的蓝图 schema **本来就是从监听里得来的**：看人在平台上正常配一遍对象/字段/布局/
生命周期，平台实际发了哪些请求、请求体长什么样，然后照着建模。

"建出来的东西跟人在平台上手配的到底差在哪"——这件事只能靠**真实配置操作的录制**回答。
本目录就是那些录制的分析产物与原始取证报告的落点。

## 为什么单独一个文件夹（而不是做进产品）

用户 2026-09-20 定稿：

## 一、裁量规则（**用户 2026-09-22 定稿，优先级最高**）

> 「**产品手册只是给你借鉴，最终决策 / 差异请让我下达，以我的决定为主。**」

⇒ 报告里凡出现「手册 ↔ 平台真机 ↔ 实现」三者不一致的地方：
**只摆差异与证据，不替用户下结论**；措辞一律是「**差异，待用户下达**」，
而不是「应按手册改」。修法选项可以列，取舍权在用户。

## 二、操作口径（**用户 2026-09-22 定稿**）：不得擅自截图或驱动那个浏览器页面

> 「你要截图的话，需要提前告知我，**不能抢我的鼠标**。」

- **截图 / 驱动页面**（CDP 操作、`page.evaluate`、导航）：**必须先告知用户并得到同意**，
  且**不得抢占鼠标与焦点**。
  背景：曾为判断"保存有没有发出请求"而未事先告知就连接页面截图，影响了用户的操作体验。
- **不受此限**：只读的 HTTP 接口（`/api/monitor/*`、`/api/browser/sessions`、`/api/health`）
  ——它们不碰页面。
- 判据（自查）：任何新脚本若要 `connect_over_cdp` / `page.evaluate` / `Page.captureScreenshot`，
  先问一句"**我告知用户了吗**"。

## 三、测量纪律（**每一条都是踩出来的，全部与工具无关**）

这几条是这份存档里**最该被继承的东西**：它们描述的是"录制这件事本身会怎样骗你"。

### 3.1 录不到 ≠ 平台没发请求

`monitor.py::classify()` 对 **PATCH / PUT / DELETE 只有路径逐字命中已知常量表才录**，
否则**静默丢弃**；`GET` 则一律丢。
⇒ 想用录制去发现"平台用的是哪个方法"时，**录制只认得它已经知道路径的那些方法**
（"陌生 API 完整保留"**只对 POST 成立**）。

**解读口径**（三种结局，事前定死，别事后猜）：
① 录到写请求 → 答案到手；
② **界面上真的变了、但没录到** → 平台用的是「非 POST + 未建模路径」——
**这本身就是答案**（排除了 POST + 已建模路径）；
③ 界面也没变 → 那一步没生效，**重做**。

⚠️ **不要用 `dropped` 增量判断**（它把 GET 一起算了）。

### 3.2 `total: 0` 是"截至此刻没有"，不是"这次没有"

实测（段 3）：连读四次实时 `stats` **四次都是 0**，而请求发出于**只差 9 秒之后**。
据此下"监听挂在别的页面上"的结论并**告诉了用户**——**那是错的**
（`stop` 落盘后是 `{'total': 52, 'trimmed': 3, 'full': 4}`，一条没丢）。

⇒ **两条纪律**：

1. **权威读数只有落盘后的 `filter-stats.json` 与 `monitor-log.json`**——
   实时 `stats` 只配用来判"链路通不通"，**不配用来判"有没有发生"**；
2. **不要用一次 0 去推翻操作者的说法**。他说他点了保存，而 0 只说明**你读早了**。
   要确认就跑一次会落盘的操作（它一定会把队列里的事件泵出来），而不是再读一次 `stats`。

⚠️ 更该记住的：实时 `stats` 是**那一刻的快照，不是最终账**。
实测同一次会话：实时 `total` 是 **240**，关窗落盘后是 **517**。⇒ **一切以落盘后的文件为准。**

### 3.3 `timestamp` 记的是"事件被分发"的时刻，不是"请求发出"的时刻

段 2 那 5 条写请求的**观测**时间戳只差 **14 ms**，而动作缓冲里最后一次点击（「保存」）
比它早 **61.4 秒**。同一形态：段 1 = **38.4 s**、段 0 = **44.5 s**；而 09-21 的六个会话
只有 **0.1–3.1 s**。两个候选机制都还没被排除：
① sync-Playwright 的事件只在 worker **进入 Playwright 调用**时才被分发，而事件队列
**没有超时**（事件可能在队列里等几十秒才跑到 handler，时间戳记的是**那一刻**）；
② **触发保存的操作不在缓冲里**——缓冲只挂 `click/input/change`，
键盘动作、iframe / shadow DOM 内的点击**都不进缓冲**。

⇒ **三条硬口径**（写结论时按这个来）：

1. **同批事件之间的相对间隔可用；跨"动作缓冲 ↔ 请求"的时间差不可用**——
   不许拿它推人工节奏，更不许写成"用户犹豫了 61 秒"；
2. **`stats` 只统计"已被分发"的事件**，而"读 `total` 验证录制"这个动作**自己会推动分发**
   ⇒ **读到 0 不能证明"什么都没发生"**。§3.2 记的「实时 240 vs 落盘 517」就是这个原因；
3. 结论里只写"这批请求的**先后顺序**"，而顺序另有**内容语义**背书
   （保存流水线：3× 下拉查询 → `GetStableComponentIds` → `SaveLayoutDetail`）。

### 3.4 开录之后，先自己证明"录得到"，再请人操作

跳过这一步的代价是**用户白演示了一整套**，而 `total: 0`——那套数据没有副本、不可恢复。

两条口径：
1. **`start` 在监听已开时不重置，而是返回实时 `stats`** ⇒ 可以在**不 stop** 的情况下
   轮询 `total`，这是唯一的非破坏性探针。
2. **不能用"新开窗口的加载流量"验证**：挂载发生在页面 `goto` 完平台**之后**
   ⇒ 那一段流量根本不在录制窗口里。要造流量，得在挂载**之后**下发一次导航。

### 3.5 窗口身份：分不清"你在哪个窗口操作"，实验就是无效的

用户原话：「**现在都分不清我在哪个页面窗口操作的，该问题不解决，后续会产生大问题。**」

而这是**接口层就没有这个信息**：会话接口只回 `page.title()`，
而平台**所有页面标题都是同一个**；URL / target id / 窗口 id 一个字段都没有。
另一侧：监听原先只挂**一个** page，平台 `window.open` 真开出的新窗口**一条都录不到**，
而统计文件里是**干净的 0/0/0**——0 的含义只是"被监听的那个页面那段时间没有任何网络活动"。

⇒ 每次开录之后、请人操作之前，先跑一次**身份探针**（只读，不抢鼠标）：
外部页面恰好 1 个 → ✅ 可判定；0 个 → 你操作什么都录不到；≥2 个 → ⚠️ **无法判定，
必须由操作者指认或关掉多余的，不许猜**。

然后做一次**握手**（唯一能证明"你的动作到了我这里"的东西）：在打算用来演示的那个窗口里
做一次必定产生请求的动作 → 读数必须 > 0。仍是 0 就**停手**，先回来对账。

（2026-09-22 补的能力：录制会**跟随同源新窗口**，且每条记录带窗口身份——
`pageLabel` / `pageUrl`。**该能力留在产品里**，见 `services/egmp/monitor/monitor.py`。）

### 3.6 分段：做一项、停一次

分段的好处主要是**可分析、可复核**，不只是防丢。实测页面关闭也会触发落盘，
所以真正的丢失窗口只有"整个应用被强杀或崩溃"。

## 四、脱敏口径（**工具已删，规则留档；这是本目录唯一一条硬规矩**）

平台流量里带着 JWT / 会话令牌 / 口令。这个仓库是要推到 GitHub 的，
原始流量一旦进了 git 历史**很难真正删掉**——那既是安全事故，也直接违反本仓铁律
19「凭据不落明文」与 26「凭据永不入日志」。

所以当年采集时的口径是：**在写文件之前就脱敏**，磁盘上从头到尾没有一份原始流量。
将来若重建工具链，**照这张表做**：

| 处理 | 规则 |
|---|---|
| 请求/响应体里的凭据字段 | **键名子串命中**（`token`/`password`/`secret`/`authorization`/`cookie`/`apiKey`/…）→ 值换成 `"***"` |
| 只在整键时才可疑的词 | `signature` / `session` / `auth` / `key` / `encrypted` → **整键命中**才打码（否则 `enableSignatures` 这种真实业务字段会被误伤） |
| **用户手打的自由文本** | `keywords` / `searchText` / `searchKey` / `searchWord` / `queryText` / `filterValue` → **整键命中**才打码。它不是凭据而是**个人数据**：人搜的经常是**人名/单位名**，而 schema 分析要的是键名与结构、用不到这些值。刻意不收过于通用的 `inputValue` 与单数 `keyword`（更像业务字段名） |
| 值本身像令牌的 | JWT（`eyJ….….…`）、`Bearer xxx`、带 `=` 填充的 base64 长串、32 位以上连续 hex、`token_urlsafe` 形状 → 整段换成 `"***"` |
| URL 里的查询参数 | 同上按键名处理；**主机名整个丢掉**（只留路径，不记录你用哪个环境） |
| 账号 id / GUID / 本机路径 | 换成稳定假名（`acct-<hash8>` / `id-<hash8>` / `<path>`） |
| 对象编码 / 字段名 / 显示名 / 页面操作文本 | **保留**——那正是要分析的东西。⚠️ **例外**：**≥24 字符**的编码会撞上"像令牌"的兜底启发式 ⇒ 被打码。这是**刻意的不对称**（偏安全）。要取回它就读运行时原始日志（本地、不入库） |

**过度脱敏与脱敏不足一样是缺陷**：把 `enableSignatures` 打掉不会"更安全"，
只会让采集到的结构缺一块，分析据此得出"平台不发这个键"的错误结论。

另外注意：Monitor 自己会把 `Login` / `RefreshToken` 这类端点整条丢掉
（`monitor.py::QUERY_POST_PATTERNS`），所以口令最密集的那几个请求根本不会被录。

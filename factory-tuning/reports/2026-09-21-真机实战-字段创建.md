## 6. 数字字段的范围值：**曾经发出去不落地，已修复并真机复验**（PITFALLS #69）

### 6.1 症状

工厂给 `demo_number__c` 发了 `"max":100,"min":0`，平台回读 `minValue=""` / `maxValue=""` ——
**值没进去**，而接口回 `data:true`、字段也建成了。只有把这两个键打出来看才会发现。

### 6.2 根因（三组对照闭合，**不是猜的**）

| 字段 | 谁建的 | 请求里的键 | 平台存下 |
|---|---|---|---|
| `demo_number__c` | 工厂 | `min` / `max` | `""` / `""` ❌ |
| `test_mu1__c` | 界面（没填范围） | 无 | `""` / `""` |
| `test_mu2__c` | 界面（填了 1 / 888888） | **`minValue` / `maxValue`** | **`"1"` / `"888888"`** ✅ |

⇒ 平台认的是 **`minValue` / `maxValue`**，而 `collect_extras` 发的是 `min` / `max` ——
**键名不符，静默丢弃**。小数位同理：平台 schema 里叫 **`scale`**（93 个键里**没有** `decimalPlaces`）。

### 6.3 修复与真机复验

`collect_extras` 里把蓝图侧的键名**映射成平台的键名**再发
（蓝图对用户仍暴露 `min`/`max`/`decimalPlaces`，接口不变）：

```
min → minValue      max → maxValue      decimalPlaces → scale
```

**真机复验**：用工厂建 `demo_number2__c`（min=5 max=666 小数位=2），请求体为
`"minValue":5,"maxValue":666,"scale":2`，平台回读：

```
minValue = '5'    maxValue = '666'    scale = 2      ← 三个键全部落地
```

**回归**：`pytest tests/test_native.py -o addopts="" -k number_field` ——
旧实现下实测 **2 failed**，修复后 2 passed。

> **一条方法论**：`scale` 当时**只有读侧 schema 佐证**（没有界面请求体），而真机复验证明它是对的。
> 也就是说 **「拿平台的读侧 schema 当键名事实源」这个做法本身可靠** ——
> 它先让我正确预测了 `minValue`/`maxValue`，又让我正确推出了 `scale`。
> 这与 #62/#63/#67 的教训是一体两面：**猜信封会错，读真机的形状不会**。

### 6.4 用户点评带来的定级变化（保留可见）

用户点评："数字字段的 min/max，这个我平时是没有做处理的，我之前演示的时候也没有填值。"
—— 也就是说这**不是一条"用户正在被坑"的缺陷**，而是"**规格承诺了、写入没兑现**"的不一致。
定级因此从"高"降到"低"。**但它仍然是真缺陷**：蓝图模型有这三个字段、
Layer2 校验还有一条「数字字段 max 必须大于 min」，而写入层不落地。

**用户随后专门演示了一次带范围值的数字字段**，那一次演示正是修复所需唯一未知量的来源。
这条记下来，是因为它示范了**正确顺序**：**先拿到界面真实请求体，再改代码** ——
而不是反过来猜键名（这个下午的 #62/#63/#67/#69 全都是照着猜的东西写出来的）。

## 7. 一条我自己的失误（记下来是因为它很容易再犯）

我第一次回读时报「6 个字段**没建出来**」——**那是我错了**，不是产品的问题。

`GaiaQueries.get_fields` 走**进程内缓存**（`get_or_set`），而我在创建**之前**
用它打印过"已有字段 12 个"，创建后再调拿到的是**创建前的旧列表**。

产品里**没有**这个问题：`orchestrate._verify()` 读之前会先 `invalidate_object_cache(code)`
（第 275 行）。**是我的脚本没做。** 补建两个字段时我加上了这一步，回读即正确。

教训：`get_object_info` / `get_fields` / `get_statuses` **都是缓存的**，
同进程内「写完立刻读」必须显式失效；而 `get_picklist` **不是**缓存的（两者口径不同）。

## 8. 平台事实：选项集不能删除（用户确认）

- 对选项集的任何写入**都不可回滚** —— 名字/选项/编码写错，会**永久留在平台上**；
- 因此 `save` 的幂等语义（按 code upsert）是**唯一的纠错手段**；
- 本次为判别 `sort` 而建的两条测试记录（`test_0903_option__c`、
  `test_0903_probe3__c`）**永久存在**，不做「待清理」处理。

## 3. 与工厂的逐键对照 ⇒ 新缺陷候选 **D-C**

工厂 `layouts.py:48-54` 发的是**4 个键**：

```python
client.post(LAYOUT_SAVE_DETAIL, {
    "id": layout_id, "basicObjectId": object_id, "sections": sections, "controls": controls,
})
```

| 项 | 真机 | 工厂 | 结论 |
|---|---|---|---|
| 端点 | `/api/platform/Layout/SaveLayoutDetail` | 同值（`endpoints.py:48`） | ✅ 一致 |
| 布局 id 键 | `id` | `id` | ✅ 一致 |
| **对象 id 键** | **`objectId`** | **`basicObjectId`** | ❌ **不符（D-C）** |
| 顶层键数 | **17** | 4 | ⚠️ 差 13 个（含 `code`/`name`/`source`/`status`/`objectTypeId`/`pages`/`isMain`…） |
| section 键数 | 62（非空 14） | 6（`id`/`name`/`code`/`type`/`columnsNum`/`sort`） | ⚠️ 差 56 个 |
| `controls` 元素形状 | **本次为空，未取到** | 7 键 | ❓ 仍未验（段 1 的目标） |

### D-C 的性质（与 D-A 同族）

`basicObjectId` 与真机的 `objectId` **不是同一个键名**。同一个文件里的**列表布局**那条却用的正是
`objectId`（`layouts.py:133` 的 `LISTLAYOUT_SAVE`）——**同一个文件内部两套口径**。
这与 **D-A**（`columns` vs `listlayoutColumns`）是同一形态：**平台自己客户端发的键名，与工厂猜的键名不一致**。

⚠️ **后果未验**：平台可能（a）忽略未知键并按请求体里没有 `objectId` 处理、
（b）静默保存到别处、（c）直接报错。三种都没见过。**不要**按"接口回成功就算对"来推——这正是 #62/#63/#67/#69 那一族的教训。

## 5. 待核实（本次**没**回答的）

1. **`controls` 的元素形状**（最重要的缺口）：这个默认布局**一个字段控件都没有**，

2. **`gridSpan` / `columnsNum` / `labelCols` 的取值语义**：本次全 `null`，只能看到键存在。

4. **`code` 为什么被脱敏成 `***`** —— ✅ **2026-09-22 已判**：原始值是 **25 字符、全 `[a-z0-9_]`、
   `PLATFORM_CODE_RE.fullmatch = True`** ⇒ 撞上"像令牌"的兜底启发式，`redact_text` 把它打成 `***`；
   而 `find_secrets`（扫描器）**豁免**它 ⇒ **这是 `redact.py` 里刻意的不对称**（脱敏侧不豁免，方向偏安全）。
   但它与 README 的"对象/字段/选项集编码**保留**"承诺冲突。
   **影响面已量化**：9 份入库会话里被打码的业务值**只有这 1 个**（其余 26 处是 `traceId`，打码正确）。
   ⇒ 处置：**不改刻意设计**，README 补上这条例外并写明**兜底口径 = 读运行时原始日志**（本地、不入库）；
   是否改成"脱敏侧也豁免"列为决策 **E7**。
5. **`source` 是否唯一标识"默认布局"**：`isMain=true` 同时成立；手册说「默认布局」与「用于创建」
   是两个互斥标记（`01D §2.4/§6.1`）⇒ 若两者 `source` 都是 2，工厂的单路径查找会**拿错布局**。

- 用户在其中**4 个控件上都选了「半行」** ⇒ 无论"半行/整行"落在哪个键上，

- 若"半行/整行"**不在** `controls[]` 里，而在 `sections[]` 的 `gridSpan` 上（段 0 里它是 `null`），
  那说明这一层的语义与手册的分层说法不一致 ⇒ **手册对、还是真机对，单独记一条**。

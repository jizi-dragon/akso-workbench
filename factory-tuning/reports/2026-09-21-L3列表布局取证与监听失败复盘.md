## 2. 缺陷 D-A：数组键名不符（真机已确证不符；后果未验）

| | 值 |
|---|---|
| 真机发的 | `"listlayoutColumns": [...]` |
| 工厂发的 | `"columns": [...]` —— `workbench/services/egmp/writers/layouts.py:119` |

### 2.1 怎么确证"工厂确实发的是 `columns`"

**不是看源码猜的**。链路上唯一可能改名的地方是客户端，而它不改名：

```python
# workbench/services/egmp/client.py
def post(self, path, body=None):                    # :210
    return self._envelope("POST", path, body or {}) # :211

def _envelope(self, method, path, payload):         # :192
    resp = self._http.request(method, path, json=payload if method == "POST" else None)  # :193
```

`post()` → `_envelope()` → `json=payload`，**原样透传**，没有信封包装、没有键名映射。

### 2.2 排除法（把"别的地方错了"逐个排掉）

| 项 | 真机 | 工厂 | 结论 |
|---|---|---|---|
| 端点路径 | `/api/platform/Listlayout/AddColumns` | `endpoints.py:52` 同值 | ✅ 一致 |
| 列元素形状 | `{fieldId, fieldPath, sort}` | `layouts.py:151` 同三键 | ✅ 一致 |
| `sort` 基准 | 1 起 | `spec.py:256` 示例 1 起 | ✅ 一致 |
| **数组键名** | `listlayoutColumns` | `columns` | ❌ **不符** |

⇒ **差别只在这一个 token 上。**

### 2.3 ⚠️ 后果**未验**（不要当成已成立）

`AddColumns` 是**全量替换**语义（`layouts.py:118` 的注释自己写着「非追加」）。
所以最坏情形是：**平台没看到 `listlayoutColumns` → 当成空列表 → 把列表的列清空**。

那就是又一次「**接口回成功、回读才发现空**」——与 #62 / #63 / #67 / #69 同形。

**但本次没有真机复现这一步**，所以：平台究竟是"忽略未知键"、"报错"、还是"清空"，
**现在不知道**。定性方法见 §9 第 2 条。

## 3. 缺陷 D-B：全量替换却不读旧列（代码已确证）

### 3.1 一行判据

```powershell
.\.venv\Scripts\python.exe -c "import pathlib;print('LISTLAYOUT_COLUMNS' in pathlib.Path('workbench/services/egmp/writers/layouts.py').read_text(encoding='utf-8'))"
# 实测 False —— writers/layouts.py 里连这个常量都没有 import
```

`LISTLAYOUT_COLUMNS = "/api/platform/Listlayout/Columns"`（`kernel/endpoints.py:50`）
全仓**只有一个调用方**：`insight/lifecycle.py:149`——那是**只读洞察层**。
`writers/layouts.py` 从头到尾没用过它。

### 3.2 刺眼之处：同一个文件里的另一个函数**恰好相反**

`build_form_layout` 先读回旧结构，再拿旧值当种子合并：

```python
detail = get_form_layout_detail(client, str(default_layout.get("id")), object_id)   # :64
old_sections = list(detail.get("sections") or [])                                    # :65
old_controls = list(detail.get("controls") or [])                                    # :66
sections = [dict(s) for s in old_sections]                                           # :69  ← 旧值当种子
controls = [dict(c) for c in old_controls]                                           # :70
```

`build_list_layout` 则**完全按蓝图重建**，一个旧列都不读（`layouts.py:142-153`）。

### 3.3 而规则**就写在这个文件的第 4–5 行**

> ⚠ SaveLayoutDetail / AddColumns 均为全量替换语义：**必须先读旧结构、合并新内容后再整体提交**
> （上游实证，**漏读合并 = 清掉平台已有布局**）。

⇒ **规则写在文件头上，两个函数里有一个违反了它。** 表单布局遵守了，列表布局没有。

### 3.4 它和平台事实正面相撞（见 §4 F16）

开了生命周期的对象上，列表布局的「状态」列**不可移除**，新建布局时也**强制要求添加**。
工厂的全量替换里**不带**那一列。⇒ D-B 不是理论问题，它必然在带生命周期的对象上发生。

### 3.5 顺带说明：`status_id__sys` **不能硬编码**

强制列**随对象变**（开了生命周期才有状态列）。所以正确修法不是"把 `status_id__sys` 补回去"，
而是 §3.3 那条规则本身：**读旧列 → 合并 → 提交**。新建布局也适用——`Save` 建完之后布局就**可读**了，
"新建"不是"没有旧列可读"的例外。

## 7. ⚠️ 采集本身的失败（本次最大教训）

### 7.1 现象

第二段（21:11:28 – 21:29）录到 **`total: 0`**。用户在这段时间里做了：
新建列表布局、表单布局（两个部分 / 5 个半行控件 / 3 个整行控件 / 调整部分顺序 / 删除两个部分）、
创建两个生命周期状态并停用一个。

**一条都没录到，而监听不会报警**——`monitor_stop` 平静地返回 `total: 0`。

### 7.2 已排除的解释

| 猜测 | 怎么排除的 |
|---|---|
| 跑的是旧产物（PITFALLS #20/#25） | 实际进程是 `D:\akso\akso-mogul\.venv\Scripts\python.exe -m uvicorn workbench.api:app`，父进程是 Electron 壳（PID 25832）；**不是** `dist/AksoServer`（9/15 那个） |
| 监听没挂上 | `monitor_start` 成功返回，且 `recorder.start()` 里的 `page.evaluate(ACTION_BUFFER_JS)` 在那个页面上**执行成功**（页面是活的） |
| 平台开在新标签页 | `http://127.0.0.1:18766/json/list` 只有 **2 个 page**：平台页 + Workbench 自己的页。**平台上不存在第二个标签页** |
| 用户在别的窗口操作 | 被监听那个 page 的 URL 是 `/admin/config/form-layout/edit?id=cec10709-…`——**正是用户描述的表单布局配置器** |

### 7.3 已确证的两条（互相矛盾，所以问题还没解决）

- ✅ **监听引擎本身是好的**：在旧 page 上由 AI 协作者**自造流量**
  （`POST /api/browser/navigate` → `entry.page.goto`）→ `total: 16`
  （全被 `classify()` 当 GET 丢掉，但 `total` 在分类**之前**就计数了）。
- ❌ **关闭会话后新开的 page** → `total: 0`，即使用户在该页面里导航进了配置器
  （SPA 路由切换至少该有一次取数据的 GET）。

### 7.4 ⇒ 两种解释，**本次没分辨出来**

| | 解释 | 含义 |
|---|---|---|
| **A** | 配置器里的操作（含"删除两个部分"）**全是本地编辑，从未点保存** | 0 条是**正常的**，不是缺陷 |
| **B** | 监听对"关闭后新开的 page"**不再收事件** | **产品缺陷** |

**分辨方法**（下次第一个动作，30 秒）：在配置器里点一次**保存**，再读实时 `total`（见 §7.5）。
`total > 0` ⇒ A；仍为 0 ⇒ B。

### 7.5 两条有用的操作口径（本次踩出来的）

**① `monitor_start` 在监听已开时返回实时 stats**（`browser_pool.py:587-589`）：

```python
if entry.monitor is not None and getattr(entry.monitor, "_active", False):
    return {"monitoring": True, "log": ..., "stats": entry.monitor.stats, ...}
```

⇒ **可以在不 stop 的情况下轮询 `total`**。这是本次唯一有效的排障手段，值得写进 README。

**② 但"开监听时那次 `_do_open` 的流量"录不到**：

```python
if entry is None or entry.context is None or entry.page is None:
    self._do_open(pw, browsers, sessions, account_id, True)   # :583 ← 内部已 goto 平台 + sleep(2.5)
...
recorder = MonitorSession(entry.page, output_dir)            # :593
recorder.start()                                             # :594 ← page.on("request") 在此刻才注册
```

⇒ **不能用"新开窗口的加载流量"来验证监听是否工作**（我第一次探针就是这么设计错的）。
要造流量，得在挂载**之后**触发（例如 `POST /api/browser/navigate`）。

### 7.6 另外两条本次确认的采集侧限制

- **`flush()` 只在 `stop()` 里被调用**（`monitor.py:222-234`）
  ⇒ 中途崩了整个会话丢光。这就是本次采用"**做一项、停一次**"分段的理由；
  `ingest.py --session <名字>` / `pick_session()` 支持按名收，**分段不会漏收**。
- **`desktop/main.js` 每个账号只建一个窗口，且没有 `setWindowOpenHandler`**
  ⇒ 平台页面里任何 `window.open()` / `target="_blank"` 都会开出一个
  **壳不管、监听看不到**的窗口。本次**未确证**是否发生过，但它是"录不到"的
  一个已知可能入口，值得单独验一次。

## 11. 后补更正（2026-09-22）：§1 那 8 条请求是**一次页面渲染**，不是"用户依次配了 10 列"

> **这一段是后补的。** 上文（§1–§10）保持原样，让"当时的认知"与"后来的认知"都能看见。

### 11.1 怎么发现的

不是靠重读请求体，而是靠一个**当时看不见的字段**：每条记录其实都带毫秒时间戳
（`traffic.jsonl` 里的 `at`，由 `ingest.py:89` 写入），但**分析器把它丢掉了**——
`analyze/model.py` 的 `Entry` 没有这个字段、`_entry_from_row` 也不读它。
于是"这些请求是在多长时间里发生的"这件事，**在分析层根本表达不出来**。

补上之后（`Entry.at` + 报告 §3 的「时刻 / 距上条(ms)」两列 + 突发警示），真机数据立刻分成两类：

| 会话 | 写请求 | 跨度 | 形态 |
|---|---|---|---|
| `acct-fb8dc317-20260921-160313` | 20 | **221 秒** | **人的节奏**：`SaveField` 每 15–33 秒一次，每次后面 0–3 秒紧跟一次 `FieldPage` 回读 |
| `acct-891a4f9d-20260921-210820` | 8 | **165 毫秒** | **一次页面事件**：菜单组 → 4 个视图计数（4 个不同 `viewId`）→ 字段定义 → `AddColumns` |

⇒ `…-210820` 那 8 条**全部落在同一个 165ms 突发里**。没有任何"人的操作"能在一百六十五毫秒内
完成菜单组查询 + 四个视图计数 + 字段定义 + 提交十列布局。它是**页面渲染/切视图时平台自己发出的一串请求**。

### 11.2 哪些结论**不变**

- **D-A（键名不符）完全不变。** 它比的是**平台自己客户端发出去的键名**
  （`listlayoutColumns` vs 工厂 `layouts.py:119` 的 `columns`）——
  与"这一发是页面渲染还是人工点击"**无关**。平台侧的线格式就是 `listlayoutColumns`。
- §1 从请求体直接读出的另外三件事也不变：列元素形状 `{fieldId, fieldPath, sort}`、
  `sort` 从 1 起、末尾固定带 `status_id__sys`。
- **D-B（全量替换不读旧列）不变**：它是代码事实，与本次采集无关。

### 11.3 哪些结论**要降级**

- ❌ **"用户在列表布局上依次配了这 10 列"这个读法不成立。** 请求体证明的是
  "平台把这个列表布局的**当前列集合**发了出来"，而**不是**"有人刚在界面上加了这 10 列"。
  它是一个**读-改-写式同步**（页面加载即把当前视图的列整体提交一次），
  这一点反过来**加强**了"`AddColumns` 是全量替换语义"的判断：连渲染都会整份重发。
- ⚠️ **F16 的"请求体"那一半证据要降级。** "开了生命周期的对象，列表布局末尾固定带
  `status_id__sys`"仍然成立，但因为它出自一次**渲染同步**，它只能证明
  "**状态列在该布局里**"，**不能**单独证明"**新建列表布局时被强制要求添加**"。
  F16 仍按**用户实测（两条）**为准——那两条是人工观察，不受本条影响。
- ⚠️ **§2.3 的"后果未验"仍然未验**，且本条**不构成**对它的任何验证。

### 11.4 教训（比这一条结论更重要）

1. **丢一个字段不会报错，只会让某类结论永远无法被检验。** `at` 在 `ingest` 里写得好好的，
   在分析层被静默丢掉；后果不是崩溃，而是**"这 8 条是不是一次突发"这个问题根本问不出来**——
   于是它被顺理成章地读成了一串人工操作。判据已补进 `factory-tuning/tests/selfcheck.py` 的 **H 组**。
2. **动作碎片（`precedingActions`）不能用来数操作数**（PITFALLS #64：上限 5 条且跨操作渗漏）。
   本次 8 条的 `precedingActions` **完全相同**（`状态 → svg → 确 定`），本身就是渗漏的证据。
   **Δt 才是**区分"一次页面事件"与"一串人工操作"的依据。
3. **"唯一一份真机证据"这种说法要配一个时间跨度检查。** 只有一条会话时，人容易把它读成
   自己想要的样子；加上跨度一栏，一眼就能看出它是不是你以为什么。判据：
   `python -c "import json,pathlib;rows=[json.loads(l) for l in pathlib.Path('factory-tuning/data/sessions/<会话>/traffic.jsonl').read_text(encoding='utf-8').splitlines() if l.strip()];ats=[r['at'] for r in rows if r.get('at')];print(max(ats)-min(ats),'ms /',len(rows),'条')"`

### 11.5 §7.6 的"`flush()` 只在 `stop()` 里被调用"要更正（2026-09-22 真机实测）

§7.6 写的是「**`flush()` 只在 `stop()` 里被调用** ⇒ 中途崩了整个会话丢光」，据此把"做一项、停一次"
当成了防丢手段。实测（2026-09-22）：

- `monitor.py:133` 有 **`self.page.on("close", self.stop)`** —— **页面关闭会触发 `stop()`**，
  而 `stop()` 里就有 `flush()`。实测关掉会话窗之后，那个会话目录里照样出现
  `monitor-log.json`（16 KB）/ `filter-stats.json` / `checkpoints.jsonl`。
- ⇒ **真正的丢失窗口只有"整个应用被强杀或崩溃"**（`close_all` 把 `sessions` 清掉、内存里的条目不落盘），
  比 §7.6 写的窄得多。**"做一项、停一次"仍然值得做，但理由是可分析、可复核，不是防丢。**

### 11.7 ★ §7.4 的 A/B 悬案结案：**是 A**（配置器里的编辑是本地行为，保存才发请求）

> **这一段是后补的。** 结论来自 2026-09-22 的一次**受控观察**，证据链比 §7 当时干净得多。

**§7.4 当时的分岔**：A = 配置器里的操作全是本地编辑、从未点保存（⇒ 0 条是正常的）；
B = 监听对"关闭后新开的 page"不再收事件（⇒ 产品缺陷）。

**2026-09-22 的受控观察**：
用户在**表单布局配置器**里做了一组**实打实的编辑**（新建 1 个「部分」+ 在该部分下新建 **4 个控件**、
全部设为**半行**），**尚未点保存**。同一时刻读监听实时 `stats`：**`total: 0`**
（该会话自 10:24:23 起就是这个数）。

而 `monitor.py:137-149` 的 `_on_request` 是**直接在事件回调里自增 `self.stats["total"]`** 的
——不走队列、不等 `drain()` ⇒ **实时读数是准的，没有滞后**。

⇒ **结论：A 成立。** 配置器里的"建部分 / 建控件 / 调宽度"**一个请求都不发**；
**点【保存】才把整份布局发出去**（点保存发什么，见
[段 0 报告](2026-09-22-真机取证-段0-默认布局保存.md)：一条 `SaveLayoutDetail`、17 个顶层键）。
⇒ §7 那次"录到 0 条"不是产品缺陷，是**没有保存**。

**这条结论的用法（很重要）**：
- **任何依赖"录到界面操作"的取证，都必须让演示者在每一步之后点保存**——
  否则录到的是空白，而空白**不会报警**（§7.1 的现象）。
- 反过来说：**"录到 0 条"本身现在是一个有信息的信号**——它说明那段时间里
  **平台上没有发生任何提交**（而不是"监听坏了"）。

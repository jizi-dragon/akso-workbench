## 2. ★★ 结论一：`gridSpan` 映射钉死 —— **半行 = 1，整行 = 2**

| 控件 code | 所属部分 | 演示者说法 | 实测 `gridSpan` | 请求体形状 |
|---|---|---|---|---|
| `test_file__c` / `test_fa__c` / `test_oo__c` / `test_daily_time__c` | `basic_info__cs` | **半行**（段 1 所示） | **1** | 23 键（服务端已有） |
| `test_time__c` / `test_option__c` / `if_ok__c` | `basic_info2__cs` | **整行**（本段所示） | **2** | 8 键（本段新建） |

两个部分的 `columnsNum` **都是 2** ⇒ `gridSpan` 是**以「列」为单位的跨列数**，
`columnsNum = 2` 时**满行 = 2**。这同时解释了段 1 为什么四个全是 `1`。

> **用户 2026-09-22 定稿：整行 / 半行只是控件的显示形式，不用过多纠结。**
> ⇒ 上面那三条"仍未验"**不再作为追究项**——保留在这里只是为了让读的人看见边界，
> 以及"我们不是查清楚了才停，是**它不值得查**"。
> 落到代码上够用的部分只有一句：工厂要发这个字段时，**半行发 `1`、整行发 `2`**，
> 并校验 `gridSpan ≤ columnsNum`。**不要再为它设计实验。**

## 3. ★★ 结论二：平台对「新建组件」与「已有组件」发**两套形状**

### 3.1 同一个组件，在两段里的两种形状（**天然的对照实验**）

| 组件 | 段 1（它**刚被创建**） | 段 2（它**已在服务端**） |
|---|---|---|
| 部分 `basic_info__cs` | **5 键**：`id` / `code` / `name` / `type` / `columnsNum` | **62 键**（其余 57 键为 `null` / `[]` / `0` / `false`） |
| 控件 `test_file__c` | **8 键** | **23 键**（多出 `sort` / `dataType` / `isRecalculateDefaultOnDependencyChange` + 12 个 `null`） |
| 部分 `basic_info2__cs` | ——（本段才建） | **5 键** |
| 控件 `test_time__c` / `test_option__c` / `if_ok__c` | ——（本段才建） | **8 键** |

**⇒ 形状不取决于控件种类，取决于"服务端是否已经认识它"。**

### 3.2 由此可解释的三件事

1. **段 1 那两条保存不是两次点击**：save#1（3276 B）发的是**精简形状**（4 个全新控件），
   save#2（6028 B）发的是**完整形状**——同一批控件、**服务端回显后**的形状。两条都是 `200 / code=0`。
   ⇒ 平台的保存链路里存在「**提交 → 回显 → 再提交**」的形态；本次（段 2）**只有一条**（§5）。
2. **新建控件不带 `sort`**：数组顺序即顺序（已有控件带 `sort: 1..4`）。
   ⇒ 工厂若只发 `sort` 而数组顺序不对（或反之），都可能与平台语义错位——**顺序本身是数据**。
3. **新建控件不带 `dataType`**，只带 `type`（`AK*`）⇒ 平台能从 `fieldId` / `type` 反推出 `dataType`。

## 6. ⚠️ 测量口径更正：`timestamp` 与 `precedingActions.at` **不能当因果用**

### 6.1 实测差异（"最后一次 DOM 动作 → 请求"的差）

| 会话 | 差 |
|---|---|
| 09-21 的 6 个会话 | **0.1 – 3.1 s**（正常人工节奏） |
| `…101457`（段 0） | **44.5 s** |
| `…102423`（段 1） | **38.4 s** |
| `…104043`（段 2，本次） | **61.4 s** |

且本段 5 条请求的**观测跨度只有 14 ms**。

### 6.2 两个候选机制（**未钉死**，谁也没被排除）

- **(a) 事件分发延迟**：sync-Playwright 的事件只在 worker 线程**进入 Playwright 调用**时被分发，
  而 `browser_pool.py:166` 的 `self._jobs.get()` **没有超时** ⇒ 事件可能排队几十秒才被 handler 记时间戳。
- **(b) 触发保存的不是缓冲里那次点击**：动作缓冲只挂 `click/input/change`，键盘动作、
  iframe / shadow DOM 内的点击**都不进缓冲** ⇒ 真正触发的那次操作没被记录。

### 6.3 两种解释下都成立的口径（**这才是要写进协议的部分**）

1. **5 条的顺序（3× 下拉查询 → 稳定 id → 保存）可以用** —— 它来自**内容语义**（保存流水线），不依赖时间戳；
2. **"点击 → 请求"的时间差不能用** —— 既不能当人工节奏，也不能当"用户犹豫了"的证据；
3. **`precedingActions` 是快照，不是因果标注**（段 1 §7.3 的同一条教训，这次又撞上）；
4. **`stats` 是观测值，不是线上真值** —— `total` 只统计**已被分发**的事件；
   ⇒ "读 `total > 0` 验证录制已生效"这个动作**自己会推动分发**（`monitor_start` / `session()` 都走 `_submit`），
   **读到的 0 不能证明"什么都没发生"**（这也解释了 README 记的 `240 → 517`）。
5. `GetDropdownListApiProject` 是**查询型 POST**（`{"pageIndex":1,"pageSize":1000}`），
   因不在 `QUERY_POST_PATTERNS` 里被归为"陌生写"（`RECORD_FULL`）⇒ 监听噪声分类的一个已知缺口。

## 1. 结论：新建一个表单布局 = **三步**

| 步 | 端点 | 关键特征 | 证据 |
|---|---|---|---|
| ① **建壳** | `POST /api/platform/Layout/SaveLayoutDetail` | **不带 `id`**，顶层 **11 键**，`source: 3`，`name: "新建表单布局"`，四个空数组 | #1 |
| ② **补内容** | 同上，**带 `id`** | 顶层 **17 键**，`isMain: false`、`source: 3`、`formEditStatus: 0`；先补 1 个 section（5 键精简形状），再补 section（62 键）+ control（8 键） | #4、#7 |
| ③ **换稳定 id** | `POST /api/platform/Layout/GetStableComponentIds` | **每次保存"含新组件"之前各调一次**（#3→#4、#6→#7） | #3、#6 |

**① 建壳的完整请求体**（脱敏后逐键，`#1`）：

```json
{"objectId": "id-84b1e458", "code": "sdfsdf__c", "name": "新建表单布局",
 "labelCol": 3, "source": 3, "status": 1, "objectTypeId": "id-d7ce42d5",
 "controls": [], "sections": [], "pages": [], "rules": []}
```

**响应体直接给出新布局的服务端 id**：

```json
{"code": 0, "errorCode": 0, "message": null, "data": "id-780a0884", "requestID": "…", "traceId": "***"}
```

⇒ 之后两次保存（`#4`/`#7`）带的 `id` **正是这个返回值**。**"新建"与"改已有的"在同一个端点上，
只差一个 `id`** —— 这与工厂现在"只会按 `source == 2` 找默认布局来改"的写法是两种形状。

**③ `GetStableComponentIds` 的真实形状**（这条我差点记错，见 §3）：

```json
// 请求：顶层 1 键；值是以【客户端 UUID 为键】的字典（**不是数组、不是裸字符串**）
{"componentIds": {"d1f859c2-a171-4a90-a351-5d78f7b3fde8":
   {"objectId": "id-84b1e458", "layoutCode": "sdfsdf__c",
    "componentType": "layout_section", "componentCode": "in__cs"}}}
// 响应：客户端 UUID → 服务端 id
{"data": {"stableComponentIds": {"d1f859c2-a171-4a90-a351-5d78f7b3fde8": "id-497474ac"}}}
```

两次调用的 `componentType` 分别覆盖 `layout_section`（新部分「信息」）与 `layout_control`（新控件「测试附件」）
⇒ **新部分、新控件都要先换 id，再进保存体**。

## 3. 一条**我差点记下的假差异**（留作方法教训）

我第一版脚本写的是 `for el in b["componentIds"]`，而它是 **dict** ⇒ 迭代拿到的是**键（UUID 字符串）**，
于是我一度读出"真机发的是裸 UUID 数组，与段 1 报告不符"。**核对全部 5 次历史调用后否掉了这条**：

| 会话 | `componentIds` 形状 |
|---|---|
| `…102423` #5 / `…104043` #4 / `…110842` #2 / `…121655` #3 #6 | **dict**（UUID → `{objectId, layoutCode, componentType, componentCode}`） |

⇒ **段 1 报告是对的**，我的读法是错的。**教训**：把 `dict` 当 `list` 迭代**不报错**，只给你一串键；
凡是"形状结论"，判据必须是 `type(x).__name__` + 原形 `json.dumps`，不能靠 `for … in …` 的观感。

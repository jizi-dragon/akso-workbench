## 1. 规则体系的分类与优先级

- **四层权限栈（对象级→记录级→角色级→状态级）**：权限集定基础能力 → DAC/共享规则定能访问哪些记录 → 生命周期角色定记录内的查看/编辑/删除边界 → 状态权限继续收紧字段、动作、附件、关系与审批矩阵。`14_DAC权限规则详解.md §概述`
- **权限集是唯一硬上限**：DAC 不能突破权限集；`能打开记录` ≠ `能编辑字段/执行动作`。`14_DAC权限规则详解.md §概述/§权限计算`
- **同层内冲突「取高不取严」**：同一用户命中多个记录角色时，按权限更高的角色结果生效；多来源可叠加。`14_DAC权限规则详解.md §权限计算`
- **手动共享是独立来源、不被自动规则改写**：DAC 刷新不会修改人工分配记录，撤销只能手工移除。`14_DAC权限规则详解.md §权限计算/§常见问题`
- **DAC 的作用域=记录级**：两类来源——匹配共享规则（按字段值自动匹配，授权主体**只能是用户**）、手动共享（用户 / 用户组 / 部门，业务端记录详情维护）。`14_DAC权限规则详解.md §规则类型/§手动共享`
- **匹配共享规则还带一层「树形层级」语义**：相等 / 相等且包含下级（全部子孙）/ 相等且包含子级（直接子节点）。`14_DAC权限规则详解.md §树形字段匹配`
- **审批矩阵的作用域=对象 + 生命周期 + 条件**，管的是**工作流参与人来源**，不是记录可见性，与 DAC 不共用机制。`20_审批矩阵配置.md §适用范围/§配置模型`
- **多矩阵同时命中时由数据定优先级**：按 `权重` 大者优先，`是否默认规则` 仅作"其他规则都没命中"时的兜底。`20_审批矩阵配置.md §审批矩阵管理对象`
- **审批矩阵的匹配方式沿用权限栈同一套语义**：相等 / 相等且包含下级 / 相等且包含子级 + 逐字段的 `匹配空值 vs 不匹配空值`。`20_审批矩阵配置.md §匹配字段`
- **查重规则产出「相似度分层结果」，不是拦截**：规则决定匹配字段/匹配方式/时间范围与最多 **3 个**相似度等级，业务端由用户动作触发，**不阻断保存**。`23_查重规则配置.md §2.3/§2.4/§5`
- **查重条数两条约束同时生效，且系统上限优先**：先按数据量上限截取、再过滤相似度下限；管理端允许填 1-200，**实际最多 20 条**。`23_查重规则配置.md §2.4/§9`
- **查重的选项字段有三种匹配语义，容易选错**：存在相同选项（任一命中）/ 包含待匹配的选项（需全含）/ 包含于待匹配的选项（被包含）。`23_查重规则配置.md §9`
- **编号规则的优先级来自「编号段顺序 + 重置依据」**：按拖拽顺序拼接；设为重置依据的日期/对象字段决定流水号何时重新起算；**公式字段不能作为重置依据**。`07A_编号规则配置.md §编号依据（重置依据）`
- **编号不做唯一性校验**：编号允许重复、系统不再提示（唯一性拦截面在索引/验证规则，不在编号规则）。`07A_编号规则配置.md §生成规则说明`
- **检查表的作用域=目标对象 + 检查表类型**：分类只是用于匹配设计的选项集，**不能当类型用**；类型与「检查表设计对象类型」为一对一。`17_检查表配置.md §检查表分类/§检查表设计对象类型/§注意事项`
- **检查表设计匹配：选项字段是「包含即命中」且可命中多条**：目标字段值包含设计字段值即成立，可一次实例化**多个**检查表设计。`17_检查表配置.md §启动检查表`
- **通知层的优先级：渠道专属模板覆盖通用模板**（勾选「覆盖通用模板」后该渠道优先用专属）；变量可用范围由发送场景决定。`12_通知配置.md §1.2`；`12A_消息变量配置.md §2.9`
- **模板类优先级：本地上传模板 > 系统默认模板**（检查表/考卷导入模板上传后，导出优先按上传模板生成）。`17C_检查表导入模板自定义上传.md §6`
- **文档标签：自动标注结果压过人工**——自动标注得到的标签业务端不可手工选择、不可手工移除，只能回管理端改词组后重算。`07C_文档标签配置.md §6.2`
- **[推断] 手册未给跨族全局优先级**：DAC / 查重 / 编号 / 检查表 / 审批矩阵分属不同拦截面（记录可见性、结果提示、编号生成、实例生成、参与人装配），14 个文件内**找不到**互相排序的规则。`26_联动规则配置.md`（联动）**不在本次阅读范围**，其优先级未核实。

## 2. 创建顺序与依赖

- **DAC 四项前置**：目标对象支持 DAC + 对象已启用生命周期 + 生命周期角色已配权限 + 权限集已授予基础能力，然后才建共享规则。`14_DAC权限规则详解.md §配置前提`
- **DAC 还依赖一个专门对象**：先建「用户角色设置」对象（对象类别选 `用户角色设置`）承载"用户+角色+匹配字段值"，再在生命周期角色上开两个开关。`14_DAC权限规则详解.md §匹配共享规则 配置步骤 1-2`
- **DAC 的维护位置反直觉**：共享规则入口跟随**生命周期角色**（`管理端>配置管理>生命周期>...>角色>目标角色`），**不在对象配置页**。`14_DAC权限规则详解.md §配置前提`
- **匹配共享规则逐条限量**：单条匹配规则最多配置 **5 个**规则字段；字段越多越难排查。`14_DAC权限规则详解.md §匹配共享规则 配置步骤 3`
- **审批矩阵 8 步顺序**：建配置（对象/对象类型/生命周期/锁定状态）→ 匹配字段 → 矩阵角色规则 → 维护矩阵管理数据（权重、参与人类型、提示说明）→ 角色对象补用户组/默认用户/可编辑性 → 按需启用默认职位管理 → 加入表单布局 → 工作流开始节点选「使用审批矩阵作为参与者」。`20_审批矩阵配置.md §常见配置顺序`
- **审批矩阵边配边自动建模**：启用后生成「审批矩阵管理」对象、「审批矩阵角色」子对象、角色规则选项集、「审批矩阵成员」对象；勾选后额外生成「审批矩阵默认职位管理」。`20_审批矩阵配置.md §创建后的自动生成内容/§配置模型`
- **审批矩阵的硬前置**：工作流开始节点只能选**该工作流关联对象上已配置**的审批矩阵——对象没配就选不到。`20_审批矩阵配置.md §开始节点配置`
- **查重配置三步**：建查重规则（对象 / 对比时间字段 / 查询条件 / 分层 / 显示字段）→ 在生命周期目标状态的**用户动作**里建「查重」动作并关联规则 → 表单布局放「重复识别发起记录」+「重复识别结果」两个部分。`23_查重规则配置.md §配置概览/§4/§5`
- **查重的两处外部依赖**：对比时间字段必须是对象上的日期/日期时间字段；「处理结论」可选值来自**关系配置**中设置的关系性质，选择后系统自动把对应记录改为该配置的目标状态。`23_查重规则配置.md §2.2/§6.2`
- **编号规则顺序**：建规则（名称/Code/对象）→ 配编号段 → 设重置依据 → 保存 → 再建「业务编号流水号设置」起始值（**仅当规则设了重置依据才可创建**）。`07A_编号规则配置.md §创建编号规则/§编号流水号设置`
- **编号规则的两个接入点**：`name__ak` 启用「由系统管理字段值(只读)」时编号规则**变成必填**；生命周期进入动作选「生成编号」时先选文本类型字段、再选适用于该对象的规则。`07A_编号规则配置.md §使用场景`
- **编号段自身的约束**：一个规则**只能有一个流水号**（位数 1-10 / 起始值 / 步长）；对象字段段只支持 文本·数字·选项(取Code)·对象类型(取Code)·日期·日期时间·状态·（返回文本/数字/选项的）公式。`07A_编号规则配置.md §流水号/§对象字段`
- **检查表 4 步顺序**：维护「检查表分类」选项 → 建「检查表类型」→ 核对系统生成结果 → 在用户动作/进入动作配「启动检查表」。`17_检查表配置.md §配置步骤`
- **建类型一次铺开五类产物**：目标对象的检查表实例对象集（检查表/章节/回答/可用答案/依赖）、页面链接、检查表设计对象类型、生命周期、工作流。`17_检查表配置.md §创建后的系统行为/§检查表实例对象`
- **检查表高级能力的额外前置**：版本控制需类型开启 + 设计对象配「创建新版本」动作 + 生命周期配旧版本取代逻辑；指派需先建「检查表指派对象」（父对象下的相关对象，含 `检查表设计`/`回答人` 字段）并在目标对象页面配好区域。`17B_检查表高级功能.md §2.3/§9.2/§9.3`
- **检查表导入模板的边界**：入口在 `配置端>常规设置>检查表设计设置`，**不改设计记录本身**，只影响后续导出结构，**不追溯已导出文件**。`17C_检查表导入模板自定义上传.md §4.1/§6`
- **输出模板的前置**：运行报告模板需目标对象字段先定义好 + 准备 Word 模板文件；数据源「主对象必须与模板所属对象一致」；**出入站关系的数据源需手动配置**（对象字段可自动匹配）。`11_输出模板配置.md §前提条件/§3.4`
- **输出模板离业务端还差两步**：生命周期相应状态的用户动作里加「生成运行报告」/「下载运行报告」，并把模板绑定到对象/文档类型或放进表单布局。`11_输出模板配置.md §3.8/§3.9/§3.10`
- **通知 6 步顺序**：选模板适用对象（所有对象 / 单个对象）→ 建通用模板 → 按渠道覆写 → 在生命周期进入动作或工作流节点引用 → 配第三方渠道参数 → 联调后看消息作业监控。`12_通知配置.md §配置总流程`
- **通知的第三方前置**：邮件需 SMTP 连通；企业微信/钉钉/飞书需先在 `系统设置>第三方设置` 完成应用基础配置；短信需供应商侧模板备案 + 服务商配置。`12_通知配置.md §前提条件`；`12B_第三方设置.md §3`
- **外部 API 实时填充是两段配置**：先在 `集成管理>接口应用管理` 建应用（主机地址）+ 接口方法（请求方式/路由）+ 入参 + 出参并置启用，才能在表单布局字段控件开「引用外部数据」。`25_外部API实时填充配置.md §1.2/§2`
- **外部 API 填充的映射前置**：必须先选定「接口方法」，入参映射与赋值才可按该方法参数定义配置；方法变更后须重新检查映射。`25_外部API实时填充配置.md §3.2/§3.3/§5`
- **文档标签依赖一条字段链**：标签 ↔ 系统内置选项集「文档标签」一一对应，文档对象共享字段 `tag__ak`（选项类型）引用它；字段须加入表单布局，业务端才可见可编辑。`07C_文档标签配置.md §5/§7 Q3`
- **配错之后的补救成本（手册明说的三处）**：
  - 审批矩阵改匹配字段 → 系统在管理对象上**新增对应字段并把旧字段设为停用**（不会就地改名）；改角色规则会同步改选项集选项。`20_审批矩阵配置.md §配置规则/§规则保存后的系统行为`
  - 编号规则变更**不修改历史数据**；改起始值时「小于已有编号 → 以已有最大值为起始」，「大于 → 从新起始值续算」。`07A_编号规则配置.md §生成规则说明`
  - 对已启用的检查表类型修改范围性配置前，建议先在低风险环境验证（自动建模产物已铺开）。`17_检查表配置.md §注意事项`

## 3. 不可逆与强制项

- **查重规则**：`Code` 与「对象」保存后不可修改，其余字段可编辑。`23_查重规则配置.md §3`
- **查重规则**：被用户动作引用则**不能删除**（提示"该规则已使用，不能删除"）；停用**不影响**已产生的查重结果数据。`23_查重规则配置.md §3`
- **查重任务**：同一条记录**不能同时发起多个**查重任务；查重是异步后台任务。`23_查重规则配置.md §6.1`
- **编号规则双锁**：**已使用的规则不允许停用、也不允许删除**（使用位置由系统自动记录）。`07A_编号规则配置.md §编号规则列表/§删除编号规则`
- **编号规则的溢出与跳过行为**：流水号超位数自动加一位、**超 10 位提示「流水号溢出」**；**字段已有值时不再生成编号**。`07A_编号规则配置.md §生成规则说明`
- **编号会突破字段长度**：生命周期生成编号时若编号长度超过字段长度，**忽略字段长度设置**生成完整编号；字段段会去首尾空格、去空格与不支持符号、超长截断。`07A_编号规则配置.md §生成规则说明/§字段编号段处理规则`
- **流水号设置**：编辑时「编号规则」**只读**（不能换规则）；启用「按业务单元管理流水号」后，业务单元字段创建/编辑均不可修改，且**全局视角也不能替其他业务单元创建或导入**。`07A_编号规则配置.md §编辑流水号设置/§创建流水号设置`
- **流水号设置**：只有**启用**状态参与编号生成；关闭业务单元开关后已建记录**保留不删除**，列表恢复原展示方式。`07A_编号规则配置.md §编号流水号设置/§按业务单元管理流水号`
- **流水号批量导入硬限制**：仅 `.xlsx`、不能有合并单元格、≤5MB、≤2000 行、≤200 列；建议仅在系统初始化或编号规则切换前执行。`07A_编号规则配置.md §批量导入流水号设置`；`07B_业务编号流水号批量导入.md §注意事项`
- **审批矩阵**：名称或 Code 与系统已有对象/字段/选项集冲突时**保存失败**；只有启用状态的配置参与匹配，停用的矩阵角色规则业务侧不显示。`20_审批矩阵配置.md §创建后的自动生成内容/§配置注意事项`
- **审批矩阵**：`是否允许修改参与人 = 否` 时发起页参与人控件只读，发起人**无法纠正**系统带出的默认名单（只能提前核对）。`20_审批矩阵配置.md §配置注意事项`
- **审批矩阵**：`参与人类型 = 用户组` 时，未维护用户组的角色无法收敛候选范围，建议启用前逐项检查。`20_审批矩阵配置.md §配置注意事项`
- **检查表类型三字段创建后不可修改**：`code`、`目标对象`、`是否测验`；且创建即触发系统自动建模。`17_检查表配置.md §变更限制/§创建后的系统行为`
- **检查表工作流属系统生成内容**：手册明确"不应手动复刻系统内置逻辑"；旧的「系统开关开启检查表功能」说法**已废弃**。`17_检查表配置.md §工作流/§注意事项`
- **检查表版本控制**：首次创建设计初始版本为 `0`，新版本默认进草稿，**只有最新版本允许继续创建新版本**，新版本批准后原已批准版本被取代。`17B_检查表高级功能.md §2.2`
- **检查表导入模板结构不可回退**：必须保持「按章节分 Sheet」，**不可改回旧版固定多 Sheet**；不可删除必填字段、不可修改必填字段名、不可调整标准字段基础结构；Sheet 名按章节且不重复；保留模板说明行。`17C_检查表导入模板自定义上传.md §7`
- **输出模板**：运行报告模板「所属对象」**创建后不可修改**（编辑时也不可改）。`11_输出模板配置.md §3.0.1`
- **输出模板**：条码字段引用的**必须是文本或数值类型字段**；合并字段名称须与对象字段 API 名称**精确匹配、大小写敏感**。`11_输出模板配置.md §3.3/§3.2`
- **输出模板**（范围外旁证）：运行报告模板**在使用时不允许删除**。`24_运行报告配置.md §`（不在本次 14 文件内，仅作关联提示）
- **通知模板**：编辑时通常**不允许修改** `Code` 和 `来源`；删除前需确认生命周期/工作流/计划任务不再引用；停用后新触发不再使用该模板。`12_通知配置.md §1.7/§7 Q4`
- **通知**：批注中 `@` 用户**当前不支持**触发通知（定向通知须走工作流、生命周期动作或通知规则）。`12_通知配置.md §7 Q5`
- **消息变量**：不是所有变量在所有场景可用——工作流变量与任务变量**只在工作流场景发送时**可用，生命周期动作发送通常不提供。`12A_消息变量配置.md §2.9`
- **消息变量**：消息模板「对象」选"单个对象"才会出现该对象业务字段；选"所有对象"只有通用字段 + 所属对象字段（选错 = 变量为空）。`12A_消息变量配置.md §2.3`
- **第三方设置**：邮箱授权码是 **SMTP 授权码（非邮箱登录密码）**；短信须先在供应商侧完成模板备案，再配签名名称/通道号/模板 ID。`12B_第三方设置.md §2.3/§2.4`
- **外部 API 实时填充**：出参赋值**不支持映射到系统字段**；入参映射与出参赋值**两侧都要求类型匹配**。`25_外部API实时填充配置.md §5`
- **外部 API 实时填充必填项**：接口方法、入参映射卡片的 `入参/值`、赋值卡片的 `出参/字段`——缺任一项则业务端**不出现查询图标**。`25_外部API实时填充配置.md §5/§6`
- **文档标签**：删除标签会**同步移除**对应系统选项；停用只表示"不用于新增或更新场景"，**不回写清理历史数据**。`07C_文档标签配置.md §4.2/§7 Q2`
- **文档标签**：「计算匹配文档数」结果**不持久化**（刷新页面可重算），不能当配置字段保存。`07C_文档标签配置.md §2.3/§7 Q1`
- **文档标签自动标注重算时机固定**：升版、起草、签入、在线编辑签入、**配置迁移完成后**——不在这些时机上就看不到新结果。`07C_文档标签配置.md §6.1`
- **DAC 的刷新是异步的**：批量导入、规则变更、配置迁移后权限结果**不会立即出现**在业务端。`14_DAC权限规则详解.md §权限刷新`
- **DAC 的手动共享不会被自动清理**（"看起来像会自动回收、其实不会"）：要撤销必须手工移除。`14_DAC权限规则详解.md §常见问题`
- **DAC 出错时的固定排查顺序（8 步）**：用户状态 → 权限集 → 对象 DAC 开关 → 生命周期角色 → 匹配字段 → 权限共享来源 → 状态权限 → 后台刷新。`14_DAC权限规则详解.md §排查顺序`

## 工厂缺口候选（供上游汇总）

- **G1（修正既有台账口径）**：T2 说"顶层声明区既不执行、也不进人工配置清单"——**前半句成立，后半句要分两处看**。`orchestrate.run_full_workflow` 返回的 `manualItems[]` 确实收不到（只从 `obj.get("rules")` 收，而顶层声明在 `Blueprint` 上），但落盘的 `spec.md` 里 `generate_review_spec` **已经**把三类列进「## 人工配置项（引擎不执行）」。所以缺的是**运行期返回值**这一路，不是"完全没有清单"。判据：`orchestrate.py:286` 与 `blueprint.py:472-483` 两处。
- **G2**：`DeclarationRuleDef.manual` / `ReportTemplateDef.manual` 默认 `True`，且**全仓库无任何代码读取该字段**（`grep '\.manual'` 仅命中 `spec.py` 的注解文本）。即"标 `manual: false` 表示该由引擎实现"这条路**当前是死的**——蓝图里写什么都一样。
- **G3**：`ObjectDef.objectClass` 是 `Literal[1]`（`blueprint.py:157`），只能建"基础"类别对象。DAC 需要的「用户角色设置」对象（`14 §匹配共享规则 配置步骤 1`）与审批矩阵自动生成的多个特殊对象类别，**在模型层就表达不出来**。
- **G4**：`LifecycleDef` 只有 `statuses` + `renameStatuses`（`blueprint.py:101-104`），**没有进入动作/用户动作/事件动作**。这一条同时封死了：编号规则接入（`07A §使用场景`）、查重动作（`23 §5`）、通知触发（`12 §2.1`）、检查表启动与指派（`17 §启动检查表`、`17B §9`）、运行报告生成（`11 §3.8`）——**六族规则的最后一公里都在同一个缺口上**。
- **G5**：`build_form_layout` 只产出 section + 字段控件，且 `invisible`/`disabled` 硬编码 `False`（`layouts.py:91-97`）。这封死了：审批矩阵部分（`20`）、查重两个部分（`23 §4`）、外部 API 实时填充的控件级配置（`25 §3`）。
- **G6**：**14 个文件里没有一项被工厂真正执行**。除 G3–G5 的结构性缺口外，其余全是"平台有独立配置入口、工厂没有对应 writer"（审批矩阵 / 查重 / 编号 / 检查表 / 输出模板 / 通知 / 第三方 / 外部 API）。需决策：补 writer，还是把这一整簇**统一划入"人工配置清单"并在确认框如实呈现**。
- **G7**：顶层声明区的模型太薄，装不下这一簇的实际语义。`DeclarationRuleDef` 只有 `name/type/target/implement/manual`（`blueprint.py:185-191`），而 `14/20/23/07A/17` 的规则都带**对象/生命周期/状态/字段/优先级/匹配方式**等结构化字段。若决定"声明→人工清单"，至少要能表达"这条规则挂在哪、由谁配"。

## 1. 权限对象模型：各是什么、谁挂谁、谁是"配置交付单位"

- **权限集 = 功能上限**，九个权限范围（应用 / 管理端 / 对象 / 字段 / 对象动作 / 附件 / 审批矩阵 / 表单布局 / API），
  是整条权限栈唯一不可被下层突破的一层。`02_权限配置.md §权限集配置范围`、`§概述 NOTE`
- **完整权限栈（六层，逐层收紧）**：用户与组织 → 角色 → 权限集 → 记录级权限（共享规则 / DAC / 手动共享）→
  生命周期角色权限 → 状态权限。`02_权限配置.md §概述`
- **角色 = 岗位职责的权限容器**：`用户 -> 角色 -> 权限集 -> 具体权限点`；多角色**按并集**计算；
  手册明说**角色属于配置数据**，应在实施/配置阶段完成首批基线（角色目录、命名规范、职责边界、绑定权限集）。
  `02_权限配置.md §角色配置/§角色分配方式`、`01H_角色管理.md §概述`
- **用户组 = 批量授权的载体**，三类：普通（手工维护）/ 动态（规则自动算）/ DAC 自动映射（由数据权限管理自动创建维护，
  **不在用户组页面手工新建**）。`01A_用户组管理.md §概述/§DAC 自动映射用户组`
- **用户不直接持有权限**，通过角色获得；用户档案上的部门/职位/业务单元决定组织归属与路由。`02_权限配置.md §用户与用户组`、
  `01_用户管理.md §创建用户 字段说明`
- **部门 = 组织树**（支撑用户归属、职位关联、流程路由、按部门筛选），可加成员与职位，支持变量逻辑值供工作流引用。
  `01B_部门管理.md §概述/§部门条件与变量`
- **职位 = 岗位定义**，挂三样：**部门 + 上级职位 + 所属业务单元**；启用状态控制能否被继续引用。
  业务单元取值有优先级：**有职位时用职位的业务单元，无职位时回落到用户档案**。`01C_职位管理.md §创建职位/§业务单元取值逻辑`
- **业务单元 = 管理边界与数据范围**（旧版叫"质量组织"），属**组织主数据**，手册要求**在实施/配置阶段优先创建**，
  再开展用户、部门、职位和权限配置。`01G_业务单元管理.md §概述/§常见问题`
- **表单布局权限 = 角色 × 布局 × 权重的策略对象**：绑定角色 + 绑定布局（按对象/对象类型分组，可排序）；
  未命中任何策略 → 显示默认布局；命中多个 → **权重高且启用**者生效。`01F_表单布局权限.md §概述/§创建与编辑策略/§绑定表单布局`
- **审批矩阵管理记录 = 业务端数据对象**，维护部门/业务单元/默认规则/权重/提示说明；其候选范围来自
  **用户组或应用角色**。`09_审批矩阵管理.md §1 数据模型/§3.2 基础字段/§4.3 参与人类型`
- **"配置交付单位"三条（正面回答本簇的核心问题）**：① **权限集 / 角色 / 表单布局权限**是**纯配置数据**——
  手册明确把它们定位在"实施/配置阶段"完成，形状不依赖真实的人。`02_权限配置.md §管理端权限`（用户与组模块含"权限集、表单布局权限"）、`01H_角色管理.md §概述`
- ② **用户**必须有真实的人；**部门 / 职位 / 业务单元**是**组织主数据**，职位还强依赖部门与业务单元。
  `01_用户管理.md §创建用户`、`01C_职位管理.md §创建职位`、`01G_业务单元管理.md §概述`
- ③ **必须先有人工组织结构才能配的**（决定工厂能不能自动建）：**用户**（真实账号）、**部门**（真实汇报层级）、
  **职位**（部门 ✓ + 业务单元 ✓ 为必填）、**用户组-成员关系**（按人）、**角色→用户/用户组的分配**（按人）、
  **表单布局权限的策略绑定**（需角色已存在）、**审批矩阵管理数据 + 默认职位**（按人与岗位维护）。
  `01B_部门管理.md §创建部门`、`01C_职位管理.md §创建职位`、`09_审批矩阵管理.md §4/§5`
- **一条对工厂最要命的依赖（手册明说）**：权限集是**唯一硬上限**，状态权限 / 生命周期角色权限**都不能突破它**；
  权限集中没有对象查看或字段编辑权限时，下层配"编辑"也不生效。`02_权限配置.md §概述 NOTE/§状态权限配置/§生命周期角色权限`
  ⇒ **对象与字段权限条目必须由人逐项加入权限集**，否则工厂建出来的对象在业务端看不见。`02_权限配置.md §对象与字段权限`（建议顺序第 1-3 条）

## 2. 不可逆与强制项（逐条）

- **角色删除"通常仅在未被用户/用户组引用时可执行"**（措辞是"通常"，非硬保证）。`01H_角色管理.md §页面结构与关键操作`
- **删除角色前必须先解除与用户、用户组、流程配置的关联**，否则"避免影响线上业务"。`01H_角色管理.md §删除`
- **需要保留审计轨迹或可能恢复使用时，停用而非删除**（两条路并存，不是唯一路径）。`01H_角色管理.md §常见问题 Q3`
- **动态用户组不支持手动添加/移除成员**（成员只能由规则算出来）。`01A_用户组管理.md §动态用户组 注意`
- **DAC 自动映射用户组不可手工干预**，要改只能回【数据权限管理】改映射规则；用户组页面上"建议仅做识别和排查"。
  `01A_用户组管理.md §DAC 自动映射用户组/§管理建议`
- **DAC 自动映射用户组不在【用户组】页面创建**——由数据权限配置触发、系统自动创建维护。`01A_用户组管理.md §常见问题 Q2`
- **职位停用是"可逆但影响不可自证"**：停用后通常不再作为新增/变更的可选项，但**历史引用是否继续生效取决于各业务模块规则**——
  手册不给统一答案，要求停用前先确认审批流 / 任务分配 / 报表依赖。`01C_职位管理.md §启用状态说明/§维护影响说明`
- **移除用户或职位前须先确认审批流 / 任务分配 / 报表统计是否依赖该关系**（部门与职位两处同款警告）。`01B_部门管理.md §部门详情与关联维护`
- **业务单元能否删除取决于页面能力与依赖关系**（手册不给硬规则）；已被人/部门/规则引用时"建议先解除依赖再处理"。
  `01G_业务单元管理.md §常见问题 Q3`
- **表单布局权限策略：策略名称与 Code 唯一**（保存时校验唯一性）；**同一对象类型下只能有一个"用于创建"布局**，
  开启一个 → 同类型其他布局**自动关闭**（改回来要逐个重开）。`01F_表单布局权限.md §字段说明/§添加时规则`
- **表单布局权限的"来源"创建时由系统生成且不可编辑**（编辑期只可改名称/描述/状态/权重）。`01F_表单布局权限.md §字段说明/§编辑范围`
- **删除布局权限策略需二次确认，删除后策略与其绑定关系一并失效**。`01F_表单布局权限.md §行内操作`
- **审批矩阵管理记录：删除记录不删已匹配到业务记录上的历史矩阵**——历史快照是冻结的；但**新记录不能再命中**已删除/停用的矩阵。
  `09_审批矩阵管理.md §2 常用操作/§CAUTION`
- **矩阵角色：删除或停用不改写已保存的历史矩阵成员**，只影响后续新匹配/重新匹配。`09_审批矩阵管理.md §4.7/§8.1`
- **矩阵角色记录会立刻影响后续新匹配的业务记录**（保存即生效），已保存过审批矩阵成员的历史记录不被自动改写。`09_审批矩阵管理.md §4.2`
- **默认职位记录只有"启用"状态才生效**；用户岗位变更后须复核，否则签批时带不出职位。`09_审批矩阵管理.md §5`
- **锁定状态一票否决**：即便用户有编辑权限，记录进入锁定状态后**也不能编辑审批矩阵成员**。`09_审批矩阵管理.md §7.3`
- **用户组规则的"自动加/退"有三个触发时机**（新用户创建 / 用户信息变更 / 规则保存），意味着组织字段一改，权限归属会跟着漂。`01A_用户组管理.md §自动加入/退出触发时机`
- **权限冲突的合并方向是"更宽松"而非"更严格"**：同一条目命中多个角色覆盖时按**更宽松行为生效**。`04E_状态权限配置.md §配置步骤/§常见问题 Q2`
  ⇒ 与 `05-permissions-rules-data.md` 记的"同层取高不取严"同向，但**来源是状态权限篇**，管理员篇未写这条。
- **环境级软开关会改变"权限到底生不生效"**：管理端权限严格模式、动作安全、关系安全、表单布局权限都参与最终结果；
  宽松模式下"管理端页面可能不会完全按权限集限制"。`02_权限配置.md §管理端权限 IMPORTANT/§权限验证与排查顺序 第 7 层`、`03_系统设置.md §4.4 权限管理控制模式`

## 4. 对 E1 的支撑：哪些只能人工、哪些原则上可由工厂建

> 本节只回答"权限 / 角色 / 组织这一族"，与 `05` 的规则族（DAC / 审批矩阵 / 查重 / 编号 / 检查表）结论并列使用。

- **先落一条工厂侧事实**：`PermissionDef` 只有 `role / roleCode? / description? / grants[]` 四个字段
  （`blueprint.py:194-199`），**装不下对象级、字段级、管理端级权限点，也装不下任何组织信息**；`Blueprint.permissions:222` 只在
  `spec.md` 的「人工配置项」里渲染成一行 `权限：{role} → {grants}`（`blueprint.py:475-476`），
  `run_full_workflow` 的 `manualItems[]` 收不到它（顶层声明区在归一化时被丢弃）。**即当前"声明"这一路也没有承载位。**
- **只能人工（依赖真实的人与组织结构）**：① **用户**——`01_用户管理.md §创建用户`；② **部门**——真实汇报层级；
  ③ **职位**——部门 ✓ + 所属业务单元 ✓ 均为必填；④ **用户组-成员关系**与**角色→用户/用户组分配**；
  ⑤ **审批矩阵管理数据 / 矩阵角色 / 默认职位**（按人与岗位维护、需定期复核）。
  `01_用户管理.md §创建用户`、`01C_职位管理.md §创建职位`、`09_审批矩阵管理.md §10.3 定期复核`
- **原则上可由工厂建（纯配置对象，形状不依赖真实的人）**：① **权限集**（九类权限范围是纯配置结构）；
  ② **角色**（名称 / 编码 / 状态 / 绑定权限集）；③ **表单布局权限策略**（名称 / Code / 权重 / 状态 + 绑定布局与排序，
  且布局本身正是工厂的产物）；④ **普通/动态用户组**（名称 / 编码 / 类型 / 成员规则，成员由系统算，不需要真实人名）。
  `02_权限配置.md §权限集配置范围`、`01H_角色管理.md §创建角色`、`01F_表单布局权限.md §创建与编辑策略`、`01A_用户组管理.md §动态用户组`
- **但"可建"≠"该建"，四条反对补 writer 的理由**：
  - **性质不同**：权限对象承载的是**治理决策**，手册给的原则是"按职责命名 / 一个角色只承载一类职责 / 可审计 / 可复用 /
    建立定期复核机制"——这些**不能从蓝图推导出来**。`02_权限配置.md §角色设计原则`、`01H_角色管理.md §管理建议`
  - **交付断点不在这里，而在权限集条目化**：权限集是唯一硬上限，工厂每建一个对象，业务端要看见就必须有人把
    **对象查看 + 字段查看/编辑**逐项加进权限集；补一个"建权限集/建角色"的 writer **并不能消除这个人工步骤**。

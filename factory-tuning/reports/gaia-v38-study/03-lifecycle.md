## 1. 创建顺序与依赖

- **总顺序（手册明说的推荐步骤）**：对象启用生命周期 → 状态/状态类型/状态流转 → 进入条件·进入动作·用户动作·事件动作·状态权限 → 生命周期角色 → 验证后发布。`04 §配置流程总览（推荐步骤）`
- 同一顺序另有三个视角的复述，互为印证：状态页内「详情 → 进入条件/进入动作 → 用户动作 → 状态权限」、条件「先流转再进入条件再动作条件」、动作「先进入动作再用户动作再事件动作」。`04 §配置顺序建议` `04H §六` `04I §推荐配置顺序`
- **一切的前置门**：必须先在**对象**上勾选"启用生命周期"，由系统自动创建生命周期；对象未启用时下游全部无从配起。`04 §前提条件` / `04C §前提条件` / `04E §前提条件` / `04F §前提条件` / `04G §前提条件`
- **状态必须先于流转**：状态流程矩阵的行/列都取自已有状态，且"已完成状态转换关系配置"是流转图的显式前置。`04G §前提条件` `04G §二`
- **角色必须先于状态权限**：状态权限按角色做覆盖，前置写的是"已配置生命周期角色"。`04E §前提条件` `04E §2 配置角色覆盖`
- **状态类型可并行于状态**：创建状态类型只需"已完成生命周期基础配置"；但**映射**必须选生命周期里**已存在**的状态。`04C §前提条件` `04C §将状态类型映射到生命周期状态`
- **阶段组在对象开生命周期之后再配，并有第二个开关**：除生命周期外还需对象上开启"生命周期阶段"开关，`stage__sys` 字段才会被创建。`04D §前提条件` `04D §生命周期阶段系统字段 → 创建前提`
- **关系类状态权限有两个额外前置**：关系必须已启用"启用关系安全设置"，且对象/父对象已启用生命周期，否则关系**不出现在**状态权限分组里。`04E §启用关系安全`
- **事件动作挂在生命周期层、不绑状态**，但与状态内动作共用同一套条件表达方式。`04H §事件动作中的条件入口` `04I §三`
- 手册给的一条前置建议：**先完成对象配置与工作流配置，再动生命周期**，避免后续反复调整。`04 §前提条件`
- 工厂侧的顺序【代码事实，非手册】：`orchestrate.py` 把生命周期排在**布局之后、工作流之前**，工作流从 `steps.lifecycle.lifeCycleId` 取生命周期 id。`orchestrate.py:245-271`
- `[推断]` 生命周期 id 拿不到时（`life_id` 为空串）**没有硬门禁**：`validate_blueprint` 对"配了 workflows 却没有 lifecycle"只给 warning。`docs\FACTORY-VERIFICATION-PLAN.md §L4 已知怀疑`

## 2. 不可逆与强制项

- **"启用生命周期"开关一旦创建不可修改**——原文两处：前提条件与版本记录 v2.7 都点名强调，必须在对象建模初期确认。`04 §前提条件` `04 §变更记录 v2.7`
- **系统自带两个状态（F17 的平台侧对应）**：生命周期由系统自动创建，开出来就带"开始/关闭"（= 初始状态/完成状态）。`04 §状态类型（初始状态→开启、完成状态→关闭）`
- **状态不可删除、只能停用（F18）**：手册只说"不能删除有文档停留的状态"；**完全不可删除**是用户真机结论。`04 §常见问题 Q1` + `docs\FACTORY-VERIFICATION-PLAN.md §8 F18`
- **开启生命周期会多出系统字段** `status_id__sys`（真机 F16-L1b）；手册对应条文是 `state__ak` 由生命周期状态接管、不再可手改。`04 §State（记录状态）→ State 控制规则` + 台账 F16/F19
- **初始状态/完成状态是系统级标识，不是普通状态**：状态流转页悬停菜单可直接"设置为初始状态/设置为完成状态"，即二者是生命周期上的**单一**标识位。`04G §二 关键操作 3` `04 §附录 状态类型分类`
- **初始状态每个生命周期只有一个**（终态"通常不可逆转"是描述而非硬约束）。`04 §附录 状态类型分类`
- **新建记录进入初始状态时不执行进入动作**（系统默认行为，非缺陷）；`已变更` 运算符在该场景也不适用。`04 §常见问题 Q3` `04I §一 NOTE` `04H §运算符`
- **新建记录进入初始状态时也不检查初始状态的进入条件**；仅从其他状态回到初始状态时才校验。`04H §1 配置进入条件 → 使用建议`
- **每个状态都必须有一个"工作流取消状态"**，默认"工作流发起时状态"；这是必配项而非可选项。`04 §工作流取消状态规则`
- **流转矩阵勾选后实时生效、无需保存**，因此误勾没有"取消保存"这条退路。`04G §二 关键操作 1`
- **每个生命周期状态只能归属于一个阶段**（同阶段可含多状态，反向不可）。`04D §状态归属规则`
- **同一对象类型只能绑定一个阶段组**；阶段组与阶段的名称/Code 各自必须唯一。`04D §详情字段说明` `04D §阶段字段说明`
- **三个阶段组开关项**：阶段组、阶段各有"启用/停用"；生命周期对象本身也有"状态"（启用/停用）。`04D §详情字段说明` `04D §阶段字段说明` `04 §编辑生命周期 字段编辑规则`
- **生命周期与状态两层都可"停用"，但手册没有给删除按钮**——通篇只有"状态：启用/停用"这类下拉，无删除操作，与 F18 一致。`04 §状态表常见字段` `04 §编辑生命周期`
- **应用范围选"特定生命周期"时"生命周期"字段才出现且必填**；"状态必填"控制映射时是否必须指定状态。`04C §范围选择` `04C §字段说明`
- **权限只能向下收敛、不能越权**：状态权限不能突破权限集的对象权限上限；同一条目命中多个角色覆盖时按**更宽松**者生效。`04E §权限评估规则` `04E §常见问题 Q1/Q2`
- **角色权限有联动强制**：勾"编辑"自动授予"查看"，勾"删除"自动授予"编辑"+"查看"。`04F §权限联动规则`
- **新增角色默认只获得"查看"**；一个用户动作**只能维护一组条件校验**（要多分支必须拆中间状态）。`04F §添加生命周期角色` `04I §二 NOTE`
- **新增状态类型后若生命周期已上线，必须先沙箱验证再推广**。`04C §与生命周期配置的关系 TIP`
- **不在本文阅读范围内的强制项**（仅点名，不展开）：布局里"状态流图"部分需**发布**后才在业务端显示。`04G §五`

## 3. 停用与状态生命周期

> 本节是全篇信息最薄的一节：8 份文档**没有任何一节**专讲"状态如何退休"。以下逐条给出手册**实际写了什么**，以及**没写什么**——「没写」本身就是工厂要防的坑。

- **停用是从哪两个入口做的**：① 状态**创建/编辑**页的"状态"下拉（控制该状态配置是否启用）；② 生命周期**编辑**页的"状态"下拉（控制生命周期本身是否启用）。`04 §创建生命周期状态 字段说明` `04 §编辑生命周期 字段编辑规则`
- **停用只影响"配置是否可用"，手册没写"记录会怎样"**：状态列表的"状态"列在手册里的唯一解释是"该状态配置是否启用"。`04 §状态表常见字段`
- **手册对"停用后已流转的记录怎么办"零覆盖**：没有迁移、没有回退、没有提示语；唯一相关的是"不能删除**有文档停留的**状态"（FAQ Q1，且不是停用条文）。`04 §常见问题 Q1`
- **手册对"能否重新启用"零覆盖**：启停是同一个下拉的两次选择，手册既未说可逆也未说不可逆。`[推断]` 既然是下拉的对称选项，重新启用大概率可行；但**不可据此在工厂里承诺可逆**。`04 §创建生命周期状态 字段说明`
- **停用态的状态是否还出现在映射/流转/权限里，手册零覆盖**（`04C §映射字段说明`、`04G §二`、`04E` 均未提"仅启用可用"——只有状态类型一处明说"仅启用可用于映射"）。`04C §字段说明 → 状态`
- **F18 的"只能停用、无撤销键"在手册里的投影**：全篇检索不到生命周期状态的删除操作/删除按钮/删除确认；对比之下角色有明确的"移除 + 确认窗口【继续】"。`04 §状态 操作列表` vs `04F §移除生命周期角色`
- **手册里唯一一条"状态退休"的正向路径是重命名而非删除**：把系统自带的初始/完成状态改名复用，是官方推荐的收敛做法（另有"修改状态名称不影响现有文档"）。`04 §状态类型` `04 §常见问题 Q1`
- **整条生命周期也有停用态**，但手册的处置建议只有"仅在需要上下线生命周期时修改状态，避免频繁切换影响业务"。`04 §使用建议（编辑生命周期）`
- **阶段组/阶段各自也能停用**，同样没有停用后的业务端表现说明。`04D §详情字段说明` `04D §阶段字段说明`
- **手册给的"退休"治理动作是终态收敛**，不是停用：终态"通常不可逆转"，配置终态时要同步核对"状态转换可达、角色权限收敛、进入动作不触发不必要联动"。`04 §创建生命周期状态 → 校验与命名建议 3`
- **工厂现状（代码事实）**：**"停用"这个词在 `writers\lifecycle.py` 里完全不存在**——只有 `create_status(... is_enabled=True)` 与 `update_status(is_enabled=...)`，且蓝图 `StatusDef` 不暴露它。`writers\lifecycle.py:24-43` `writers\blueprint.py:89-92`
- **工厂连"改状态"这条路也是断的**：唯一的状态修改动词走 `client.request("PATCH", …)`，而 `EgmpClient` **没有 `request` 方法**（只有 get/post/paged_post），调用即 `AttributeError`。`writers\lifecycle.py:42` vs `client.py:192-226`
- **这个断点被测试台架掩盖**：`FakeEgmpClient` 既**有** `request`（`fakes.py:99`，只 append 一条 trace 就返回 `{"ok": True}`，**不改任何状态**），又预置了平台默认状态，于是示例蓝图的重命名路径走路过测试却什么都没做。`tests\fakes.py:99-101` `tests\fakes.py:41-44` `tests\test_native.py:54,147-151`
- **因此工厂的 `renameStatuses` 在真机上大概率是 AttributeError 而不是"改名失败"**：`build_statuses` 仅当"找到系统状态且新名字不同"才调 `update_status`，示例蓝图恰好命中该分支。`[推断]`（依据上述两处代码事实，未真机验证）
- **AGENTS.md 规则 36 同族**：缺"停用"动词不会报错、不会让测试变红，只会让"先建后用、用错再停"的流程走不通，最后表现为模型输出"请你到页面上把那个状态停用"。`AGENTS.md §1 规则 36`

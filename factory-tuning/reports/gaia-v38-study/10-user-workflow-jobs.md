## 1. 工作流在业务端实际怎么跑

### 1.1 发起链路（从"在哪个状态能发起"到"状态变了"）

- 前提三件：记录处于可提交状态（手册举例"草稿"）、用户有"提交"权限、按钮可用。`01_发起审批.md §前提条件` / `§操作步骤 2`
- 按钮点不动时的两个官方解释：**当前状态不支持提交**（举例"已是生效状态"）或**没有提交权限**。`01_发起审批.md §常见问题 Q1`
- 发起弹窗里要填：审批人、到期日期、提交说明、附件（仅当工作流配了附件字段）；配了审批矩阵时多一块"审批矩阵参与者"。`01_发起审批.md §操作步骤 3` / `§操作步骤 4`
- 矩阵必填角色没人时**提交被拦**：界面红色高亮、提示"请完成第 N 项的配置"，补齐后才能提交。`01_发起审批.md §操作步骤 4` / `§常见问题 Q3`；`08_审批矩阵.md §提交校验`
- 若节点要求电子签名，提交环节还要：读签名说明 → 输账号密码 → 选签名含义（如"我已创建并确认此内容"）。`01_发起审批.md §操作步骤 6`；`03_电子签名.md §场景二`
- **【改状态时刻 ①】** 提交成功后记录从"草稿"→"审批中"，内容被锁定不可编辑，审批人收到任务通知。`01_发起审批.md §结果验证`
- `[推断]` "审批中/草稿"是**举例用的状态名**，不是系统固定状态；能发起的状态由工作流"启动状态"字段限定，**不设置则不受指定状态限制**。`05_工作流配置.md §2.1 创建页字段表` `§2.2 详情区域字段`
- `[推断]` 提交这一步本身**不保证**任何具体状态名，只保证"进入被配置成接收该流程的那个状态"。

### 1.2 处理链路（任务怎么被做完）

- 待办入口：首页"我的任务"视图 + 顶部导航"任务"菜单；移动端任务列表按配置开放。`02_完成任务.md §从首页查看` / `§从任务菜单查看完整列表`；`07_用户任务.md §展示位置`
- 审批任务只有两个动作：**批准**、**拒绝**；评审任务="完成评审"；签署任务="签署"；领取任务="领取、添加参与人"。`02_完成任务.md §任务类型`
- 批准：点批准 → 填审批意见（可选/必填视配置）→ 需签名则输密码 → 确认批准。`02_完成任务.md §批准文档`
- 拒绝：点拒绝 → 填拒绝原因（**通常必填**）→ 确认 → **文档返回给发起者修改**。`02_完成任务.md §拒绝文档`
- 批准/拒绝/完成评审时可在提交窗口上传附件，附件与本次处理记录一起保存并进工作流时间线。`02_完成任务.md §完成任务时上传附件`
- 领取类任务默认不在你名下：要先在【我的任务】>【可领取】点【领取】，任务才转入【待处理】。`07_工作流入门.md §3.2 处理"可领取"任务`
- 批量送审（多文档一起送）成功后系统**只生成一个审批待办**，审核人在同一任务里处理整批文档。`04_批量审批.md §关键行为` / `§常见问题 Q1`
- 外部协作也产出任务：临时账号登录处理，或**回复邮件**（正文含配置的关键词如"同意/拒绝"，邮件主题须含任务业务编号）。`02_外部协作.md §协作方式` / `§通过邮件完成任务`
- 外部协作的结果核验明说"任务状态在系统内同步更新"，即邮件回复也是一条合法的完成任务通道。`02_外部协作.md §结果验证`

### 1.3 会改变记录状态的时刻（★ L5 第 ⑤ 条的判据来源）

- **① 提交审批**：状态从"草稿"→"审批中"，内容锁定。**这是唯一一条手册直接写死"提交必然改状态"的时刻。** `01_发起审批.md §结果验证`
- **② 拒绝/退回**：手册说"文档将返回给发起者修改"、"文档通常返回草稿状态"。`02_完成任务.md §拒绝文档` / `§常见问题 Q3`
- `[推断]` ②的"返回草稿"是**通常**而非必然——它取决于拒绝分支上是否挂了"修改状态"动作节点，或者生命周期里草稿状态是否可达。`01_产品介绍\06_生命周期与工作流.md §集成方式`（图里写"拒绝 → 状态 → 草稿"）
- **③ 动作节点（修改状态）**：批准/拒绝这类**任务动作本身不改状态**，状态变更由流程里的"动作"节点执行，或由用户动作单独触发。`05D_动作节点配置.md §1.2 动作设置区` / `§1.4.1`（"修改状态：修改当前记录的生命周期状态"）
- **④ 直接扭转状态**：详情页【扭转状态】/【修改状态】是与工作流并行的一条改状态通道，且同样可能弹电子签名。`03_电子签名.md §场景四`；`09_CA电子签名.md §场景二`；`10_电子签名_数字身份认证.md §场景三`
- **⑤ 取消工作流**：记录自动迁移到该状态的**"工作流取消状态"**，默认值就是"工作流发起时状态"；若该状态被改成指定状态（如"评审未完成"），取消后进那个状态。`04_对象生命周期配置.md §工作流取消状态规则`
- `[推断]` 所以**取消工作流也是一次状态变更**，且它的目标状态由"取消时记录所处的那个状态"上的配置决定——同一流程在不同状态取消，落点可能不同。
- **⑥ 动作节点"修改状态为工作流启动时状态"**：把记录状态恢复为流程启动时的状态，手册明说适用"撤回、退回或补偿处理"。`05D_动作节点配置.md §1.4.1`
- **⑦ 作业改状态**：对象操作 / 文档操作作业执行 `修改状态` 也会改记录状态，审计里操作用户显示为**系统**。`12_作业管理.md §4.1.3` / `§10 审计追踪`
- **⑧ 生命周期进入动作**：进入某状态时自动执行的 `修改状态`（第 18 项进入动作）也是一次状态推进，且不可见。`04I_生命周期用户动作、进入动作、事件动作配置.md §一、配置进入动作`
- ⚠️ **⑦⑧ 与活跃工作流互斥**：作业动作选"修改状态"时必须显式决定"是否在执行前取消活跃工作流"，不取消而记录上有活跃工作流，**作业会执行错误并记异常日志**。`12_作业管理.md §4.1.3 动作配置`（对象）/ `§4.2 创建文档操作作业`（文档：可能无法直接修改状态）

### 1.4 任务与工作流的终态及其后果

- **任务级**：用户任务只有两个状态——`待处理 Open` / `已完成 Complete`，变更进审计追踪。`07_用户任务.md §状态说明`
- **任务级**：工作流任务的状态取值散落在"更新共享设置"的事件枚举里：`任务指派 / 任务完成 / 任务取消 / 任务重新指派 / 任务移交 / 任务领取 / 撤销领取 / 任务代理`。`05B_工作流任务节点配置.md §1.2 更新共享设置`
- `[推断]` 合起来看，任务终态至少有四种：**完成 / 取消 / 移交（换人，非终态）/ 代理**；而"撤销领取"是把领取类任务退回可领取池的一次**回退**，不是终态。
- **取消任务**：任务状态更新为"已取消"（以页面显示为准），不再由当前责任人执行；但**取消任务不影响串行指派逻辑**。`06_管理活动工作流.md §2. 取消任务`；`05B_工作流任务节点配置.md §1.6 NOTE`
- **工作流级终态（业务端）**：`进行中` / `已完成` / `已取消` 三态；取消会**终止该流程下未完成的任务**且流程不再流转。`06_管理活动工作流.md §工作流状态` / `§1. 取消工作流程`
- **工作流级终态（配置/监控侧）**另有 `已失败`、`已暂停`（暂停=等待人工干预），异步步骤失败时按指数退避重试。`05_工作流配置.md §5.1 实例状态` / `§5.2 作业重试机制`
- **拒绝的后果**（不是终态，是回退）：记录交回发起人修改，审批要重新走一遍；已经处理过就不能撤回，必须"退回后修改"。`02_完成任务.md §常见问题 Q3`；`01_发起审批.md §常见问题 Q4`
- **撤回的真相（两处口径不一致，逐字记下）**：发起页说"如尚未处理，可撤回修改后重新提交"；完成任务页 FAQ 说"**通常不能撤回**，请联系工作流管理员"。`01_发起审批.md §提交后可以做什么` / `02_完成任务.md §常见问题 Q2`
- 用户任务完成后**不支持直接撤回**，只能重建任务或补一条纠正任务。`07_用户任务.md §常见问题 Q3`
- **已完成/已取消的流程不可再执行管理动作**（重新分配/取消任务/移交/改截止时间全部失效）。`06_管理活动工作流.md §注意事项`
- **超时的三种后果**（按配置）：发超时提醒 / **升级给上级** / 工作流暂停等待人工干预。`02_完成任务.md §超时后果`

## 2. 任务与人的关系

### 2.1 任务出现在哪里

- 三处：首页"我的任务"视图、顶部导航"任务"菜单、移动端任务列表（按系统配置开放）。`02_完成任务.md §查看待办任务`；`07_用户任务.md §展示位置`
- 任务列表字段能当"责任链证据"用：任务责任人、**工作流负责人**、任务类型、工作流、截止日期、**接受时间**、**移交前责任人**、来源业务单元。`02_完成任务.md §待办任务信息`
- 通知消息只在两个入口：首页顶部消息图标（站内信面板）+ 首页消息列表；消息里带链接时可直接点进业务页面。`03_通知消息.md §功能简介` / `§站内信面板内容`
- 删通知**不动业务**：不影响记录、任务、审批或日志。`03_通知消息.md §删除通知消息` / `§常见问题 Q4`
- 首页任务量大的时候按"关联对象状态"筛选——**这是从任务列表反查记录状态的入口**，L5 验证时可直接用。`02_完成任务.md §在首页检索任务`

### 2.2 参与人怎么被决定

- 决定权在**配置端**，业务端只做确认与增删：任务节点的"将任务分配给"= 工作流发起人 或 参与者组（参与者组在开始节点定义）。`05B_工作流任务节点配置.md §1.1 常规设置`
- 参与者五种添加方式：发起人选择 / 使用角色 / 自定义动作 / 使用字段 / **使用审批矩阵**。`05A_开始节点配置.md §参与者添加方式`
- 审批矩阵满足 5 个条件才可见：配置启用 + 布局放入且未隐藏 + 有查看权限 + 数据满足匹配条件 + 匹配到的矩阵管理记录启用。`08_审批矩阵.md §入口与可见范围`
- **发起即快照**：改矩阵成员**不影响已发起的流程**，只影响新发起；"重新指派/移交"后的新责任人**不会反向写回矩阵成员**。`08_审批矩阵.md §常见问题 Q3` / `§进行中工作流的参与人管理 NOTE`
- 发起人可被排除：矩阵规则可按配置排除发起人；任务节点也有"不允许工作流发起人接收此任务"。`01_发起审批.md §操作步骤 4`；`05B_工作流任务节点配置.md §1.1`
- 发起时对矩阵的调整只影响本次流程（删成员/补成员），"允许用户添加角色"开启时才可加自定义角色。`08_审批矩阵.md §发起时可调整内容`
- 在途追加人有限制：可补未选过的可选角色，**不能删除已有参与人，也不能给已完成步骤加人**；新增后是否生成新待办由规则判定。`07_工作流入门.md §2.2 在途流程追加参与人`；`08_审批矩阵.md §进行中工作流的参与人管理`
- ⚠️ 配了人也可能做不了：被分配人若**没有记录访问权限**，可能收到通知但无法完成任务。`07_工作流入门.md §2.2 注意事项` / `§常见问题 Q3`

### 2.3 会签与或签在业务端的差别

- 手册**没有统一使用"会签/或签"这对词**，业务端看到的是三种不同说法，必须两两对齐：`05_工作流配置.md §6.2` 用会签（全部通过）/或签（任一通过）；`05B §1.6` 用并行指派/串行指派；`08_审批矩阵.md §串行与并行规则` 用串行/并行。
- **并行（≈会签）**：一次性给所有参与人生成任务，所有人可同时处理；未完成者会**阻塞流程推进**。`05B_工作流任务节点配置.md §1.6 并行指派`；`03_电子签名.md §常见问题 Q3`
- 并行在业务端的可见形态：`任务类型=并行` + 任务分配模式"系统指派"时，发起人看到"**将任务分配给以下所有参与人**"，组中所有用户都需完成此任务。`05B_工作流任务节点配置.md §1.5 任务分配模式`
- **串行（≈逐级审批）**：按参与人顺序依次生成任务，**上一个完成后才生成下一个**；参与人选择顺序就是分配顺序。`05B_工作流任务节点配置.md §1.6 串行指派`
- 串行可配**提前结束条件**：条件类型"任一断言包含于"，逻辑值取任务上**必填的审批意见**；选"至少一个断言等于"时命中一个就停止生成后续任务并进下一节点，选"所有/没有断言等于"时按已完成任务整体判断，不满足则**进入判断节点 else 分支**。`05B_工作流任务节点配置.md §1.6 串行任务提前结束条件`
- 矩阵侧同构：串行按参与人顺序依次派发（强制逐级审批），并行同时派发给该角色下成员（并行会审或共同确认）。`08_审批矩阵.md §串行与并行规则`
- **领取（第三种人-任务关系）**：`任务分配模式=任务领取` 时任务对所有候选人可用，页面提示"**可用于所有用户**"，谁领谁做，**并非所有人都必须完成**。`05B_工作流任务节点配置.md §1.5`
- `[推断]` 会签的"全部通过"与串行的"全部走完"后果不同：并行漏一个 = 流程卡住；串行漏一个 = 后面的人根本还没收到任务（任务未轮到你）。`02_完成任务.md §常见问题 Q1`（"任务还未轮到您（等待前一步骤完成）"）

### 2.4 移交、重新分配、代理的规则

- 移交是**一次性、永久性交接**：责任人变更为接收人，**原责任人不再处理该任务，也不再接收对应消息和待办**。`05_移交任务.md §功能说明` / `§提交后结果`
- 任务面板会显示 **移交自**（移交前责任人），这是核对"谁原本该做"的唯一字段。`05_移交任务.md §功能说明` / `§常见问题 Q3`
- 硬约束：**不能移交给自己**——候选人列表自动排除当前责任人；重新分配同理。`05_移交任务.md §前提条件` / `§admin批量移交 关键配置项`；`06_管理活动工作流.md §1. 重新分配`
- 提醒任务移交时要额外选策略：`移交`（始终移交）/ `跟随任务设置`（由任务上的设置决定）。`05_移交任务.md §用户单次移交 步骤 5`
- 是否真的移交由**任务上的设置逐条判定**：允许移交→执行；不允许→保留原责任人；跟随任务设置→按当前配置。**批量移交允许部分成功**。`05_移交任务.md §移交判定逻辑` / `§常见问题 Q1`
- 管理员批量移交在"工作代理"菜单下的【工作移交】：移交内容= `工作流` | `待办`，移交方式= 全量 / 按模块 / 按对象 / 按明细。`05_移交任务.md §管理员批量移交`；`01E_工作移交.md §创建页字段说明` / `§移交方式选项`
- 批量移交**由后台作业异步执行**，异常可重试直到完成或失败；成功项显示"移交自"，不可移交项提示原因并保留原责任人。`05_移交任务.md §执行机制与结果展示`
- 口径不一致（逐字记）：用户指南写移交方式三种（全量/按模块/按明细），管理员指南写四种（多一个**按对象移交**）。`05_移交任务.md §关键配置项` vs `01E_工作移交.md §移交方式选项`
- 代办移交范围 = 移交人**未完成的代办**；**培训任务不在代办移交范围内**；已完成的工作移交记录不再执行。`05_移交任务.md §注意事项`
- 培训任务能否移交/代理由管理员配置决定，禁止时**不显示移交或代理入口**。`05_待办任务.md §培训任务的移交与代理`
- **计划中的任务也可移交/重新分配**——尚未到达执行时间的计划内待办支持提前安排人员。`05_移交任务.md §用户单次移交 NOTE`；`05_待办任务.md §计划中的任务`
- **外部协作任务的特例**：外部任务**不允许责任人自行移交或重新指派**，其他操作与内部一致。`02_外部协作.md §常见问题 Q4`
- **代理（区分于移交）**：任务节点可勾"不允许代理"；"工作代理是临时委托、通常有时间窗口，工作移交是归属转交、执行后按结果变更责任人"。`05B_工作流任务节点配置.md §1.1`；`01E_工作移交.md §常见问题 Q1`
- `[推断]` 代理在业务端的形态是"**代人处理**"：任务仍属于原责任人（与移交的永久换人相反），所以工作流任务节点的开关才把它和"不允许移交"并列成两个独立开关。

### 2.5 任务与人之间会发什么消息

- 用户任务的 5 条触发规则（接收者是关键）：创建任务→接收者；重新指派→**新**接收者（任务指派通知）+ **原**接收者（任务重新指派通知）；移交任务→新接收者；完成任务→**任务 Owner/创建者**。`07_用户任务.md §通知与提醒`
- 通知是否发、走什么渠道、模板内容都取决于配置。`07_用户任务.md §通知与提醒`
- 催办是一条独立通道：工作流配置允许时可对久未处理/临近截止的任务催办，入口、可催办次数、提醒方式与对象随流程配置而变；同一任务两次催办有**最短间隔**（如 60 分钟）。`02_完成任务.md §催办任务`；`04I_...配置.md §54 催办`；`05B_工作流任务节点配置.md §1.4（催办时间间隔）`
- **通知参与者 ≠ 改状态**：手册明说"通知仅影响消息提醒，**不会直接改变流程状态**"。`06_管理活动工作流.md §3. 通知参与者`
- 点【催办】的动作在配置端是一个**用户动作类型**（第 54 项"向待办处理人发送催办提醒"），即催办按钮也要人配出来。`04I_生命周期用户动作、进入动作、事件动作配置.md §系统支持的用户动作类型`

## 3. 作业与计划任务

### 3.1 "作业"是什么

- 定位：作业用于**按预定时间自动执行后台任务**；入口 `配置环境 > 运维管理 > 作业管理`，实例监控分 `计划作业 / 运行作业 / 历史作业`。`12_作业管理.md §概述`
- 三个基本概念：**作业定义**（内容+执行计划的一组配置）、**作业实例**（一次具体执行记录）、**作业计划**（频率+时间+时区）。`12_作业管理.md §1. 作业的基本概念`
- 两种分类：按执行方式 = 计划作业（周期反复）/ 临时作业（系统事件触发、只执行一次）；按维护方式 = 自定义 / **标准作业（系统内置，不可删除）**。`12_作业管理.md §1.` / `§5.3` / `§9. 系统内置作业`
- 常见作业类型：对象操作、文档操作、URL 调用、计划导出、文档定期回顾、同步组织架构（另有 SDK 作业）。`12_作业管理.md §1.` / `§4.3`~`§4.7`
- 简报类作业由**简报订阅功能自动创建**，管理员不必手工新增，通常只用于查看与排查。`12_作业管理.md §1.` / `§4.4`
- 创建作业的必填骨架：名称（1–200、唯一）、Code（1–200、唯一）、执行计划（必填）、状态（**默认停用**）、责任人（部分类型非必填）、时区（直接影响计划时间与监控显示）。`12_作业管理.md §4. 创建作业` / `§4.1.1`
- **状态默认停用，启用后才立即生成下一条计划作业实例**。`12_作业管理.md §4 状态字段备注` / `§6.2 计划作业`
- 执行周期六档：每分 / 每小时 / 每日 / 每周 / 每月 / 每年，时间精确到分钟，**必须同时确认时区**。`12_作业管理.md §3. 执行计划`

### 3.2 作业能干什么

- **对象操作作业**四动作：`修改状态` / `发送消息` / `无操作` / `创建相关记录`；`无操作` 不改数据，通常只配消息提醒用。`12_作业管理.md §4.1.3`
- **文档操作作业**五动作：`无操作` / `修改状态` / `发送通知` / `创建相关记录` / `计算培训完成率`；`修改状态` 需再选生命周期、文档版本（最新版本 / 最新稳定版本 / 当前版本）、是否修改状态、目标状态、触发时间。`12_作业管理.md §4.2`
- 对象作业的配置四件套：**动作 / 对象 / 执行条件 / 触发时间**（触发时间 = 以哪个日期字段作触发依据）；执行条件可叠加多条并按逻辑关系组合。`12_作业管理.md §4.1.3`
- 消息设置 = 消息模板 + 收件人 + **在触发日期前多少小时发送**；可"添加动作"配多条提醒。`12_作业管理.md §4.1.4`
- `文档定期回顾` 作业为满足条件的文档自动创建定期回顾记录；`同步组织架构` 按计划同步业务单元/部门/职位/用户及其引用关系。`12_作业管理.md §4.5` / `§4.6`
- SDK 作业的区别只在动作配置里填 `SDK编码`，指定执行哪段 SDK 逻辑。`12_作业管理.md §4.7`

### 3.3 作业 × 配置 / 工作流 / 编号规则

- **作业与工作流是两套并行的改状态通道**，且作业会撞上工作流（见 §1.3 ⑦）。`12_作业管理.md §4.1.3` / `§11 使用建议`
- 生命周期**进入动作清单里有"取消工作流"（第 31 项）**，与作业的"取消活跃工作流"是两个不同入口的同一后果。`04I_生命周期用户动作、进入动作、事件动作配置.md §系统支持的进入动作`
- 作业编码**被接口引用**：接口路由编辑前要确认"编码是否已经被工作流、作业、SDK 或其他配置引用"。`05_接口应用管理.md §6.3 编辑接口路由`
- **作业与编号规则的关系**：作业本身不含"生成编号"动作；生成编号是**生命周期进入动作第 22 项**（`按编号规则生成业务编号`），另有进入动作"批量生成相关对象编号"（第 38 项）与动作节点"批量生成相关对象编号"。`04I_生命周期用户动作、进入动作、事件动作配置.md §一、配置进入动作 → 系统支持的进入动作（22 / 38）`；`05D_动作节点配置.md §1.4.2 批量与辅助动作`
- **作业与编号规则只有间接关系**：对象作业改的是记录状态/字段/相关记录，作业**不能自己造编号**；要让作业驱动的流程里出编号，得在目标状态的**进入动作**里挂"生成编号"。`12_作业管理.md §4.1.3 动作配置`；`04I_生命周期用户动作、进入动作、事件动作配置.md §一、配置进入动作（22 生成编号）`

### 3.4 作业的生命周期与异常处理

- 计划作业生成新实例的场景 5 种：首次启动加载作业计划 / 配置迁移后重排期 / 新建作业并启用 / 编辑后重新启用 / 上一实例完成后自动生成下一周期。`12_作业管理.md §6.2`
- 会**取消已生成但未执行实例**的操作 3 种：删除作业 / 停用作业 / 取消作业计划。`12_作业管理.md §6.2`
- 编辑一个**启用中**的作业，进编辑页后状态自动变 `停用`，保存前要重新设回启用。`12_作业管理.md §5.1 编辑作业`
- 删除作业：定义移除 + **未执行实例一起删除** + 已完成历史实例保留追溯；**标准作业不允许删除**。`12_作业管理.md §5.3`
- 历史作业五态：成功 / 已取消 / **执行错误**（部分数据处理失败）/ **运行失败**（内部错误）/ **跳过**（未在计划周期内正常启动）。`12_作业管理.md §7.3 历史作业`
- 异常规则四条：排期失败 **5 小时后自动重试**，仍失败标 `跳过`；上一实例未完成而下一周期已到 → 新实例会生成但结果可能为失败；实例连续运行 **>24 小时强制取消并把作业置为停用**并通知责任人；运行错误自动通知作业责任人。`12_作业管理.md §8.2` / `§8.1`
- 对象/文档作业执行后写入**对象审计追踪 / 文档审计追踪**，审计里的操作用户显示为 `系统`。`12_作业管理.md §10`

### 3.5 工作日历被谁引用

- 工作日历是**内置标准对象**，维护工作日、休息日、企业自定义假日与调休补班；**入口菜单要配置人员手工加、权限集要手工授权**，否则业务端看不到。`15_工作日历管理.md §概述` / `§访问路径` / `§5.1 权限集` / `§5.2 菜单配置`
- 必填只有两个：**编码**、**工作日**（名称非必填）；编码是"用于识别和引用"的键。`15_工作日历管理.md §2.2 基本信息字段`
- 休息日用于"**截止日期、提醒日期和调度时间的跳过计算**"，默认周一至周五为工作日。`15_工作日历管理.md §3.1` / `§3.2`
- **工作流任务节点的到期日期**：类型选 `公式` 时可用 `CalcWorkDay(StartData,Hour,WorkCalendarCode)`，实现仅按工作日算截止时间。`05B_工作流任务节点配置.md §1.1 到期日期设置`
- **工作流预警日期**同样可用 `CalcWorkDay(StartData,Hour,WorkCalendarCode)`，仅在工作日触发提醒。`05B_工作流任务节点配置.md §1.1 预警日期设置`
- **任务提醒的发送日期**（类型选 `公式` 时）同公式。`05B_工作流任务节点配置.md §1.4 发送日期补充说明`
- **公式字段**可调 `IsWorkday(DateTime[,Calendar])`（判是否工作日）与 `CalcWorkDay(DateTime,NumOfDay[,Calendar])`（按工作日偏移），`Calendar` 参数不传则用**系统默认工作日历**；示例里直接写日历名 `IsWorkday(date__c, "默认工作日历")`。`06_公式配置.md §IsWorkday()` / `§CalcWorkDay()`
- 手册点名的关联影响四处：工作流**任务截止日期**计算、工作流**预警或提醒日期**计算、**任务调度**执行日期计算、其他基于工作日口径的推算；建议优先**停用**而非删除已被引用的日历。`15_工作日历管理.md §6. 关联影响` / `§1.2 注意` / `§4.3`
- ⚠️ 存量不回算：改日历后已有任务截止日期**未必自动变化**，因为"有些场景在任务创建时就已完成日期计算"。`15_工作日历管理.md §常见问题 Q2`

### 3.6 工作日历是不是"编号规则的重置依据"？—— **不是**

- 编号规则的重置依据只有三类：**日期、对象字段、相关对象字段**；设为依据后流水号按依据值不同重新生成序列（选项：仅显示 / 显示且设为重置依据 / 仅设为重置依据）。`07A_编号规则配置.md §编号依据（重置依据）`
- **公式类型字段不能作为重置依据**（明说的硬约束）。`07A_编号规则配置.md §编号依据（重置依据）NOTE`
- 日期编号段只支持五种格式（`YYYYMMDD` / `YYYYMM` / `YYYY` / `MM` / `YY`），**没有"按工作日历的年份/期间"这一说**。`07A_编号规则配置.md §日期`
- `[推断]` 于是"日历 → 编号重置"的唯一潜在通路是"公式字段调 `IsWorkday(...,"我的日历")` 再拿它当重置依据"，而这条通路被上一句明令封死 ⇒ **工作日历与编号规则目前没有可配置的连接**。
- 日期段作为重置依据时会按"所选依据的值不同"重置，`[推断]` 即"跨年/跨月自动从起始值重来"，与工作日历无关。
- 顺带记下编号规则的挂载点（工厂侧相关）：`name__ak` 启用"由系统管理字段值(只读)"时必须选编号规则；或由**生命周期进入动作"生成编号"**挂到一个文本字段上。`07A_编号规则配置.md §name__ak 字段使用编号规则` / `§生命周期进入动作使用编号规则`
- 编号规则**已被使用就不允许删除**（提示"此编号规则正在使用，不能删除"），且编号规则变更**不修改历史数据**。`07A_编号规则配置.md §删除编号规则` / `§生成规则说明`

## 4. 对工厂的启示

### 4.1 只有人能做的（AGENTS.md 规则 36 的形状：缺动词不报错，只让流程走不通）

- **提交/批准/拒绝/退回/移交/重新分配/取消任务/取消流程/领取/催办/添加参与人**——这一整条链在手册里**全部只有界面路径**，没有任何接口描述；只读研究也不该据此假设端点存在。`01_发起审批.md`、`02_完成任务.md`、`06_管理活动工作流.md`、`07_用户任务.md`、`07_工作流入门.md §五`
- **"走到状态真的变了"这一步只有人能触发**：提交、直接扭转状态、取消工作流三个改状态入口都在界面上；工厂能造出流程与绑定，但造不出"这一次点击"。`01_发起审批.md §操作步骤`；`03_电子签名.md §场景四`；`06_管理活动工作流.md §1`
- **电子签名的凭据只有人手里有**：密码是当前登录密码，CA 需 UKey 或扫码，数字身份认证需人脸/短信；密码连错还可能触发账户锁定。`03_电子签名.md §如何完成电子签名` / `§常见问题 Q2`；`09_CA电子签名.md §使用前准备`；`10_电子签名_数字身份认证.md §支持的认证方式`
- **审批意见是人的决策输入，且能改变流程走向**：串行提前结束条件直接读"任务上设置的审批意见（必填）"，选错就进 else 分支。`05B_工作流任务节点配置.md §1.6 串行任务提前结束条件`
- **矩阵里"必填但没人"只能由人补齐**：这是提交前的界面校验，不补齐连提交按钮都过不去。`01_发起审批.md §常见问题 Q3`；`08_审批矩阵.md §提交校验`
- **邮件回复完成任务也依赖人**：外部人员回邮件、邮件主题要含业务编号、邮箱要一致，系统只是定时扫收件箱解析。`02_外部协作.md §通过邮件完成任务`
- **日历要人录**：法定假日与调休补班每年人工维护一次，漏录会让所有按工作日算的截止日期集体偏移。`15_工作日历管理.md §3.2 建议`

### 4.2 工厂建不出来、但会静默让流程走不通的配置

- **工作流保存后是"未启用"**：不能被动作选中、不能在业务端发起；**编辑必须升版**（新版本 `编辑中`，旧版本仍启用），只有再次点启用后续新发起才用新版本，且**旧实例不随版本切换**。`05_工作流配置.md §2.2 版本与状态 1–5` / `§2.3`
- **对象必须先启用生命周期**（自动生成生命周期，且该选项创建后不可修改）；没有生命周期就没有 Status，工作流与状态绑定全部落空。`04_对象生命周期配置.md §前提条件` / `§State 与 Status`
- **"启动状态"决定在哪个状态能发起**；不设置=不限状态，设置错=按钮在你以为的状态上不出现。`05_工作流配置.md §2.1 创建页字段表`
- **生命周期"用户动作"决定按钮可见性**，判据是权限三态：执行=允许发起 / 查看=按钮可见但不可点 / 隐藏=按钮不可见。**这正是 L5 第 ④ 条"能看到提交按钮"的机制**。`05_工作流配置.md §4.3`
- `[推断]` 工厂的 `bindToStatusCode` 对应的是**手动启动入口**（用户动作"发起工作流"），与手册的"启动状态"不是同一个字段——验证 L5 第 ④ 条时要同时确认这两处，别只查一个。`04-workflow-automation.md §1.4`（工厂侧实现对照）；`04I_...配置.md §用户动作类型 1 发起工作流`
- **取消工作流会改状态**：每个生命周期状态都有"工作流取消状态"，默认"工作流发起时状态"；只造状态不确认这一项，取消后记录可能落到你没预期的状态。`04_对象生命周期配置.md §工作流取消状态规则`
- **审批矩阵要过 5 道门才可见**（启用 + 布局放入 + 查看权限 + 数据匹配 + 矩阵记录启用），少一道就"配了像没配"，且不报错。`08_审批矩阵.md §入口与可见范围`
- **矩阵"默认职位管理"与签名的"需要选择职位"联动**：条件匹配且用户有多个职位时优先带出矩阵预设职位，否则要用户手动选；该能力仅当"默认职位管理"实例启用时生效，并可用于批量工作流。`08_审批矩阵.md §默认职位管理（启用时）`
- **工作日历编码是公式的硬依赖**：`CalcWorkDay(...,WorkCalendarCode)` 里的日历必须存在且业务端可见（菜单 + 权限集双授权），否则公式拿不到值。`15_工作日历管理.md §访问路径` / `§5.1`
- **任务节点的到期/预警/提醒要人配**：到期日期六种来源、预警日期只两种、提醒三模式（不提醒 / 用策略 / 自定义）；不配就没有到期时间，任务列表的"超期"判据全部失效。`05B_工作流任务节点配置.md §1.1` / `§1.4`
- **签名是节点级开关**：不勾"需要电子签名"不报错，只是签名窗口不弹；启用了数字身份认证还要用户安全策略绑定对应策略。`03_电子签名.md §常见问题 Q1`；`10_电子签名_数字身份认证.md §使用前准备 2–3`
- **外部协作要单独配**：回复邮件完成任务需管理员预配审批关键词与邮件通道，推送到第三方签署平台要先配签署平台与"获取签署结果"用户动作。`02_外部协作.md §通过邮件完成任务` / `§文件推送至外部签署平台`
- **作业与工作流会互撞**：对象/文档作业的"修改状态"若不勾"取消活跃工作流"，记录上有活跃工作流时**作业执行错误并记异常日志**（文档场景则是"可能无法直接修改状态"）。`12_作业管理.md §4.1.3` / `§4.2`
- **作业启用才排期、编辑会掉成停用**：建完不启用 = 永不执行；编辑后忘重新启用 = 排期静默停止。`12_作业管理.md §4` / `§5.1`
- **标准作业不能删**，也不能创建平台未开放的内置作业类型。`12_作业管理.md §9`
- **编号规则被引用就不能删**，且工厂侧的"编号"能力只能落在进入动作或 `name__ak` 上，作业与日历都帮不上。`07A_编号规则配置.md §删除编号规则` / `§name__ak 字段使用编号规则` / `§生命周期进入动作使用编号规则`

### 4.3 给 L5 第 ⑤ 条的验证设计提示

- 一次"走一遍"至少要看**两个状态快照**：提交前（原始状态）+ 提交后（应变成的状态），再叠加**内容锁定**（不可编辑）作为第二证据——手册把"锁定"与"状态变了"并列写在同一处结果验证里。`01_发起审批.md §结果验证`
- 若被测流程的批准分支终点不是靠任务动作改状态，就必须**确认流程里真的有"动作 → 修改状态"节点**，否则"提交后状态变了"只在提交那一步成立，批准后反而看不到第二次变化。`05D_动作节点配置.md §1.4.1 修改状态`
- **拒绝分支要单独走一遍**：拒绝的可见后果是"交回发起人修改"，状态是否回到原状态取决于配置而非必然。`02_完成任务.md §拒绝文档` / `§常见问题 Q3`
- **取消流程也是一条改状态路径**，且落点由当前状态的"工作流取消状态"决定，适合作为第 ⑤ 条的补充用例（不需要人做审批结论，只需点取消）。`06_管理活动工作流.md §1. 取消工作流程`；`04_对象生命周期配置.md §工作流取消状态规则`
- 反查记录状态的两个界面入口：列表页**生命周期状态**字段上的活跃工作流图标、以及任务列表按"关联对象状态"筛选。`06_管理活动工作流.md §从列表入口查看并管理活跃工作流`；`02_完成任务.md §在首页检索任务`

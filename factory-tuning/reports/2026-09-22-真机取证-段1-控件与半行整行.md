## 3. ★ 新缺陷候选 **D-D**：控件的键名与词汇表都不符

工厂 `layouts.py:91-97` 造出来的控件是 **7 键**：

```python
controls.append({
    "id": ..., "sectionId": section_id, "fieldId": field_id,
    "fieldCode": field_code,                    # ← 真机叫 code
    "ctrlType": CONTROL_TYPE_BY_DATA_TYPE[...], # ← 真机叫 type，且值域完全不同
    "sort": sort, "invisible": False, "disabled": False,   # ← 真机里没有这两个键
})
```

| 工厂发的键 | 真机对应的键 | 判定 |
|---|---|---|
| `fieldCode` | **`code`** | ❌ 键名不符 |
| `ctrlType`（值 `attachment`/`object`/`date`…） | **`type`**（值 **`AKAttachment`**/`AKSelectorObject`/`AKDateTime`…） | ❌ **键名与词汇表都不符** |
| `invisible` / `disabled` | 真机是 **`visible`** / **`readOnly`**（且为 null 表示"不覆盖"） | ❌ 键名不符（这正是 `AGENTS.md` 说的"写了等于没写"） |
| — | `gridSpan` / `attrs` / `dataType` / `name` | 工厂**完全不发** |

**已实测的真机 `type` 取值**（4 个控件）：`AKAttachment`(附件 8)、`AKSelectorObject`(父对象 16 / 对象 15)、`AKDateTime`(日期时间 7)。
⇒ 词汇表是 **`AK<组件名>`**，而工厂那套（`input`/`number`/`attachment`…）**是自造的**。

### 3.1 为什么闸门没抓到它（闸门的边界，要写清楚）

`keygate.py` 只扫描 **`client.post(..., {字面量})` 的实参**；
而控件是**循环里 `controls.append({...})` 拼出来的**，不在 post 的实参里 ⇒ **扫不到**。
⇒ **闸门能覆盖"顶层字面量请求体"，覆盖不了"拼装的子结构"**。
本次是靠**人工对照真机数据**发现的——所以 `audit_keys.py` 那一步不能省。

## 7. ★★ 第二个发现：新建部分/控件要先"**稳定 id**"——工厂缺了这一整步

段 1 那两个"未建模"端点里，`/api/platform/Layout/GetStableComponentIds` **不是普通查询**，
它是平台客户端保存流程里的一个**协议步骤**：

```
请求  {"componentIds": {
         "<浏览器里生成的 UUID>": {"objectId": "id-84b1e458", "layoutCode": "***",
                                   "componentType": "layout_section", "componentCode": "basic_info__cs"},
         "<浏览器里生成的 UUID>": {"objectId": "id-84b1e458", "layoutCode": "***",
                                   "componentType": "layout_control", …}, …}}
响应  {"stableComponentIds": {
         "<浏览器里生成的 UUID>": "id-e25f78ec",   ← 服务端分配的真实 id
         "<浏览器里生成的 UUID>": "id-40e2dac5", …}}
```

**⇒ 平台自己客户端的两段式**：先在浏览器里给**新建的**部分/控件生成 UUID →
调 `GetStableComponentIds` 让服务端把它们"稳定"成真实 id → **然后**才发 `SaveLayoutDetail`。

**工厂的做法**（`layouts.py:77`、`:92`）：`"id": str(_uuid.uuid4())` —— **自造的 UUID 直接进请求体，
从不调这个端点**。

### 7.1 新缺陷候选 **D-E**

| | |
|---|---|
| **症状** | 新建的部分/控件带着浏览器自造的 UUID 提交，平台可能（a）接受、（b）静默丢弃、（c）错绑——**三种都没见过** |
| **证据强度** | **真机确证"平台客户端会做这一步"**（本次请求/响应全文）；工厂不做是**代码确证**；**后果未验** |
| **为什么值得单列** | 它不是"键名写错"，而是**少了一整个协议步骤**——`#62/#63/#67/#69` 那一族（接口回成功、回读才发现空）最典型的缺口形态 |
| **与已有缺陷的关系** | 与 **D-C**（顶层键 `basicObjectId`）、**D-D**（控件键名与词汇表）**叠在同一条链路上**：三者任一都可能让"保存成功"变成"没保存对" |
| **判据（可复跑）** | `python -c "import json,pathlib;rows=[json.loads(l) for l in pathlib.Path('factory-tuning/data/sessions/acct-fb8dc317-20260922-102423/traffic.jsonl').read_text(encoding='utf-8').splitlines() if l.strip()];print([r['path'] for r in rows])"` —— 真机序列里 `GetStableComponentIds` **在** `SaveLayoutDetail` **之前** |

### 7.3 关于 F33（"两条 `SaveLayoutDetail`"）——**2026-09-22 更正，别过度解读**

出正式报告后拿到动作缓冲：**`确 定 → 保 存 → 保 存`**。据此**不能**得出"一次点击被平台展开成两条"：

- 两条保存相隔 **29 ms** ⇒ **不可能是两次人工点击**；
- 而动作缓冲里**确实有两次「保存」** ⇒ 也不能断言"只点了一次"；
- 缓冲**上限 5 条且会跨操作渗漏**（PITFALLS #64）⇒ 那两次「保存」里可能有一次来自更早的时刻。

⇒ **正确的表述**：只能说"**这个会话里出现了两条保存**"；**"为什么是两条"未定**。
若要定性，判据是：让演示者**只点一次**保存、其余什么都不点，再看条数——
**这正是"整行对照实验"可以顺带回答的问题**（见 §5 待核实 1）。

> 教训（与 §1.1 同源）：**一条请求旁边挂着什么动作，不等于这条请求由那个动作发出。**
> `precedingActions` 是"最近 5 个 DOM 动作"的快照，**不是因果标注**。
>
> **2026-09-22 段 2 更新（本条已收口一半）**：段 2 里**一次「保 存」点击只发一条**，
> 且段 1 那两条的**形状差异**（#1 精简 8 键 → #2 完整 23 键）说明它是平台的
> 「**提交 → 回显 → 再提交**」；两段各一个样本 ⇒「为什么那一次是两条」仍不下定论。
> 详见[段 2 报告](2026-09-22-真机取证-段2-新建部分与整行.md) §3.2 与 §5。
> ⚠️ 同时更正 §1.2 的读法：**动作缓冲与请求之间的时间差不能当因果**
> （段 1 = 38.4 s、段 2 = 61.4 s，而 09-21 的会话只有 0.1–3.1 s）——见该报告 §6 与 PITFALLS #74。

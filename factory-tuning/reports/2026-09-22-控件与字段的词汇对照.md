# 控件是字段的投影 —— 字段元数据（93 键）与控件（23 键）的逐词对照

> **触发**：用户 2026-09-22 的提示——「这些控件本质上就是引用的字段的信息」。
> **数据**：`FieldsByCodes` 的**响应**（未被建模 ⇒ 全量保留，字段对象 **93 键**，
> 见 `data/sessions/acct-891a4f9d-20260921-210820/traffic.jsonl`）
> ＋ 布局保存体里的控件元素（段 1–4，**23 键** / 精简 **8 键**）。
> **代码**：`layouts.py:23-27`（工厂那张 14 项词表）、`:91-97`（控件拼装）。

---

## 0. 一句话

用户说得对：**控件 = 字段的投影 + 布局专有信息**；而且这条把 **D-D 的成因**说清楚了——
工厂写的 `invisible` / `disabled` **不是随手猜的**，它们是**字段层**的词
（字段有 `invisible` / `editable`），被**搬进了控件层**（控件层叫 `visible` / `readOnly`）。
**"跨层串词"，比"瞎猜"更隐蔽**，因为它每一个词在平台里**都真实存在**，只是不在这一层。

但有一件事**不能**从字段读：**控件的 `type`（`AK*`）**——字段那 93 个键里**没有它**（§3）。

---

## 1. 字段层有什么（93 键，实测）

与"控件长什么样"直接相关的键：

| 字段层的键 | 例值 | 控件层对应 |
|---|---|---|
| `code` | `name__ak` | `code`（**同名同值**） |
| `name` | `名称` | `name`（**同名同值**） |
| `dataType` | `1` / `7` / `15` / `18` / **`19`** | `dataType`（**同名同值**，但**可以缺席**，段 4 的 `name__ak` 就是） |
| `isRequired` | `False` | `required`（**改名**） |
| `invisible` | `False` | **`visible`**（**改名 + 取反**） |
| `editable` | `True` | **`readOnly`**（**改名 + 取反**） |
| `componentType` | `ComponentType_Object` / `ComponentType_Workflow_Version` / `None` | —— **控件层没有这个词** |
| `format` | `YYYY-MM-DD HH:mm:ss` | 控件 `attrs` 里可能体现 |
| `maxLength` / `scale` / `picklistId` / `referenceObjectId` … | | 控件的字段级约束来源 |

**⇒ 控件只多了三样字段没有的东西**：`sectionId`（挂哪个部分）、`gridSpan`（半行/整行）、
`sort`（次序）；其余全是字段信息的**搬运或改名**。

---

## 2. ★★ D-D 的成因：**跨层串词**（不是瞎猜）

| 工厂在**控件层**写的词 | 它其实来自**哪一层** |
|---|---|
| `invisible` | **字段层**（字段确实叫 `invisible`） |
| `disabled` | **字段层的 `editable` 的意译**（字段没有 `disabled`，但语义在那一层） |
| `fieldCode` | 蓝图/内部命名（字段层叫 `code`） |
| `ctrlType` + `input`/`object`/`date`… | 自造（既不是字段层也不是控件层的词） |

> **这条比"猜错了"更值得记**：`invisible` 在平台里**真是个合法键**——
> 只不过它属于**字段**，不属于**控件**。所以任何"键名看起来眼熟就发过去"的做法
> 都会**静默**地发错层，而接口**照样回 200**。
> ⇒ 判据不能是"这个词眼熟吗"，只能是"**它在这条请求的哪一层出现过**"——
> 这正是 `keygate.py` 现在做的事（按**端点 + 同 writer 模块**取样本）。

---

## 3. ⚠️ 但控件 `type`（`AK*`）**不在字段里**（这条要纠正一半）

在 93 个键里按 `type|component|ui|layout|render|widget|control|display` 筛，候选只有：

```
componentType = 'ComponentType_Object'      ← 另一套词汇，且多数为 None
createObjectType / documentTypeIds / iconType / returnType = None
isRequired / isDisplayDefaultValues / displaySettingValueWhenEmpty = 布尔
dataType = 19
```

**没有任何一个键的值是 `AK*`**（全量数据里 `AK*` **只出现在 `Layout/SaveLayoutDetail` 的请求体里**）。

⇒ **结论**：控件 `type` 是**布局层**才知道的事，**必须由工厂派生或实测**——
段 1/3/4 那张 `dataType → AK*` 表（**9 个 dataType / 7 个类型**）因此**仍然必要**，
它不是我"纠结出来的"，而是**这一层确实没有来源**。

---

## 4. ★ 顺带两个新事实

1. **`dataType 19` 存在**（`relation_object_id__ak` 任务类型、`workflow_config_id__sys` 工作流），
   而工厂那张表只有 **14** 项（1/2/3/4/5/7/8/13/14/15/16/17/18/23）——**没有 19**。
   ⇒ 工厂的 dataType 视野**本身就不完整**（这也解释了为什么"未知即失败"是必需的）。
2. **`componentType` 是第三套词汇**（`ComponentType_Object` / `ComponentType_Workflow_Version`），
   工厂**完全没有建模**。它与 `AK*` 的关系**未知**（样本里那两类字段都还没被拖进布局过）。
   ⇒ **不要**把它们当同一件事。

---

## 5. 对修法方案的影响（三条，都是**收敛**）

| 项 | 变化 |
|---|---|
| **D-G**（布局只认识本次创建的字段） | **用户这句提示就是它的正解**：控件既然是字段的投影，就该**从平台读字段**（`FieldsByCodes` / `FieldPage` 是工厂已在用的通道），而不是只认 `field_map` 里自己刚创建的那些。修法从"补一次读"升级为"**以字段为准**" |
| **D-D** | ①`AK*` 表**仍必要**（§3），且**9 个实测 / 多对一 / 缺 13/14/17/18/19/23 一律显式失败**；②**布尔键按控件层的名字发**：`visible` / `readOnly`（**不要**把字段层的 `invisible`/`editable` 搬过去）；③`required`（不是 `isRequired`） |
| **字段层新缺口** | `dataType 19` 与 `componentType` 工厂**都没有概念** ⇒ 记进认知文档的缺口表（**不是**缺陷卡，是"视野缺口"） |

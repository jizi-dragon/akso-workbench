## 3. 经验教训

### 3.1 平台知识（可复用）

全部 15 条见 `docs/FACTORY-VERIFICATION-PLAN.md` §8（F1–F15）。最该记住的四条：

1. **判"成功"必须看平台回读。** 业务失败也是 HTTP 200，错在 `code` 里；
   `SaveBasicObject`/`SaveField` 只回 `{code:0, data:true}`，**不回 id**。
2. **键名的事实源是平台的读侧 schema + 界面的真实请求体**，不是蓝图侧的字段名。
   本次先靠读侧 schema（93 个键）正确预测了 `minValue`/`maxValue`，又正确推出了 `scale`。
3. **「对象(15)」≠「父对象(16)」**：前者是引用关系（记录可独立存在），
   后者是父子关系（子不能脱离父存在，层级 ≤ 3）；平台的关系记录里 `type` 一个是 2、一个是 1。
4. 🔴 **选项集不能删除** —— 对它的任何写入**不可回滚**。
   这条改变了"测试"的性质：**对无撤销键的资源做写入试探 = 留下永久垃圾**。

### 3.2 方法论（比知识更重要）

| # | 教训 | 出处 |
|---|---|---|
| M1 | **先拿到界面真实请求体，再改代码。** 不要反过来猜键名 | #62/#63/#67/#69 全是照着猜的东西写的 |
| M2 | **夹具照真机抄，否则回归会反过来守着错误行为** | `tests/fakes.py` 硬编码了同一个错路径 + 错形状，测试因此一直绿；改成真机形状后新断言**当场 4 条全红** |
| M3 | **断言必须被证明会红。** 每条修复都跑了"退回去 → 应当变红 → 还原" | 本仓纪律；本次 6 处修复全部做了 |
| M4 | **找端点时先看已经跑通的那几条，从命名结构反推** | 我第一轮沿着仓库里已有的常量穷举 20 个候选（全 404），差点误判成"本环境没有选项集回读接口"；正确路径是 `/BasicObject/picklist/{code}`，结构一目了然 |
| M5 | **恒红的门禁等于没有门禁** | 脱敏误报、扫描器假阳性都会让门禁失去意义；两次都补了**形状豁免**（只加在扫描器侧 + `fullmatch`） |
| M6 | **"没提交"不等于"没泄漏"，只等于"还没泄漏"** | #65 的明文只在本地产物里，但下一次 `git add -A` 就会带进去 |
| M7 | **探测前先问「这个操作有撤销键吗」** | #68；本次为此永久留下 2 条选项集记录 |
| M8 | **同进程内"写完立刻读"必须显式失效缓存** | 我自己的取证脚本漏了 `invalidate_object_cache`，当场误报"6 个字段没建出来"（产品里 `_verify()` 是对的） |
| M9 | **选测试用例时先读现成的清单逐条打勾，别凭印象** | 我凭"常见类型"的印象挑字段，漏掉的恰是**最有业务含义**的两个（父子关系、时区语义）——而 `DATA_TYPE_NAMES` 里早有正确答案 |

### 3.3 我自己犯的错（如实记录）

| 错误 | 后果 | 更正 |
|---|---|---|
| 用 `git checkout -- <目录>` 清噪声 | **误伤批次一已批准的 `make_fixture.py` 信封修正 + 夹具产物** | 按原样重建并逐字核对；教训：回滚要按**具体文件**，因为"噪声"和"已批准的改动"常在同一目录里 |
| 断定"选项集没有任何可用的回读路径" | 写进了一份报告 | 报告已重写并**保留误判成因**；根因是我没从已跑通的端点反推命名结构（M4） |
| 用 `precedingActions` 判断"用户改了几个输入框" | 两次都判断错了 | 动作缓冲上限 5 条且会跨操作渗漏（#64），**它数不了操作数** |
| 取证脚本漏失效缓存 | 误报"字段没建出来" | 产品里没问题；是脚本的错（M8） |
| 建字段时凭印象挑类型 | 漏建「日期时间」「父对象」 | 用户点评后补建；`DATA_TYPE_NAMES` 里早有答案（M9） |

## 1. 结论

**创建成功，并且已被独立回读验证。**

| 项 | 值 |
|---|---|
| 名称 | `测试09-03选项集` |
| 编码 | `test_0903_option__c` |
| 选项 | 选项A(`A__c`, sort 0) / 选项B(`B__c`, sort 1) / 选项C(`C__c`, sort 2) |
| **选项集 id** | `id-fbc23efc`（经回读取得） |

## 2. 工厂实际发出的请求（抓包）

`POST /api/platform/ObjectPicklist/save`

```json
{"name": "测试09-03选项集", "code": "test_0903_option__c",
 "options": [{"name":"选项A","code":"A__c","status":1,"operations":1,"sort":0},
             {"name":"选项B","code":"B__c","status":1,"operations":1,"sort":1},
             {"name":"选项C","code":"C__c","status":1,"operations":1,"sort":2}]}
```

## 3. 与界面形状的差异

界面（2026-09-21 采集）发同样的三件，**外加三个数字键** `"0"`/`"1"`/`"2"`——
把每个选项在顶层又按下标重复了一遍。**工厂不发这几个键。**
看起来是前端表单序列化的产物（`options` 数组已完整表达同样内容）。
**平台认哪个键未验证**（两条路都能建出来，说明至少 `options` 是被认的）。

## 4. 回读端点：常量里的路径是**错的**

仓库里的常量（`kernel/endpoints.py`）：

```
OBJECT_PICKLIST = "/api/openapi/v1.0/ObjectPicklist/{code}"      ← 实测恒 404
```

**正确路径**（本次实测找到）：

```
GET /api/openapi/v1.0/BasicObject/picklist/{code}                 ← HTTP 200
```

规律很直白：OpenAPI 把子资源挂在对象下——
`/BasicObject/field/{code}`、`/BasicObject/lifecycleStatus/{code}`，
选项集同样应该是 **`/BasicObject/picklist/{code}`**。当初写成平级的 `/ObjectPicklist/` 是猜的。

**为什么初版会误判**：我只沿着"仓库里已有的常量"以及类似的列表端点名字去找
（穷举了 20 次，全 404），却没有**从已跑通的那三条端点反推命名结构**。
已跑通的三条就在眼前，结构一目了然——这是本次最该记住的一条方法论。

### 响应形状（关键）

`data` 是**选项数组**，不是选项集对象：

```json
{"code":0,"message":null,"data":[
  {"id":"id-c4b703fc","objectPicklistId":"id-fbc23efc","name":"选项A","code":"A__c","sort":0}, ...]}
```

⇒ **选项集的 id 在 `data[0]["objectPicklistId"]` 里**，不在 `data["id"]`。

### "不存在"长什么样

不存在的编码**不是** 404、也不是空数组，而是 **HTTP 200 + `code:500`
+ `message:"Object reference not set to an instance of an object."`**
（平台把空引用漏成了 .NET 异常文案）。

## 5. 这两处偏差 —— **已修复**（2026-09-21，用户批准）

改前代码有两处偏差，**都会静默**：

1. **路径错**（`/ObjectPicklist/` → 应为 `/BasicObject/picklist/`）
2. **取 id 的方式错**：`picklists.py` 用 `meta.get("id")`，而 `data` 是**列表**，
   会 `AttributeError`；该异常被 `try/except` 吞掉，于是 `picklistId` 恒为 `None`。
   正确取法是 `data[0]["objectPicklistId"]`。

**实际改法**：只改常量 + 在 `queries.py::get_picklist` 里**统一把选项数组归一化成 dict**
（`{"id": data[0]["objectPicklistId"], "code", "options"}`）。三个消费者
（`resolve_picklist_id` / `create_picklist` / `picklist_exists`）**一行都没改** ——
把形状差异收在一个函数里，比在三个调用点各修一次更不容易再错。

| | 修复前 | 修复后（真机复验） |
|---|---|---|
| `create_picklist` 的 `picklistId` | 恒 `None`（异常被吞） | 有值 |
| `Idempotency.picklist_exists()` | 恒 `None` ⇒ 永远判「不存在」 | 能判对 |
| `resolve_picklist_id()` | 恒 `None` ⇒ **选项字段建出来没有选项集** | `test_0903_option__c` → 真实 id；不存在的编码 → `None` |

> 第三条是最要命的：`batch_create_fields` 里 dataType=4 的字段靠
> `resolve_picklist_id(code)` 拿 id，拿不到就**不往请求体里放 `picklistId`**，
> 于是"选项字段"变成一个没有选项集的选项字段，而接口照样回 `data:true`。
>
> ⚠️ **夹具也一起修了，这才是它能活这么久的原因**：`tests/fakes.py` 里
> **硬编码了同一个错路径、且返回 dict**（真机返回选项数组）—— 夹具是照着错常量猜的，
> 所以测试一直绿。改成真机形状后，新增的 4 条断言在旧实现下**全部变红**，
> 其中一条直接打出症状：`SaveField` 请求体里**根本没有 `picklistId`**。
> 而修改前跑全量是 **29 passed** ⇒ 这条链路此前**零覆盖**。

## 6. 已判定：`save` 的语义（用户批准后做了试探）

**试探**：新编码 `test_0903_option_probe__c` + **已存在的名称** `测试09-03选项集`。

**结果**：`code:500 名称重复`。**没有创建任何记录**（后续回读该编码确认不存在）。

⇒ **模型成立**：`save` 按 `code` 定位记录、**同时全局校验名称不与其他记录冲突**。
同一条记录原样重发 = 更新自己，不冲突（实测两次 save 后仍只有 1 条）。

**推论**：重跑蓝图**不会**产生重复选项集，只是白跑一次。
所以"幂等层对选项集失效"这条的实际危险度**低于**初版的判断——
但它仍然会让**选项字段拿不到 `picklistId`**（§5 第三条），那条是真会坏的。

## 7. `sort` 之谜 —— **已解开**（2026-09-21 用户重演示 + 三次判别实验）

初版把这条记成"未解释的观测"。用户重新演示了一次创建选项集（会话
`acct-fb8dc317-20260921-171511`，单次 save），加上三次判别实验，结论如下。

**观测矩阵**（`options[].sort` 一律发 0/1/2）：

| 场景 | 顶层数字键 `"0"/"1"/"2"` | 平台存下的 sort |
|---|---|---|
| **新建** · 界面 | **有** | **1 / 2 / 3** |
| **新建** · 界面（上一次那条） | **有** | **1 / 2 / 3** |
| **新建** · 工厂（API） | 无 | **0 / 1 / 2** |
| **新建** · API + 补上数字键（probe3） | **有** | **1 / 2 / 3** |
| **更新** · API + 补上数字键 | **有** | **0 / 1 / 2**（原样） |

⇒ **规则**：**新建**时若请求体带顶层数字键，平台**按选项位置重排成 1-based 并忽略
`options[].sort`**；不带数字键则认 `options[].sort`。**更新**时一律认 `options[].sort`。

**为什么必须做三次实验才敢下结论**（过程比结论值钱）：

1. 先试"给已有选项集补数字键" → 没变 ⇒ 排除了数字键；
2. 但这里有个混淆：**"sort 会不会是建时定、之后不可改"**？于是用 5/6/7 试了一次
   → **改了** ⇒ 说明第 1 步的实验有效，"数字键不是原因"成立；
3. 剩下唯一没试过的格子是「**新建** + API + 数字键」。补做 → **1/2/3** ⇒ 原因锁定。

**对工厂的实际影响**：

- 工厂**不发**数字键 ⇒ 它的 `sort` 被**如实保存**（0-based），而界面建的是 1-based。
- **相对顺序两者一致**，所以显示顺序相同 —— 现状**不构成缺陷**。
- ⚠️ **但有一个将来会咬人的点**：如果哪天工厂往一个**界面已建的**选项集里**追加**选项
  并按 0-based 序号算 `sort`，就会与既有的 1/2/3 撞号（追加第 4 个给 sort=3，
  与既有的第 3 项同号）。**要追加就应先读现有最大 `sort` 再 +1。**

> ⚠️ **遗留数据**：为做第 3 步实验新建了 `测试09-03选项集_probe3`（`test_0903_probe3__c`）。
> 平台没有删除选项集的接口，需要**人工在界面上清理**。

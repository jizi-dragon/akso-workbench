## 3. ★★ 结论二：`GetStableComponentIds` 是**增量**的（D-E 的实现要点）

| | 段 2 | 段 4 |
|---|---|---|
| 请求体 | **1002 B / 4 个组件** | **210 B / 1 个组件** |
| 组件 | 1 个新建部分 + 3 个新建控件 | **只有 `name__ak`（`layout_control`）** |

段 4 明明**新建了一个部分 + 两个控件**，却只为**一个**组件换了稳定 id。
合理解释（与观测一致）：**只有"当前还没有服务端 id"的组件才需要换**——
`basic_info3__cs` 与它那两个控件的稳定 id 在**更早**（我没在录的那段时间里）就换过了，
所以这次只剩 `name__ak` 待换。

**闭环依旧成立**（第二个样本）：请求键 == 响应键；
`name__ak` 在保存体里的 `id` **逐字等于**响应给的稳定 id（`39ad0137-…`）。

⇒ **D-E 的实现要求更具体了**：不是"每次保存前把所有新建组件都稳定一遍"，
而是「**只对还没有服务端 id 的组件调**」——多调不会错，但会与真机行为不一致，
而"多调一次"正是那种**看不出问题、事后也难归因**的偏差。**建议按增量实现。**

## 5. 那个落在「基础信息2」下的控件 = `name__ak`

演示者随后报「又在部分『基础信息2』下增加了一个控件」，与这一批里的 `name__ak` 吻合：

- 它的 `sectionId` 指向 **`basic_info2__cs`**（不是新部分 `basic_info3__cs`）；
- `componentCode` 是 **平台自生成**的（后缀 `__ak`），不是演示者取的名；
- `type: AKInput`，**请求体里根本没有 `dataType` 这个键**（8 键的精简形状）；
- 它是这一批里**唯一**被 `GetStableComponentIds` 处理过的组件。

> ⇒ **一条要记的读法**：**"没有 `dataType`" ≠ "不是控件"**。
> 精简形状下 `dataType` 可以缺席，而 `type`（`AK*`）在。
> 工厂若坚持"先有 dataType 才能定 type"，就会在这一类组件上卡住（见 D-D 的修法）。

## 7. 对修法方案的影响

| 项 | 变化 |
|---|---|
| **D-D** | `AK*` 表**9 个实测 dataType**（覆盖了最常用的文本/数字/是否/选项/日期时间/附件/对象）；**表形 = dataType → type（多对一）**；**仍缺 5 个，继续显式失败** |
| **D-D 的 `dataType` 依赖** | 真机自己发过**没有 `dataType`** 的控件 ⇒ 工厂**不能**把 `dataType` 当"定 type 的唯一依据"；取不到时应**报错或走"按字段类型查表"**，不许默默退化成 `input`（那两处兜底见段 1 §8.1） |
| **D-E** | **按增量实现**：只对"还没有服务端 id"的组件调；返回的 id 必须**逐字**写进保存体（两个样本都逐字相等） |
| **D-D 的验收面** | 修完发出去的新控件，形状不必凑 23 键（F48），但**键名与 `AK*` 值必须与这一节的两张表一致** |
